# 真实业务场景验收目录

这里的用例用于回答一个比“某个节点能不能跑完”更具体的问题：

> 当调度器、包装器或工作组协议在未来重构后，一项真实工作是否仍会在正确的人、正确的
> 自动化步骤和正确的失败边界之间流转，并留下可核验的业务产物？

因此，每个场景必须同时具备：

- 可通过公共 API 创建或导入的生产格式定义；
- 确定的初始资料、角色职责和验收标准；
- 至少一个需要调度器作出取舍的非 happy path；
- 对任务状态、运行谱系、提示词上下文、工作树实物和人工门的联合断言；
- 对“不应发生”的副作用作反向断言，例如成功步骤被重复执行、失败后提前进入审批、
  取消后仍写文件，或未批准就发布。

测试只用确定性桩替代外部模型进程。HTTP、认证、SQLite、调度器、子进程、Git
worktree、协议解析和人工恢复仍走生产实现。

## 首批可执行场景

| ID    | 业务问题               | 编排形态                | 关键非 happy path                      | 必须保住的业务结果                                                       |
| ----- | ---------------------- | ----------------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| WF-01 | 线上缺陷修复与受控发布 | 预定义 Workflow         | 第一轮验证不通过，需要第二轮修复和复审 | 只有通过验证且经人工批准的版本成为最终输出；修复差异和审计证据可追溯     |
| WF-02 | 多文档合规审阅         | 预定义 Workflow         | 人工驳回汇总稿，要求带上一版证据修订   | 每份文档独立审查且只汇总一次；驳回只重跑草稿生成，不重复已完成的文件审查 |
| WG-01 | 客户数据迁移作战室     | `free_collab` Workgroup | 批次中一张迁移卡自报失败并重新开放     | 已成功卡不重做；失败卡在预算内重新分派并完成；最终产物经人工完成门确认   |

选择预定义 Workflow，是因为步骤、数据类型和审批顺序由组织流程预先确定；选择
Workgroup，是因为任务拆解、领取和失败后的重新分派需要成员在运行时协商。

### WF-01：线上缺陷修复与受控发布

**初始资料**

- 一个可克隆的本地 Git 仓库；
- 可复现的缺陷描述、影响面和验收约束；
- 一组确定性回归检查。

**业务流**

1. 修复 Agent 在隔离 worktree 内修改实现；
2. 独立验证 Agent 检查实现与回归结果；
3. 第一轮未满足验收标准时，质量门把失败证据写入工作树，Loop 下一轮修复必须读取；
4. 验证通过后生成发布证据并进入人工审批；
5. 批准后才投影最终交付结果。

**回归不变量**

- 第一轮实现与失败证据必须保留在同一工作树；第二轮不得从空仓重新开始或只靠轮次
  猜测修复内容；
- 审计、测试和质量门必须分别呈现
  `needs-fix/failed → clean/passed`，最终发布包只能消费最新 `clean` 结果；
- 最终差异同时包含实现与验证产物，且来自同一任务 worktree；
- 人工门打开前不能把任务标为 `done`；
- 被批准的是最新验证通过的结果，不能消费旧 attempt 的输出；
- 用例不执行真实 push；“未批准不得发布”由无外部发布副作用和状态断言共同保证。

### WF-02：多文档合规审阅

**初始资料**

- 多份待审 Markdown 文档；
- 一份对所有分片一致的合规政策。

**业务流**

1. Fanout 按文档路径分片，审查 Agent 只看自己的文档与广播政策；
2. Join 等待所有分片后，由单个 aggregator 去重合并发现；
3. Publisher 在草稿目录生成可供 Review 消费的多文档结果；
4. 人工驳回时，Publisher 带着上一版输出和拒绝原因修订；
5. 人工逐篇选择并批准后，独立 Releaser 只物化接受项并投影实际发布路径。

**回归不变量**

- 一个输入文档对应一个稳定 shard，不能漏审或重复审；
- aggregator 在全部 shard 结束前不得运行，且只运行一次；
- Review 必须直接消费普通 Agent 的文档输出，不能绕过类型与来源校验；
- 驳回只重跑允许修订的 Publisher；Fanout 的已完成分片与 aggregator 不重跑；
- 未接受的草稿不能出现在 `published/`，发布路径必须由 Review 下游生成；
- 任一 shard 失败时不得提前打开人工门或发布不完整结果。

### WG-01：客户数据迁移作战室

**初始资料**

- 一份 125000 条记录的迁移批次范围，以及“记录数精确一致且 checksum verified”的对账阈值；
- 一个可写迁移负责人和一个只读风险评审者，两者都提供独立规划意见；
- 一个负责最终确认的人工成员。

**业务流**

1. 成员分别完成初始规划，迁移负责人创建 schema 冻结、加密导出校验和回滚任务卡；
2. 引擎将多张卡批量派发给成员；
3. 某张卡首次明确返回 `failed`，其余卡正常完成；
4. 引擎只把失败卡重新开放并再次派发；
5. 所有卡完成后进入人工完成门，批准后任务结束。

**回归不变量**

- 成功卡的 `attempt` 和工作树产物保持不变；
- 失败卡产生独立的新执行 attempt，历史 run 仍可追溯；
- 重试预算只由失败卡消耗，不能连带消耗同批其他卡；
- 每次结果都与具体任务卡关联，不能用一条批次摘要冒充全部成功；
- 最终批准前，任务保持人工可见的待确认状态。

## 下一批高风险场景

以下场景价值高，但需要独立 harness 或精确故障注入，不与首批普通矩阵混跑：

| ID    | 场景                                                   | 需要新增的验证能力                                                               |
| ----- | ------------------------------------------------------ | -------------------------------------------------------------------------------- |
| WG-02 | 生产事故响应：调查、止损、验证、人工上线窗口与回滚方案 | human assignment 的真实交付闭环、处理中取消、完成门驳回后追加 rollback 卡        |
| WG-03 | Workgroup 资源校验到启动之间发生并发 Agent 变更        | Agent 内容 revision/closure hash 与 Workgroup version 一起原子校验并冻结后再调度 |
| WF-03 | API 与 SDK 两仓协同升级                                | 两个真实仓库的 typed context、成对验证、任一仓失败时的一致回滚                   |
| RC-01 | Workflow 在 Loop/Fanout 与人工暂停期间崩溃恢复         | 精确 barrier 后杀 daemon，重启后验证 generation、effect 和人工轮次不重复         |
| RC-02 | Workgroup 在 assignment/message turn 中崩溃恢复        | CAS、host run 和 effect 各窗口的故障注入；卡片、消息、结果与文件均 exactly-once  |

崩溃用例禁止依赖固定 `sleep` 猜测窗口；必须由测试桩写入 barrier，测试观察到 barrier 后
再终止 daemon，并复用同一个 `AGENT_WORKFLOW_HOME` 重启。

当前 seed 会拒绝检查时已经存在的 Agent/Workgroup 契约漂移，但公共启动 API 还不能把 Agent
内容 revision 与 Workgroup version 放进同一个原子 fence。WG-03 用于锁定这个
check-to-launch 窗口；在该服务端契约落地前，示例不宣称能阻止校验完成后的并发 Agent 修改。
