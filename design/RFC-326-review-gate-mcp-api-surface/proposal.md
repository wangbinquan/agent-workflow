# RFC-326 评审门的 MCP / API 完整面 —— 让设计文档能在本地被检视并提交意见

状态：In Progress（2026-08-25 落档；同日三轮五路设计门后修订为 v4；用户同日批准 v4 与 D5 / D6 两处范围澄清）
关联：RFC-005（设计文档人工评审门）、RFC-009（意见编辑）、RFC-013（历史版本）、RFC-051（rehype 阶段锚点高亮）、RFC-079（多文档评审 + 逐篇采纳）、RFC-129（采纳继承与 stale）、RFC-142（多文档轮次史）、RFC-241（上一版意见锚进 diff）、RFC-099 / RFC-285 / RFC-324（作答权边界、作者校验、observer）、RFC-303（来源终止围栏）、RFC-247（MCP 远程接入：本 RFC 补齐其 D11 / T18 未落地的一半）、RFC-294（后台目标架构：`collaboration` 上下文首片）、RFC-317（架构守卫棘轮）、RFC-319（e2e 能力账本）

## 1. 背景

用户诉求原文：**「现在的 agent workflow 的 MCP 和 API 没有检视设计文档的接口，导致没有办法让设计在本地检视文档并提交意见，你需要开一下这个接口来支持这类能力。」**

### 1.1 仓内的「设计文档检视」是什么

就是 RFC-005 建成的**人工评审门**：`review` 节点把上游 agent 产出的 markdown（`doc_versions`）停下来等人审，人在网页里选词写意见（`review_comments`，带复合锚点）、然后做 approve / iterate / reject 三决策；iterate 时意见被渲染进 `{{__review_comments__}}` 回灌上游重跑（`services/review.ts:3082-3104`）。RFC-079 又把它扩成多文档模式（`list<path<md>>` 逐篇意见 + 逐篇采纳），RFC-013 / RFC-142 加了历史版本与轮次史。数字员工的方案节点也走同一个门（`modules/task-execution/domain/digitalEmployeeHost.ts:193` 注入的正是 `{{__review_comments__}}`）。

### 1.3 后果

一个在本地跑 Claude Code / opencode、用 PAT 连上平台 MCP 的「设计」（设计人员，或替他检视的本地 agent）今天能做的只有：看待审列表、读单文档正文、按一个按钮（而且 iterate 那个按钮是坏的）。**看不到多文档评审的其余各篇、看不到上一版和上一轮的意见、提不了任何一条意见**——而「提意见 → 回灌重跑」恰恰是这个门存在的理由。REST 虽然全，但要程序方自己拼出 DOM 语义的复合锚点，等于没开。

## 2. 目标

- **G1** 本地 AI 客户端通过 MCP 就能完成一整轮评审：找到待审 → 读正文（单 / 多文档、当前 / 历史）→ 逐条提意见 → 逐篇采纳 → 做决策，**与网页评审的能力面一致**。
- **G2** 提意见只需要给**正文里逐字出现的一段引文**（`quote`）+ 可选的第几次出现 / 所在章节，完整锚点由服务端按 markdown 源文解析；找不到或歧义时**明确报错并列出候选**，**简化锚点路径绝不猜**。（网页提交的完整锚点走 P5 的兼容性规范化——新增「偏移 + 上下文双匹配即采信」，其余沿用既有策略；G2 不承诺改写这条 legacy 路径。）
- **G3** REST 与 MCP **同一条路**：MCP 工具仍经 `Dispatcher` 走 `/api/reviews/*` 路由（RFC-247 §4 的结构性保证），REST 端点同步接受简化锚点，脚本与其它客户端同样可用；不出现第二个更弱的授权面。
- **G4** 意见与决策既能**逐条**提交，也能**一次打包**（`submit_review` 携带 `comments[]` / `selections[]`）；打包与决策的**全部评审持久状态**在**一个数据库事务**里落地——任一校验失败零写入，写入阶段不再有半决策态。
- **G5** 网页评审页对任何**自洽**锚点（含 MCP 提交与网页提交）**按源文偏移精确高亮**：引文含行内标记（`**` / 反引号 / 转义 / 实体）、跨段落、锚在含标记的标题上、落在围栏代码块里，都在正确位置出现 `<mark>`；只有公式（KaTeX 输出）与图表（mermaid / plantuml）不高亮；不再有「按序号猜」的全局回退。
- **G6** 把 RFC-247 门工具**零测试**的债一并还掉：工具表、分发、权限过滤、错误脱敏、e2e 全部有锁，并加一条「路由 ⟷ 工具双向完整」的棘轮。
- **G7** 按 RFC-294 种下 `collaboration` 上下文的第一片（评审锚点 domain 纯函数 + exact public 入口），让「架构演进」是真的。

## 3. 非目标

- **N1** 不做 MCP `resources` / `prompts`（RFC-247 D10 只做 `tools`，不变）。
- **N2** 不新增权限点：读走「读恒开」，写走既有 `tasks:execute`；作答权边界仍是任务成员（owner / collaborator）或管理员（RFC-099 D5/D7，`routes/reviews.ts:53-80`；RFC-324 observer 不是作答主体）。**非任务成员在 MCP 上同样只能读不能写**。
- **N3** 不改评审存储与数据模型：`doc_versions` / `review_comments` 零迁移、零回填；文档级意见用既有锚点字段表达（P4）；存量意见行按其 `occurrenceIndex` 定位（P17）。
- **N4** 不做服务端 diff：历史版本以正文 + 当时意见返回，对比由本地客户端自己做。
- **N5** 不做 CLI 子命令：MCP 面向 agent、REST 面向脚本，已经覆盖「本地」两种形态。
- **N6** 网页改动**只限**评审高亮链路：`rehypeWrapAnchors`（源文偏移模式 + 统一非重叠计数）、`Prose`（传入源文、`React.memo`）、`ReviewDocPane`（把偏移传给插件）、`CodeBlock` / `ShikiPre`（围栏代码块通过 Shiki `decorations` 保留 `<mark>`）；不改评审页布局、侧栏、决策对话框、diff 视图（RFC-241 的 merged 文档路径保持文本模式）。
- **N7** 不把 `services/review.ts`（3.5k 行）整体迁进 `modules/collaboration`；本 RFC 只种 domain 纯函数 + public 入口这一片，应用服务的迁移留给后续 RFC-294 波次。
- **N8** 不改 RFC-247 的工具注册语义：未授权工具**不注册**（`mcp/server.ts:43-50`），硬调得到 SDK 的 unknown-tool 协议错误；`describe_capabilities` 负责解释缺哪个点。
- **N9** 不改 `renderCommentsForPrompt` 的四行结构（e2e `review-comments-to-rerun-prompt.spec.ts` 锁着它）。
- **N10** 蒸馏入队（`enqueueDistillJob`）**不进**决策事务：它今天就是决策之后的 best-effort 独立写入（失败被吞、绝不阻塞决策，`services/review.ts:2634-2640`），本 RFC 保持这一语义并把它明确列为提交后效果（P14）。

## 4. 用户故事

- **US1（本地检视 + 逐条意见）** 设计人员在本机 Claude Code 里说「看看平台上等我审的设计文档」。agent 调 `list_pending_gates` 拿到待审项，`get_review` 读到 `design.md` 正文与已有意见，逐段读完后调 `add_review_comment(quote: "POST /api/v1/orders/cancel", commentText: "取消应幂等，带 idempotency_key")`，再对「order_status enum」提第二条。网页评审页实时多出两条意见，`<mark>` 精确落在那两处（WS 事件既有）。
- **US2（歧义引文）** agent 想对第二次出现的 `order_status` 提意见，只给了 `quote`。服务端回「`order_status` 出现 3 次：occurrence 1 在 `## Data Model`、2 在 `## Interfaces`、3 在 `## Sequence`，请传 `occurrence` 或 `section`」。agent 补 `occurrence: 2` 后落地；或传 `section: "Interfaces"` 一次命中。编号始终是**全文序号**，与错误里列的、落库的、网页用的是同一个数。引文打错字时，错误里给出最多 5 条带位置的近似片段（`sourceText` / `offsetStart` / `sectionPath`），仍不自动选用。
- **US3（打包提交）** agent 读完后一次性 `submit_review(decision: "iterated", reviewIteration: 0, comments: [{quote…}, {quote…}, {commentText: "整体缺成本估算"}])`。第三条没有 `quote`，锚到文档标题行。三条意见与决策在一个事务里落地，上游 designer 重跑，提示词里三条都在。若其中一条 `quote` 编错，整次调用 422、零写入。若写入阶段出错（磁盘 I/O），事务回滚，run 仍 awaiting，`reviewIteration` 不动，原样重发即可（重复意见按内容去重，不会双份）。
- **US4（多文档）** 测试用例评审（RFC-079）有 23 篇。`get_review` 给出 `documents[]`，agent 用 `get_review_document(docVersionId)` 逐篇读，对第 7 篇提意见（带 `docVersionId`），最后 `submit_review(approved, selections: [1–20 accepted, 21–23 not_accepted])` 一次完成采纳与通过，`accepted` 端口输出的正是这 20 篇。省略 `docVersionId` 提意见会被 422 拒绝，而不是静默挂到任意一篇——**哪怕这一轮只有一篇**（多文档模式按 `itemIndex` 判定，不按篇数）。
- **US5（对比上一轮）** 复审时 agent 调 `list_review_history` 看到 v1 被 iterate、v2 待审；`get_review_document(v1 的 docVersionId)` 拿到上一版正文与当时的三条意见，本地对比后判断 agent 是否真的改了。
- **US6（只读令牌）** 一个只勾了读的 PAT：`tools/list` 里只有读工具（`list_pending_gates` / `list_reviews` / `get_review` / `get_review_document` / `list_review_history`）；硬调 `add_review_comment` 得到 SDK 的 unknown-tool 错误，`describe_capabilities.toolsUnavailable` 指出它缺 `tasks:execute`。
- **US7（脚本）** CI 脚本用 `curl` 打 `POST /api/reviews/:id/comments`，body 只有 `{ "quote": "…", "commentText": "…" }`，同样落地；老客户端继续传完整 `anchor` 也照常工作，且落库时偏移会被修正到真正命中的那一处。
- **US8（含标记的引文、标题与代码块）** 文档标题是 `# API \`v2\` **design**`。agent 对整篇提意见（无 `quote`）：网页在标题上出现连续的 `<mark>`（`API v2 design`）。agent 引用 `` `order_status` ``（带反引号）：精确高亮在行内代码上。agent 引用围栏代码块里的 `const order_status = "pending"`：Shiki 高亮完成后的代码里同样有 `<mark>`。
- **US9（撤权竞态）** 协作者 A 正在提交 iterate（要回滚工作树），owner B 同时把 A 移出任务。两者串行：B 先落地 ⇒ A 在任何外部效果前得到 403；A 先落地 ⇒ B 的变更在 A 提交之后生效。**不存在「A 已回滚工作树、然后被 403」的形态。**

## 7. 验收标准

### 锚点解析（纯函数，`modules/collaboration/domain/reviewAnchor.ts`）

- **AC-1** `quote` 唯一出现 ⇒ 完整锚点：`offsetStart/End` 为源文绝对偏移、`selectedText` = 引文、前后各 30 字上下文（越过文首 / 文末则截断）、`occurrenceIndex = 1`、`sectionPath` 为标题面包屑、`paragraphIdx` 为该标题之后、引文所在块之前的顶层段落 / 围栏 / 引用块数（列表、表格、分隔线、HTML 块计 0；无标题时首块不计，对齐前端 `anchor.ts:76-109`）。
- **AC-2** 多次出现、未给 `occurrence` ⇒ `review-anchor-ambiguous`，候选按**全文序号**列出（`occurrence` / `sectionPath` / `offsetStart` / 前后上下文）；给了 `occurrence` ⇒ 命中该全文序号（即使只有一次出现也校验，`occurrence: 2` 对单次出现 ⇒ `review-anchor-occurrence-out-of-range`）；候选收集上限不影响解析——`occurrence = 1001` 命中第 1001 处，唯一命中位于第 1000 处之后的章节时 `section` 照样命中。
- **AC-3** `section` 匹配标题面包屑的任一段（含 `#` 前缀或不含均可）或整串；`section` 无任何出现落在其中 ⇒ `review-anchor-section-not-found` 并列出可选章节；`section` + `occurrence` 且该出现不在章节内 ⇒ `review-anchor-occurrence-not-in-section` 并列出章节内的全文序号。
- **AC-4** `quote` 不在正文 ⇒ `review-anchor-not-found`，附最多 5 条**结构化近似建议** `{ sourceText, offsetStart, sectionPath }`（大小写不敏感 / 空白折叠命中），仍不自动选用；引文范围内出现新起的标题行 ⇒ `review-anchor-crosses-heading`；空正文 ⇒ `review-anchor-empty-document`。
- **AC-5** 无 `quote` ⇒ 锚到标题行：第一个 ATX 或 Setext 标题的源文文字，`occurrenceIndex` 指向标题所在那一次出现（即使同样文字在标题前的段落里也出现过）；无标题 ⇒ 第一个非空行；带 `occurrence` / `section` 却无 `quote` ⇒ 由 schema 拒绝。
- **AC-6** CommonMark 子集精确：围栏 ` ``` ` / `~~~`（缩进 ≤ 3、同字符、闭合长度 ≥ 开启、未闭合延伸到文末），四反引号包三反引号的示例里的 `#` 不算标题；ATX 开头 `#` 串 **1–6 个且后接空白 / 行尾**（`#######` 与 `####### x` 不是标题），允许 0–3 空格缩进、空格或 tab 分隔、尾部 `#`；引用块 / 列表内的 `#` 行**不**视为章节标题（记为近似）；**标题识别与跨标题检测共用同一份扫描结果**。
- **AC-7** CRLF 正文：偏移按原文计算，标题文字 / 首行文字不带 `\r`；`section` 用无 `\r` 的文字能匹配。
- **AC-8** 有界（断言机制，不断言墙钟）：1 MB 正文 + 单字引文 ⇒ ambiguous，`candidates.length ≤ 50`、`total` 为**精确**总数、`truncated = true`、扫描只做一遍；同一请求 200 条引文共用一份文档模型；累计扫描超过预算 ⇒ 422 `review-anchor-budget-exceeded`；引文可含换行、CJK、tab；引文位于表格 / 列表 / 引用块内均可解析。

### 锚点规范化（`services/review.ts`）

- **AC-9** 服务端解析的锚点落库后与解析器输出**逐字段相同**（不经重算）；`body.slice(offsetStart, offsetEnd) !== selectedText` 的服务端锚点是编程错误，抛 500 而非静默修正。
- **AC-10** 客户端完整锚点：`offsetStart` 恰为某次出现且上下文匹配 ⇒ 原样采信；否则按既有上下文策略选出现，且落库 `offsetStart/End` 被修正到该出现；设计门 F2 的周期性表格用例（第 3 处）落库 `occurrenceIndex = 3`、`offsetStart = 114`。

### REST

- **AC-11** `POST /api/reviews/:id/comments` 接受 `{ quote?, occurrence?, section?, commentText, docVersionId? }` 与既有 `{ anchor, … }` 两种形态；两者同时给 ⇒ 422 `review-comment-invalid`；长度超限 ⇒ 422；body 超 1 MiB ⇒ 413，**低报 / 畸形 `Content-Length`、chunked 超限同样 413**。
- **AC-12** 落库后 `GET /api/reviews/:id` 的 `comments[].anchor` 与解析器输出逐字段一致；响应携带 `warnings`。
- **AC-13** 多文档：省略 `docVersionId` ⇒ 422 `review-doc-version-required`（含单篇轮）；非本 run pending 成员 ⇒ 404 `doc-version-not-found`。
- **AC-14** `POST /api/reviews/:id/decision` 接受可选 `comments[]` / `selections[]`；校验失败（任一锚点无效 / selection 目标非法 / 多文档 approve 采纳不齐 / `selections` 里 `docVersionId` 重复 / 迭代号过期 / 非成员 / 来源围栏关闭）⇒ 4xx 且**零写入**——`doc_versions`、`review_comments`、`node_runs`、`node_run_outputs`、`merge_state`、`memory_distill_jobs` 六表相关行与 WS 事件计数全部不变。
- **AC-15** 打包 iterate 成功 ⇒ 打包意见与此前逐条意见一起进入 `commentsJson` 快照与 `decisionReason`，上游重跑提示词包含全部意见；从**全部 `unselected`** 起步的打包 `selections[]` + `approved` 一次完成逐篇采纳，`accepted` / `approval_meta` 两条输出行逐字等于按打包后视图计算的子集，被批的 `selectionStale` 清零。
- **AC-16** 锚点校验失败一律 422（不再 500）。

### 事务

- **AC-17** 决策路径（单 / 多文档、approve / iterate / reject、含打包）的**全部评审持久状态**写入在**一个** `dbTxSync` 内提交（用事务计数桩断言恰好一次）；蒸馏行在提交后单独写入，其失败不影响决策（桩抛错 ⇒ 决策仍成功且评审状态已提交）；在归档之后人为注入失败（损坏 `workflowSnapshot` / 删除 multi-inline 采纳正文 / 事务内抛错 / 工作树回滚后事务抛错）⇒ 响应 4xx，六表相关行**回到调用前**，run 仍 `awaiting_review`。
- **AC-18** WS 事件只在提交后发出：事务失败的用例里事件计数为 0。
- **AC-19** 重跑行铸造、上游行取消、兄弟级联、自身状态 CAS 都走 `…Tx` 同步变体；`transitionNodeRunStatusTx` / `mintNodeRunTx` 与既有异步版本对同一输入产生逐字段相同的**全部受影响行**（含被 `abandonSupersededMergeStates` 退役的旧 merge state 行）与相同的错误码。
- **AC-20** 成员资格线性化：`rollbackFlag = true` 的 iterate 与「移出该成员」并发——先撤权 ⇒ 决策在**任何**工作树操作前 403 `not-task-member`、零写入、工作树逐字节未动；先决策 ⇒ 撤权在决策提交后生效；来源围栏已关闭 + `rollbackFlag = true` ⇒ 回滚桩**未被调用**；`PUT /members` 排队中携带旧 owner 快照的请求在锁内重读后被拒。

### MCP

- **AC-21** 工具表新增 `list_reviews` / `get_review_document` / `list_review_history` / `add_review_comment` / `update_review_comment` / `delete_review_comment` / `set_review_document_selection`；`submit_review` 入参增加 `comments[]` / `selections[]` 且 `decision` 引 shared 枚举；三种决策经 MCP 都真实落地。
