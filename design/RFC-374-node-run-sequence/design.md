## 1. 现状

### 1.1 铸造

唯一 INSERT 在 `TE/infrastructure/nodeRunMintParticipant.ts:82` 的 `nodeRunMintProgram`（:34-84）：可选的容器主键读（:43-52）
→ 可选的 tasks 点读（:61-75）→ insert。RFC-369 之后程序内没有其他写。锁定它的测试：`T/rfc098-node-run-mint-grep-guard.test.ts`
（单一 INSERT 文件）、`T/architecture/rfc359-w6-node-run-insert-lineage-completeness.test.ts`、`T/rfc144-stale-replay-regression.test.ts:792-816`
（只有一次 `.from(nodeRuns)`、无 `.update(nodeRuns)`、无 `lt(nodeRuns.id`、一次 `.insert(nodeRuns)`）、
`T/rfc359-w47-node-run-mint-program.test.ts:367-390`（阶段顺序 container? → task? → insert，零 update）、
`T/rfc369-node-run-supersession.test.ts:230-277`（AC-2：两个 SERIALIZABLE 同任务铸造在屏障后各执行一次）。

铸造调用方在 PostgreSQL 上的事务：调度器 `lifecycle.mint` 为 READ COMMITTED（带 owner 围栏 UPDATE）；重试占位、仓库准备重试、
人工门停驻 / 结算、工作组 host 账本为 SERIALIZABLE；review 空列表停驻、review 决定 rerun、clarify 派发为 READ COMMITTED
（后两者对 tasks 行 FOR UPDATE）。SQLite 上全部是写租约 + `BEGIN IMMEDIATE`。PG `serializable()` 对 40001 / 40P01 重放最多
10 次；23505 从不重试。

### 1.2 迁移机制

- SQLite：drizzle-kit 生成，最新 `0259_rfc370_hosted_deployment`；admission 逐字节重放；携带比二进制更新回执的库会被拒绝
  （所以旧二进制不会写已迁移的 SQLite 库）。`T/upgrade-rolling.test.ts` 钉 `HEAD_TOTAL_MIGRATIONS = 259`。
- PostgreSQL：历史不可变，升级只能经 `bun run --filter @agent-workflow/backend db:rfc349-postgresql-schema --append <id>` 生成；
  每次升级必须对应至少一个 SQLite 迁移；头合同必须等于 `buildLogicalSchemaContract()`。升级种类只有 V1～V7
  （索引 / 新表 / CHECK 替换 / 表退役 / 源修订时钟 / 归属元数据 / 全唯一索引改部分），`logicalIndexAdditions` 拒绝任何行变更，
  `appendLogicalIndexes` 拒绝已有表上的唯一索引——**今天不能给已有表加列**。
- 托管 verify 允许较旧二进制服务于回执扩展了其历史的 schema，蓝绿期间旧二进制会继续插入不带新列的行。
- SQLite `AUTOINCREMENT` 主键投影为 PG `BIGINT GENERATED BY DEFAULT AS IDENTITY`；逻辑复制对每个 identity 列 `setval`，
  不变量检查 `nextval > max`。独立 sequence 不受合同、复制与不变量支持。

## 2. 排序合同

shared 新增 `SH/nodeRunOrder.ts`（从 `SH/index.ts` 导出）：

- `NodeRunOrderKey { id: string; seq: number | null }`——`seq` 必填（可为 null），漏选该列的投影编译失败；
- `compareNodeRunMintOrder(a, b)`：都有 `seq` 比 `seq`（同任务内不会相等，id 只作理论平局）；都没有比 id；只有一方有时，没有的一方更旧；
  这是全序、可传递；
- `isNewerNodeRun`、`newestNodeRun`、`nodeRunOrderAnchor(rows, id)`（把 `triggerRunId` / `sinceRunId` 一类 id 锚点解析为行键，
  行不存在时才回退到 id）。

SQL 写法在各站点内联（不新增跨 context import）：升序 `engineOf(db).ascNullsFirst(nodeRuns.seq), asc(nodeRuns.id)`；降序
`engineOf(db).descNullsLast(nodeRuns.seq), desc(nodeRuns.id)`（两种 capability 已存在于 `PP/capabilities.ts`）。SQL 孪生的
「S 比 R 新」：

```
(S.seq IS NOT NULL AND (R.seq IS NULL OR S.seq > R.seq))
OR (S.seq IS NULL AND R.seq IS NULL AND S.id > R.id)
```

domain 谓词调用比较器。

## 3. 分配

| 方案 | 同任务并发（PG SERIALIZABLE） | SQLite | 备份 / 复制 / 托管初始复制 | 旧二进制 | 判定 |
| --- | --- | --- | --- | --- | --- |
| `max(seq)+1` | 对 (task_id, seq) 索引的范围读带回 RFC-369 的页级谓词锁环；READ COMMITTED 下重复值 23505 不重试；破坏 rfc144 与 RFC-369 AC-2 | 可 | 可 | NULL | 否 |
| tasks 行计数器 `UPDATE … RETURNING` | 同任务 SERIALIZABLE 铸造在 tasks 行上写写冲突 40001，AC-2 会互等；破坏 W47「零 update」；与对 tasks FOR UPDATE 的 review / clarify 事务耦合锁序 | 可 | 可 | 计数漂移 | 否 |
| PG SEQUENCE | 无等待 | 需第二套机制 | 合同 / 迁移种类 / 复制 `setval` / 不变量都不支持独立 sequence | — | 否 |
| **identity 分配表** | `INSERT … RETURNING` 取 identity `nextval`：无读、无等待、无谓词锁；RFC-369 锁原样通过 | `AUTOINCREMENT`：单调、不复用、随事务回滚 | 现有 identity 机制自动 `setval(MAX)` 与 `nextval > max` 不变量 | NULL，由追平处理 | **采用** |

新表 `node_run_seq_allocations`：`seq INTEGER PRIMARY KEY AUTOINCREMENT`、`task_id TEXT NOT NULL`、`node_run_id TEXT NOT NULL`、
`allocated_at INTEGER NOT NULL`；无外键（不级联、不耦合归档）、无二级索引；表名前缀使其 owner 自动归 task-execution。

铸造程序：container? → task? → **allocate**（`tx.insert(nodeRunSeqAllocations).values({ taskId, nodeRunId: record.id, allocatedAt }).returning({ seq })`）
→ `insert(nodeRuns).values({ ...values, seq })`。必须先分配再插入——先插入再 UPDATE `node_runs.seq` 会读 `node_runs` 主键页，
重现 RFC-369 的环。`seq` 遵循分配顺序：因果有序的铸造等于提交顺序；真正并发的铸造任一顺序都是合法全序。
`NodeRunLifecyclePersistence.mint` 端口签名不变，调用方不能指定 `seq`。

## 4. Schema 与迁移

### 4.1 列与索引

- `node_runs.seq INTEGER`，可空，追加为**最后一列**（与两种引擎的 ALTER 物理追加一致）。必须可空：SQLite 不能加无默认值的
  NOT NULL 列且常量默认值会撞唯一索引；旧二进制插入不带它；加性行桥恢复旧归档时为 NULL；测试夹具不带它。
- `UNIQUE INDEX idx_node_runs_task_seq ON node_runs(task_id, seq)`，全索引（不用部分索引）：两种引擎的唯一索引里 NULL 互不相等；
  避免部分谓词的方言差异；同时服务任务内的 `ORDER BY seq`。

### 4.2 迁移（只 DDL）

- SQLite `0260_rfc374_node_run_seq.sql`（drizzle-kit 生成，每个断点一条语句）：建分配表、`ALTER TABLE node_runs ADD seq integer`、
  建唯一索引；`meta/0260_snapshot.json` 与 `_journal.json` 追加。
- PostgreSQL `0036_rfc374_node_run_seq`（在 0260 存在后生成）：V2（新 identity 表）+ 新增的 **V8**。

### 4.3 V8：已有表追加列（platform）

- 追加列必须位于一个活跃 KEEP 表的列末尾，可空或带字面量默认值，不得是主键、identity、唯一命名或外键；
- 已有表上的唯一索引只有在包含同一步追加的列时才允许；
- 重放把追加折叠进逻辑合同（`appendLogicalColumns` + 唯一性例外）；投影出的 `CREATE TABLE` 记为「被替换」，可执行语句是
  `ALTER TABLE … ADD COLUMN`（同 V3 的 CHECK 替换模式）；
- `applyPostgresqlIndexUpgrade` 接受 version 8；`resolvePostgresqlRowBridge` 在 `allowNewTables` 时折叠列追加，只含索引的桥保持严格；
- 恢复写入器的 INSERT 列清单必须取自 `bridge.source`，使新可空列得到 NULL（核实 `PP/logicalDatabaseRestore.ts` 及其写入器）。
- 文件：`PP/postgresqlMigrationSequence.ts`、`PP/postgresqlSchema.ts`（导出单列 DDL 渲染）、`PP/postgresqlMigrationHistory.ts`、
  `packages/backend/scripts/rfc349-postgresql-schema.ts`、`PP/schemaContract.ts`（`RFC349_SOURCE_TABLES` 增加新表）、
  `design/RFC-349-postgresql-provider-one-click-migration/schema-contract.{json,md}`（用 `db:rfc349-contract` 重新生成）。
- 这是 W7 余项（RunRole、scope、generationSeq 等）也需要的通用能力。

## 5. 存量追平

作为 `TE/application/bootExecutionRecovery.ts` 的第 0 步（两种 daemon 都调用：SQLite `cli/start.ts`、PG
`cli/postgresqlDaemonApplication.ts`；托管下经 `bootstrap/executionInitialization.ts` 在获得执行权后运行，失败即冻结实例）。
该函数已经 fail-closed 且在 HTTP 与自动 resume 之前运行，两个 daemon 根无需改动。

算法（纯规划器 + store；每任务或每批任务一个事务；以 `WHERE seq IS NULL` 幂等；可中断续跑）：

1. 循环 `SELECT DISTINCT task_id FROM node_runs WHERE seq IS NULL LIMIT k` 直到为空。
2. 对每个任务，设 P 为已有 `seq` 的行：
   - P 为空：一条语句把该任务的空行按 id 序赋值 (1−N)..0（`ROW_NUMBER() OVER (ORDER BY id) − COUNT(*) OVER ()`），保持既有 id 序；
   - 否则：`id > max(P.id)` 的空行（托管回滚期间旧二进制的写入，确实更新）按 id 序取分配器新值；其余空行按 id 序取
     `min(P.seq) − k … min(P.seq) − 1`（唯一性只在任务内，安全）。
3. 检查 `max(node_runs.seq) ≤ max(node_run_seq_allocations.seq)`（无分配时 ≤ 0），违反则以 `node-run-seq-allocator-behind` fail closed。
4. 分批删除 `seq < MAX` 的分配行（`BOUNDED_DELETE_MAX_ROWS` / `deleteByCandidates`），保留最大值行，使复制时的 `setval` 仍正确。

窗口函数（SQLite ≥ 3.25）与 `UPDATE … FROM`（SQLite ≥ 3.33）两种引擎都支持；`node_runs.id` 在 PG 上是 `COLLATE "C"`，与 SQLite
BINARY、JS 字符串比较同序。它们只用于追平，不用于迁移。健康库上的成本是一次只走索引的空值扫描。

文件：`TE/domain/nodeRunSeqBackfill.ts`（规划器）、`TE/application/ports/nodeRunSeqBackfillStore.ts`、`TE/application/nodeRunSeqBackfill.ts`、
`TE/infrastructure/nodeRunSeqBackfillStore.ts`（新）；`TE/application/ports/taskExecutionPersistence.ts` 增成员、
`TE/composition/taskExecutionPersistence.ts` 接线、`TE/application/ports/bootExecutionRecovery.ts` 扩 Pick 与报告计数、
`TE/application/bootExecutionRecovery.ts` 第 0 步与日志。

共存：正向蓝绿——激活前全为 NULL，展示按 id 序；激活后追平把既有行放到 ≤ 0、比已分配行更新的旧二进制行放到其上方。回滚——
规则 2 处理；激活前展示上旧二进制行显示为更旧（仅展示）。恢复旧归档——分配表为空、行为 NULL、追平给 ≤ 0。恢复 / 复制新库——
`seq` 逐字复制、`setval(MAX)`、identity 不变量成立。

## 8. 与 RFC-370 的时序

RFC-370 的 0259 / 0035 是**未发布**的整体重生成产物（RFC-370 v3 V11：未发布迁移按最终 schema 重新生成为一组；正式 M0 库停在
0034）。本 RFC 的 0036 链接到 0035 的摘要：

- 若在 RFC-370 冻结其迁移之前提交，RFC-370 之后的 schema 改动只能追加在 0260 / 0036 之后，不能再重生成 0259 / 0035
  （否则本 RFC 的迁移链要随之重生成）。
- 本 RFC 还会改动 RFC-370 自 2026-10-14 以来改过的多个文件（`db/schema.ts`、迁移 journal、`postgresqlMigrationSequence.ts`、
  `postgresqlMigrationHistory.ts`、`schemaContract.ts`、`scripts/rfc349-postgresql-schema.ts`、`bootExecutionRecovery.ts` 与端口、
  `nodeMechanics.ts`、`wrapperMechanics.ts`、`taskRouteOperations.ts`、collaboration `review.ts`、`services/task.ts` 等）。

因此建议在 RFC-370 冻结（或发布）其迁移之后再派发实施；届时以当时的迁移编号为准。

## 9. 测试策略

用 `describeEachProvider`（本地 `AW_TEST_PROVIDERS=sqlite`，CI Ubuntu 双引擎）；只断言相对顺序，不断言 `seq` 绝对值。

1. shared 比较器：seq 序、NULL 比 seq 旧、NULL 对 NULL 按 id；随机混合的传递性与全序性质测试；锚点解析（存在 / 缺失）。
2. picker 与判定单测：id 序与 seq 序相反的夹具，覆盖 §1.3 A～E 全部语义站点与 lifecycle invariant T3。
3. 铸造行为（双引擎）：同任务连续铸造严格递增；同毫秒 200+ 次铸造；后铸造行 id 更小（显式 id、工作组 host 预选 id、review rerun id）
   ——它是最新、被取代的一代受 RFC-369 merge 围栏与重放排除约束（这会翻转 RFC-369 AC-7 情形 2 对真实铸造的结论，属预期修正）；
   时钟偏移。
4. 冲突回归（PG）：RFC-369 AC-2 原样通过且两行 `seq` 不同且非空；READ COMMITTED 并发铸造无 23505；工作组 leader + member 提交
   的 SERIALIZABLE 重放次数为 0；W47 与 rfc144 源码锁（rfc144 增加「`insert(nodeRunSeqAllocations)` 恰在 `insert(nodeRuns)` 之前一次」）。
5. supersession 对拍：扩展 `T/rfc369-node-run-supersession.test.ts` 的混合 NULL 与 id / seq 倒置夹具，SQL 结果集等于纯函数结果集。
6. 追平：全空任务、旧二进制行、早于 P 的行、幂等、注入故障中断后续跑、清理保留最大行、不变量违反 fail closed、在
   `runBootExecutionRecovery` 中先于 reap 运行、SQLite 启动测试中追平失败导致启动失败、托管只在激活后运行；oracle：追平后存量行
   按 `seq` 与按 id 排序一致。
