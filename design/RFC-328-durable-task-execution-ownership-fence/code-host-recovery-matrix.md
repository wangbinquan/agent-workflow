# RFC-328 code-host recovery / transport matrix

> 状态：Approved implementation contract；用户于2026-08-26随RFC-328完整决策面批准，语义变化仍会使D10批准失效。
> 当前实现基线：`HEAD=origin/main=a23c1a4113ad849bfbded4524ae063ce1eacd6c1`；本地候选以`packages/shared/src/codeHost/actions.ts`的29 actions为registry、以`packages/backend/src/services/codeHost/call.ts`为transport执行器，并由独立manifest/fake oracle逐provider/candidate对拍；候选尚未把未发布内容写成hosted终态。
> 产品原则：功能远大于安全。不得用笼统`no-replay`删除既有transport/manual retry；每次真实send要可审计，unknown时只暂停无actor的auto，actor manual retry始终可重新授权。

## 1. 固定语义

### 1.1 Transport policy profiles

| Profile               | 当前/目标行为                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `T-READ`              | GET：network exception与5xx最多3次；429/Retry-After最多3次。read不进入mutation effect，但仍受timeout/size/redaction合同。                          |
| `T-POST`              | POST：network exception/5xx不自动重发；429/Retry-After最多3次。维持current行为。                                                                   |
| `T-IDEMPOTENT-METHOD` | PUT/PATCH/DELETE：network exception、5xx、429/Retry-After最多3次。维持current `IDEMPOTENT_METHODS`行为；不因本RFC的安全偏好收紧。                  |
| `T-FALLBACK`          | 只有当前candidate收到完整404/405响应，才按registry顺序尝试下一candidate；权限/参数/限流/5xx不切candidate。每次candidate send分别记effect attempt。 |

上述“最多3次”来自current`MAX_ATTEMPTS=3`，不是generic recovery coordinator重新推导的默认值。实现后每个transport send都先分配单调effect attempt；禁止HTTP helper在attempt ledger外隐形重发。policy允许下一send时，前一attempt写`retry-authorized`与原始application evidence；timeout/reset等ambiguity不会因“允许重试”被改写成未发生，logical结果必须聚合全部attempt。later applied维持current成功结果并留`prior_ambiguity` audit；later failure不能把早期ambiguity洗成definitely-not-applied。

### 1.2 Recovery profiles

| Profile         | 适用语义                                                          | response-loss后的行为                                                                                                                                                                                                      |
| --------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `R-READ`        | 只读                                                              | 按`T-READ`；不创建mutation receipt。                                                                                                                                                                                       |
| `R-EXACT`       | 已知provider object ID，重复请求收敛，且可回读exact postcondition | probe exact object；已达成则adopt，明确未达成才按transport/recovery policy创建下一attempt。                                                                                                                                |
| `R-STATE`       | 状态设置/集合增加/merge/cancel等可验证业务postcondition           | 回读exact MR/PR/run/status/label/assignee状态；已达成adopt，明确未达成才创建下一attempt。不能只看HTTP method。                                                                                                             |
| `R-RUN-RETRY`   | 对exact pipeline/run做retry                                       | act前冻结run attempt/job generation；probe确认generation已推进则adopt，未推进才retry。                                                                                                                                     |
| `R-PARTIAL`     | probe只能证明一个方向                                             | probe若能证明未执行，才可在同一operation generation retry；另一方向仍ambiguous并进入`R-ACTOR`流程，不能把“对象不见了”自动解释成目标动作成功。                                                                              |
| `R-ACTOR`       | create/reply/trigger等无法无歧义定位新对象                        | transport policy照旧；任一send最终仍unknown则task-wide closure写`requires-actor`。既有manual node/parent retry在同一command transaction记录actor decision；worker随后创建下一operation generation的attempt 1，不永久封禁。 |
| `R-UNSUPPORTED` | provider不支持                                                    | admission/validation失败；零HTTP send。                                                                                                                                                                                    |

Classifier公共下限：完整2xx/202/204按endpoint合同为`applied`；fetch前本地validation/build失败为`definitely-not-applied`；timeout/reset或provider返回但无法由本profile证明结果时为`ambiguous`。404/405只有声明`T-FALLBACK`时能证明当前candidate路由未执行并进入下一candidate。429按对应transport profile保留current retry；它不是generic takeover proof。

### 1.3 独立证据要求

- manifest/matrix只描述预期，fake provider行为不得从被测manifest生成；fixture要独立实现“先落地再断连”“未落地返回429”“落地后返回429（非标准/违约server）”等输入。
- 对标准provider，错误地把`R-ACTOR`改成`R-STATE`、删probe字段或改错object scope必须使测试失败。
- `mr.approve`的oracle必须独立制造三种response-loss后漂移：HEAD advance、GitLab approval reset、GitHub review dismissal；三者都不得因“当前HEAD当前actor已批准/未批准”而伪证旧request结果。正常request/success、既有429与manual retry另有正向fixture，确保`R-ACTOR`分类不收缩approve功能。
- 对custom，正向oracle锁住current调用次数；不能把“更安全”当成改变`T-IDEMPOTENT-METHOD`/`T-POST`的理由。
- actor manual retry是正向验收路径，不是stop gate绕过；必须记录actor、source、unknown operation generation/attempt、decision revision、bound intent和下一operation generation/attempt 1。
- aggregate oracle必须成对覆盖“attempt 1已落地后断连，attempt 2按current policy继续”：attempt 2明确失败时旧ambiguity仍在、本operation generation不能写definitely-not-applied；attempt 2明确成功时保持current成功能力并留prior-ambiguity audit。

实现T20前仍要用system-mocks的stateful fake为每个profile跑contract fixture；真实GitHub/GitLab测试只验证provider版本差异，不取代独立fake。若某self-managed版本缺probe endpoint，binding降为`R-ACTOR`只暂停auto，manual功能仍在；不能直接把整个action标unsupported或永久封禁。
