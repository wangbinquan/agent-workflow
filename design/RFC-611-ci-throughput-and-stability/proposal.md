# RFC-611：CI 吞吐、分片均衡与失败信号

## 授权与背景

用户 2026-11-26 要求全面分析 AW GitHub CI 的耗时与高失败率，阅读诊断后明确指示「按你的推荐来实施」。本 RFC 将已批准的第一层建议具体化；不再次请求同一实施授权。

诊断读取最近 300 次 main push，深查最近 100 次。其中初始快照 95 次终态为 45 success、43 failure、7 cancelled；成功运行中位 51.3 分钟，平均 550.4 runner 分钟。43 次 failure 中 16 次仅外部故障、22 次测试/内容/预算、5 次混合。7 次 cancelled 中 6 次是 job 超时。CI required 平均另排队 15.4 分钟。

基线是主 CI run 45772006810，SHA 170f3e2cc32ce7c20c58afc1b2660eec75315d65：44 backend artifacts 精确覆盖当时 3081 文件，实际 395.42 runner 分钟；旧权重 360.32 分钟。最长 backend job 14m03s，已占 15 分钟预算 93.7%。当前 HEAD 8cf8ee11d 的文件新增必须单独识别，不能伪装为已测。

## 目标与非目标

- 保留每个原始 SHA 的完整主 CI 终态及 CI required 的全成功判定，限制同分支完整矩阵的同时展开数。
- 保留现有测试全集、provider、平台、故障步骤、断言与 job/test 预算；改善分片和夹具。
- 让静态错误尽早产生独立 advisory 信号，不将它冒充正式门禁。
- 将仓内断链与外部站点临时故障分开：提交门查全部仓内链接与变更文档的外链，全历史外链由周期检查承担。
- 提供可以反复使用的计时刷新、完整性核对和时长证据。

不取消旧 SHA 的完整 CI，不购买或假设独立 runner 容量，不把历史升级矩阵移出每次提交，不改变生产升级协议，不整体放宽超时，不以重跑成功证明缺陷已修复。

## 验收标准

1. 同 ref 主 CI 最多两条 run 执行，其余保留排队；同 run 重试使用同一 lane，CI required 全部旧依赖仍必须成功。
2. CI feedback 独立命名、可取消旧反馈、不进入 required 判定；质量缓存必须有可靠失效条件。
3. 后端权重更新来自完整的成功原始 artifacts；缺片、重复、非法值或来源文件全集不符拒绝更新，已删除路径不复活，未测新文件明示。
4. Playwright 使用原生发现和运行，文件级分配无遗漏/重复，原 grep/project、文件内串行、workers、retries 保持；新增文件自动参与。
5. JSON barrier 原子发布，意外子进程失败迅速显示原错误；故意 kill 和正常历史退出不误报。
6. 构建未成功时对应 E2E 不下载不存在产物，上游失败仍使 CI required 红。
7. 所有开发与回归用例完成后集中验证；发布后跟踪 exact-SHA CI。新的耗时目标需 hosted 数据验证，不以静态预测冒充收益。

## 能力影响

产品能力及测试覆盖不收缩。全历史外链的可用性不再阻塞每个无关提交，发现时机改为每日；改动文档外链和全部仓内链接仍是提交门。此项是用户已接受诊断建议中的检查策略调整，单独保留可见的 nightly 结果。
