- 状态：Done（2026-08-01；三轮设计门与固定 SHA 实现门均
  `APPROVED — P0=0/P1=0/P2=0`；代码 SHA
  `1fbbd46388d458afda526115786c045ea17ac133` 的 main CI run `30700645728` 全绿）
- 日期：2026-08-01
- 触发：用户要求重做任务列表 UX，并明确「任务会比较多，所以任务行高度小一些」；随后确认按推荐方案推进。
- 相关 RFC：RFC-036（任务可见性）、RFC-108（生命周期告警）、RFC-165（执行主体）、
  RFC-192（现行任务列表）、RFC-203（失败码）、RFC-232（Owner 列）、RFC-243（父子任务）。

## 1. 背景

当前 `/tasks` 已能查看状态、名称、主体、Owner、仓库、开始时间、耗时和父子任务，但它仍是
「功能逐项叠加」后的宽表，而不是适合大量运行记录的任务运行中心：

1. 页面首屏同时铺开 8 个原始状态 chip、子任务范围、主体范围和名称搜索；用户需要先理解
   技术状态枚举，再决定从哪里开始筛。
2. 桌面表格有 8 列且使用 `TableViewport minWidth="lg"`。在常见 1280px 窗口里，Owner、仓库、
   开始与耗时不能同时稳定扫读；窄屏则依赖横向滚动。
3. 页面请求 `GET /api/tasks?limit=500`，只有单个状态在服务端过滤；主体和名称只在这 500 条
   窗口内做前端过滤。任务继续累积后，搜索结果可能被静默截断。
4. RFC-243 默认只返回顶层任务，另设「仅顶层 / 含子任务」切换。前者需要逐层展开，后者又把
   父子任务拍平成一张表；用户必须切换数据形态，才能回答「现在有哪些任务需要处理」。
5. 搜索不覆盖子任务；展开子任务也不继承当前状态、主体和搜索条件。筛选结果与展开结果可能
   属于两个不同集合。
6. 当子任务可见而父任务不可见时，现有 flat 模式会从前端再探测父任务详情，只为决定是否
   渲染链接。列表本身应直接给出安全的树上下文，不应靠客户端权限探针补齐。
7. 后端 `listTaskSummaryRows` 使用 `.select({ task: tasks })`，会为列表读取
   `workflow_snapshot`、`inputs`、`ref_closure_json` 等大字段；高任务量下，这比行高更早成为
   容量瓶颈。

问题的核心不是再压缩几像素，而是要把「定位需要关注的运行 → 看懂上下文 → 进入详情」变成
同一条高密度、可分页、权限一致的路径。

## 2. 目标

- **G1 业务视图优先**：首层只保留「全部 / 进行中 / 需处理 / 已结束」四个业务视图，默认
  「全部」；原始状态进入高级筛选。
- **G2 高密度扫读**：桌面普通父任务行目标高度 56px、子任务行 48px；不是固定裁切，Owner、
  本地化文案或辅助技术要求更多空间时允许自然增高。
- **G3 信息重组而非丢失**：将主体、仓库、短 ID、定时来源收拢为任务的次级元信息；保留独立
  执行状态、时间和 Owner，避免横向滚动才能看完整行。
- **G4 一棵任务树**：移除「仅顶层 / 含子任务」切换。所有子任务始终归入父任务分支；筛选命中
  子任务时，返回必要的可见祖先上下文并自动展开。
- **G5 全量服务端查询**：搜索、业务视图、精确状态、主体、归属范围和启动来源都作用于 actor
  可见的完整任务集合，不再依赖最新 500 条的客户端窗口。
- **G6 有界分页**：使用确定性的 keyset pagination，默认每批 50 个兄弟分支、上限 100；根层和
  任意子层均可继续加载。
- **G7 授权与归属筛选分层**：先按 actor 的真实读取权限建立 authorized set，再把「我参与的 / 与我
  共享 / 全部归属」作为 self-match 筛选。祖先、父子边和 `parentAvailability` 只看 authorized
  set；父任务未授权时，子任务作为安全根节点展示，前端不再探测父任务。
- **G8 轻量后端投影**：列表主查询只选展示所需列，不读取 workflow snapshot、inputs 或引用闭包；
  Owner、告警与失败码继续批量补齐，禁止 N+1。
- **G9 响应式而非横向搬运**：桌面为紧凑记录网格，≤720px 改为单列记录布局；移动端不依赖横向
  滚动，展开和主操作满足至少 44px 触控目标。
- **G10 可恢复交互**：筛选写入 URL；刷新、前进后退和复制链接保持同一结果。分页、子分支、
  实时更新和错误分别有明确状态，不因局部失败清空整页。

## 3. 已确认的产品决策

- **D1 — 完整前后端改造**：不是只改 CSS；新增列表专用分页 wire，并重写 `/tasks` 的查询与
  信息架构。现有通用接口保持兼容。
- **D2 — 默认「全部」**：进入 `/tasks` 时展示 actor 可见的全部任务记录，不默认收窄到进行中
  或顶层任务。
- **D3 — 子任务统一入树**：移除列表范围切换；父子关系是稳定信息架构，不再让用户在嵌套与
  flat 两种数据模型间切换。
- **D4 — 紧凑但不牺牲可读性**：56px / 48px 是普通内容的目标值，不是 `height` 硬限制；长
  Owner 保留可见的 username/stable id 并允许换行。
- **D5 — 四个业务视图允许重叠**：「需处理」是行动队列，不是终态分区。失败任务同时属于
  「需处理」和「已结束」；等待人工的任务同时属于「进行中」和「需处理」。
- **D6 — 精确状态降级为高级筛选**：所有 `TASK_STATUS` 仍可组合过滤，但不再占用首屏一整行。
- **D7 — 首版不伪造步骤进度**：动态 fan-out、wrapper、重试和工作组没有统一且准确的 `3/5`
  语义。首版显示真实状态、告警、失败摘要与计时，不从 `node_runs` 猜测百分比；准确进度需要
  单独定义运行时投影后再引入。
- **D8 — 首版不做批量动作**：列表承担定位与进入详情，不在本轮加入多选、批量取消、删除或
  重试，避免把高风险生命周期动作塞进密集行。
- **D9 — 语义嵌套列表而非伪 tree table**：桌面仍呈现五列记录网格，但 DOM 使用原生嵌套
  `<ol>/<li>`、稳定 branch id 与原生 link/button；不在 native table sibling rows 上只补
  `aria-level`，也不引入需要 roving focus 的半套 `treegrid`。
- **D10 — 列表稳定优先于事件内联改写**：task/member/alert 事件只把 operations 数据标记为 dirty；
  用户刷新或 15 秒兜底后从第一页原子重建，不凭 WS payload 猜 Owner、facet 或树结构。

## 4. 用户故事

1. 作为运维者，我进入任务页就能按匹配分支的最近启动顺序看到全部可见任务，并立即知道哪些
   正在运行、哪些需要我处理。
2. 作为拥有大量历史任务的用户，我能搜索名称、ID、主体或仓库；结果来自完整数据集，不会因为
   任务排在第 501 条以后而消失。
3. 作为工作流负责人，我能在同一分支里理解父任务和调用产生的子任务；搜索命中深层子任务时，
   仍能看到它所属的可见上下文。
4. 作为只能看到某个子任务的协作者，我能直接从该子任务根行进入详情；页面不会暴露、探测或
   生成一个无法访问的父任务链接。
5. 作为笔记本或手机用户，我无需左右滚动即可读取任务、状态、时间和 Owner，并能可靠点按
   展开按钮与主链接。
6. 作为键盘和辅助技术用户，我能用原生链接进入详情、用带 `aria-expanded` 的按钮展开分支，
   并在筛选或实时刷新后得到可理解的结果数量播报。

## 5. 验收标准

1. `/tasks` 首层视图为「全部 / 进行中 / 需处理 / 已结束」，默认「全部」；业务视图的状态与告警
   口径由 shared 常量单源定义并有穷举测试。
2. 原始状态、主体、范围和启动来源进入「筛选」面板；搜索与全部筛选均写入并可从 URL 恢复，
   未知/重复参数被 canonicalize。
3. 新 endpoint 对完整 authorized 集合执行过滤与搜索，返回严格 schema 的有界页面；默认 50、
   最大 100，按匹配分支 `branchStartedAt` 倒序，相同值以 task id 确定性打破平局。
4. 根层与子层都支持 cursor；正常滚动期间没有重复行，实时刷新后的客户端按 id 去重并从第一页
   重新建立分页边界。
5. 所有可见子任务只在父任务树中出现一次；筛选命中子任务时返回可见祖先作为 context row，
   分支自动展开；用户手动折叠优先，直至筛选条件变化。
6. 父任务未授权或数据异常形成 dangling parent 时，可见子任务成为根行并显示中性的「父任务
   不可用」上下文；response 不包含任何不可见父任务的名称、状态、Owner、仓库或其他投影，
   前端不发父任务权限探针。正常删除继续遵守 RFC-243 `ON DELETE CASCADE`，不会留下持久 orphan。
7. 桌面普通父行目标 56px、子行 48px，列收敛为「任务 / 执行 / 时间 / Owner / 展开」；长内容
   不破坏列宽，Owner 的唯一身份不靠 hover 才能读取。
8. 390×844 和 390×568 下不产生页面级或列表级横向溢出；移动端以单列记录布局呈现，主要触控
   目标至少 44px，筛选面板和软键盘场景仍可操作。
9. 初始 loading、空数据库、无匹配、首层失败、子分支失败、分页失败均使用既有公共反馈组件；
   子分支失败不移除父行，分页失败不清空已加载内容。
10. 列表查询不选择 `workflow_snapshot`、`inputs`、`ref_closure_json` 或完整 task row；Owner、告警、
    失败码与子分支计数按页批量查询，无逐行 HTTP/SQL。
11. task/alert create/status/delete/member-change/open/promote/resolve 都能使 operations 页面进入 dirty
    状态；成员变更使用 before/after audience 并集，并在现有 WS actor revalidation **全部完成后**才
    广播，避免 frame 被冻结窗口丢弃；正常删除对级联集合逐 task 使用删除前冻结 audience 授权事件，
    新增/移除成员与 child-only actor 都不会长期保留错误列表。刷新时不改变 URL 筛选，且不会在
    扫读中途静默插行。
12. 现有 `GET /api/tasks` 默认数组 wire、`include_owner`、`include_children`、`parent_id`、详情页
    `useTaskChildren`、首页与既有 WS message 形状保持兼容；仅 additive 新增 member-change /
    alert-resolved 通知，只有 `/tasks` 页面迁移到新 endpoint 与 operations-specific sync hook。
13. shared/backend/frontend 定向测试、全量门禁、desktop/mobile Playwright、axe、VoiceOver/键盘、
    视觉基线与实现门均通过；RFC 文档与真实行为一致。

## 6. 非目标

- 不修改任务状态机、调度、恢复、取消、删除资格/级联或告警判定；允许补齐列表真值所需的
  member-change、alert-resolved、删除 audience 通知与可等待的 WS revalidation adapter，但不改变
  既有授权判定或其他调用点的 fire-and-forget 语义。
- 不重做任务详情页、首页最近任务、定时任务列表或任务创建流程。
- 不加入批量取消/删除/重试、行内生命周期操作、列自定义或任意排序。
- 不在首版实现虚拟滚动、FTS 索引或准确的节点步骤百分比；分页和轻量投影先解决当前容量问题。
- 不改变 overview 默认排除子任务的 RFC-243 口径；业务视图计数仅属于新任务列表 endpoint。
- 不扩大 `tasks:read:all`、owner/collaborator 或任何资源 ACL。
- RFC 获批不自动授权 commit、push 或发布。
