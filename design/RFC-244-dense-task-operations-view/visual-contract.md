# RFC-244 · 任务运行中心视觉契约

状态：Accepted visual baseline（2026-08-01）

## 目的

本文件把用户确认的首版交互原型转成仓库内可审计、可自动回归的视觉契约。原始可交互原型位于
Codex 会话产物 `task-list-ux.html`；会话外路径不是长期构建输入，因此从本文件起，以这里的规则、
对应 source-lock、Playwright geometry 与截图基线共同作为 RFC-244 的视觉验收依据。

技术设计中的 ACL、分页、统一任务树、真实执行状态和公共组件约束继续有效；它们不能成为偏离已批准
界面结构的理由。

## 必须保持的桌面结构

1. 标题、副标题、新建任务、业务视图、搜索、筛选与任务列表处于同一个有边框和轻阴影的 surface。
2. 标题区在上，业务视图与搜索/筛选在下一层；列表表头直接承接工具区，不拆成数个相互悬浮的卡片。
3. 行的视觉列为「任务 / 执行 / 时间 / Owner / 进入详情提示」。最后一列只放无障碍隐藏的右向
   chevron，提示整行可进入任务详情。
4. 有可见子任务时，展开按钮放在任务名左侧。展开按钮控制分支，不占用最后一列，也不触发行导航；
   无可展开分支的行保留同宽 spacer，使任务名对齐。
5. 普通父行以 `min-height: 56px` 为密度目标，子行以 `min-height: 48px` 为目标；长 Owner 等必要正文
   允许自然增高，不以固定高度裁切。
6. 任务名保持单行省略，并通过原生详情链接与 `title` 恢复完整名称。次要信息退到一行 metadata，
   不把 repo、ID、来源全部做成高对比 chip。
7. 展开的子任务位于父行下方的 inset well：桌面左缩进 55px、右侧留白、左侧强调色 rail、轻微底色，
   让层级关系先于状态色被识别。子行仍使用相同列网格。

## 必须保持的移动端结构

1. 业务视图只在自身容器内横向滚动；页面与结果列表不得横向滚动。
2. 搜索和筛选保持同一工具行，搜索获得剩余宽度；窄于 430px 时可隐藏筛选文字但保留图标与可访问名。
3. 同一语义 DOM 重排：任务与执行状态优先，时间和 Owner 后置；不维护第二套移动列表。
4. 展开按钮扩大到至少 44×44px；右侧详情 chevron 可隐藏。子任务 well 在移动端仍保留缩进和 rail。
5. 390×844 与 390×568 均不得产生 document、main 或列表级横向 overflow。

## 有意保留的产品化差异

以下差异是经技术设计约束后的增强，不视为偏离原型：

- 高级筛选使用公共 `Dialog`、`Form`、`Segmented` 与 `MultiSelect`，不复制原型里的内联 checkbox
  panel。
- 不展示原型中的虚构 `N/M` 进度；只展示后端持久化的状态、告警、失败摘要和运行/排队时间。
- 子任务始终使用服务端 ACL 树与有界分页；不恢复旧的「显示子任务」双形态开关。
- 行、空态、错误、dirty banner 与加载更多使用现有公共组件和现有设计 token。

## 自动验收

- source-lock：surface、左侧展开/右侧详情 chevron、单行任务名、inset child well。
- Playwright geometry：1280×800 下展开按钮位于任务名左侧，详情 chevron 位于 Owner 右侧；父/子
  普通行分别不高于 64/56px（必要长正文除外）。
- responsive geometry：390×844 与 390×568 下展开按钮至少 44×44px，搜索/筛选同排，无横向
  overflow，child well 仍相对父行缩进。
- visual baseline：macOS 本地预检与 hosted-Ubuntu exact-SHA 截图均需人工查看，而不是只接受 snapshot
  像素更新。
