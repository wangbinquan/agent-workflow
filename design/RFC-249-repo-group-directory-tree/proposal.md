# RFC-249 — 仓库组目录树：一等目录节点与紧凑编排

> 状态：**Approved（用户于 2026-08-03 明确批准）**
> 日期：2026-08-03
> 前置：RFC-248 已完成；本 RFC 只重做仓库组的定义模型、管理交互与目录快照，
> 不改它已经落地的权限域、记忆 scope、diff、只读、sparse 与自动提交语义。

## 1. 背景

RFC-248 把仓库组实现成一组扁平的 `members[]`。每个成员自己填写
`mountPath`，前端再从这些路径反推一棵只用于展示的树。这满足了运行时，却造成
两个产品问题：

1. 用户心智是「先有目录树，再把仓库挂到节点」，当前产品却要求逐行填写
   「仓库 + 完整挂载路径 + ref + subdir + readonly」。目录不是数据，只是字符串
   的偶然前缀；因此无法保存纯目录，也无法表达「先建结构，稍后挂仓」。
2. 高频场景是根下平铺很多仓库。当前每个仓占一张多字段卡片，选 20 个仓要重复
   20 次添加、选择和填路径；右侧再放一份重复预览，信息密度低且移动端更拥挤。

这不是换颜色或缩小间距能解决的问题。只改前端会继续把目录伪装成路径字符串，
并且纯目录会在保存、任务启动或重新运行时丢失。

## 2. 目标

- 仓库组的唯一产品模型是一棵**显式目录树**；根节点固定存在，路径为 `''`，
  UI 显示为 `/`。
- 每个目录节点可以不挂任何资源，也可以挂一个代码仓或一个子仓库组；挂载后仍可
  继续拥有子节点。
- 根节点与其它节点同构，允许挂仓，但界面与文案中没有「主仓」概念。
- 优先优化「根下平铺 10–32 个仓」：多选已有仓、批量粘贴 URL、自动生成目录名、
  批量只读与批量移动均是一轮操作。
- 编辑器保持紧凑：一棵可编辑树就是主界面，点中节点才展开一行就地设置，不再常驻
  成员卡片和重复的右侧检查器。
- 纯目录进入持久化、布局预览、任务冻结快照、重新运行与工作区物化全链，不能只在
  浏览器内存在。
- 既有 RFC-248 仓库组无损迁移；当前所有 repo/ref/subdir/readonly/子组引用及最终
  仓库挂载路径保持一致。

## 3. 非目标

- 不引入「主仓」「默认仓」「owner repo」或仓库间依赖关系。
- 不把仓库组改造成任意文件管理器；只管理目录节点与资源挂载，不上传或编辑普通文件。
- 不改变任务的仓库 diff、结构化 diff、分片 key、只读告警、自动提交推送和记忆注入
  语义；它们仍只围绕实际仓库工作树工作。
- 不支持手工调整同级节点顺序。同级节点按名称稳定排序；拖放只改变父节点。
- 不新增权限点或 per-resource ACL。继续复用 `repos:read/create/update/delete`。

## 4. 术语

- **目录节点（node）**：仓库组里可持久化的一等实体，由相对任务根的规范路径唯一
  标识。根节点路径为 `''`。
- **挂载（attachment）**：目录节点上可选的一项资源，类型为 `repo` 或 `group`。
  一个节点至多一个挂载。
- **纯目录**：没有挂载的节点。它仍会保存、预览并在组任务启动时创建。
- **定义树**：某一个仓库组直接保存的节点集合。
- **展开树**：递归展开子组后，以任务根为基准合并得到的目录节点与仓库布局。
- **最近祖先仓**：从一个纯目录向根回溯，路径最深的已挂仓节点。

## 5. 决策清单

### D1 — 目录节点是唯一事实源

仓库组从 `members[] + mountPath` 切换为 `nodes[] + attachment?`。每个定义必须显式
包含且只包含一个根节点；每个非根节点的直接父目录也必须显式存在。前端不再从仓库
路径猜目录，后端也不维护第二套成员表示。

### D2 — 根节点普通化

根节点固定显示为 `/ 工作目录`，不可删除、不可改名、不可移动；它可以不挂资源、
挂仓或挂子组。挂在根上的仓只是「挂载路径为 `/` 的仓」，不是主仓。内部为兼容
`tasks.*` 镜像列仍需选定 `task_repos[0]`，该顺序不出现在产品语义里。

### D3 — 一个节点至多一个挂载

挂载是 `null | repo | group` 三态。仓与子组互斥；纯目录不带 `ref/subdir/readonly`。
`readonly` 属于挂载而不是目录：仓挂载只影响该仓，子组挂载按 RFC-248 继续向内取
只读并集。

### D4 — 挂仓节点仍可有子节点

禁止再把「叶子节点」和「仓库节点」画等号。仓挂在 `/apps` 后，`/apps/web` 仍可
存在并继续挂另一个仓。RFC-248 的嵌套 worktree、占用检查与 `.gitignore` 预置
commit 语义保持不变。

### D5 — 纯目录进入全链

纯目录必须：

- 保存在组定义中；
- 出现在组列表、编辑器与任务详情的布局树中；
- 进入启动时的不可变任务快照；
- 在工作区中真实创建；
- 使用 `sourceTaskId` 重新运行时从冻结快照恢复，而不是重新读取当前组定义。

只保存 UI 外壳但不落到任务工作区不算完成。

### D6 — 纯目录内文件的归属

纯目录本身不是仓库：

- 位于某个已挂仓节点内部时，新文件天然属于**最近祖先仓**，沿用 Git 自身语义；
- 不位于任何仓内部时，它是组空间里的非版本化目录，内容不进入仓库 diff 或自动推送。

编辑器对后者显示「未纳入版本控制」提示，但不禁止创建；这与今天没有根仓的组空间
根目录语义一致。

### D7 — 子组仍是节点挂载

保留 RFC-248 的组套组。子组挂在节点 N 时，其根与 N 合并，其余节点以 N 为前缀
展开。N 仍可有本组自己的子节点：

- 同路径的纯目录合并为同一个目录；
- 一边纯目录、一边仓挂载时合并为一个挂仓节点；
- 同一路径出现两个实际仓挂载时保存失败；
- 只读从子组挂载向其展开仓传播，不影响 N 的本地子节点。

### D8 — 平铺场景以批量添加为主入口

编辑器顶部主操作为「添加仓库」，打开可多选的现有仓列表；一次确认创建所有对应
节点。并列提供「粘贴 URL」：一行一个 URL，逐行校验，一次确认加入。单仓逐个添加
仍可用，但不是唯一入口。

### D9 — 自动目录名可预测

批量添加时，以仓库 URL 的最后一段去掉 `.git` 生成目录段；非法路径字符折叠为
`-`。目标父节点下：

- 同名纯目录且尚未挂载时，直接把仓挂上去；
- 已有挂载或同批冲突时，依次使用 `name-2`、`name-3`；
- 比较大小写不敏感，结果在保存前可逐项改名。

### D10 — 单树面板，不做双份预览

编辑器只保留一棵可编辑树。树行常态只显示：目录名、挂载资源短名、可选
`@ref` / `subdir` / `只读` 标签和子节点数。选中一行后，在该行下方展开紧凑设置；
切换选择时前一个设置收起。不再永久展示右侧预览和每成员一张多字段卡片。

服务端干跑预览继续存在，负责递归展开、碰撞与上限校验；结果以行内错误、顶部摘要
和子组的只读展开预览呈现，而不是复制一棵第二树。

### D11 — 分清「解除挂载」与「删除目录」

- **解除挂载**：保留目录与全部子节点，只移除该节点上的仓/子组。
- **删除目录**：删除整个子树；若子树含挂载，确认框必须显示将移除的目录数与挂载数。
- 根节点只能解除挂载，永远不能删除。

删除 cached repo 或 force 删除被引用子组时，服务端也采用「解除挂载、保留目录」；
不能像 RFC-248 那样把整行成员连同路径一起删掉。

### D12 — 移动与改名是子树操作

重命名节点只改当前目录段并同步重写全部后代路径；移动节点只更换父节点并保留整棵
子树。根、移入自身后代、大小写冲突、保留路径和重复挂载均在本地预检并由服务端
再次校验。

### D13 — 拖放是快捷方式，不是唯一通道

桌面支持把节点拖到另一个目录下；拖放不承担同级排序。键盘、触屏和辅助技术始终
可通过「移动到…」选择器执行同一操作。失败时保持原树不变，并把原因写进
`aria-live` 区域。

### D14 — 多选后批量修改

复选进入批量模式，可对多个节点执行：设为只读/可写、移动到、解除挂载、删除。
只读操作跳过纯目录并在结果摘要中报告；批量移动若任一项目冲突则整批不应用，避免
一半成功后难以恢复。

### D15 — 同级稳定排序

同级节点按目录段大小写不敏感排序，再以原字符串兜底；目录树没有手工顺序字段。
仓库物化顺序也固定为「路径深度、规范路径」；同源仓分支后缀因此可预测。

### D16 — 容量与保存不变量

- 直接定义最多 128 个目录节点（含根）；
- 展开子组后最多 256 个目录节点；
- 展开后最多 32 个仓、组嵌套深度最多 5，沿用 RFC-248；
- 普通保存必须至少展开出一个仓；force 删除外部资源仍可能留下暂时不可启动的空组，
  启动时继续以 `repo-group-empty` 明确拒绝。

### D17 — wire 断代必须失败关闭

管理 API 的规范写入字段从 `members` 改为 `nodes`。旧客户端若继续 PUT
`members`，服务端显式返回 422 `repo-group-members-retired`，绝不依赖 Zod 默认
剥离未知字段后把组保存成空树。响应带 `schemaVersion: 2`。

这是一次有意的管理契约断代；任务启动仍只传 `repoGroupId`，定时任务、记忆绑定和
既有任务读取不受影响。

### D18 — 任务冻结目录树

新建组任务时把**展开后的所有节点路径**写进独立任务快照表。重新运行读取
`task_repos + task_space_nodes`；旧任务没有节点快照时，从 `task_repos.mount_path`
及其祖先补出最小目录闭包，保持可重放。

### D19 — 单仓 baseline 只覆盖退化树

只有同时满足以下条件，才落回 RFC-248 的单仓字节级 baseline：

- 展开后只有一个仓；
- 仓挂根、`subdir === ''`；
- 展开树只有根节点。

根下只要还有一个显式目录，就走组空间物化，以保证目录真实存在且能被冻结重放。

### D20 — 目录创建不跟随符号链接

平台创建纯目录时逐段 `lstat`：已有目录可复用；普通文件、Git 管理文件或符号链接
一律拒绝，不能让递归 `mkdir` 经仓库内 symlink 逃出任务根。错误返回具体节点路径，
失败物化沿用现有组空间的全量回收租约。

### D21 — 权限与敏感信息不变

读、建、改、删继续使用 `repos:*`；组、仓 URL 继续只返回脱敏形态。批量粘贴 URL
只在保存时导入，预览仍为纯读，不能因用户每敲一行就创建 `cached_repos` 垃圾记录。

### D22 — 响应式与可访问性是交付门

- 桌面树行视觉高度目标 36px，设置行按内容展开；移动端交互目标不小于 44px。
- 390px、736px 与桌面宽度无横向溢出；深层缩进达到阈值后改用短缩进 + breadcrumb，
  不把内容推到屏外。
- 所有仅 hover 出现的操作在 focus 时也出现；树使用正确的 `tree/treeitem`、
  `aria-level/expanded/selected`；拖放有完整键盘替代。
- 完成 zh-CN / en-US 文案，不用颜色单独表达挂载、只读、选中或错误。

### D23 — 资源与启动表面保持同一套紧凑交互

- `/repos` 的「远端仓库 / 仓库组」使用页面级下划线 Tab，不再把两个资源类型做成
  突兀的分段按钮；内容区仍是对应的可访问 tabpanel。
- 仓库组列表展开目录树时，复用任务列表的展开按钮、动效、焦点与 ARIA 契约，不再
  单独维护一套字符箭头。
- 创建任务时，仓库和仓库组是**同一个代码空间选择器**里的两类选项；选中仓库组后
  目录树在同一行内展开，切换来源不替换成另一张卡片。
- 未选择代码来源时，只显示这个选择器。手工 URL 是选择器里的显式入口，选择后才
  展开 URL 输入；仓库已选中或 URL 有效后才显示分支与自动同步说明。

## 6. 核心用户流程

### 6.1 平铺添加很多仓

1. 新建仓库组，输入名称；树里已有不可删除的 `/ 工作目录`。
2. 点击「添加仓库」，一次勾选 20 个缓存仓。
3. 系统在根下生成 20 个目录节点并挂仓，自动处理同名冲突。
4. 用户可直接保存；需要统一只读时全选后点一次「设为只读」。

整个流程不要求逐仓手填完整路径。

### 6.2 从平铺整理成层级

1. 新建 `apps`、`libs` 两个目录。
2. 多选若干仓并「移动到 apps」；或在桌面拖到 `apps` 行。
3. 路径与后代同步更新，服务端预览重新校验嵌套冲突。

### 6.3 节点挂仓并继续向下

1. 在根节点挂 monorepo。
2. 在根下创建 `vendor/sdk`，把另一个仓挂到 `sdk`。
3. 任务启动继续使用 RFC-248 的外层仓排除与嵌套 worktree 机制；界面从不把根仓
   称为主仓。

### 6.4 解除仓但保留结构

1. 选中 `services/payments`，点击「解除挂载」。
2. `services/payments` 与其子目录仍在树中；可以马上挂另一个仓。
3. 若删的是缓存仓或被引用子组，force 后也得到相同结果。

## 7. 验收标准

### 数据与契约

- **AC-1** 迁移后每个 RFC-248 组都有显式根及完整祖先闭包；展开后的仓路径、
  ref、subdir、readonly、子组链与迁移前逐项一致。
- **AC-2** 节点可无挂载、挂仓或挂子组；挂载节点可有子节点；根节点同构且无主仓文案。
- **AC-3** 保存拒绝缺根、多根、缺父、大小写碰撞、非法路径、双挂载、仓/节点/深度
  超限与展开后零仓。
- **AC-4** 同路径纯目录合并；纯目录与单一仓挂载合并；两个仓挂载碰撞返回 422，
  错误体含路径及两条来源链。
- **AC-5** `members` 写入显式 422，不能被静默剥离；API/MCP 文档只示例 `nodes`。
- **AC-6** force 删缓存仓或被引用子组只解除相应挂载，目录和后代保持不变。

### 运行时

- **AC-7** 纯目录在组空间真实落盘；已有安全目录幂等复用，文件或 symlink 占用返回
  可操作 422，失败后无残留 worktree/owned root。
- **AC-8** 任务冻结全部展开节点；组随后改动或删除，`sourceTaskId` 仍恢复原目录树。
- **AC-9** 旧任务无节点快照时可从仓挂载路径恢复最小闭包。
- **AC-10** 只有「根节点 + 一个整仓」走现有单仓路径；多一个纯目录即走组空间。
- **AC-11** 纯目录内文件按最近祖先仓归属；无祖先仓目录中的文件不伪装进任何仓 diff。
- **AC-12** 既有 nested repo、readonly、sparse、wrapper-git、multipart、diff、结构化
  diff、自动提交推送与记忆测试不回退。

### UX

- **AC-13** 一次多选可加入至少 20 个已有仓；一次粘贴可解析至少 20 行 URL；自动
  目录名冲突可预测且保存前可改。
- **AC-14** 默认树行不展示完整设置表单；选中一个节点只展开该节点的一行设置。
- **AC-15** 解除挂载与删除子树是两个清晰操作；含挂载子树的删除确认显示影响数量。
- **AC-16** 多选支持批量 readonly、移动、解除挂载、删除；原子失败不留下半套结果。
- **AC-17** 桌面拖放与「移动到…」得到同一树变换；根、自身后代与冲突目标不可选。
- **AC-18** 组列表展开、编辑器、任务详情共用同一目录树投影，不再由仓路径临时猜树。
- **AC-19** 390px / 736px / 桌面均无横向滚动；长 URL/组名可读，不以永久省略号
  隐藏唯一识别信息。
- **AC-20** Chromium + WebKit 通过鼠标、键盘与触屏路径；焦点恢复、`aria-live`、
  树语义和 44px 移动端目标通过检查。资源页使用下划线 Tab；组列表与任务列表共用
  展开按钮；任务启动的仓库/仓库组共用单一选择器，初始无 URL/分支输入，手工 URL
  与分支按上述条件展开。

### 质量

- **AC-21** shared/backend/frontend 针对纯函数、迁移、CRUD、预览、物化、重放、
  force detach、响应式与交互均有正反向测试。
- **AC-22** 全仓 `typecheck`、`lint --max-warnings 0`、`test`、`format:check` 全绿；
  真实浏览器视觉基线在 macOS 与 hosted Ubuntu 均核验。

## 8. 风险与控制

| 风险                        | 控制                                                                  |
| --------------------------- | --------------------------------------------------------------------- |
| 旧客户端 PUT 后丢纯目录     | `members` 显式退役错误 + `schemaVersion: 2`，不做有损双写             |
| 子组与本地节点展开后碰撞    | 服务端同一份展开代数，保存/预览/启动三处复用并返回来源链              |
| 纯目录经 symlink 逃出工作区 | 逐段 `lstat`、拒绝 symlink/非目录、根路径 containment 复核            |
| 任务重跑丢目录              | 独立 `task_space_nodes` 冻结快照；旧任务才走可证明的最小闭包 fallback |
| 批量操作局部成功            | 前端纯函数先算完整结果，服务端仍以一次 PUT + OCC 原子提交             |
| 紧凑导致触屏难点            | 桌面 36px 视觉密度与移动端 44px 点击目标分开定义                      |
| 组嵌套放大节点数            | 直接 128、展开 256、仓 32、组深 5 四道预算                            |

## 9. 需要批准的设计结论

批准本 RFC 即表示接受以下产品语义：

1. 目录节点成为持久化的一等数据，纯目录会在任务中真实创建并冻结重放；
2. 根节点可挂仓但没有主仓概念；内部兼容镜像顺序不外露；
3. 节点可挂仓或子组且仍可有子节点，解除挂载保留目录；
4. 平铺以批量添加为主，编辑器改为单棵紧凑可编辑树；
5. `members` 管理 wire 断代为 `nodes`，旧写入明确失败而不做有损兼容；
6. 桌面拖放只是快捷方式，移动端/键盘使用同一套「移动到…」操作。
