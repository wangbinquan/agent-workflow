# RFC-626 升级必达与最短耗时：自动升级不因数据而停，同一份数据只处理一遍

- **状态**：Draft（待用户批准；批准前不改任何生产代码）
- **来由**：v0.20.0 发布前，用户 2026-11-26「现在现网大量部署0.19.2，如果升级到当前版本，数据能否在新版本启动的时候快速完成数据迁移，
  不要数据迁移还迁移几个小时」。2026-11-27 看到实测结果后：「三件都做，先立 RFC 去掉升级里的重复处理，你要让升级时间做到最小化」
  「升级为什么会拒绝，不允许拒绝啊，必须升级成功啊」。同日逐项裁决见 §1.3。
- **修订关系**：
  - 修订 RFC-395 `migration.md` §4 的 2026-10-24 裁决（仍可继续的任务若旧运行事实无法证明，列为阻塞项，由人先在旧版本结束或取消任务）：
    自动升级改为由程序结束这类任务。
  - 修订 RFC-398 `proposal.md` 的 2026-10-30 裁决①「有阻塞项才拒绝并逐项给出指引」与非目标「不自动确认可确认项」：
    自动升级不再因数据拒绝。
  - RFC-395 的目标结构、逐行处置与回执模型不变；RFC-398 的进程关系、锁、自动会话记录、PostgreSQL 建库与发布版升级矩阵不变。

本文里「自动升级」指 `start` 或 `migrate` 遇到 v0.19.2 及更早版本的库时自动进行的那次数据库升级（RFC-398）；
「人工流程」指操作者自己执行 `db migration plan → run --approve` 的那条路径。

## 1. 背景

### 1.1 实测（本机，2026-11-26 / 27）

被测数据是本机真实使用半年的库，归一到 v0.19.2 的发布形态：有效数据 1.07 GB、608,903 行；`runs/` 等内容目录共 827,742 个文件、
12.6 GB。被测程序是提交 `c91fc614a` 构建的单二进制。机器同时在跑别的任务，绝对值偏慢，各阶段的比例可信。下文称它为**参考数据**。

| # | 场景 | 结果 |
| --- | --- | --- |
| M1 | SQLite，原样 | 跑了 20 分 06 秒后**拒绝**：37 个 5～7 月留下的未结束任务（中断、等评审、等人工）产生 296 条阻塞项 |
| M2 | SQLite，先在副本里把这 37 个任务改成已取消 | 成功，**70 分 50 秒**；峰值内存 10.7 GB；新增磁盘占用峰值约 16 GB，结束后留存约 7.7 GB |
| M3 | PostgreSQL（同一份数据经 v0.19.2 的一键迁移搬过去），家目录里没有内容文件 | 跑了 27 分 35 秒后**拒绝**：27 条阻塞项，全部是「记录引用的文件不在磁盘上」（技能快照 15 条、必需内容 12 条） |
| M4 | PostgreSQL，带全部内容文件 | 实测进行中，结果补入本表 |
| M5 | PostgreSQL，`tasks` 表达到 937 行 | **必然失败**，见 R4（本机参考数据只有 537 个任务，所以 M3、M4 没有撞上） |

M2 各阶段耗时（取自升级回执的 `phaseTimings`）：

| 阶段 | 耗时 | 做了什么 |
| --- | ---: | --- |
| 生成计划 | 1207 s | 冻结一次旧库、盘点一次内容文件、**预演**一次完整转换 |
| 切换前备份 | 669 s | 再冻结一次、再盘点一次、做备份 |
| 停写后冻结 | 668 s | 第三次冻结、第三次盘点、核对备份 |
| 冻结后复核 | 898 s | 第二次**预演**完整转换 |
| 正式转换与校验 | 800 s | 第三次完整转换并写入新库、校验 |
| 切换与自检 | 5 s | |

### 1.2 根因

- **R1 拒绝是规定出来的，不是转不了。** 转换器对「旧运行事实无法证明」的行本来就有不阻塞的处置——保留为只读历史；
  只在所属任务还可继续时才改成阻塞（`modules/task-execution/infrastructure/migration/run/evidence.ts:118`），
  处理办法写的是「在旧版本结束或取消任务后重新计划」（`modules/system-operations/domain/epochSwitch/remediation.ts:19-31`）。
  自动升级只要计划里有一条阻塞项就拒绝（`modules/system-operations/application/epochSwitch/autoUpgrade.ts:254-258`）。
  内容文件缺失、技能目录缺失等同理：都能表达成「这份内容已不存在」，现在却让整次升级停下。
- **R2 同一份数据被反复处理。** 自动升级沿用人工流程的三段式——先计划、再备份、停写后再来一遍——
  而自动升级从头到尾持有守护进程锁，旧库在这期间不会变。逐条读源码数得（SQLite 路径）：整库内容摘要 157 次、整库拷贝 12 次、
  内容盘点 3 次、完整转换 3 次、目标库收尾校验 2 次。参考数据上一次整库摘要 12.5 秒，仅摘要一项就约 33 分钟。
  计划阶段的 CPU 剖析与此吻合：55% 的时间在整库摘要里（`platform/persistence/migration/rawSourceReader.ts:127-160`，
  调用点在 `sqliteSourceReader.ts:121-125,241-242` 与 `freeze/sourceAccess.ts:639-650`）。
- **R3 转换本身的时间大部分花在记账上。** 同一次剖析里，转换规则真正的转换逻辑只占转换引擎时间的约 2.5%；其余是重复序列化：
  排序比较函数里每比较一次就把整行重新序列化一遍（`conversion/receipts.ts:372`）、结束时把暂存库整个重读一遍算摘要
  （`conversion/engine.ts:458`）、暂存行用带缩进并逐行排序键名的 JSON 存取（`conversion/staging.ts:149`、
  `schema/canonical.ts:42`）、落库前把刚算过的单元摘要再算一遍（`infrastructure/epochSwitch/conversionSink.ts:81`）。
  暂存库因此膨胀到源库的约 9 倍。
- **R4 PostgreSQL 另有四处。** ①把旧库拷到暂存库时每批 1000 行、整批一条 `INSERT`
  （`platform/persistence/migration/offlineSourceUpgrade.ts:198`、`legacy/postgresqlLogicalTarget.ts:597`），
  `tasks` 表在 v0.19.2 的 PostgreSQL 结构里有 70 列，937 行起超过协议每条语句 65535 个参数的上限——用同一个数据库客户端验证：
  936 行通过，937 行报 `query has too many parameters`。任务数达到 937 的 PostgreSQL 实例今天升不过去。
  ②「旧库没变」的核对在 PostgreSQL 上是服务器端全表排序并把整库以 JSON 传回客户端再摘要，一次 60～90 秒，
  一次升级里约 63 次。③写新库时每条语句最多 100 行、900 个参数（`target/loader.ts:83`），是按 SQLite 的上限定的。
  ④旧库拷到暂存库之后要先过一组为旧版本「搬到 PostgreSQL」写的业务不变量检查
  （`legacy/postgresqlLogicalTarget.ts:694-700`），不满足就失败，进不到转换。本机参考数据在 SQLite 形态下就有 417 行不满足其中一条
  （有聚合头而没有事件），v0.19.2 自己的「搬到 PostgreSQL」因此在这份数据上失败。
- **R5 环境问题发现得晚，空间还会算错。** 磁盘空间在预演之后才判断（`application/epochSwitch/planner.ts:575`），库的结构不是发布版写出的
  要等第一次整库摘要和拷贝之后才报（`platform/persistence/migration/supportedSources.ts:421`）。M1 的拒绝出现在第 20 分钟。
  所需空间按 SQLite **文件大小**的倍数估算（`platform/persistence/migration/freeze/capacity.ts:29-33`、
  `domain/epochSwitch/capacity.ts:25-41`）；参考数据的文件是 24.7 GB、有效数据只有 1.07 GB，M2 的计划里估出来是 151.8 GB，
  当时可用 153.4 GB——只差 1.6 GB 就会以空间不足被拒绝，而升级实际新增的占用峰值约 16 GB。
- **R6 内存与磁盘随数据量放大。** 82.8 万条的内容清单在内存里同时存在多份，并以 168 MB 的带缩进 JSON 反复序列化（一次升级 13 遍）；
  转换引擎按行累积键与摘要。参考数据峰值 10.7 GB，数据量大一个量级的实例会因内存不足失败。

### 1.3 用户裁决（2026-11-27）

| 问题 | 裁决 |
| --- | --- |
| 未结束、但旧运行记录新版本接不上的任务 | 自动结束，标为**已取消**，写明原因；历史只读保留；升级报告逐个列出。数据完整的未结束任务照常继续 |
| 记录引用的文件已不在磁盘上；行本身已损坏 | **能留则留，其余封存并列出**：文件缺失的记录保留，内容显示为文件已不存在；放不进新库的行原样封存，不出现在界面上 |
| 磁盘不够、PostgreSQL 账号不能建库、库的结构被人改过 | **几秒内报出并给处理办法**，不动任何数据 |
| 历史数据（事件、观测类，占体积约七成）是否后台补转 | **一次转完全部数据** |
| 新库没通过自检、已自动撤回之后再启动 | **停下，执行重试命令后再升**（维持现状） |
| 现网数据库类型 | SQLite 与 PostgreSQL **都很多**，两条路径都要做到不拒绝、耗时最小 |

## 2. 目标

- **G1 不因数据而停。** 自动升级遇到发布版本在正常使用中会留下的任何数据状态，都完成升级并启动服务。
  程序替人做的每个决定按 §5 A 组的固定规则进行，不依赖人工输入。
- **G2 环境问题几秒内报出。** 磁盘空间、PostgreSQL 能否建库、库结构是否来自发布版、`config.json` 是否合法、是否另有未完成的迁移操作，
  都是与数据量无关的检查，在读取数据、写入任何东西之前判断完；不满足时数秒内退出，给出可直接执行的处理办法，
  旧库、家目录与 PostgreSQL 服务器上不留任何新增物。
- **G3 耗时最小。** 一次自动升级里，旧库只冻结一次、内容文件只盘点一次、数据只转换一次并直接写入新库、备份只做一份、
  新库只校验一次。参考数据：SQLite 不超过 6 分钟（现 70 分 50 秒），PostgreSQL 不超过 15 分钟。
- **G4 资源有界。** 参考数据上峰值内存不超过 4 GB（现 10.7 GB）；升级新增的磁盘占用峰值不超过 8 GB（现约 16 GB），
  完成后留存不超过 5 GB（现约 7.7 GB）；空间估算按有效数据量而不是文件大小。内存不再随行数、文件数成倍放大。
- **G5 结果可查。** 升级结束时的报告与日志逐项列出：哪些任务被结束及原因、哪些内容标为缺失、哪些行被封存。
  被结束的任务在任务页显示原因。
- **G6 PostgreSQL 不受任务数限制。** 修复 R4①。
- **G7 进度输出保留。** 每个阶段照常逐行报告进度；阶段名随单遍流程调整。

## 3. 非目标

- **不改人工流程的交互。** `db migration plan` 仍逐项展示阻塞项，`run --approve` 仍要求人批准；想要本 RFC 的自动处置，
  用 `db migration auto`（与 `start` 触发的是同一条路径）。人工流程受益于 R2、R3 的提速，行为不变。
- **不涉及托管（CrewStation）形态。** 自动升级只在单机部署触发，托管形态仍走人工流程。
- **不覆盖经桥接升级的 PostgreSQL 旧基线。** v0.18.18 / v0.18.19 的 PostgreSQL 库要先经一层 SQLite 桥接（RFC-398 §3.8），
  桥接阶段因数据不满足约束而失败的情形不在本 RFC 的自动处置之内，行为与现在相同。v0.19.x 的库不经过桥接。
- **不做「核心数据先转、历史后台补」**（用户已选一次转完）。
- **不新增数据库层的批量通道**（`COPY`、跨库直拷、模板建库）。记账开销去掉之后它们的收益有限，留作后续。
- **不改新库的表结构与 schema history**；封存与决定记录复用既有的迁移元数据表。
- **不提供新的回退手段。** 旧库、备份照旧保留，回退办法不变（`docs/release-upgrade-rollback.md`）。
- 数字员工「回复检视意见」丢失的缺陷另行修复，不在本 RFC。

## 4. 用户故事

- **运维 A**（SQLite，几十个半年前留下的中断任务）：换上新二进制执行 `start`。日志先报「开始升级」，几分钟内逐阶段报进度，
  随后服务起来。日志和升级报告列出 37 个被结束的任务；打开其中一个，状态是已取消，原因写着「升级时结束：旧版本的运行记录无法在新版本继续」，
  历史运行、对话、文档都能看。
- **运维 B**（PostgreSQL，1500 个任务，清理过一批 `runs/` 目录）：`start` 之后十来分钟服务起来。报告里列出 12 条「内容文件已不存在」，
  对应的任务页该处显示文件已不存在，其余照常。
- **运维 C**（磁盘只剩 1 GB）：`start` 在几秒内退出，日志写明还差多少空间、需要多少、在哪个目录；旧库没有被动过，
  腾出空间后再 `start` 即可。
- **运维 D**（升级到一半机器断电）：再次 `start`，从中断处接着做，不需要任何命令。
- **开发者**：升级报告与日志足以回答「程序替我做了哪些决定」，不必读转换器源码。

## 5. 行为影响清单（请逐项确认）

下列各项改变了自动升级现在的行为。A 组是数据的处置：A1～A3 的方向已由 §1.3 裁决，这里写出落到各类数据上的具体结果；
A4～A10 是按同一原则（能照旧版本自己的方式处理就照它，新库能表示的保留，其余封存）推出来的，请确认。
B 组是流程上的变化。每一项的依据见 design §3.2～§3.5。

**A 组：数据怎么处置**

| # | 现在（升级拒绝的情形） | 改为 | 升级后的表现 |
| --- | --- | --- | --- |
| A1 | 未结束任务的旧记录无法支撑继续执行：v0.15 之前派发、此后一直没结束的运行；工作流快照、挂载、澄清记录对不上；旧服务被强行终止时停在准备工作区、打开评审门等中间步骤；任务的必需内容文件已不在磁盘上 | 程序把该任务**结束为已取消**，效果等同在旧版本里取消它：等评审、等人工的节点与未答的澄清一并收尾，原因写「升级时结束」；它的可取消子任务随之取消 | 历史全部保留。之后能做的与任何已取消的任务相同：不能恢复；其中旧运行记录无法证明的任务也重试不了（既有的只读历史限制），其余的（只因中间步骤停在半途而结束的、随父任务取消的子任务）可以由人手动重试。数字员工不会自动重跑被这样结束的任务。数据完整的未结束任务（含正常停在等评审、等人工的）不受影响 |
| A2 | 记录引用的内容文件不在磁盘上，或磁盘上的内容与登记的不一致（被人改过） | 记录照常保留，该处内容登记为**已不存在**；磁盘上的文件不动 | 界面上该处显示内容不存在。不把改过的内容当作登记的那份呈现 |
| A3 | 技能的目录或版本快照缺失、被改动；技能的创建、保存、导入停在半途 | 技能按产品已有的**隔离**状态保留——这也是 v0.19.2 自己启动时对这类技能的处理；停在半途的操作记录一并了结。从未发布成功的空壳技能封存 | 被隔离的技能不出现在技能列表里，名字仍被占用；把目录恢复完整后，下次启动自动恢复可用。引用它的代理仍在，用它发起任务时明确报「引用了被隔离的技能」 |
| A4 | 个别行无法解析、违反旧库自身约束、放不进新库 | 该行原样**封存**在新库的迁移归档里，不进入业务表；通过外键依赖它的行一并封存 | 不出现在界面上；旧库原样保留，可对照 |
| A5 | 已下线功能的遗留没有了结：旧「代码工作」里未完结的条目（现在需要人逐条确认）、尚未终结的旧任务书（v0.19.2 里的「旧 Mission」） | 旧代码工作按已确认的既有路径整体归档，确认人记为「自动升级」；未终结的旧任务书逐条封存 | 新版本不再运行这两类旧流程；已终结的旧任务书照常保留为历史 |
| A6 | 记录引用了不存在的用户或记录（任务属主、用户的创建人、协作者的添加人） | 记录保留，解除这处引用：属主、创建人置空；协作者的添加人改记为系统用户 | 属主为空的任务只有管理员与协作者可见；协作者资格不受影响 |
| A7 | 代理的技能 / MCP / 插件引用里有无法确认的条目 | 代理保留，去掉无法确认的那一条引用 | 代理少一条引用，报告列出是哪一条 |
| A8 | 定时任务的配置无法解析或其本地路径无法探测 | 定时任务保留并**停用**，写明原因 | 详情页显示原因，修好配置后可重新启用 |
| A9 | 缓存仓库的地址无法还原（密钥缺失或换过） | 缓存仓库照常保留，地址保持旧库里的样子；任务与定时任务照常按地址关联它 | 该仓库显示为地址不可用、不能刷新，重新添加后恢复 |
| A10 | 其它保留类：`config.json` 里残留的旧默认值键、来源无法确认的技能融合与记忆、事件族切换模式不是可分发 | 运行时条目照常转换并登记默认值未带入；融合与记忆走既有的隔离结果；事件族按一次模式切换处理 | 与旧版本运行时的实际行为一致；不补投旧模式下记下的事件 |

每一项都逐条进入升级报告与日志。

**B 组：流程**

| # | 现在 | 改为 | 影响 |
| --- | --- | --- | --- |

仍会让自动升级以**错误**结束、但不属于「因数据拒绝」的情形（design §3.6）：转换程序自身的缺陷、库已损坏到违反旧库自己的类型约束、
系统用户或全局登录策略行被人删除、升级中途环境变化（磁盘写满、数据库断连）、新库没通过自检；以及 §3 列出的经桥接升级的
PostgreSQL 旧基线在桥接阶段的失败。这些情况下旧库不动，可重试。

   它们等评审、等人工的节点与未答的澄清已收尾，不出现在待办与「需关注」里；其余任务状态不变；
   升级前处于等评审、等人工的正常任务在升级后能继续走完。

   缺目录的技能为隔离状态，报告逐条列出；把技能目录放回后重启，技能恢复可用。
