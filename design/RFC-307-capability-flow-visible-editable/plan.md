## 1. 拆分原则

三个 PR，每个都能独立交付价值、独立跑绿门禁：

- **PR-1「看得见」** —— 没有它，后两个 PR 无处可挂。做完用户就能看到五条能力长什么样。
- **PR-2「改得动」** —— 在 PR-1 的图上接配置写回。
- **PR-3「能上手」** —— demo 数据；放最后是因为它要用到前两个 PR 的界面才有意义可验。

> 顺序上 PR-3 可与 PR-2 并行，但**验收**必须在 PR-1 之后（否则 demo 播出来也没地方看）。

## 4. 风险与前置

| 风险                                         | 处置                                                                             |
| -------------------------------------------- | -------------------------------------------------------------------------------- |
| 画布组件吃的是工作流节点形状，投影出来的不是 | **适配而非改造**：薄适配层，画布零改动（design §2.2）                            |
| 合同本身可能就有孤立 artifact                | T2 的健全性断言会先把它照出来——这是收益不是障碍                                  |
| demo 轮次污染 `/code` 指标                   | **Q-D 待确认**：默认「计入但 UI 标注」；要排除需加列（与「零 schema 变更」冲突） |
| 多人并发树上动 `routes/code.ts` / `code.tsx` | 本轮已知 RFC-305/306 在动前端 shell 与权限面，按仓规精确 `git add`               |

## 5. 不在本 RFC 范围

- **结构可编辑**（增删步骤、重连边）—— 要打破 RFC-304 的 D3，且有状态步的不变量会退化成
  用户连线正确性。等第一层用起来后再判断（proposal §4）。
- **能力流程真的跑在工作流引擎上** —— 需要先把 5 个有状态步收成平台节点（proposal §7）。
- 改 RFC-304 执行面 / 跨轮编排（工作项、租约、抢占）。
