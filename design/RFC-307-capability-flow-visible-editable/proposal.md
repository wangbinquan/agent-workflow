# RFC-307 · 能力流程可见可改（产品视角）

> 技术设计见 [design.md](./design.md)，任务分解见 [plan.md](./plan.md)。
> 前置：[RFC-304 代码能力平台](../RFC-304-code-capability-platform/proposal.md)（Done，2026-08-17）。

## 1. 背景：用户原话

> 「这个工作流，我现在又没有一个可以执行可以看的流程，都不知道实际是什么样的，
> 甚至我都不知道应该怎么去编排这个流程。」

这句话指向的不是使用姿势问题，是**产品缺口**，而且落差是可测量的：

| 时点     | 用户能看到什么                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 跑之前   | `GET /api/code/capabilities` 只返回**能力名 + agent 槽位**。流程本身在界面上不存在                     |
| 跑起来后 | `/code` 活动面把阶段渲染成 `<ol>` **纯文本列表**（`code-stages-{roundId}`），不是图                    |
| 画布上   | 每轮合成的 snapshot 里只有**一个** `code-round` 节点——它自己的注释写明「存在只是为了详情页有东西可画」 |

整个平台以**画布**为核心表达方式（工作流、工作组、任务详情都是图），唯独 RFC-304 交付的
五条能力是一个不透明方块。用户面对的是：**看不到、所以不敢开；开了也不知道刚才发生了
什么；想调整则完全无从下手。**

## 2. 事实核查：可配面其实早就建好了，只是没跟流程绑在一起

写本 RFC 前按源码逐条核实（`file:line` 见 design §2），结论是**不需要打破 RFC-304 的
D3 裁决**（阶段序列不落 `workflow_definitions`）就能让流程「改得动」：

| 用户想改的东西               | RFC-304 早已建好的机制                                 | 今天在哪              |
| ---------------------------- | ------------------------------------------------------ | --------------------- |
| 某个 AI 步用哪个 agent       | `StageDef.agentSlot` → 绑定 `agentBySlotJson`          | 模板表单里的一段 JSON |
| 某个 AI 步的 prompt          | `promptBySlotJson`                                     | 同上                  |
| 某个 script 步跑什么脚本     | `StageDef.scriptSlot` → 框架 `scriptsJson`             | 同上                  |
| 阈值 / 开关                  | `paramSchemaJson` + `paramDefaultsJson` → `paramsJson` | 同上                  |
| **在某一步前后插自己的逻辑** | **钩子**：每个阶段边界可挂 `pre`/`post`，`hooksJson`   | 同上                  |
| 钩子能回传什么               | `StageBase.injectable` **白名单**                      | 合同里已声明          |

也就是说：**能力流程的「行为」本来就是用户可配的，只是配置入口是一堆 JSON 表单，
与「这一步在流程里的位置」完全脱节**。用户在表单里看到 `agentBySlot: {"reviewer": "..."}`，
无从知道 `reviewer` 是在十三步的哪一步、改了会影响什么。

同时，**结构**（有哪些步、怎么连）是平台写死且版本化的，这是 RFC-304 的确定性宪法：
十三步里只有两步是 AI，其余是程序步与脚本步；`injectable` 白名单的注释写明了理由——
「没有它，钩子可以重定义序列依赖的任何产物，『程序步是确定性的』就只维持到有人写了个
有创意的钩子为止」。

## 3. 目标

1. **看得见**：能力流程以**图**呈现，跑之前就能看；跑起来后同一张图叠上运行态。
2. **改得动**：图上直接改行为——选 agent、改 prompt、编辑脚本、调参数、挂钩子——
   写回既有两层模板，不新增第二套配置形态。
3. **能上手体验**：装好即有**可点开的样例**，不需要先接一个真实 GitLab 才能看见东西。

## 4. 非目标（写清楚，避免范围蔓延）

| 非目标                             | 理由                                                                                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **结构可编辑**（增删步骤、重连边） | 要打破 D3，且那 5 个有状态步（台账 / 发布意图 / 边沿结算）的不变量会从平台保证退化成用户连线的正确性。RFC-304 收尾修的 20+ 处缺陷里有数处正是这类。**先让第一层用起来，再用真实反馈判断缺不缺** |
| 改 RFC-304 的执行面                | 本 RFC 只加读侧投影与配置写回，不碰 `StageEngine`、不碰跨轮编排（工作项 / 租约 / 抢占）                                                                                                         |
| 把 `code-round` 变成用户可编辑节点 | `SYNTHESIZED_ONLY_NODE_KINDS` 由四套机制共同守着，动它属于 D3 范畴                                                                                                                              |
| 让能力流程真的跑在工作流引擎上     | 这是另一个方向（见 §7），需要先补平台节点；本 RFC 不做                                                                                                                                          |

## 5. 用户故事

- **US-1（看）**：我在 `/code` 选一条能力，能看到它十三步长什么样、哪两步是 AI、
  每步吃什么产物吐什么产物——**在我给任何仓开启它之前**。
- **US-2（跟）**：一轮跑完（或正在跑），我打开它看到的是**同一张图**，每步按
  done / running / failed 着色，失败那步直接显示原因，AI 步能点进去看模型调用。
- **US-3（改）**：我在图上点 `review-shard` 这一步，弹出的是它的槽位配置——换 agent、
  改 prompt；平台同时**高亮所有共用该槽位的步骤**，明确告诉我「改这里会同时影响那几步」。
- **US-4（插）**：我在 `publish` 这一步前点「＋」，挂一个自己的 `pre` 钩子脚本，
  界面按 `injectable` 白名单告诉我这里允许回传哪些键。
- **US-5（体验）**：我全新装一套，`/code` 里就有一份可点开的样例模板与一条示例流程，
  工作流列表里也有对应的 demo 工作流可以打开看；**不需要先接 GitLab**。

## 6. 验收标准

- **AC-1** `/code` 能在**未开启任何能力、无任何轮次**的情况下展示任一能力的完整流程图，
  节点区分 program / ai / script / invoke 四类，边由 `requires`/`produces` 推导。
- **AC-2** 图与运行期**同源**：同一份 stage contract 既驱动执行也驱动渲染；
  合同改了图必须跟着变（由测试锁定，不允许前端手抄一份）。
- **AC-3** 打开一个已结束的轮次，看到的是同一张图叠了状态色；失败步显示 `error`；
  AI 步可展开该步的模型调用（复用既有 attempts 面）。
- **AC-4** 图上点 AI 步 → 改 agent / prompt → 保存 → 写回 `capability_bindings`，
  且**共用同槽位的其它步骤在图上同时高亮**。
- **AC-5** 图上点 script 步 → 编辑脚本 → 保存 → 写回 `capability_frameworks.scripts`。
- **AC-6** 图上任一阶段边界可挂 `pre`/`post` 钩子并保存；界面按该步的 `injectable`
  白名单显示「这里允许回传哪些键」，未声明则明确显示「此处钩子不能回传数据」。
- **AC-7** 权限如实：无 `capability-bindings:update` 只能看不能改；无 `scripts:author`
  不能编辑框架脚本（与 RFC-304 既有判据一致，不新增权限点）。
- **AC-8（体验面）** 全新库启动后：`/code` 模板面有一份 **demo 框架 + demo 绑定**；
  工作流列表有 **2–3 条 demo 工作流**；活动面有**一条已完成的 demo 轮次**可点开看图与状态。
  全部幂等播种、明确标注为示例、**删掉不会被重新播种**（沿用 RFC-153 运行时行的先例）。
- **AC-9** demo 数据不依赖任何外部服务：不连 GitLab/GitHub、不起子进程、不发网络请求。

## 7. 与「能力流程改用工作流实现」的关系

调研（本轮）确认：单轮的**步骤形状**工作流已能表达绝大部分——AI 步 → `agent-single`、
脚本步 → `script`、出站调用 → `code-host-call`、分片 → `wrapper-fanout`、
`invoke` 子序列 → `call-workflow`（RFC-243）、条件路径 → **RFC-306 分支端口**。
十一个程序步里 **6 步**用现有节点即可表达。

真正卡住的是 **5 步有状态的**（`reconcile` / `publish` / `settle-stale` / `ledger` +
发布临界区）——它们读写**跨轮持久状态**（指纹台账、发布意图两段式），按定义活在一次
DAG 执行之外。

本 RFC **不做**这件事，但它是通向那里的必经一步：先让人看见十三步长什么样，
才谈得上判断「哪几步该开放给工作流拼装、哪几步该收成一个平台节点」。
真要做，形态大概是把那 5 步收成**一个** `code-publish-review` 节点——但那要等
第一层跑起来、有真实反馈之后再立 RFC。

## 8. 开放问题（呈用户确认）

- **Q-A 槽位 vs 阶段**：可配面按**槽位**（`reviewer` / `analyst`），一个槽位可能被多步
  共用，图上不是一对一。本 RFC 取**槽位为一等公民**（点某步 → 配该槽位 → 高亮同槽位各步），
  改动小、语义不变。另一选择是拆成按阶段配，更直观但要改数据形状（`agentBySlot` →
  `agentByStage`）并迁移。**默认取前者**，若不同意请指出。
- **Q-B demo 轮次的真假**：AC-8 的「已完成 demo 轮次」是**播种的历史行**（明确标注示例），
  而非真跑出来的。真跑需要 code host。**默认取播种**；若你更想要「一键跑一轮真的」，
  需要接 system-mock，成本更高、且只在开发环境可用。
- **Q-C demo 工作流的内容**：默认放 2–3 条**能对照能力流程**的示例（如「审代码→给结论」
  的简化版），让用户能直观对比「平台内置的十三步」与「自己拼一条」。若你想要别的主题请说。
