# RFC-311:数据库性能治理与十万级列表渲染(proposal)

- 状态:Draft(待批)
- 日期:2026-08-18
- 证据档:本目录 `audit-2026-08-18.md`(六路并行审计全量 findings,含全部 `file:line`)

## 1. 背景

生产环境(数千任务、十万级 webhook 投递)数据库已 2.2GB,用户报告**"所有操作都慢"**;
具体到界面:任务列表在 ~2000 任务时渲染很慢,远端仓页在 ~280 仓时渲染很慢。目标是
**十万级后台数据下前台仍可秒级渲染、全站操作恢复毫秒级**。

2026-08-18 六路审计(后台 services×2 / modules+索引对账 / 后台循环热路径 / 数据治理 / 前端数据消费)
定位出五层叠加的根因,全部有 `file:line` 证据(见证据档):

1. **L1 常驻高频轮询 × 全表物化**:shell 收件箱三个徽章端点每 15s × 每 tab,底下分别是
   node_runs+tasks+workflows 三张全表全列(reviews)、tasks 全表全列两遍(clarify)、逐任务 N+1
   (workgroup);首页 10s×2 与 overview 60s 同型。只要开着浏览器,daemon 每十几秒就同步搬运
   数百 MB~GB 级数据,而 bun:sqlite 是**单条同步连接**——搬运期间所有 HTTP/WS 一起冻结。
2. **L2 交互路径放大**:`/api/tasks/page` 每页请求全量物化全部任务+每行相关子查询+双递归 CTE
   后才 LIMIT;任务详情 node-runs `SELECT *`(含 prompt_text 等大列)被 WS 每秒 2 次触发重拉;
   调度器每 tick 全列拉任务全部 node_runs;/repos 是 280 仓 × 双全表扫的 N+1。
3. **L3 周期 burst 与功能性坏死**:备份在主连接同步 `VACUUM INTO`(2.2GB ≈ **全站冻结 30-90s**);
   事件归档器的巨型 `DELETE IN` 超 SQLite 32766 绑定参数上限**必然报错→归档死循环、表只涨不缩**;
   stuck 检测/orphan 回收/invariants 等每 5min~hourly 的 O(全表) 扫描。
4. **L4 数据体量**:事件归档水位只按行数(默认 100 万行 ≈ 3GB 才触发,**生产从未触发过**);
   `node_run_events` 占库 ~73%;十几张零清理无界表;DELETE 永不回收空间、全库无 VACUUM;
   备份 prune 从不执行(2.0GB 备份堆积)、`opencode-stores/` 2.9GB 退役死数据。
5. **L5 前端**:全仓零虚拟化、零行级 memo;除 3 处外所有列表端点全量拉取;每行 2 个 30s tick
   订阅导致全列表同帧重渲染;WS invalidate 无节流;多页 10-30s 整表轮询。

## 2. 目标

- **G1 常驻负载归零**:徽章/overview/首页轮询全部降为索引化 `count(*)`/窄投影;空闲 daemon
  (含一个打开的浏览器 tab)每秒 DB 时间 < 5ms。
- **G2 交互路径 O(页)**:`/api/tasks/page` 只为返回的一页付费(十万任务下 P95 < 150ms);
  任务详情/调度/repos 列表全部窄投影或聚合化;`/api/cached-repos` 支持十万仓分页。
- **G3 周期任务有界**:所有定时循环 O(活跃集);归档器在任意规模单轮有界、永不因参数上限失败。
- **G4 备份不冻结**:备份移出主线程,备份期间 API 正常响应;备份保留策略真正执行。
- **G5 体量封顶**:事件归档增加字节维度水位;终态任务超保留期自动**归档到归档目录并从库中删除**
  (数据不丢、前台不可见);空间可回收;退役死数据可一键清理。
- **G6 十万级列表**:/tasks 与 /repos 在十万级后台数据下首屏可交互 < 1.5s、滚动流畅
  (可视区外不渲染 DOM);沉淀可复用的虚拟化 + 分页公共原语供其余页面接入。
- **G7 防回归**:关键查询带 EXPLAIN QUERY PLAN 断言与新旧实现 oracle 等价测试;
  提供十万级 seed 的本地性能基准脚本。

## 3. 非目标

- 不换存储引擎、不引入第二条数据库连接、不做 Worker 化查询执行(备份子进程除外)。
- 事件"写入即落盘 JSONL、DB 只留活跃尾部"——**二期**(2026-08-18 用户拍板选保守档)。
- 不引入 FTS5 全文搜索(LIKE 语义保留,只做形状优化)。
- 资源六页(agents/skills/mcps/plugins/workflows/workgroups)的**端点分页化**缓行(数据量千级;
  本 RFC 只做 workflows 列表投影瘦身与公共原语,接入清单见 plan.md 后续项)。
- 不做 RFC-294 的结构搬迁(本 RFC 是横切性能修复,就地修;详见 design.md §1 对齐说明)。
- 归档任务的界面内回看/恢复工具(归档格式自描述,恢复工具可另立 RFC)。
- 在线 VACUUM(会长冻结;提供停机 CLI compact + 可回收空间提示)。

## 4. 用户故事

- 运维在生产开着 5 个浏览器 tab,daemon 的 API 响应不因徽章轮询产生可感知抖动。
- 用户在 2000(乃至十万)任务下打开 /tasks:首屏一秒内出现,滚动加载顺滑,展开子树即点即开。
- 用户在 280(乃至十万)仓下打开 /repos:搜索、过滤、刷新、删除都即时响应。
- 运维点"立即备份":备份在后台进行,期间任务照常调度、页面照常刷新。
- 运维配置"终态任务保留 180 天":超期任务树被完整归档到 `archive/` 目录后从库中消失,
  DB 与 `runs/` 磁盘占用随保留期封顶;需要考古时归档目录里有自描述的 JSONL 快照。
- 观看一个运行中的任务详情页,daemon 不再每秒两次反序列化数十 MB 的 prompt/快照大列。

## 5. 能力影响清单(RFC-224 事故沉淀条款,逐项呈确认)

本 RFC 有行为面变化的条目如下;**其余全部改动(窄投影、count 化、索引、聚合化、分批化)不改任何
wire 形状与语义**,以 oracle 等价测试锁定。

| # | 变化 | 影响面 | 缓解 |
|---|---|---|---|
| C1 | **终态任务自动归档**(新能力,默认**关闭**):开启并配置保留期后,整树终态且超期的任务从所有列表/详情消失(404 与不存在同形),数据以 JSONL 快照 + 事件日志 + runs/ 目录形式保留在 `~/.agent-workflow/archive/tasks/` | 开启后历史任务不再可在界面回看 | 默认关;设置页显式开启并填保留期;另有 admin 手动批量归档入口;归档目录自描述可考古 |
| C2 | **workflows 列表 API 不再返回完整 `definition`**,改返回 `nodeCount` 等摘要(详情端点不变) | 依赖列表端点拿完整定义的外部 PAT 脚本需改走详情端点 | 前端唯一消费点(`routes/workflows.tsx:172-174`)同步改造;API 文档标注 |
| C3 | 事件行会**更早**归档到 JSONL(新增字节维度水位,默认全局 ~256MB) | UI 读取无缝(既有 fallback `services/eventsArchive.ts:165`);直接查 DB 的外部脚本会看到更少行 | 阈值可配;JSONL 路径稳定 |
| C4 | **备份保留策略开始真正执行**:pre-migration/manual 备份新增数量上限(默认保最近 10 个) | 旧备份文件会被自动清理 | 上限可配;0=保持现状不清理 |
| C5 | WAL checkpoint 循环**默认开启**(原默认 0=关) | WAL 文件尺寸行为变化,无能力损失 | 间隔可配,0 仍可关 |
| C6 | 三张同形事件表(memory_distill / intent_turn / mcp_runtime_test)与 `webhook_trigger_fires`、`user_access_audit`、`mcp_probes` 新增保留期清理(默认 90 天/终态后 30 天,可配) | 超期流水行被删除 | 各自可配,0=不清理 |
| C7 | `/api/cached-repos` 新增分页参数与封套(`{items, nextCursor, facets}`);**无参调用保持全量兼容**一个过渡版本 | 前端同步改造;外部脚本无参调用不受影响 | 版本注记 + API 文档 |

## 6. 验收标准

以 `scripts/perf-seed`(新增)生成的基准库(**10 万任务 / 300 万 node_runs / 千万级事件行 /
10 万 webhook 投递 / 500 仓**)为准,在开发机实测:

1. `/api/tasks/page`(默认视图首页)P95 < 150ms;翻页/切视图 P95 < 150ms;facets 正确。
2. `/api/cached-repos`(分页后)单页 P95 < 100ms。
3. 三个徽章端点 + `/api/overview` 单次 < 10ms。
4. 空闲 daemon + 一个打开的 /tasks tab:每秒 DB 累计耗时 < 5ms(以慢查询日志/计时点核对)。
5. 归档器在千万行事件表上单轮 < 1s、分批推进、无参数上限错误;字节水位生效后事件表稳态 ≤ 配置值。
6. 备份进行中,`/api/tasks/page` 仍 P95 < 300ms(不被 VACUUM INTO 冻结)。
7. 前端 /tasks、/repos 在基准库下:首屏可交互 < 1.5s,滚动 60fps 量级(可视区 DOM 行数恒定),
   30s 时钟 tick 只重渲染可视行。
8. 开启任务归档(保留期 N)后:超期任务树完整出现在归档目录(manifest 校验通过),库内相关行清零,
   UI 404;未超期/未终态/被引用的任务不受影响。
9. 全部既有测试绿;新旧查询 oracle 等价测试绿;EXPLAIN QUERY PLAN 断言绿。
