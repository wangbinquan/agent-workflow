# 会议室预约方案 · 第一版需求决定文档（20人团队 / 3间会议室 / 两周交付）

## 一、已决定（用户明确选择）
- 功能边界：只做查看空闲、预约、取消、同一会议室同一时段冲突拦截、记录与会前提醒。不做自动释放、处罚和审批流。
- 分配规则：完全先到先得（FCFS）。
- 时间槽：30 分钟固定槽，整点/半点起止。
- 除冲突拦截外无其他自动化约束。
- 记录与提醒：同时启用（不做纯记录周、不做分段对照）。
- 「想约但约不到」采集：前台或组长口头询问并人工记录（零开发）。
- 空占口径：把「未签到且未提前取消」只标记为疑似空占，由会议发起人事后补充是否实际使用；未补充的记录保持未知，不直接用于处罚或推导精确爽约率。
- 至少采集信号：① 预约总量与取消时间点；② 预约后的签到/实际使用；③ 想约而未约成的被拒/候补需求。

## 二、暂定（provisional，未定案）
- 爽约/空占处理：暂定先记录爽约并提供会前提醒，两周内不自动释放、不处罚。用户原话：「我们还不知道空占是否是主要矛盾。」
- 理由（用户原话）：「没有历史基线，先观察两周再决定是否增加强制规则。」

## 三、接受的代价（用户已确认）
- 短期空占仍可能发生，并需承担每周人工核对成本。
- 记录与提醒同时启用 → 基线被提醒效果稀释，只能解释为「提醒后的空占」，无法还原自然空占率。
- 人工记录被拒需求 → 样本依赖自觉，易漏记，口径不统一。
- 先到先得 → 无配额/优先级，可能出现团队间争抢（本版接受）。

## 四、尚未验证 / 未知
- 空占率、冲突次数、提醒是否有效，均尚未验证。
- 并行启用提醒后无法还原自然空占率。
- 自报未使用记录可能漏记，不当作精确爽约率。
- 空占是否为主要矛盾，仍未知。

## 五、验证安排
- 验证负责人：产品负责人（用户以「验收场景角色」指名的角色）。
- 复核方式：产品负责人每周汇总预约、冲突及自报未使用记录，两周后与团队代表复核。
- 复核时点/触发：试行两周后复核；若一周内出现三次有记录的实际冲突，提前讨论。
- 待补：负责角色为场景角色命名，未落实到具体具名人员；验证任务排期未确认，尚未安排。

## 六、明确不做（本版排除）
