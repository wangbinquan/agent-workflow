# RFC-378：脑图澄清的主动思考与决定复核

> 状态：Done（2026-10-19）。用户于 2026-10-18 在原型与设计完成后明确批准“按你的推荐进行实现与自主验收，并提交上库到远端”。RFC-372 的轻量合同继续有效，实际证据见 [acceptance.md](acceptance.md)。

## 1. 背景与证据

在正式托管 AW 上，以“20 人、3 间会议室、两周交付、没有冲突和爽约基线”创建真实任务 `01M58Y88V382560PC14KHCS8BQ`，使用实际模型生成四个问题，完成选项、自定义答案、修改确认、两次深入追问、视图切换、刷新恢复和最终提交。证据与 TreeLearn 对照见 [research.md](./research.md)。

现有能力已能保存与确认回答，但存在六项直接影响体验的缺口：

1. 起步需理解 Agent、反问节点及连线，缺少脑图澄清起步模板。
2. 全景显示问题和确认数量，不能直接复核自己的决定；四题的单子项分类产生了两层装饰性结构。
3. 推荐把没有基线的判断写成确定事实；互相独立的参数捆成套餐，可同时成立的验收维度被做成单选。
4. “已确认回答”与“决定有依据、可以定案”未分开呈现，明确写着尚待验证的答案也形成全绿。
5. 追问动作泛化，托管实例实际执行还固定走本地工厂，连续两次找不到 `opencode`。
6. 停止反问只确认流程动作，没有复核决定、接受的代价、未知事项和验证安排。提交后的最终文档尚未返回，不能认为完整链路已通过。

## 2. 目标与范围

- G1：使用现有工作流起步模板，选择一个已有代理即可生成脑图澄清与结果输出连线。
- G2：在全景中同时读到问题、回答摘要和决定状态；能从疑点或选中文字主动提出追问。
- G3：把用户确认的回答与用户决定的成熟程度分别表达，允许保留未知并暂定推进。
- G4：在提交前明确复核关键取舍、待验证事项及责任；相同内容完整进入原提交和最终输出。
- G5：本地与托管均能真实生成分支追问，并验证最终任务完成，失败与取消可恢复。

所有能力均复用现有 clarify 问题、答案 JSON、协作草稿、确认依据、提交和任务续跑。不会引入独立 MindmapSession、第二份答案库、签署系统、复核任务调度器或无限聊天树。验证负责人和复核时机是这次决定的内容，不自动分派任务或发送消息。

## 3. 用户流程

### 3.1 开始

在现有工作流编辑器的“从模板开始”中增加“脑图澄清”。用户选择有文本输出的现有代理，模板展示用途、输入与结果，再经原 validate-draft / 应用模板流程生成 input → agent ↔ clarify → output。任务仍经原启动入口。缺少合适代理时给出创建入口，不偷偷创建或修改代理。

### 3.2 看全局与作答

根节点使用业务标题；自动折叠仅有一个子分类且无直接问题的展示层级，真实路径仍在目录与面包屑中。问题卡片显示问题、一至两行当前回答摘要、已确认回答状态，以及用户显式标注的“已决定 / 暂定”。

逐题仍使用原 QuestionForm。决定补充作为可展开区域：决定状态、依据、接受的代价、仍待验证、验证负责人、复核时机。选择“暂定”时直接展开待验证与复核安排；选择“已决定”仍可填写并保留未知与复核安排，不声称事实已验证。决定状态可以不标注，其他补充仍可独立填写。旧答案和新生成的问题均不自动预填状态或待验证事实。

修改回答或决定补充会使本题确认失效，两个视图与提交摘要共享同一答案。所有回答都已确认时显示“本轮回答已确认”，旁边保留暂定和未标注数量，不把未知涂成已解决。

### 3.3 主动深入

每个问题提供“检查依据”“考虑代价”“比较其他做法”“我想追问”。前三项只把具体指引填入原追问编辑框，用户可改写后发送，不静默启动模型。

支持在问题、选项说明、推荐理由或自己的回答中选中文字，点击“针对这段追问”，显示可移除的引用及当前分支。无文本选择时仍可直接输入。生成结果仍是同一轮下的少量澄清问题，明确说明“围绕疑点补充问题”；不假装该入口是通用聊天回复。

生成期间可继续作答、切换分支和取消；失败保留原内容、显示重试入口。公开提示解释“暂时无法生成追问，已有回答已保存”，技术详情折叠，普通用户不被要求查看 daemon 日志。

### 3.4 提交前复核

脑图模式的原“提交并继续 / 停止反问”先打开共用复核面板。展示当前真实答案的确定性摘要，不再调用模型改写用户决定：

- 每项决定、依据与代价；
- 所有已填写的待验证事项和复核安排，不因决定状态而隐藏；暂定但尚未指定验证负责人 / 时机的内容明确标示；
- 尚未成功的追问提示；
- 本次是“继续澄清”还是“按这些决定生成结果”。

可返回具体题目修改。缺少回答、未确认、草稿保存失败或仍有在途追问时沿用原阻断；暂定和缺少验证安排以明确文字保留，允许用户决定推进，不逼用户填假信息。最终按钮仍调用原 submit 一次，保持 self/cross、部分锁定与原指令语义。

### 3.5 结果

最终生成继续沿用原任务输出。脑图答案的提示词显式区分人的决定、未验证假设、接受的代价和复核安排；停止反问不授权模型把未知改成事实或替用户认领责任。提交成功、生成中、结果完成分别显示，以真实任务状态和输出为准。

## 4. 问题内容约束

- 一题聚焦一项可独立决定的取舍；独立的粒度、期限、时长和配额按重要性拆问，保留原每批上限。
- 可同时成立的验收维度使用多选或分别提问，单选只表达互斥方案。
- 推荐可以保留，但必须说明适用假设和代价；没有证据时使用条件性语言，不把未知基线说成事实，不使用无依据的“唯一”。
- 分类只表达有效分组，单子项不为显得结构化而反复增加层级。
- 追问优先检视依据、反例、后果与验证安排，尊重已有回答，不强制每题都填写长理由。

## 5. 验收标准

| 编号 | 可观察结果 |
| --- | --- |
| AC01 | 脑图起步模板能用已有代理经原校验生成完整输入、澄清回路和结果输出；无合适代理时有可理解的下一步。 |
| AC02 | 全景直接展示回答摘要和显式决定状态；业务根标题、简化分类、完整路径与节点导航均正确。 |
| AC03 | decided / provisional 与 confirmedBasis 分开；旧数据缺省不伪造判断；任何决定内容修改使确认失效。 |
| AC04 | 选区引用、四种追问入口与自由指引均能沿原同轮分支生成；可取消、失败保留、可重试，不提交答案或提前续跑。 |
| AC05 | 单机和托管都使用 bootstrap 已选的执行设施；托管控制面无 `opencode` 时仍可追问；运行时冻结与观测归属正确。 |
| AC06 | 决定补充从本地草稿、服务端草稿、刷新、协作更新、锁定答案、封存、派发到续跑不丢失；归属与确认比较覆盖新增内容。 |
| AC07 | 复核面板与全景、聚焦使用同一份答案；可定位修改；暂定、缺少责任安排和失败追问明确可见。 |
| AC08 | 确认后只发生原提交一次；继续/停止、self/cross、部分锁定、旧问答保持行为；在途追问和保存失败等原阻断有效。 |
| AC09 | 初始与追加问题遵循原子取舍、多选兼容、条件性推荐与简洁分类；使用本次无基线场景进行真实模型验收。 |
| AC10 | 最终提示和实际文档保留用户原话、暂定状态、未知、代价、负责人和复核时机；不得补造证据或责任人。 |
| AC11 | 桌面与 390/320px、浅/深色、键盘及文本选择可用；既有大图规模能力保持。 |
| AC12 | 从起步到真实追问、编辑、刷新、复核、最终输出及任务 done 的完整旅程通过，记录 task / run / output；模拟与真实证据分开。 |

## 6. 审核与完成口径

本轮原型及 RFC 审核通过后，先完成 AC01～AC12 的生产实现和全部测试用例，再集中验证。质量门以 GitHub Actions 的确切 SHA 为准；真实部署与浏览器验收单独记账。部署到正式服务前必须有具体发布候选与用户授权，既有正式 AW 保持运行。

原型演示不等于生产实现或模型有效性证明。一次代理走查也不等于真实参与者研究；后续用户试用观察其是否主动质疑推荐、表达取舍、指出待验证事项和复核责任，不以填写字段数量或分支数量计成功。
