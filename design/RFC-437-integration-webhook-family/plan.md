## 集中验证（2026-11-03，候选基于 `a64e68f9a`）

全部实现与用例写完后一次进行。

- **静态**：`tsc` 0 错；eslint `--max-warnings 0` 与 promises 配置无告警；改动的 TS 文件已按 prettier 格式化。
- **全量 SQLite**（`bun run test:backend`，四分片）：23286 pass / 23 fail，另有文件级错误。逐条归因：
  - **本 RFC 的问题，已修**：
    - 分发器依赖合同里有一个从未使用的 identity-access `public/queries` 类型。迁入 integration 后它成了 design §3.1 DAG 之外的 offered 边，
      RFC-376 的 off-DAG 基线与计数上限、RFC-294 §B1 账本因此报出。处理是删去这个死依赖，不登记新债（design §0）；
    - RFC-305 授权围栏用例仍读分发器旧路径，测试套件策略「模块级读取的源码路径必须存在」随之报出；
    - RFC-437 新用例的事件中心假实现对每条观测都返回同一批投递，通知被重复计入。问题在用例自身，被测逻辑与原路由一致。
  - **只在未提交的工作树出现**：路由错误码棘轮按 git 索引取文件，索引里仍有已删的旧路由。导出仓库里候选已提交，该用例通过。
  - **负载超时，与本 RFC 无关**：
    - 涉及 RFC-396 MR 候选桥 8 条、RFC-167 dw-confirm 3 条，以及 RFC-075 自动提交、wrapper fan-out、RFC-370 V16、RFC-363 工作区分页各 1 条；
    - 同一时限下逐个文件单独复跑全部通过（37 / 29 / 3 / 6 / 8 / 4 pass）。
- **复验**（SQLite，`--isolate`）：修正后的文件连同架构测试与受影响的源码锁，151 个文件 1495 pass / 4 skip；唯一错误是上面那条
  只在未提交工作树出现的路由错误码棘轮。
- **导出仓库**（`a64e68f9a` 的 `git archive` 加候选路径，提交后运行，同时接 PostgreSQL 真库）：
  - 共 255 个文件：按已提交源码出报告的用例、路由错误码棘轮与 API 合同覆盖、提及 Webhook 的双引擎用例 96 个、本 RFC 改动的用例，去重后合并；
  - 结果 3683 pass / 2 fail / 4 skip：
    - RFC-359 W5 组合根路由面：PostgreSQL 应用在四路并行下启动超时，单独复跑两个引擎都通过，路由面逐字一致；
    - RFC-437 位置用例：原断言 `services/webhook/` 目录不存在，但导出仓库从归档解出后留下一个空目录（git 不跟踪空目录）。
      改为断言其中没有源码，复跑通过。
- **P0 变异 lane**（`scripts/rfc359-p0-mutations.ts`，SQLite 与 PostgreSQL）：每个引擎 17 个阶段（当前绿、15 个历史回归变异各自变红、当前再绿）全部符合预期，源文件哈希前后一致。
- **计数复核**：import `services/` 的路由 24 个；深引模块内部的路由 3 个（`code.ts`、`capabilityTemplates.ts`、`scheduledTasks.ts`）。

## 实现门（本会话自审，只审功能）

按路径限定在本 RFC 的改动，结论 PASS：

- 入站接收：判定顺序与原路由逐条相同（未知适配器仍计未匹配额度、限流先于读正文、读正文先于解封）；落库的投递状态与原因、
  HTTP 状态码与响应体不变；装配缺件时不挂载入站面的条件不变；
- 投递重放：错误码与文案不变，可用性先于读投递判定；三种标记与 `webhookDeliveryOutcome` 逐字等价；终态唤醒、逐个通知与通知失败被吞不变；
- 分发器、触发器、端点、终态工作区清理只改依赖来源，删去的只是零消费者的转出、零调用的函数与从未使用的依赖字段；
- 路由、方法、权限点、令牌访问与公开理由不变，`server.ts` 的挂载先后不变。
