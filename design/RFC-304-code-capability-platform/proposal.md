## 1. 背景

用户诉求在澄清过程中经历了三次扩张，最终形态远超最初那句话。原始诉求：

> 利用 MR 创建的 webhook 来触发 MR 检视，并且能在代码行上提问题，一次可以提很多个问题，
> 主要是要挂在代码行上而不是全局评论里。

在逐条澄清五类能力的业务目标时，用户先后追加了三条改变形状的要求：

> 写个代码工具集，承载所有代码能力，包括 issue 修复，代码检视，根据评论修改代码等。

> 在流程环节前后还可以插件化注入脚本操作工作树，比如附加提示词、额外下载必须文件等。

> 提交完 MR 之后会有一个 MR 监视器能力，监视 MR 的状态……修复是有优先级的，比如先修冲突、
> 再修评论、最后修 CI，CI 又分先修编译再修 codecheck 和 UT 覆盖率等。不同的修复要注入不同的
> 提示词，所以还要有个 agent 选择器。

### 1.1 平台今天已有什么

本 RFC 的绝大部分基建**已经存在**，这是它能成立的前提：

| 环节 | 现状 | 锚点 |
| --- | --- | --- |

| 触发上下文 | 30 个 `{{trigger.webhook.*}}` 冻结变量 | `docs/webhook-triggers.md:186` |

### 1.2 三个真缺口

1. **一节点一请求。** RFC-269 §3 明确把批量列为非目标，而检视意见的条数是运行期才知道的。
2. **行级定位无从构造。** GitLab 的 `position` 需要 `base_sha`/`start_sha`/`head_sha`（来自
   `GET /merge_requests/:iid` 的 `diff_refs`，**不在那 30 个变量里**），未变更的上下文行还要
   `old_line` 与 `new_line` 成对；GitHub 要 `commit_id`+`path`+`line`+`side`。让 agent 自己拼这个
   结构必然大面积 400。现有的 `comment_position_json` 只在 note 事件有值，且是「别人那条评论的
   位置」，不是「我要提的问题的位置」。
3. **没有跨事件的业务对象。** 平台今天的最长生命周期单元是一个 task（一次执行）。而这五类能力
   全都锚定一个外部对象、被同一对象的**多次**事件驱动、并且必须**记得上一轮做过什么**。

4. **issue 事件面完全不存在**（设计门核实，初稿漏判）。`CODE_HOST_EVENT_TYPES`
   （`packages/shared/src/schemas/webhook.ts:19`）只有 push / tag_push / mr_× 4 / note /
   pipeline_× 2 共十项，**没有任何 issue 事件**；而且 note 事件被显式限制在 MR 上——GitLab adapter
   对 `noteable_type !== 'MergeRequest'` 直接拒绝（`gitlabAdapter.ts:277`，detail 写着
   "v1: MR comments only"），GitHub adapter 对非 PR 的 issue comment 同样拒绝
   （`githubAdapter.ts:336`）。**后果是双向的**：issue 打标签进不来（D3 的入口之一），
   issue 里的反问答案也回不来（D2 的回写分支）。这一块必须作为本 RFC 的实现内容新增，
   不能假定现成。

## 2. 两条宪法

本 RFC 的一切设计从这两条推导，它们优先于本文其余任何条款。

### 2.1 产品边界宪法（用户原话）

> 本平台承载与人的交互：1、输入问题、设计文档 2、反问人澄清问题。
> 其他的都承载在 MR 上，MR 评论驱动的代码修复 + 平台自动化流程。

直接后果：**平台不重造代码平台的界面**。不做 MR 列表、不做检视结果浏览页、不做意见管理台。
`/code` 只有配置、模板、发起入口、度量四块，加上一张运行状态图。所有"看结果、给反馈、催进度"
的日常交互都发生在 MR 上。

### 2.2 架构宪法：确定性调度（用户原话）

> 我要做的是确定性调度流程，不是给一句提示词让 AI 自己决定怎么跑。只要不需要用 AI 的地方全部
> 都程序化，只有必须用 AI 的地方才调度 AI，并且每个 AI 用 envelope 封死，返回不符合要求就重试
> 或重跑，输出确定性结果后再继续。

拆成五条可执行规则：

- **R1** 凡能由程序判定的，一律程序化：拆块、分类、排序、截断、去重、定位解析、发布、落账。
- **R2** AI 只出现在真正需要判断的地方：看代码找问题、写修复代码、理解需求描述。
- **R3** 每个 AI 步骤声明输出 schema，用 envelope 封死；平台在**下一步之前**校验。
- **R4** 校验不过：带错误反馈在同会话重试 N 次；仍不过则丢弃会话、换新会话重跑。
- **R5** 输出确定化之后才继续。任何"AI 说什么就是什么"的直连都不允许。

后果可以量化。MR 检视这条流程十三步里**只有两步是 AI**：

```
resolve-target      程序   从事件取 MR 标识、分支、sha
prepare-worktree    程序   worktree + checkout
fetch-diff          程序   git diff origin/<target>...HEAD
split-diff          程序   按目录层级聚合，受体量上限约束
review-shard        ⟨AI⟩   看代码找问题        → envelope: findings[]
review-global       ⟨AI⟩   跨文件接口一致性     → envelope: findings[]
validate-findings   程序   结构/字段/行号存在性校验 → 不合格按 R4 重跑
gate                程序   严重度阈值 + 单轮上限，确定性排序截断
resolve-positions   程序   diff_refs → position 组装
reconcile           程序   与台账三集合对账：持续存在 / 新增 / 已消失
publish             程序   草稿攒齐一次性发布
settle-stale        程序   **发布成功后**才处理已消失的意见（provider-specific）
ledger              程序   落台账
```

CI 修复同理，八步里两步 AI；**错误分类由脚本做，不是让 AI 读日志说"我觉得这是编译错"**。
这条宪法还直接否掉了一个自然但错误的设计：**agent 选择器必须是脚本，不能是 AI**。

## 3. 系统结构

```
入口层   需求实现（issue 标签 / 平台界面 / 平台 API）· MR 检视（webhook 配置触发）· 人手工提的 MR
             ↓ 产出或纳入 MR
监视层   MR 监视器 —— 事件唤醒 → 采集 → 分类 → 仲裁 → 选 agent → 起一轮 → 回到采集
             ↓ 派活                                    ↑ 循环至 MR 合并 / 关闭
动作层   检视 · 改评论 · 修 CI（编译 → codecheck → UT 覆盖率）· 报告冲突（不修）
             ↑ 每种动作 = 一条阶段序列（平台写死、版本化）
可插层   入口脚本 · 采集脚本 · 分类脚本 · 仲裁选择器脚本 · 阶段边界钩子
```

### 3.1 外部系统适配原则

平台原生只对接 **GitLab / GitHub** 两个代码平台。任何公司自建系统（issue 分发、CI 流水线、
文档库、工单）一律通过**脚本适配器**接入：平台只定义输入输出 schema，不猜对方的 API。
以后接第三个自建系统是加一个适配脚本，不是改架构。

### 3.2 两层配置

| 层 | 内容 | 谁维护 | 权限档 |
| --- | --- | --- | --- |
| **部门层：脚本框架** | 入口 / 采集 / 分类 / 仲裁选择器脚本、**钩子**、参数默认值 | 一个部门一人，全部门共用 | `scripts:author`（= daemon 全凭据面） |
| **小组层：能力配置** | 每步用哪个 agent、提示词、阈值与上限（覆盖部门默认） | 各小组自管 | 普通 agent 资源权限 |

风险最高的那层恰好也是维护者最少的那层。一个能力只能引用一个框架，不同能力可引用不同框架。
两层各内置一套：一套「标准 GitLab/GitHub 框架」（不接任何自建系统、开箱即用）+ 五套默认 agent 绑定。

### 3.3 定制的边界

**阶段序列平台写死、不可自定义。** 各组定制的是 agent / 提示词 / 脚本 / 参数。这样平台才能保证
结构性正确（`resolve-positions` 与 `reconcile` 一定在 `publish` 之前、`settle-stale` 一定在
`publish` **之后**）——序列一旦
可自由编排，拼错顺序的后果是"评论全发在错误的行上"这类无法回收、极难归因的故障。

定制结果存为**模板资源**（新一类资源，复用 owner / visibility / grants / 复制），
导入导出走 RFC-271 配置包 zip，依赖闭包与脱敏索引全部现成。

## 4. 目标

- **G1** MR 事件或 @叫触发代码检视，意见**挂在代码行上**，一次提交多条，一次通知。
- **G2** 大 MR 按目录层级聚合拆块并行审 + 一轮全局关联审，单 agent 上下文保持小。
- **G3** 行级定位由**平台**解析（拉 `diff_refs`、组装 position、锚定失败降级），agent 只说文件与行号。
- **G4** MR 监视器持续跟进到合并/关闭：采集状态 → 按优先级仲裁 → 选 agent → 起一轮 → 循环。
- **G5** 评论驱动改码：能用原生 suggestion 就用，大改动走"贴 diff + 作者确认后推送"。
- **G6** 需求实现：issue 标签 / 平台界面 / 平台 API 三个入口进来，产出一个 MR。
- **G7** CI 修复：状态采集与错误分类由脚本适配自研流水线，按编译 → codecheck → UT 覆盖率优先级修。
- **G8** 工作项模型：跨事件、跨天、跨轮次的业务对象，带台账与幂等。
- **G9** 阶段引擎：每条能力一条写死且版本化的阶段序列，每个边界可挂钩子。
- **G10** 两层配置：部门脚本框架 + 小组 agent 绑定，权限与风险对齐。
- **G11** 采纳度量：resolve 信号与代码实变信号分列记账，为将来"要不要卡流水线"提供依据。
- **G12** 运行呈现为一张三层状态机流转图（工作项 → 当前轮阶段 → 每次 AI 调用），可切轮次回看。

## 5. 非目标

- **N1 不修冲突。** 只报告。冲突合错是静默的——编译过、测试过、逻辑错了。（用户拍板）
- **N2 不管主干流水线。** 只管 MR 上的。机器自动往 `main` 推修复的风险不可接受。
- **N3 不做序列自定义。** 见 §3.3。
- **N4 不重造代码平台界面。** 见 §2.1。
- **N5 不扩 agent 的环境变量白名单。** RFC-269 立的凭据边界一个字节不动；需要凭据的一律走脚本。
- **N6 不动 fanout。** 本 RFC 不依赖 wrapper-fanout。它内层只支持 `agent-single`
  （`dispatchFanoutShardAttempt` 里的 `inner.kind !== 'agent-single'` 守卫，
  `services/scheduler.ts:7357`）且内层无上游解析，扩展是 RFC-294 W8 的独立课题，另立新号。
- **N7 不做轮询。** 监视器由事件唤醒，唤醒后跑一次采集脚本。
- **N8 不接 GitLab / GitHub 以外的代码平台。**
- **N9 不做 AI 决策的调度。** 见宪法 R1/R2。
- **N10 不做跨 MR 的批量操作面。**

### E. MR 监视器与 CI 修复

| # | 议题 | 拍板 |
| --- | --- | --- |

## 7. 新增能力面的代价（逐项呈报）

本 RFC **不关闭任何既有能力**，CLAUDE.md §RFC workflow 第 7 条的「能力收缩型 RFC」门槛不触发。
但它新开的能力面必须逐项摆上台面：

- **C1 平台首次自主写代码并推送。** 此前平台的写能力止于代码平台对象（评论、状态、标签）。
  现在它会往真实分支推提交。封堵：真推送锁 MR 作者（bot 开的 MR 锁发起人）；suggestion 路径
  完全不需要写权限；推送前校远端 sha，变了就放弃。
- **C2 脚本挂载点 = daemon 全凭据面。** 脚本完整继承 daemon 环境（`services/scriptRun.ts:325`，
  RFC-276 的明确设计）。能写部门框架脚本或钩子的人，等于能读到平台持有的全部 token。故这一层
  归 `scripts:author`（RFC-253 对它的定义正是"可造成宿主执行"），且**不下放到小组层**。
- **C3 外部数据进入 prompt 的面变宽。** issue 正文、MR 评论、CI 日志都是外部可写文本，且现在
  会进入 agent 上下文。这不是本 RFC 新开的面（RFC-263 的 `comment_text` 已经能），但量级变了。
  缓解：继续走 RFC-200 的注入边界围栏，且所有入口内容有长度上限。
- **C4 任务量显著放大。** 每个活跃 MR 的每一轮都是一个 task。缓解：同一工作项串行 + 新轮抢占
  旧轮（基于旧代码的结论本来就过期）+ 平台全局并发上限 + 独立任务类型可筛选，避免淹没人工任务。
- **C5 模板分享传递信任。** A 组的模板导入 B 组时，其 agent 提示词、脚本一并进入 B 组的执行面。
  缓解：配置包已有 `requirements`（导入方需自备）与 `secrets[]`（脱敏位置索引）两套机制；
  脚本仍受导入方的 `scripts:author` 约束，不因来自包内就自动获得授权。
- **C6 采纳率数据的解读风险。** 「作者 resolve」可能只是想清掉红点。故两个信号**分列**存储，
  不合成单一指标，避免将来据此做"卡流水线"决策时被误导。

## 8. 用户故事

1. **提了 MR，十分钟后有人审了。** 开发者推完分支开 MR，webhook 起检视工作项；worktree checkout
   源分支，按目录拆成四块并行审，再跑一轮跨文件关联审；十几条意见过阈值与上限闸门后攒成草稿，
   一次性发布——MR 上只响一次通知，行级评论精确落在改动行，两条锚不上的并进总览评论。
2. **reviewer 说"这里改成 X"，机器改了。** reviewer 在行上 @叫；改动小，机器直接回一个原生
   suggestion 块，作者点 Apply 就应用了——全程没有任何人往分支推过代码。
3. **改动大，走确认推送。** 涉及三个文件的重构，suggestion 表达不了；机器把 diff 贴在线程里，
   作者回一句 `@aw push`，机器校远端 sha 未变后推送。期间别人推了新 commit，机器放弃并回帖请重叫。
4. **issue 打个标签，第二天来看 MR。** 报告人给 issue 打上约定标签；机器读不懂复现步骤，在 issue
   评论里反问两个问题；报告人回答后机器继续，定位、修复、写测试、跑目标仓门禁、自己审一遍自己的
   改动，最后开一个 MR，描述里写清根因与修法。这个 MR 随即被检视流程接管。
5. **CI 红了，机器按优先级修。** 自研流水线失败，GitLab pipeline webhook 唤醒监视器；采集脚本拉回
   门禁状态，分类脚本判定为两个编译错加三个 codestyle；仲裁脚本按优先级返回本轮工作包（先编译）；
   选择器脚本挑中"编译修复 agent"及其提示词；修完在同一 worktree 里依次处理完这批，跑一遍检视确认
   没有删测试骗绿，统一推送一次。三轮没修好就交人。
6. **部门配一次，各组用起来。** 部门的工具人配好脚本框架（对接自研流水线与 issue 分发）；A 组基于
   它绑定自己的检视 agent 与提示词、把阈值调到只发 P1 以上；B 组复制 A 组的配置改了提示词；C 组
   在另一个实例上导入 A 组的配置包 zip，按 `requirements` 提示补上自己的凭据即可运行。

## 9. 验收标准

**检视与发布**

- **AC-1** MR open 事件触发检视，行级评论落在正确的行上，且一次事件只产生**一次** MR 通知。
- **AC-2** 一个改动 40 个文件的 MR 被拆成多块并行审，且随后有一轮全局关联审；分块结果可在状态图上看到。
- **AC-3** agent 报的行不在本次 diff 中时，该条降级进总览评论并计入 `degraded` 计数，节点仍算成功。
- **AC-4** agent 在检视中修改过工作树后，其上报行号仍锚定**原始 diff**，不受自身改动影响。
- **AC-5** 严重度低于阈值的意见不上行级评论；超出单轮上限时按严重度截断并在总览中写明未展开条数。
- **AC-6** 第二轮检视做**集合对账**：仍然存在的问题不重发但**原线程保持未解决**；已消失的才被
  resolve；新增的正常发布。且清理发生在发布**成功之后**——发布失败时上一轮反馈原样保留。
- **AC-6b** 同一文件里两处不同位置、正文相同的问题**各自独立发布**，不被指纹吞掉。
- **AC-7** 台账中 `resolved` 与 `code_changed` 两列独立记录，可分别查询；工作项 `closed` 时对
  未标记 `code_changed` 的意见做一次终局比对回填。
- **AC-7b** 同一 MR 上，检视轮与监视器轮**不并发**：一方持 MR lease 时另一方排队；发布/推送前
  复核 lease 与 `baselineSha` 仍有效，过期则放弃本轮产出。

**确定性契约**

- **AC-8** AI 步骤输出不合 schema 时，先带错误反馈同会话重试，达上限后换新会话重跑；两级都耗尽才判阶段失败。
- **AC-9** 流程中不存在"AI 输出未经程序校验直接进入下一步"的路径（源码层负扫描锁定）。
- **AC-10** agent 选择器、错误分类、优先级仲裁三处**均无 AI 参与**（源码层锁定）。

**监视器与修复**

- **AC-11** pipeline webhook 到达后跑一次采集脚本，不产生任何轮询调用。
- **AC-12** 仲裁脚本一次返回多个修复项时，在同一轮同一 worktree 内依次完成并**只推送一次**。
- **AC-13** 修复 diff 若删除断言 / 新增 skip / 减少测试行，检视会将其作为高严重度问题提出。
- **AC-14** CI 修复三轮未成功则停止并回帖汇总每轮尝试与失败原因；工作项落 `handed_off`，
  **后续 pipeline 事件不会自动开始第四轮**，且 MR 与 `/code` 上显示由谁接手、如何解除。
- **AC-14b** 配额计数键是 `(工作项, 失败指纹)`：作者推新代码导致的**另一个**失败重新计数，
  不吃掉上一个 campaign 的配额。
- **AC-14c** issue 打标签可启动需求实现；issue 评论里的回答能被收取并关联到具体那一问；
  issue 侧双向通道不可用时该入口**拒绝启用并说明原因**，不静默回退到平台反问。
- **AC-14d** 部署侧无任何唤醒源（既无 GitLab pipeline 事件、也未接 wake 入口）时，
  CI 修复能力在矩阵里标为不可用并说明原因，而不是配好了却永不触发。
- **AC-15** 检测到冲突时只回帖报告，不产生任何写操作。

**权限与凭据**

- **AC-16** 仓库写权限者可叫机器发 suggestion；非 MR 作者叫推送被拒并说明原因。
- **AC-17** bot 开的 MR 上，发起需求的人可叫推送，其他人不可。
- **AC-18** 小组层配置界面不能创建或修改任何脚本与钩子；尝试写入被拒。
- **AC-19** 一枚勾满矩阵权限的 PAT 拿不到部门层脚本框架的写权限。
- **AC-20** 脚本与钩子的环境中可见 daemon 凭据，但 agent 进程的环境白名单**逐字节未变**（对照测试）。

**配置与模板**

- **AC-21** 小组配置引用部门框架；部门改了默认阈值，未覆盖该项的小组随之变化，已覆盖的不变。
- **AC-22** 模板导出为配置包 zip，含依赖闭包与 `requirements`；在另一实例导入后可运行。
- **AC-23** 阶段契约升版后，声明了旧版本的钩子**显式报需要迁移**，不静默跳过。
- **AC-24** 内置框架（不接任何自建系统）+ 内置 agent 绑定可在**不编写任何脚本**的前提下跑通
  GitLab 检视；最小配置 = 在仓库 × 能力矩阵里开一个开关（"零配置"不等于"不用开开关"）。

**平台面**

- **AC-25** 状态图三层可展开：工作项状态 → 当前轮阶段 → 每次 AI 调用（含 envelope 校验结果与重试次数）。
- **AC-26** 可切换到历史轮次查看当时走过的路径与停留位置。
- **AC-27** `/code` 产生的任务在任务列表中带独立类型，可筛选，不淹没人工任务。
- **AC-28** 同一 MR 在新事件到达时**先落 `superseding`、epoch +1**，旧轮到达终态后才开新轮；
  全程不产生孤儿运行行。
- **AC-28b** 一轮在 `publish` / `push` 前若发现自己的 epoch 已过期（被抢占），**放弃产出**而不是照发。
- **AC-29** 进入 `awaiting` 前被确认的改动已固化为不可变产物并带 digest；唤醒后推送的内容与该
  digest 一致，且 **AI 阶段未重跑**。
- **AC-30** 并行分片各自拥有独立的一次性工作树：两个分片同时改同名文件互不可见；同一输入重复
  执行得到同一组 findings。
- **AC-31** fork 场景两家各跑通一条：源分支能 checkout；fork PR 的 CI 事件经 head SHA 映射唤醒
  **唯一** MR，零命中或多命中时不唤醒并记事件。
- **AC-32** 矩阵每格显示 `disabled` / `misconfigured` / `ready`；`misconfigured` 时逐条列出缺什么
  并各带一键修复入口。

## 10bis. 「跑稳了再加码」的加码路径

B2 拍板「先当参考不阻塞，记采纳率，跑稳了再加码」。**加码本身不在本 RFC 范围**，但本 RFC 必须
为它留下入口，否则将来要加码时会发现数据不可用、开关无处放：

- **数据**：两个采纳信号分列存储（C6）+ 终局比对回填（design §2.4），保证样本不缺最后一轮。
- **开关位**：小组层能力配置预留 `blockingLevel` 字段，本 RFC 固定为 `none` 且 UI 不暴露。
  将来加码只需放开取值（如 `p0-blocks` ⇒ 有 P0 时把 commit status 设为 failed），不需要改数据模型。
- **判据**：加码应由**该仓自己的**采纳率数据支撑，而不是全平台平均——所以度量按仓库维度聚合。
