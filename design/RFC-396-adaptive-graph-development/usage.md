# RFC-396 使用与验证合同

本页描述实现候选；实际验证状态见 [验收记录](./validation.md) 和 [实施计划](./plan.md)。

1. 新工作在数字人类型中选择 `graph-development@2`，绑定已经登记的仓库。基础 MR 岗位支持图设计、代码生成、MR 提交、评审和冲突看护。需要完整 CI 看护时，先在“图驱动研发 · 完整 MR 看护（配置流水线连接）”岗位草稿中选定并发布企业流水线连接，再发布岗位、创建员工和工作。平台不会替团队选择任意企业连接。已有 Case 保持启动时冻结的员工、岗位与工具版本，后来修改岗位不会自动升级正在运行的工作。历史 `graph-development@1` 与内置旧岗位仍可读取和运行。
2. 提交原始需求和附件，进入 Case 的“设计”页。平台先保存模型，再通过原澄清页面提问；等待回答时设计仍可阅读。原选项、自定义原话、暂定状态和未知责任不由模型补写。
3. 在当前图组合选择元素、边或路径，可补充澄清、调整组合、检查例外、比较提案并明确应用。固定图仍会提示依据变化；布局缩放和折叠不改变语义版本。无适合表达器时保留语义列表和缺口。
4. 在“编辑设计与验证安排”中检查需求的验收义务。代码执行必须选择实际发布的 verification profile 精确版本，人工验收需写具体操作和观察。未安排、缺少测试引用或无法运行均不会显示为已通过。实现依据里的义务都要在交付前对候选核对通过，候选验证才会放行交付；MR 创建后才能观察的事（CI 结果、看护修复、合入或关闭决定）由 MR 看护负责。真实设计员有时会把这类条件写成人工义务（2026-10-28 企业与托管验收各遇到一次），此时在审核前拆分该义务：交付前的检查留在原元素上，交付后的条件挂到可在预览时排除的元素上，或直接在预览实现依据时排除对应元素。否则 Case 会停在候选验证，提示存在未完成的验收项。
5. 选择实现范围并预览实现依据，检查完整冻结语义与原始回答，再请求人工审核。审核通过以后还要显式发起实现。拒绝/迭代保留原决定，编辑后创建新依据并重新审核。
6. 代码和用例生成完成后，平台对实际 Git candidate 进行结构、引用、profile 和有限行为验证。失败留在 Case 等待处理；实现限制生成待应用反馈提案。若其中的限制不是真实缺口（例如待人工核对、待平台执行 profile、已批准的范围边界），在该提案上「判定不构成缺口」并写明理由：判定只覆盖这一轮实现报告，之后的看护修复仍然有效，新的实现轮需要重新判定。需要模型重新出报告时可再次发起实现，代码已完整时本轮允许不改动。人工验收绑定精确 candidate tree，后续代码变化令原判断过期。
7. 在执行链接查看并下载工作区，在验证条目检查原始回执、输出尾部和完整文件型报告；支持原字节报告下载和证据包导出。实现依据可导出，设计可读取历史版本。
8. `graph-development@2` 创建 Case 时分别指定 MR 目标分支与源分支；源分支可由平台生成，必须与目标不同。图验证形成内部候选后，同一 Case 继续提交 MR 并看护，直到仓库侧确认合入或关闭。MR 创建成功不会被显示为完成。代码评审、CI 失败与冲突修复都复用既有数字人的处理链路；每次发布修复前重新确认已批准的设计、当前候选及验证证据。设计或审批发生变化时回到澄清和审核。仅回复的评审不改代码，平台不自动合并或部署。
9. “交付与持续看护”显示 MR 链接、源/目标分支、当前 head/target、评审、流水线与审批。旧提交的绿灯明确标成旧版本，不能满足当前合并条件。没有配置 CI 连接的基础岗位不会假定 CI 通过；配置入口指向完整 CI 岗位。新建 MR 需要真实存在的目标分支提交。已有冻结的 graph@1 Case 可继续无提交仓库的内部候选流程。新工作使用 graph@2，须先在托管仓库建立真实目标分支；平台不会虚构 MR 目标，也不提供通过新建旧版工作绕过该条件的入口。
10. 历史 `graph-development@1` 保持原行为：未指定发布分支时交付内部候选提交；指定后推送分支并记录回执，不承诺 MR 看护。终态后的补充澄清新建关联 Case。

## 图组合选择

模型按当前需求生成候选视图，平台对必需关注点、覆盖增益、冗余、阅读/生成预算与固定项进行确定性选择。图数不是预设；可为一张或多张，不能满足的关注点单列缺口。现有 flow、sequence、state、data、decision-table、composite 是版本化表达适配器，不是固定交付图包。最优仅指给定候选与当前评分预算下的选择，不声称全局设计最优。

## 有限行为校验适配器

状态机或决策表的 execution obligation 可以指定 modelCheck：实际 profile 版本、候选内 `repo:` 程序、输入样本、深度/路径/超时上限。程序从 stdin 读取 JSON。状态机请求含 input、actions（actionRef、参数）与断言引用，返回实际 `states` 和 `assertions`；决策表请求含 input，返回实际 `outputs` 和 `assertions`。程序应调用候选中的真实业务实现，不能回显预期值。

平台从模型独立计算有限路径或规则期望，与实际程序输出比较。达到边界、缺失事件/断言绑定、规则冲突、无法执行都明确记录；有限样本通过不构成所有输入的形式证明。执行环境摘要包含可观察本地运行条件，不覆盖未声明的远端服务。

## 验收证据口径

四类证据分别为结构检查、设计批准、代码执行、人工验收。每项绑定语义依赖、依据 digest、候选 tree、profile 版本与可用环境；缺产物或输入变动时标记未知/过期。代码与符号追溯的 reference-checked 仅证明候选文本可定位。

人工验收只针对本次依据包含的义务。打开验收窗口后若候选、依据、义务或范围改变，需要关闭后重新核对；系统不会将原观察自动绑定到新代码。profile 使用已批准的准确 revision，后续发布或归档资源不会自动改变在途合同；该 revision 不可读取或内容不匹配时不能复用原通过记录。

实现报告的 `limitations` 应记录没有履行的已批准范围。已经批准的范围边界、等待平台执行和待人工核对分别说明；平台仍要求真实 profile 回执和对应候选的人工验收，不能用模型自称完成替代。测试通过后发现遗漏时，仍通过反馈、设计变更、重新审核和候选验证处理。三条真实案例及其失败恢复见 [真实验收](./real-model-acceptance.md) 和 [精确版本汇总](./real-model-summary.json)。

`rfc396-graph-development.spec.ts` 的三个旅程使用确定性模型协议夹具，产品状态、Case、原生人工门、Git 与浏览器均为真实路径；它们不构成真实模型效果证明。真实模型、PostgreSQL、托管执行与 hosted CI 应分别登记。
