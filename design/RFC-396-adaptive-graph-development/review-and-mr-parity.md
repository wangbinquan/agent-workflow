# RFC-396 全面回顾与 MR 能力补齐

2026-10-22。用户要求从易用性、界面可读可理解和功能正确性全面反思当前实现，随后明确：这个数字人也必须补齐原数字人的 MR 提交和监控能力。本文是原获批 RFC 的补充合同；不新增第二条执行链。用户已允许本任务内部多个 agent 并行调研执行，仍禁止向其他独立会话派活或协调。

## 1. 当前结论与证据边界

2026-10-23 接续的真实care补例发现R23：CI采集、分类、实际修复Task、重新执行profile和同MR新head均已发生，但新树的通过记录被当前投影误标过期。准确2e的实际DB/Git/原始回执与因果链见[诊断](./graph-care-projection-diagnostic-2026-10-23.json)。这是本RFC生产缺陷，不能放宽freshness断言。R23 修复已改为通过既有 stage 读取当前真实树，并在 finally 中清理；独立功能静态复核通过，Bun 1.4.3 的 SQLite 集中回归 3 pass / 0 fail、61 assertions（2.89s）。首次及修复发布后无差异保持 current，旧树、实际文件漂移、环境/读集变化和不可读取场景均保留失效断言。PostgreSQL、三平台 CI 与新准确 artifact 的 care 完整旅程仍待本轮候选发布后验证。

本轮起点 `main@4aadd9169ff9429ad457793208373b2ca6bfa6cd`。`graph-development@1` 的 `deliver-result` 只形成内部候选提交、可选推送分支，随后 terminal / graph-development.delivered，既没有创建 MR，也没有进入看护。这不是原研发数字人的完整交付能力。此前三个真实模型案例、托管候选和 CI 通过证据仍有效，但其结论范围只到当时的内部候选交付；不得外推为 MR 生命周期通过。

全面回顾发现的功能反例也重新打开原验收结论。诊断脚本在内存端口上调用实际领域函数/规划应用，证明八种反例，未声称真实数据库、模型或浏览器验收。本轮浏览器不可用；已有截图只能证明历史页面。此前 E2E 经 API 建立员工/工作并提交澄清答案，不是全程通过界面完成的新用户旅程。

源码基准是 `development-automation/composition/employeeTypePackage.ts`、`digitalEmployeePlatformWorkItems.ts`、`digitalEmployeeWorkspace.ts`、`employeeCaseDetailProjection.ts`，以及现有 Event Center、Case/Reaction/Task 与 source-control public participants。

## 3. 实现合同

### 3.1 版本与能力组合

发布 `graph-development@2`，以 graph 核心能力加共享 MR lifecycle 组合。保留已冻结 `graph-development@1` 的内部候选/可选分支语义与旧岗位、工具版本，不把历史任务静默升级成远端提交。新 MR 岗位必须提供完整可运行的图工具与 MR 修复工具；缺少 provider 连接或必要工具时显示具体配置原因，不在生成代码后才假称完成。

共用 lifecycle descriptor、合同、context codec、事件/订阅规则与平台 work item，保持真实 typeRef；不能把 graph 伪装为 development，也不能复制一套会分叉的 MR 调度状态机。OS 初始受理与被调用受理传入已冻结的 typeRef 和真实 Case ID，让 codec 根据实际版本决定行为。既有 development 的版本判断保持其原边界。

### 3.2 从图候选接入 MR

图独立校验通过后，形成内部提交及交付材料，把相同的候选、提交、上传计划和冻结依据交给现有 employee case workspace/candidate 持久化端口。工作现场通过既有 checkpoint/restore 迁移；不写数字员工 OS 私表，不新造任务工作区引擎。交接的可重放标识属于同一 Case，下一项工作是 publish-mr，Case 保持活动。

MR source branch 与 target branch 必须明确分开。未指定 source 时使用既有平台生成规则；target 使用图设计的仓库基线分支。既有历史直接推分支模式只属于旧任务语义。空仓仍可设计、实现和形成无父提交；如果代码平台的 MR 目标分支没有真实提交，显示“先建立目标分支并重新确认基线”的实际阻塞，不编造 MR 或伪造完成。

### 3.3 看护期间的图约束

修复工具读取批准的 basis、需求来源、追溯及实际失败材料。修复代码或冲突后，平台针对当前业务树重新执行图验证与已登记 profile，验证通过才进入推送；初次通过的候选证据不能复用为修复后的通过证明。单纯不改代码的评审回复保留原语义，不制造空提交。

评审提出新需求、改变业务规则或批准依据过期时，应回到原图设计/澄清/审核入口；新的实现继续使用当前 MR 工作现场，不回到最初的旧 workspace。需求模型、源分支 head、目标分支 target、候选 tree、profile、环境是不同维度；UI 只对实际匹配的结果显示当前通过。

### 3.4 用户看到的状态

主页面分别展示：设计待确认、实现与本地验证、待提交 MR、MR 看护中、CI/评审/冲突/审批待处理、可合入但仍等待、已合入、已关闭、取消/失败。提供 MR 链接与 source→target、准确 head/target、最近观测时间、具体阻塞与下一步。内部提交只是一个产物状态，不能显示为 MR 交付成功。

原型先补充这些状态；生产界面沿用现有 Case 详情投影和公共组件。字段、状态和下一步使用用户能理解的文字，原始技术证据按需展开。设计批准与外部审批分别显示。

## 6. 本轮实现与验收边界

T17～T19 的生产实现和测试用例已写齐，进入 T20 集中验证。默认 MR 岗位和完整 CI 岗位草稿已接入正常启动与 unstarted 应用组合；完整 CI 岗位需要团队明确配置连接。正在运行的 Case 保持原冻结岗位，不能靠后改岗位获得新增 CI 能力。

候选型证据按当前工作区派生 tree 判定；人工验收后端与界面均绑定准确范围。批准的 profile revision 只要仍可读取且 digest 一致就继续有效，资源发布新版本或归档不会暗换在途的已批准合同。重复交接、真实冲突 merge、基线刷新、证据读取失败和人工撤回均有回归。具体测试数字、失败原因与修后复验见 [validation.md](./validation.md)。

本轮仍明确保留这些边界：CUA inventory 没有浏览器，创建 iab 返回 unavailable；后继已使用准确 `ae210` 的 GitHub artifact 在真实 Playwright 浏览器完成预约全页面旅程，最新摘要与320/390px实际文本边界均已验收并目检截图，见 validation。MR E2E 使用受控模型与 code host，不能替代真实 GitLab 企业连接验收；新实现未部署到旧托管验收实例。接续只读核实旧服务因 `ENOSPC` 无法启动、节点可用字节为0，CS/GitLab/registry读取失败另记，见[就绪证据](./hosted-readiness-2026-10-23.json)。

无变化重验的接续修复明确区分当前已发布候选与新代码候选：核对持久化head、真实tree、发布身份和当前原生批准后，使用原候选父基线重新验证，保存新的graph证据与handoff，复用原commit继续 `observe-mr`。新basis材料必须取得新批准并进入后续care；旧版与新版交付回执重放也核对批准和当前树。真实代码变化仍产生当前head的正常子提交。现有 `ensureMergeRequest` 不更新已存在MR的标题/描述，因此同tree但发布输入变化时，在任何commit前明确报 `graph-mr-publication-inputs-changed`，保留现有MR和提交，要求通过新工作重新准备和审核；不冒称已更新外部说明。代码/用例与实际执行结果分别记录在 validation，未取得新候选证据前不标整体通过。
