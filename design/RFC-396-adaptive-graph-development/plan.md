## 1. 执行纪律

当前补充合同：[review-and-mr-parity.md](./review-and-mr-parity.md)。T17～T19 生产与测试用例已齐并以 `ba7b8c6c4a03` 发布；T20 已取得真实 PostgreSQL 156/0、SQLite 对应修后回归、43 项前端交互及独立实现门 PASS。末次本地前端类型检查存在已核实的并发在制错误，精确边界见 validation.md；MR E2E、实际浏览器、真实企业连接与 T21 的 exact-SHA CI 分别记账。最新逐项裁决见 [完成度审计](./completion-audit-2026-10-23.md)。

1. 本 RFC 包含澄清、代码生成、验证完整闭环，不得以“先做图编辑器”替代退出目标。
2. T00～T02 是实现前设计工作；实现获批后完成 T03～T12 的全部生产代码、接线及测试用例编写，再集中进入 T13～T16 验证。
3. 开发期只做必要语法/格式静态检查，不通过分批跑功能测试或实现门代替剩余开发。
4. 集中验证发现本人缺陷后修复相关范围并复验；有效候选内容不变时复用结果，不因无关 HEAD 前进重复全量。
5. 只在现有主 checkout 的 main 工作。保留并发内容；Git 发布短时串行、检查共享 index、精确路径清单；不跨 session 发消息。
6. 原型、设计门、实现门、真实模型、provider 执行、exact-SHA CI 和部署分别记账。

2026-10-24 UTC R23 修复补记：R23 修复已改为通过既有 stage 读取当前真实树，并在 finally 中清理；独立功能静态复核通过，Bun 1.4.3 的 SQLite 集中回归 3 pass / 0 fail、61 assertions（2.89s）。首次及修复发布后无差异保持 current，旧树、实际文件漂移、环境/读集变化和不可读取场景均保留失效断言。PostgreSQL、三平台 CI 与新准确 artifact 的 care 完整旅程仍待本轮候选发布后验证。 后继 main `52d642b102bb7cab4f8907aeb31a3139a5604c49` 已由对应会话修正 checkpoint 源码守卫；[CI 40059956104](https://github.com/wangbinquan/agent-workflow/actions/runs/40059956104) 终态 **47 success / 2 failure**，只余 Static scans 与派生 CI required。它未包含本轮尚未发布的 R23 修复与新增 care 用例，不能代签新候选。

## 3. 原型和设计确认内容

- 场景一：预约流程 → 新增并发冲突 → 新增优先级规则，验证图组合能改变和收敛。
- 场景二：异步通知 → 乱序/重复 → 退款例外，验证时序、状态、规则的互相定位。
- 场景三：已有模块改造 → 接口约束变化 → 验证失败，验证从证据回到代码与设计。
- 在同一原型中展示无足够材料、只有一张图、某关注点无支持表达器、固定视图过期、代码已生成但验证失败等状态。
- 确认默认范围为既有或已登记空仓库；不包含代码托管项目创建和自动部署。
- 锁定状态/决策表的首批可执行验证能力。选择具体库时使用当前官方文档与实际兼容性证据，不凭已有研究名词决定依赖。

## 5. 真实旅程与效果评估

## 7. 提交与发布建议

Draft 文档作为独立的小提交。实现获批后按相互可解释的领域内容拆提交，但只在完整开发与用例齐备后集中做功能验证；不得发布缺消费方的能力后宣称完成。实际工作遵守主 checkout/main 规则，不新建开发分支或 PR。

每次发布核对空共享 index、路径 allowlist、完整暂存 diff、提交内容与真实共同贡献者。正常 fetch/同步，保留所有并发内容；未知暂存项或不能安全同步时只暂停发布，报告具体阻塞。

文档发布的 CI 只证明该提交的检查状态；不能替代原型、设计门或本功能实现验收。

本次按用户完整实现及远端交付授权，先发布已完成确定性集中验证的实现候选，保留 In Progress 并消费 exact-SHA CI。T15 的最终接受仍依赖 T14；先提交候选不等于豁免真实模型、实际部署验收或降低 Done 条件。
