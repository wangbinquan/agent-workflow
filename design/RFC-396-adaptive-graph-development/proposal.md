> 配套：[技术设计](./design.md)、[实施与验收计划](./plan.md)。
> 设计调研基线：`main@3fcb14dbf8ab27cf451934942ea6b9cd647077f8`。完整实现与后续修复已发布至 `67795ed462`，对应主 CI 49/49 success；三个真实模型旅程与实际托管闭环均已完成。共享 main 后继 CI 尚未整体通过，准确退出状态以 [验收记录](./validation.md) 为准。

## 1. 背景与用户要求

用户提供《Agent Workflow 脑图反问节点设计》（2026-10-12 第 2 版），希望新增一类数字人，提供基于图的澄清、代码生成和校验。随后明确补充：

> 根据不同需求，应该能自适应生成最优的图组合，而不是确定性的几个图。

因此，本 RFC 的核心是根据目标、疑点、已有材料和使用阶段规划视图组合，并让同一份设计贯穿澄清、实现和验证。4+1、C4、时序、状态、数据关系等都是可选表达方法，不是固定交付清单。视图可以随需求新增、细化、合并、替换或归档。

原始提案中值得保留的是：人的原话与 AI 建议分开、确认绑定内容、图与依据关联、局部深入、范围收敛、设计可追溯。原提案的表名、独立脑图 session、完成命令和续跑方案不直接继承。RFC-372 已明确退役扩大实现，本次以新数字人的完整研发需求重新定义必要业务内容，不恢复第二套 clarify 生命周期。

## 3. 产品目标与边界

### 3.1 目标

- G1：用户从数字人入口提交需求，系统识别关键问题，解释为什么选择当前图组合。
- G2：用户可针对对象、关系、路径或整个视图澄清，保留原话、暂定决定、未知和成立条件。
- G3：多张视图引用一致的设计内容，表达方式和阅读顺序随需求变化。
- G4：将明确版本和范围的设计转为实现材料，生成完整代码与对应测试。
- G5：真实验证结果能回到需求、设计规则与场景；区分模型检查、程序验证和人的验收。
- G6：变化只影响实际依赖的结果，历史决定与证据可追溯，暂停/取消/恢复复用现有执行机制。

### 3.2 首版完整范围

1. 新类型、内置岗位和默认工作流；入口同时接受需求正文与已有附件。
2. 既有仓库的增量需求，以及用户已创建并登记的空仓库中的新应用需求。仓库读取用于建立真实基线；没有代码时明确显示空基线。
3. 关键问题、共享设计模型、动态视图规划、局部追问、版本差异、实现前设计复核。
4. 首批表达能力包括关系/流程、时序、状态、数据关系、规则决策表；可以按业务用途构造视图，也可以组合多个表达面。它们是能力库，不是每项需求必画的固定五张图。
5. 代码和测试生成、既有执行验证接入、按设计义务展示证据、设计变化后的影响提示。
6. 人可直接获得设计材料、候选代码差异和验证报告；已配置的正式交付继续经过既有研发发布能力，发布结果单独显示。
7. 单机/托管与 SQLite/PostgreSQL 使用同一业务规则；两种 provider 和两种执行部署路径分别验收。

### 3.3 非目标

- 不建设新 Agent 调度器、项目管理系统、知识图数据库或独立 MindmapSession。
- 不承诺数学意义上的全局最优选图、完整代码语义恢复、全部路径的形式化正确性。
- 不让模型在任务期间生成并安装新的可执行渲染器/验证插件。新表达能力通过正常版本发布扩展。
- 不自动创建代码托管项目、购买资源、合并变更或部署应用；这些不是首版闭环的完成条件。
- 不将任意手绘图或任意图源自动反解成可靠代码；表达能力不足时明确材料用途与缺口。
- 不迁移旧员工、旧任务或普通脑图，不改变其提交、继续/停止反问和发布行为。

## 4. 自适应图组合的产品合同

### 4.1 “最优”的可执行定义

在当前需求、受众、材料与成本约束下，选择能充分支撑关键判断、实现和验证，且阅读与维护负担尽量小的组合。推荐依据包含：

- 覆盖了哪些关键问题，仍有哪些问题没有合适表达；
- 每张图相对现有图提供了什么额外信息；
- 对实现与验证有何用途；
- 重复程度、阅读成本、更新成本及当前支持能力。

系统可以展示取舍与排序，不把自评分数包装成正确性或完整性证明。缺乏足够材料时先问一个有帮助的问题，不补造架构。明确且简单的需求允许只用一张图；不为达到固定张数或层数制造内容。

### 4.2 自适应过程

1. 从需求、代码和已采纳判断提取当前关注的问题；用户可以新增、改重要性或指出遗漏。
2. 模型提出候选视图，每个候选声明用途、覆盖问题、范围、依据、表达方式和尚缺材料。
3. 程序检查能力适配、引用与覆盖合同，比较组合的增量价值；用户固定的视图参与约束。
4. 生成选中组合，展示原因和未覆盖问题。视图里的假设使用明确标记。
5. 用户作答或修改设计后，仅重新规划受影响的部分；调整预览解释新增、替换、合并或归档原因。
6. 关键判断和本次验收方式已明确时可以结束澄清。允许有边界的暂定推进，未解决事实仍按原状交付。

候选目录不是固定业务模板。规划器可以定义“预约为何失败”“切换期间旧新数据如何共存”等新的业务视角。表达器提供语法与可验证语义，不决定需求必须用什么组合。

### 4.3 自适应示例

以下只用于说明与验收构造，不是需求类别到图组合的硬编码路由。

| 当前需求     | 初始疑点与可能视图                 | 新信息与调整                                                               |
| ------------ | ---------------------------------- | -------------------------------------------------------------------------- |
| 会议室预约   | 用户怎样操作：旅程/流程            | 多人抢同一时段：增加并发时序；规则优先级成为核心后增加决策表，收起重复表达 |
| 异步支付通知 | 重复与乱序：事件时序、状态迁移     | 新增退款：扩展相关状态和路径；已有数据结构足够明确时不追加 ER 图           |
| 旧模块改造   | 哪些调用受影响：依赖与变更影响     | 发现接口改变后补交互；部署不变时不生成部署图                               |
| 空仓库新应用 | 目标与领域边界：场景关系、概念关系 | 随澄清逐步增加数据或行为视图，不在信息不足时臆造技术拓扑                   |

## 5. 完整用户旅程

### 5.1 进入与首次建议

用户选择图驱动研发数字人，输入需求并选择已登记仓库。已有工具配置由岗位提供；缺少可运行模型、仓库或必要工具时显示具体配置入口。用户不必先理解工作流连线。

系统读取需求与相关仓库事实，展示当前目标、最重要的疑点和初始图组合。每个视图以业务问题命名，表达类型作为次级信息。当前没有足够依据的部分标为未知。

### 5.2 图上澄清与设计

左侧是目标与待处理问题，中间是当前视图，右侧是选中元素的说明、依据、人的判断、相关代码与证据。窄屏依次展开，保留原有键盘、目录和搜索能力。

选择对象、关系或路径后可“解释依据”“检查例外”“比较方案”“继续追问”。问题与答案仍落入原 clarify，设计模型保存来源引用，不建第二份可编辑答案。AI 对回答的整理是建议，采纳也不等于把用户未标记的成熟程度改为“已决定”。

布局调整不改变设计版本。规则、状态迁移、接口等语义修改形成明确差异。自动规划不能删除用户决定；替换视图时保留能回到原内容的历史记录。用户固定的视图允许标为过期，但不能悄悄移除。

### 5.3 形成实现依据

用户查看本次范围、实际采用的设计、未决假设、验收方式和代码基线，通过现有 review 确认一个具体版本。必要条件尚未满足时说明缺口；非关键未知可以明确保留，不强制每个字段、每张图都签署。

后端从当前版本确定性生成实现依据，展示审批对象与实际交付对象的一致性。模型不能在确认后再改写需求并称为同一版本。

### 5.4 生成、验证与交付

数字人按实现依据生成完整代码和对应测试，再集中执行本次计划的验证。结果按需求/规则/场景关联，可定位代码与原始执行证据。界面分别呈现代码已生成、程序验证结果、人工验收结果和配置的发布结果。

代码偏离设计时修复代码；设计本身有疑点时回到具体决定；没有证据时显示待验证。不得为了使结果通过而自动放宽需求或验收标准。

### 5.5 后续变化

需求变化产生新的设计版本，显示受影响的视图、实现范围和验证义务。运行中的任务继续使用其原绑定版本，不能悄悄换输入。用户可保留旧候选、取消旧执行或在其结束后生成新候选，均使用现有任务控制。

## 8. 成功指标与判断限制

观察关键疑点遗漏、用户能否解释设计依据、错误关联/过期证据数量、完成任务的时间与调用成本，以及用户主动新增、替换或删除视图的原因。视图数量、树深、点击确认数不是设计质量指标。

推荐质量评估使用不同需求与同一需求变化的成对案例，比较固定图组合与自适应组合的疑点发现、理解负担和交付正确性。模型建议由人评判，结构与执行结果由程序检查。一次模型走查只证明案例功能，不证明长期普遍收益。

## 9. 状态与实现门槛

用户已明确授权完整实现与远端交付。可交互原型和独立功能设计审查已完成本轮准备，实际证据见 design-gate.md；原型使用演示数据，未伪记为用户亲自操作或生产验收。实现、CI、部署和真实模型验收分别记账。

获批后先完成全部生产实现、接线与测试用例，再集中验证。任务依赖是开发组织方式，不授权分段实现、分段验收代替完整闭环。

## 10. 调研来源

资料核对日期：2026-10-21。原始用户文件为 `agent-workflow-mindmap-clarify-design.md`（2026-10-12 第 2 版），不把个人 Downloads 路径作为实现依赖。本 RFC 已记录其与本次有关的目标和取舍。

- [RFC-372](../RFC-372-mindmap-clarify/proposal.md)：现有脑图投影及已移除的扩大范围。
- [RFC-378](../RFC-378-mindmap-decision-review/proposal.md)：主动追问、人的决定与提交复核。
- [RFC-294](../RFC-294-backend-layered-target-architecture/proposal.md)：领域归属、模块边界及执行能力复用。
- [C4 Diagrams](https://c4model.com/diagrams)：只选择有价值的层级，不能据此推导固定交付组合。
- [Structurizr DSL cookbook](https://docs.structurizr.com/dsl/cookbook/)：同一模型、多视图与自定义视图的参考。
- [Graphologue 原论文](https://arxiv.org/abs/2305.11473)：图上的局部提问与非线性信息探索；不是代码正确性证明。
- [Draco 研究](https://idl.uw.edu/papers/draco)：约束和偏好驱动推荐。研究对象是数据可视化，本 RFC 迁移的是方法，需另行验证软件设计场景效果。
- [Kiro Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/)：需求、设计、任务与实现产物。
- [Spec Kit Agentic SDD](https://github.github.com/spec-kit/reference/agentic-sdd.html)：跨规范、计划和任务的一致性检查。
- [Stately Graph & Paths](https://stately.ai/docs/graph)：行为模型的路径生成与事件/断言绑定；具体库版本在实现时锁定。
