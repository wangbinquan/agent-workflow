## 第二次真实任务的完整路径

1. 在任务创建页面创建上述任务，采用预置“性能、可靠性”的冻结工作流。
2. 回答服务峰值 50 QPS、查询 P95 ≤ 200ms、提交 P95 ≤ 500ms；可靠性选择 99.9%、RTO ≤ 5 分钟、RPO ≈ 0，并逐题确认。
3. 点击“性能”分类，要求 AI 也考虑数据库慢查询、索引、SQL 预算、连接池与容量。实际新增两题直接位于“性能”下，与服务性能题横向并列，均无 `parentQuestionId`。
4. 回答慢查询题为标准档，再深入“索引变更怎样验收和防回归”。实际新增一题只以慢查询题为父节点，显示在下一层。生成期间切到连接池题作答，原生成没有抢走选中题，取消操作仍可从弹窗访问。
5. 从根节点补问遗漏的“用户体验”，实际新增该分类及高峰限流/超时恢复题，没有挂到任何已有问题下面。
6. 在居中弹窗选择“说明繁忙原因、保留表单、提供重试时间与一键重试”。关闭再打开后选择保持；在 320px 宽度确认，全部六题变绿。
7. 返回脑图，原“提交并停止反问”及原确认框提交成功；TaskEngine 续跑真实模型并完成输出节点。实际文档包含全部六项决策，在任务产物页和 Markdown 预览中可见。

没有把模型回复等同于平台验收成功：任务完成、轮次提交、确认依据和最终输出均由原 API/数据库及浏览器分别核对。文档中的具体业务架构建议是模型输出，本验收不证明该会议室系统已实现或达到其性能指标。

## 失败与修复记录

- 第一任务曾被开发重载中断，恢复后实际完成；一次追问缺少分类字段，严格校验拒绝后重试成功。保留原失败记录。
- 第二任务首次分类补问返回了缺少嵌套 `mindmap` 的模型输出，接口返回 422 `missing mindmap category: perf-slow-query-index-budget`，未追加问题且原答案保留。补充明确输出结构后成功。第一次根补问在 180 秒 native 请求期限后报 `clarify-followup-timeout`，未追加；随后重试成功。录制来源注明这两次恢复，不把首次请求写成成功。
- 真实视觉检查发现公共 Dialog 样式优先级使弹窗位置偏上，已以组合 class 明确居中及最大尺寸；四个尺寸的 E2E 对实际中心坐标做 1px 容差断言。
- 生成中切换到另一分类会隐藏取消入口，已改为弹窗固定工具区始终展示当前在途请求的取消操作；组件回归覆盖关闭、重开、切换节点后取消。
- 适应全图到约 73% 时过早进入简略标签，碰撞剔除使相邻题只剩点。卡片保留阈值调整到 60%，低倍率标签按实际节点间距限宽；回归验证 73% 与 50% 的兄弟题均可见。5000 节点仍采用视口裁剪/概要层级，不挂载完整问卷。
- 集中验证初次有一项测试误用未导入的 `test`，已改为该文件原有 `it`，相关九项最终通过。

## System Mock 固化与集中验证

两份录制分别是 [原实际任务](../../packages/system-mocks/src/runtime/fixtures/rfc372-real-mindmap.json) 和 [分类方向实际任务](../../packages/system-mocks/src/runtime/fixtures/rfc372-real-directions.json)。问题、选项、实际答案、成功指引与最终文档来自完成任务；只规范化问题/Agent ID 和请求/确认 token。原生运行来源、实际失败及恢复事实保留。

## 发布状态

本次 UX、类别目标及真实录制候选的源代码和功能验证已完成。当前共享 main 的 13 份 architecture/status 清单含其他会话未发布源码的投影；直接覆盖会丢失并发输出，完整提交清单但不提交其源码则会使 canonical 原样比对失败。本次已使用原扫描规则在私有证据目录准备自身候选清单，未写回共享文件、未使用替代 index/工作树，也没有发送跨 session 消息。

功能源码和设计不与这些在制清单争用，可按精确路径独立提交；清单同步作为明确的未闭合项保留。发布时核对完整 SHA、远端同步和该 SHA 的终态 CI，本地证据目录保存结果。旧 `304c4108c` 的通过项与全仓失败仅是历史证据，不能签本次 UX 或全仓 CI 通过；清单同步与新 CI 结论闭合前，RFC 保持 In Progress。
