## 1. 背景

RFC-382 与 RFC-386 之后，仍有四条路径在 SQLite 上每次调用都用旧的 `createTaskDriveCoordinator` 现建协调器，或在两个 provider 上语义
不同（2026-10-21 只读研究，`services/task.ts` 记为 T）：

1. **人工门唤醒**（T:3131-3194）：SQLite 的门控续跑 worker 用旧协调器，等驱动空闲后提交，进程级交接表跨会话持有每次调用的依赖；
   没有执行结束的记忆提炼，引擎异常被吞（任务停在运行中直到空闲超时或重启修复）。PostgreSQL 由会话协调器驱动：本进程正在驱动时
   跳过，下一个 worker 周期（约 1 秒）或决定事件认领；差别只在延迟。
2. **工作组房间续跑**：SQLite 在 HTTP 请求内用旧协调器驱动（同上缺陷，提交后的驱动错误还会抛给 HTTP 调用方）；PostgreSQL 只做预检、
   不驱动（`driveAfterCommit` 为空操作），房间准入不发事件，只能等 1 秒轮询。PostgreSQL 空操作的「多进程」理由已不成立（worker 在同一
   守护进程）。
3. **仓库准备重试**：SQLite 原子地把任务置回待执行并写续跑意图，克隆在驱动中进行，失败异步记到任务上（与 RFC-287 G7 的启动延后
   准备一致），但用旧协调器（引擎异常被吞）；PostgreSQL 在 HTTP 请求内同步克隆，错误直接抛给调用方，并发靠进程内集合守卫，启动时的
   自动续跑逐个等待克隆。
4. **融合**：SQLite 经旧的 `startTask` 启动（旧协调器：引擎失败后任务停在运行中；未挂上驱动时静默返回一个永不驱动的任务）；
   PostgreSQL 手工插行、自建生命周期端口与协调器，失败时**不按认领世代**终结该任务的全部意图，并且冻结的是未套内建布局的原始定义
   （SQLite 与启动内核都会套）；取消也是一份手写实现，缺少共享取消投影中的评审变更队列与清理认领两步。

另有驱动释放时的工作区收尾：SQLite 只清理 Webhook 终止任务并吞掉错误，PostgreSQL 用 `finalizeClaimedWorkspace`（失败时抛错，会让
等待结算的提交失败）。两者的适用范围实际相同（释放时唯一可能存在的认领是 Webhook 终止清理），差别在错误处理。

## 2. 目标

- **G1 门控唤醒**：两个 provider 都由会话协调器驱动，采用 PostgreSQL 的模型（本进程正在驱动时跳过，由 worker 或事件认领）。
- **G2 房间续跑**：一个中立实现：预检 + 提交后尽力驱动（记录日志、提交之后绝不抛错），worker 仍是持久的兜底所有者。
- **G3 仓库准备重试**：一个中立命令：保留 PostgreSQL 的准入检查，以 SQLite 的原子准入（置回待执行 + 续跑意图）取代进程内并发守卫，
  由会话协调器在后台驱动。
- **G4 融合**：一个中立适配器：按启动内核的方式冻结定义（套内建布局），经会话协调器驱动，失败经会话上报（按认领世代），未挂上驱动
  时报冲突错误，取消调用会话的取消命令。
- **G5 驱动释放收尾**：两边都用 `finalizeClaimedWorkspace`，在释放边界尽力而为（记录日志、保留认领给恢复）。
- **G6 `createTaskDriveCoordinator` 不再有生产调用方**（RFC-294 出口判据）：删除它；旧的测试入口（`startTask`、`wakeHumanGateContinuation`、
  `resumeDynamicWorkflowExecution`、`retryRepositoryPreparation`）改为基于 RFC-386 工厂的仅测试包装，留待 W4 删除。

## 3. 非目标

- 两个 provider 运行时函数合一、执行绑定工厂、删除 SQLite 路由启动包装与 provider 命名别名：RFC-388（纯重构）。
- SQLite HTTP 装配并入中立挂载表、删除测试回退：RFC-389。
- 唤醒提示与租约过期的其他机制：不改。
- 不改 API 路径、事件、schema；不做任何安全相关改动。

## 4. 用户可见变化

两个 provider：

1. **房间确认后立即续跑**：PostgreSQL 不再等最多 1 秒的轮询；SQLite 提交之后的驱动错误不再抛给确认请求。
2. **驱动释放时的工作区清理失败不再让请求失败**：记录日志、保留认领，由维护的启动 / 定时恢复处理。

单机 SQLite：

3. **门控续跑、房间续跑、仓库准备重试与融合任务**：引擎异常即把任务置为失败（此前停在运行中）；按现行策略做执行结束的记忆提炼
   （融合任务除外，与现状相同）；设置实时生效。
4. **融合启动未挂上驱动时报错**，不再静默返回一个永不运行的任务。

PostgreSQL（单机与托管）：

5. **重试仓库准备立即返回**：克隆在后台进行，失败时任务显示失败与 git 输出（此前请求阻塞到克隆结束，失败作为 HTTP 错误返回）；
   并发重试由原子准入拒绝。启动时的自动续跑不再逐个等待克隆。
6. **融合失败只终结该次认领的意图**；融合任务冻结的工作流定义套用内建布局（与其他启动一致）。

## 5. 验收标准

- **AC-1 出口判据**：后端没有 `createTaskDriveCoordinator`；生产代码中 `new DefaultTaskDriveCoordinator(` 只在 RFC-386 的工厂内（结构锁）。
- **AC-2 行为**：§4 每一条都有双引擎回归与「旧接线」对照用例（design §5）。
- **AC-3 旧锁与账本**：受影响的旧锁改指新位置，不放宽断言意图；`architecture/counts.json` 不升。
- **AC-4 CI 全绿**：推送后 exact SHA 的 GitHub Actions 全绿。

## 6. 已作出的取舍（用户授权本会话按推荐决定，可推翻）

1. **门控唤醒采用 PostgreSQL 模型**：持久意图保证不丢，差别只在 ≤1 秒的延迟；去掉进程级交接表与「交接与 worker 同时认领」的告警噪声。
2. **房间续跑提交后尽力驱动**：即时、两边一致、提交后不出错；worker 是持久兜底。
3. **仓库准备重试统一为异步**：与 RFC-287 G7 的启动延后准备一致，会话协调器的延后准备步骤两边都已具备。
4. **融合经会话协调器**：不再需要每次调用的运行配置覆盖（生产从同一实时来源读取；`binaryOverride` / `awaitScheduler` 只在测试使用，测试改用
   模块组的测试接缝），只保留 `completionMode`；失败字样统一为会话的 `task drive failed` / `task-drive-failed`（没有消费方读融合专用字样）；
   融合任务继续不做记忆提炼（准入本就拒绝内部任务）。
5. **驱动释放收尾尽力而为**：与 RFC-381 对 MR 终止清理的选择一致，捕获放在 `taskDriverRelease.ts`（命令本身仍抛错，已有锁）。
6. **旧测试入口保留为仅测试包装**：避免一次性改写几十个测试文件；W4 删除。
7. **偏离项**：无。
