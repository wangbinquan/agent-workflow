# RFC-370：Agent Workflow 在 CrewStation 上的托管部署

状态：In Progress · 2026-09-28。用户已批准实现、部署及提交上库到远端；按阶段 A → M0～M4 执行，独立设计门状态单独记录。

配套：[技术设计](./design.md) · [实施计划](./plan.md) · [源码证据](./evidence.md)。

## 1. 问题与目标

用户要求设计 aw 在 CS 上部署的 RFC。前序 CS RFC-033 已补代码托管 webhook 生产者及网关入口，但这只解决事件进入平台的问题，尚未把 aw 的身份、工作区、执行和事件消费接到平台。

用户已确认选择“完整接入 CS 能力”。本稿采用完整托管形态：**aw 拥有工作流、数字员工、事件响应规则、业务权限和任务结果；CS 拥有业务部署、平台身份、算力、任务工作卷、原生执行、执行租约及事件传输。** 保留 aw standalone 作为同一产品的另一种部署配置，不复制一套工作流引擎。

用户进一步确认实施顺序：**阶段 A 先重构缺少 adapter 切面的模块，补齐平台中立端口、本地 adapter 和调用者接线；阶段 B 再按“必要能力先行、先部署可用、逐项收编”的顺序编写各模块独立 CS adapter；不等待全部 adapter 完成才首次部署。** 阶段 A 必须可以独立交付并保持现有 standalone 行为，验收通过后才开始阶段 B 的生产实现。后续用户已明确批准实现、部署及上库，批准记录适用于本 RFC。

当前 aw 已支持 PostgreSQL，已有 Task／Source Control 工作区合同和统一 webhook 持久受理，但进程收据仍是 PID，本地文件路径仍广泛参与运行。CS v3 已提供任务、Agent／command 子任务、材料、事件游标、文件读取、切槽租约和恢复请求。把当前 aw 镜像放进 CS 服务槽不能自动满足这些合同，尤其不能假定服务容器磁盘持久、preview 不执行任务或重启后没有孤儿执行。

## 2. 交付目标与用户流程

1. 管理员在 CS 建立一个 aw DigitalWorker 项目，选服务／任务规格和获准的运行镜像、Agent 档位、MCP 连接、Secret 与事件订阅；发布工具解析实际 UUID，不能使用别的项目的样例 UUID。
2. 用户从 CS 正式应用地址进入 aw，无需再次登录 aw。aw 仍按自己的用户和资源权限判断能否查看、启动或恢复任务；平台管理员不因身份头自动成为 aw 管理员。
3. 在 aw 中创建工作流、Agent、工作组或数字员工，运行时看到对应 CS 执行资源及失败原因；Agent 和脚本在 CS 任务资源中运行，aw 服务槽只承担业务控制及展示。
4. GitLab／GitHub → CS producer → cs-events → aw durable inbox → 原 integration／事件中心 → 原响应规则与 Task／Reaction。平台已投递、aw 已受理、业务执行完成分别展示。
5. aw 发布、切槽或重启后，新执行拥有者接管已有 CS 执行收据和事件游标；没有确认进程退出时不重新派发。CS 恢复请求也进入 aw 的业务授权和恢复判定。

## 3. 范围与 8 个适配面

“8 个”按稳定职责边界计数，不等于 8 个文件、方法或都要新造端口。既有合同可复用时优先接线。

| 编号 | 适配面                  | aw 保留的责任                                      | CS 接入内容                                             |
| ---- | ----------------------- | -------------------------------------------------- | ------------------------------------------------------- |
| H1   | 部署配置与数据库启动    | 配置校验、领域迁移、provider 一致性                | 平台环境／Secret、现有 PG provider、探针与迁移 Job      |
| H2   | HTTP／WebSocket 身份    | Actor、资源 ACL、审计、业务管理员授权              | 目标服务受众的身份 JWT、来源 JWT、登录入口              |
| H3   | 工作区与 Git 效果       | 来源封存、分支／worktree／merge 规则、写入串行化   | persistent 工作卷、command 效果、版本化文件读取         |
| H4   | Agent／command 执行传输 | NodeRun／系统执行判定、信封、预算与业务终态        | v3 子任务、取消／消息、事件／结果／原生 session         |
| H5   | Runtime 配置与执行材料  | 资源选择、快照、能力要求、声明与实际核验           | 获准的 profile／image／MCP／Secret、不可变材料          |
| H6   | 非工作区文件与产物存储  | 技能、插件内容、快照、归档、附件的所有权／保留策略 | CS 对象空间保存不可变内容；AW PG 保存引用和操作日志     |
| H7   | 执行权、发布交接与恢复  | 调度／后台任务所有者、业务恢复和提交 fence         | v3 claim／renew／activate、migration／handoff、恢复请求 |
| H8   | CS 事件受理             | provider 归一化、MR 控制、规则匹配、幂等 launch    | EventDelivery、来源校验、持久 ACK、重投及死信关联       |

Dockerfile、Manifest、发布脚本和前端模式提示是上述适配的交付物，不额外算一个领域扩展点。PostgreSQL 不是新增数据库 provider；CrewStation 不是第三种 Agent 协议。

### 3.1 两阶段交付

| 阶段               | 交付内容                                                                                                                                        | 完成标准                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| A：适配切面重构    | 盘点 H1～H8 的既有合同；缺失部分补 application-owned ports、local／现有 provider adapter、精确 composition 入口；业务与系统调用者统一经端口执行 | 无 CS 运行依赖，原身份、文件、进程、事件与恢复行为保持；接口与架构守卫、双 OS／双数据库 CI 和功能实现门通过，形成独立可发布版本 |
| B：CS 独立 adapter | 在各 owner 模块外层实现 CS 协议翻译和入站接入；补平台中立公共机制、托管装配、发布材料与迁移                                                     | 通过 B1～B4 对应前置验证和全部托管验收项，完成实际 CS 部署与能力等价验证                                                        |

阶段 A 不要求重构 RFC-294 全仓历史债务，只覆盖完整托管必经的全部入口与后台效果；已有合格端口直接复用。阶段 B 不在业务层堆叠 CS 判断，也不将各域适配合并为一个全局业务服务。“独立 adapter”指 owner 模块内独立目录、明确导出与依赖约束，本 RFC 不要求每个 adapter 独立发布 npm 包。

### 3.2 阶段 B：先部署，再逐项收编

| 里程碑                | 新增可用能力                                                                  | 必须完成的适配与现场验收                                                                                 |
| --------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| M0 首次可用部署       | 从 CS 打开 aw、登录、编辑并持久保存工作流／资源                               | H1／H2／H6 必要部分：镜像、Manifest、PG／内容、身份、迁移与探针；实际发布到本机 CS，重建服务后数据仍可用 |
| M1 首个远程任务闭环   | 手动运行一条代表性工作流，查看输出、取消及重启后对账                          | H3／H4／H5 的最小完整纵向路径，以及该路径必需的 H7 执行权／失租约／恢复对账；在 M0 安装上增量部署验收    |
| M2 执行能力逐项收编   | 逐步接齐双 runtime、完整 Git／多仓、插件／MCP／系统 Agent、复杂工作流和工作组 | 按能力矩阵一项一项实现和发布；每项验证普通运行、取消／失败及恢复，不把全能力证明压到最后                 |
| M3 事件与平台运维闭环 | CS webhook 驱动 aw 规则／Reaction，平台恢复与升级交接完整可用                 | H8、剩余 H7 和对应 UI；可在各自前置执行能力就绪后逐项交付，不等待无关能力                                |
| M4 完整托管交付       | 全部目标能力等价，支持旧实例迁入与正式切换                                    | C1～C8 和 B1～B4 全部闭合、AC 全量通过，迁移／回退实证与发布证据齐全                                     |

M0 是可实际使用的控制面部署，不只是容器存活；暂未接入的执行、事件派发等入口明确显示未就绪，不能接受后无限排队或假装成功，也不能在服务槽偷偷回退本地 spawn。用户已确认按此顺序逐步开放能力；阶段性未开放是有清单的中间状态，不能据此删减最终完整接入目标。B1～B4 按里程碑中实际用到的能力检查，不将完整插件等价、旧 PAT 迁移或大历史容量验证全部设为 M0 的前置条件。完整能力影响及旧实例切换仍按原验收和批准记录处理。

## 4. 非目标与阶段边界

- 不把 DAG、循环、工作组、Reaction 或事件响应规则搬到 CS，不把 CS 事件目录当 aw 的业务事件类型目录。
- 不要求为本 RFC 完成 RFC-294 全部存量架构迁移；本次新增实现必须按该架构落位。
- 不先以“单容器内继续 spawn + 挂宿主 home”的方式宣称完整托管完成。
- 首次部署使用新业务库；M0 不启执行派发，M1 起只有一个 active 调度者；既有实例迁入是后续交付阶段，必须先停写、导出与对账。不做运行中跨部署迁移或生产库原地切换。
- 一个 CS 项目对应一个 aw 安装边界；不在本期增加 aw 跨 CS 项目的多租户功能。
- 不把旧 CS v1/v2 执行当静默降级；旧 aw standalone 按原合同继续使用。

## 5. 能力影响清单（待确认，不能默认为已批准）

| ID  | 既有能力／影响                                    | 托管形态方案与不能静默退化的条件                                                                            | standalone       |
| --- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------- |
| C1  | 本地密码、OIDC、PAT／daemon token 登录            | 浏览器改为 CS 身份；不在同一入口自动回退本地登录。已有 PAT 的自动化客户端需明确服务入口和授权方案后才能迁入 | 保持             |
| C2  | 任意宿主目录、绝对路径、用户 home 中配置          | 转为工作区／内容引用；宿主路径必须经迁移导入并校验，不能映射成空目录                                        | 保持             |
| C3  | 自定义 binary、模型参数、extraArgs、provider 网关 | 映射到经过授权及验证的 CS profile／镜像；字段不等价则列为迁移阻塞，不能丢参数或绕平台自建 Agent 进程        | 保持             |
| C4  | 依赖 Agent、插件、MCP、启动 inventory、子会话证据 | 逐项能力对拍；CS 当前 DTO 未直接表达的部分先完成协议验证／必要平台增补，不能把缺证据写成成功                | 保持             |
| C5  | 下载／备份／归档／手工上传和编辑资源              | 内容持久化迁移、文件权限与校验和对账；不把镜像构建目录或临时盘当唯一副本                                    | 保持             |
| C6  | 直连 webhook 和 CS 转发同时开启                   | 同一逻辑 source 默认仅启一个 transport；切换有水位与对账，不能声称跨两种无共同 ID 的入口天然 exactly-once   | 保持直连         |
| C7  | 多个 daemon／preview 同时运行                     | 同一生产安装只允许 active 租约拥有者产生后台效果；preview 可读及验证，完整试跑使用独立 CS 开发环境／数据    | 保持原单实例语义 |
| C8  | 无限制运行时间、无限体积输出、长期原生会话取证    | 按 CS 实际能力和保留窗口预检，aw 主动归档；不支持的工作流必须阻止迁移并说明原因，不可截断后报成功           | 保持既有配置     |

H5 的能力不足不是“先禁用然后算 Done”的许可。按用户已确认的完整接入目标，交付判据为已有目标用例保持能力；C1～C8必须有等价迁移方案，不能以子集交付关闭本RFC。

## 6. 验收标准

| ID    | 可复验结果                                                                                                                                                                                                                                                        |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC00  | 阶段 A 独立验收：H1～H8 调用者清单全部落到已复用或新补齐的端口／adapter；实际 local adapter 保持原行为、无 CS 运行依赖；架构守卫、双 OS／双数据库 CI 与功能实现门通过。阶段 B 的生产 adapter 编写不得早于此门通过                                                 |
| AC00B | 阶段 B 增量交付：M0 完成实际 CS 发布、登录／编辑／持久保存／Pod 重建验收后才推进后续里程碑；M1 起每项能力都有可运行版本、状态提示与现场证据。不得将首次部署推迟到全部 adapter 完成                                                                                |
| AC01  | 新项目按发布材料完成安装，PG 迁移恰好一次；重建服务 Pod 后配置、资源内容、历史与密钥仍可用                                                                                                                                                                        |
| AC02  | CS 登录进入 aw；身份映射、令牌到期、现有业务权限、用户撤权和 WS 重新连接均符合合同；平台 admin 不自动获得 aw admin                                                                                                                                                |
| AC03  | 两种 Agent 协议、脚本、系统 Agent（意图、蒸馏、评审等）都走同一执行边界；完整 prompt／skills／MCP／subagents／profile 与能力观测对拍                                                                                                                              |
| AC04  | Git／多仓／隔离分支／merge、上传、二进制文件、依赖产物在远程卷可用；并行写入和取消期间不能污染其他任务                                                                                                                                                            |
| AC05  | DAG、循环、fan-out、call／fusion、工作组、人工澄清／评审、数字员工 Reaction 的业务结果与 standalone oracle 一致                                                                                                                                                   |
| AC06  | 丢创建回执、断流、重启、重复结果、usage 重投、unknown 进程和超出保留窗口均不重复执行／计费，不伪造终态                                                                                                                                                            |
| AC07  | 蓝绿并存、旧 epoch 延迟请求、租约过期、交接／迁移失败、回退及所有后台扫描器证明只有一个效果拥有者                                                                                                                                                                 |
| AC08  | 两 provider webhook 支持矩阵、MR 乱序控制、重复／死信重放、事件受理提交后丢 ACK、ACK 后进程崩溃通过真实 PG 与实际 CS 链路；同 producer 多 endpoint、逐目标局部失败、跨订阅去重及重投期间路由修改保持原目标集合（含空集合）；MR受理与两类观测间崩溃按稳定 key 补齐 |
| AC09  | CS 侧恢复五种动作和 aw 侧恢复指向同一业务意图；权限、generation／attempt／材料／原卷不符拒绝；丢回执不创建第二次执行                                                                                                                                              |
| AC10  | 资源超过额度可解释且可恢复；关闭任务后确认实际资源释放再退额，取消不靠服务 Pod 本地 kill                                                                                                                                                                          |
| AC11  | 明确发布／回退步骤、托管迁移报告、三层事件状态与诊断关联；真实浏览器走用户流程，不能仅证明 HTTP 200                                                                                                                                                               |
| AC12  | standalone 的双数据库／双 OS 与现有工作流行为回归；精确 SHA CI、架构守卫、双方契约测试及独立集群验收证据分列                                                                                                                                                      |

## 7. 需裁定的设计决策

D1 完整托管、D7 先切面重构后 CS 独立 adapter、D8 CS 必要能力先行并先部署后逐项收编已由用户确认；本稿提出 D2 保留 standalone、D3 八个职责适配面、D4 一个 active 调度者、D5 首次全新安装后再迁旧数据、D6 事件经 CS 持久传输并复用 aw 规则。H5/H6 的验证闸门及 C1～C8 能力影响一同参与评审。阶段 A 的 AC00 通过不代表完整托管完成，RFC 仅在阶段 B 全部验收后关闭。

用户此前对 CS RFC-033 的批准与本 RFC 分开记录；本 RFC 随后已得到“批准实现、批准部署、批准提交上库到远端”的明确批准。旧实例具体映射和正式切换仍需基于实际迁移清单，不自动选择某个现有实例。
