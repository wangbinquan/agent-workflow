## 根与 owner 覆盖

SQLite 与 PG daemon 都通过 `bindDaemonHostOwners` 选择相同十九项：intent queued、task、maintenance、MCP、reports、webhook terminal、after-commit、resource limits、idle timeout、backup、submodule refresh、import GC、human continuation、committed events、memory、development wake、digital employee、event center、fusion。每项有自己真实的 start/正常 stop/loss quiesce/drain，不新增空 owner 以凑数量。

embedded 使用自身 Task/Intent/MCP 及实际提供的 webhook/report；借用 DB 的关闭归调用者，不造 daemon PID lease、定时备份或十九项后台循环。其 `resume` 保持严格控制结果，`resumeForServing` 显式提供已就绪资源 HTTP 的启动路径。

实际 daemon 的一次启动现在先完成资源会话，再尝试同一 host 激活；执行启动阻塞时只有已就绪且状态确认为 standby/draining 的 selected 会话可以继续监听。native、资源初始化失败、closed 或无关失败仍抛原错误。GET status 不触发恢复，POST recover 调用原 SO 队列；它不代发业务 kill，不伪造原结果/readyGroups。

Memory 原恢复有独立行级入口；正常在途 selected tick 不能被 cold recovery 接管。恢复回执之后，宿主仍由显式重试激活。前端保留资源草稿、旧任务状态与失败反馈，不能将控制回执当任务 done。
