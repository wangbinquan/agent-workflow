## 1. 为什么重设计

[审视记录](../rfc370-372-review-2026-10-14.md) §4 与本次复核的结论：

| 问题                         | 现状                                                                                                                                                                                                                   | 后果                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 执行权（H7）是第二条平行路径 | 生产 daemon 不传宿主执行配置，永远是 `native`；19 个后台 owner 的四阶段生命周期（start / pause / quiesce / drain）、恢复族、写生命周期、准入租约只有测试在走。SQLite 根约 33 处、PG 根约 13 处在判断走新路径还是旧路径 | 新路径没有生产流量验证；任何改动都要同时维护两条路径；执行权概念散布在 73 个源文件 |

阶段 A 中**已经在生产路径上**、方向正确的部分保留：H1 配置 / 安装端口、H2 HTTP / WS 认证参与者、H3 Source Control 工作区端口、H5 材料端口、H6 各 owner 的内容端口、H8 webhook 受理与传输分离，以及各自的本地适配器与回归用例。

## 2. 设计原则

1. **一条业务路径**：单机与托管走同一套 TaskEngine → WrapperRuntime → NodeExecutor → ExecutionKernel 与同一组后台任务。差异只在装配根选择的适配器，domain / application / engine 不出现 `if (crewstation)`。
2. **端口按语义而不是按进程定义**：执行端口交换“调用 + 归一化事件 + 结果”，工作区端口交换逻辑引用，内容端口交换不可变内容引用；本地文件路径、PID、CS wire DTO 都只出现在各自适配器里。
3. **崩溃即退出的执行权**：不在进程内做“失权 → 暂停 → 排空 → 再授权”的状态机；失去执行权的托管实例退出，由平台重启为待命实例。
4. **平台合同不够就补平台**：CS 表达不了的能力在 CS 仓按其流程立 RFC 补合同，不在 aw 里绕平台（例如用命令子任务冒充平台 Agent、在服务槽 spawn）。
5. **装配集中**：新的托管装配放 `src/bootstrap/`；`cli/` 只保留命令入口。SQLite / PG 两个 daemon 根的合并属于 RFC-294 的 DaemonContainer 波次，不在本 RFC 内做，但本 RFC 不再向两个根增加分叉。

## 3. 目标架构

### 3.1 部署形态与唯一选择点

- 新增 `deployment.mode = standalone | crewstation`，由环境变量 `AW_DEPLOYMENT_MODE` 显式指定，默认 `standalone`；不按“发现了 CS 环境变量”自动切换。
- `crewstation` 模式只支持 PostgreSQL（`CS_DATABASE_URL`），复用 RFC-359 的 PG provider，不新增 SQL 实现。
- 选择只发生一次：`bootstrap/deployment.ts` 读取模式，构造该模式的适配器选择项（执行、工作区、内容、身份、配置、执行权、事件入站），交给既有 PG daemon 根。两个 daemon 根已有“未传选择项即用本地实现”的注入方式，托管只是传入另一组选择项。

### 3.2 H7 执行权：崩溃即退出

**端口**（system-operations `application/ports/executionAuthority.ts`）：

```ts
type ExecutionAuthorityState =
  | { kind: 'standby'; reason: string | null } // 尚未取得或正在交接
  | { kind: 'active'; fence: ExecutionFence } // 可以产生外部效果
  | { kind: 'frozen'; reason: string | null } // 平台冻结（迁移 / 交接）
interface ExecutionFence {
  readonly epoch: number
  readonly token: string
} // 托管时 token 编码 leaseId + instanceId
interface ExecutionAuthorityPort {
  readonly mode: 'standalone' | 'crewstation'
  current(): ExecutionAuthorityState
  /** 首次进入 active 时 resolve；之后离开 active 由 onLost 通知 */
  whenActive(): Promise<ExecutionFence>
  onLost(listener: (state: ExecutionAuthorityState) => void): () => void
  close(): Promise<void>
}
```

公开状态 `GET /api/execution/status` 是它的投影 `{ mode, state, reason }`（shared `ExecutionStatusSchema`）；HTTP 门控与状态路由读同一个按 app 实例登记的读取器（`platform/http/executionAvailability.ts`），MCP 绑定调用走同一条注册处理链，因此同样受门控。

**本地实现**：启动即 `active`（epoch 1），永不丢失。单机 daemon 的单实例仍由既有 flock 保证，行为与今天相同。

**CS 实现**（system-operations `infrastructure/crewstation/`），按 CS 官方 v3 样例的协议：

1. 每 5 秒一次 tick：读 `/v3/business-execution/control`；有迁移操作时，把本库控制行写为 `frozen` 并回报 `migrations/:op/ready`；否则 `claim` → `renew` → 本库写 `preparing` →（有交接操作时回报 `handoffs/:op/ready`）→ `activate` → 本库写 `active`。租约 30 秒、续租 10 秒按 CS 能力值。
2. 本库控制行 `hosted_execution_control`（单行：epoch、owner、phase、expires_at）只增不减；旧世代或旧实例的写入被拒。

**daemon 生命周期**：

- HTTP 服务启动即监听，资源读写不需要执行权。
- 后台任务集合（今天原生启动的那组：任务调度、意图队列、维护、MCP 诊断、webhook 终态、提交后事件泵、资源上限、空闲超时、定时备份、子模块刷新、导入回收、人工门继续、提交事件、记忆蒸馏、开发唤醒、数字员工、事件中心、融合对账）**在执行权首次进入 active 时启动一次**。单机版启动即 active，所以与今天完全相同。
- 托管实例在已经 active 之后离开 active（租约丢失、冻结、交接给新版本）：停止接收新请求、按既有优雅关闭流程关闭后台任务与 provider、以非零码退出；平台重启后作为待命实例重新竞争。已提交到 CS 的执行不受影响，由新的执行权持有者按持久绑定接管（§3.3）。
- 待命实例上，声明了 `executionGroup` 的 HTTP 路由返回 503 `execution-standby`（可重试）；`GET /api/execution/status` 返回 `{ mode, state, reason }`。

**写屏障**（仅托管）：凡是记录“将要产生 CS 效果”的业务事务（派发意图、取消、恢复），在同一事务内对控制行 `SELECT … FOR UPDATE` 校验 epoch / owner / active / 未过期；CS 侧再按 fence 拒绝旧世代变更。两者都满足才算有效效果。单机实现为空操作。

**前端**：执行门控只在 `mode === 'crewstation'` 时生效；单机版或状态未知时不禁用执行入口。待命 / 冻结时显示横幅与原因。

**删除**（以引用分析为准，单机原生路径实际在用的保留）：system-operations 的 `hostExecutionAuthority` 应用 / 装配 / 写生命周期 / 准入；`cli/daemonHostExecution{Bootstrap,Owners,Recovery}.ts`、`cli/embeddedHostExecutionApplication.ts`；各后台 owner 的 `startAuthority` / `quiesceAuthorityLoss` / `drainAuthorityLoss` 变体与 `canDispatch` / `whenActive` / `reportFailure` 穿线；`/api/execution/recover`；platform 层的可用性全局表；对应的测试。

P1 实际删除范围（2026-10-14 按引用分析与提交历史核对）：

- 任务执行的 host 写入目的 / 写选择 / 写上下文 / 准入 / 认领失败 / 驱动终结 / 资源恢复写入整套（`select*Writes` 转发在单机下恒等于直接字段，内联回 `persistence.nodeRuns` 等）；
- “原执行恢复”机制：意图回合执行权与冷恢复、记忆蒸馏执行回执与续跑、系统 Agent 执行回执与原进程恢复、MCP 诊断冷启动模式、融合工作区端口，以及它们的恢复端点（`/api/execution/recover`、`/api/memory-distill-jobs/:id/recover`、`/api/mcps/:id/runtime-test-sessions/:sessionId/recover`、意图回合 recover）和前端恢复按钮。托管重启后对仍在运行执行的接管改由 §3.3 的 `ExecutionPort.adopt` 承担；
- 冷维护服务 / 冷提交后事件泵 / 执行权轮询绑定，以及 `executionAuthority` 无关的根级 host 分支；
- 两张只被上述路径读写的表：`system_host_execution_write_contexts`、`memory_distill_execution_receipts`（SQLite 0257 / PostgreSQL 0033）；
- 依赖 RFC-370 逆变换链复原“原始根源码”的源码 oracle（W29、MCP 诊断族的根完整性 AST 钉死，及其逆变换 helper / fixture）。

保留：路由上的 `executionGroup` 标注（改为新门控）、Agent / 系统 / 诊断 / 脚本执行族与执行效果端口（M1 由 §3.3 重塑）、启动恢复族、H1 / H6 的配置与内容端口。

### 3.3 H4 / H5 执行：调用 + 归一化事件

**端口**（task-execution `application/ports/execution.ts`，取代 `executionEffect.ts`）：

```ts
type ExecutionInvocation =
  | {
      kind: 'agent'
      executionId: string
      workspace: WorkspaceLocation
      runtime: RuntimeSelection
      prompt: string
      material: AgentMaterial
      resumeSessionId?: string
      timeoutMs?: number
    }
  | {
      kind: 'command'
      executionId: string
      workspace: WorkspaceLocation
      argv: string[]
      env: Record<string, string>
      timeoutMs?: number
    }
type ExecutionEvent =
  | RuntimeEvent /* 既有驱动产出的归一化事件：文本、工具起止、会话、用量 */
  | { type: 'output'; stream: 'stdout' | 'stderr'; text: string }
interface ExecutionOutcome {
  outcome: 'succeeded' | 'failed' | 'timeout' | 'canceled' | 'unknown'
  exitCode: number | null
  sessionId?: string
  reason?: string
}
interface ExecutionPort {
  run(
    invocation: ExecutionInvocation,
    sink: ExecutionSink,
    signal: AbortSignal,
  ): Promise<ExecutionOutcome>
  /** 托管重启后按持久绑定接管仍在 CS 上运行的执行；本地实现对已退出进程返回 unknown */
  adopt(executionId: string, sink: ExecutionSink, signal: AbortSignal): Promise<ExecutionOutcome>
}
```

- `executionId` 是 aw 自有的稳定身份（node_run + attempt，或系统执行 ID），CS 的 requestKey 由它派生，HTTP 超时重试沿用原键，不因丢回执重复创建。
- **本地实现**：既有 `RuntimeDriver.buildBusinessSpawn` + 托管进程 + `driver.parseEvent`，把逐行 stdout 解析成事件后交给 sink。解析从调用方挪进适配器，调用方不再接触原始行。
- **CS 实现**：先按 §4 编译材料（`POST …/materials`），再提交 `kind=agent` 或 `kind=command` 子任务；用 `events/stream`（断线按 cursor 补页）消费 `text` / `tool-*` / `session` / `usage` / `output` / `result`，映射成同一种事件；`result` 带 `finalCursor`，尾流取完才结束。持久绑定表 `hosted_execution_bindings`（task-execution 拥有：executionId ↔ CS task / subtask / attempt / cursor / materialDigest）支持重启后 `adopt`。
- **调用方不变的部分**：信封解析、端口输出、预算、用量记账（RFC-371 v2）、会话捕获、节点状态转换仍在 application / engine，只是输入从“原始行”换成“事件”。
- 所有执行入口统一走这个端口：任务单 / 多 Agent、工作组、脚本、系统 Agent（意图、记忆蒸馏、评审、提交说明、追问生成等）、MCP 诊断、运行时冒烟。托管时没有任何入口在服务槽本地 spawn。

### 3.4 H3 工作区

- 一个 aw 任务对应一个 CS 业务任务（persistent 卷），首个执行前按 `aw-task:<installation>:<taskId>` 幂等创建，标签带 aw 任务 ID；任务删除时关闭并按终结策略回收。
- 仓库在卷内 `/work/repos/<slug>`；隔离节点 / fan-out 分片的 worktree 在卷内各占稳定目录；合并仍由 aw 的写锁串行裁决。
- Git 与工作区维护（clone / fetch / worktree / 快照 / diff / 合并 / 提交）在任务容器里以命令子任务执行，命令由 aw 的任务镜像内置工具 `aw-workspace` 提供；文件读取走 CS 版本化文件接口；新任务的输入文件经对象存储随任务创建传入。
- Source Control 现有端口（准备、维护、存在性、Git、候选、读取、上传、隔离、冲突）各增加一个 `infrastructure/crewstation/` 实现，共用一个工作区命令客户端；Task 继续只依赖 SC 公开合同。
- 托管仓库只能是远程 URL（克隆进卷）；单机“本地目录仓库”在托管下不存在，见 §6。

### 3.5 H6 内容

- platform 提供中立字节存储机制（本地文件 / CS 对象存储两个实现），各 owner（技能、插件、资源包、意图工件、评审工件、任务提示词 / 端口 / 归档、数字员工证据）保留自己的引用、版本与保留规则，元数据在 aw 数据库。
- CS 实现按 RFC-035：上传 → 提交 → 引用固定后才发布可消费版本；稳定 requestKey 支持丢回执后沿原操作恢复。

### 3.6 H2 身份

- 托管时 HTTP / WS 认证参与者校验 `x-cs-identity-token`：issuer `crewstation`、JWKS（`CS_JWKS_URL`，不取自请求）、aud `service:<CS_PROJECT>/<CS_SERVICE>`、subject `user:<uuid>`。
- 外部身份映射 `external_identities(installation, issuer, subject) → aw 用户`，首次访问建最低权限用户，不按 email 合并；初始业务管理员来自部署配置的 CS subject 名单。平台角色不自动成为 aw 管理员，aw 的资源 ACL 不变。
- 服务来源（事件投递、恢复回调）校验 `x-cs-source-token`，与用户令牌是两个互不替代的入口。

### 3.7 H1 配置、数据库与探针

- 托管时应用配置存数据库（system-operations 拥有），在设置页编辑；主密钥等来自 CS Secret 注入的环境变量，不在临时盘生成。
- 迁移由 CS 发布流水线的 `migrationCommand`（`agent-workflow migrate`）单入口执行，业务进程不各自迁移。
- `/live` 只证明进程可响应；`/ready` 证明配置、schema、内容存储与路由可用，**不等待执行权**（否则待命版本永远无法就绪切流）。

### 3.8 H8 事件入站

沿用 v1 design §7 的合同：`POST /integrations/crewstation/events` 只在托管模式挂载，事务 inbox 先持久化再 204，按 `(installation, producer, eventId)` 冻结目标集合，逐目标进入既有 verified-webhook 受理与两类观测；直连与 CS 转发同一逻辑来源只启一个通道。

### 3.9 恢复

持有执行权的实例按 CS v3 样例消费恢复请求（claim → 本库受理 → 执行 → 记录）；五种动作映射到 aw 既有的任务恢复 / 节点重试命令，并复核业务 ACL、generation / attempt / 材料摘要。aw 页面发起的恢复走同一业务入口。

## 4. 托管能力等价与 CS 侧补齐

| aw 能力                                  | 托管机制                                                               | 是否需要改 CS            |
| ---------------------------------------- | ---------------------------------------------------------------------- | ------------------------ |
| Agent 提示词正文                         | 原生配置叠加里的 Agent 定义（过渡期可用 `systemPrompt`）               | 是                       |
| Agent 权限、工具、温度等 frontmatter     | 原生配置叠加里的 Agent 定义；平台保留键（模型、凭据、二进制）不可覆盖  | 是                       |
| Skills                                   | 材料 `skills`；超过材料上限时改为对象支撑                              | 大体积时是               |
| 远程 MCP（用户在 aw 里随时创建）         | 内联 MCP 定义（URL + 密钥头），不要求事先在 Manifest 登记              | 是                       |
| 本地 stdio MCP                           | 内联本地 MCP 定义；命令须在 Agent 镜像内存在                           | 是                       |
| 插件（含 aw 的启动清单插件）             | 原生配置叠加里的插件文件                                               | 是                       |
| 依赖 Agent（子代理）                     | 原生配置叠加里的子代理定义（运行时内部委派，按 CS 能力标为不透明委派） | 是                       |
| 节点模型 / 变体                          | aw 运行时 + 模型 → CS Agent 档位映射；变体等模型选项视 CS RFC 结论     | 映射不需要；模型选项需要 |
| 自定义二进制、模型网关                   | CS 管理员的算力档位                                                    | 否（平台配置）           |
| 会话续跑                                 | `resumeSessionId`（按档位能力）                                        | 否                       |
| 用量                                     | CS `usage` 事件                                                        | 否                       |
| 脚本 / Git                               | 任务容器内命令子任务                                                   | 否                       |
| API 自动化（PAT、`/api/mcp` 外部客户端） | 需要 CS 用户域的令牌访问方式                                           | 待 M3 前核实             |

需要的 CS 合同变更在 CS 仓按其流程（`proposal/rfc/`、作者批准、本地 `bun run check`、六项 CI、本机部署）单独立 RFC，暂名“业务 Agent 原生配置叠加材料”；批准前 aw 侧先按 CS 现有合同推进 M0、M1，缺口能力在托管模式启动前明确拦截并说明原因，不静默降级。

## 5. 交付顺序

每一步都是：完整实现与用例 → 集中验证 → 按路径提交推送 → 确切 SHA CI 全绿 →（M0 起）部署到本机 CS 并在浏览器验收。

执行端口重塑（§3.3）从 P1 移到 M1 开头：它要按本地与 CS 两个实现一起定形，放在 CS 适配器之前、同一步里做，避免先按单机形状定一次、接 CS 时再改一次。P1 只做删除与执行权端口，保持每步可单独评审。

### 5.1 M0 实施细化（2026-10-14，按源码核对）

托管服务槽只跑 HTTP 控制面：无持久卷、无 git、无运行时二进制（CS RFC-035 §2：配置 / 权限 / 版本指针 / 小型技能文本进 aw 的 PG，插件包等字节进对象存储，容器本地盘只是可重建缓存，主密钥来自平台 Secret）。M0 只做控制面，执行在 M1。

- **选择点**：`cli/deployment.ts` 读取 `AW_DEPLOYMENT_MODE`；`crewstation` 时校验必需环境变量（`CS_DATABASE_URL`、`CS_JWKS_URL`、`CS_PROJECT`、`CS_SERVICE`、`PORT`、`AW_SECRET_KEY`；`AW_ADMIN_SUBJECTS` 与 `CS_OBJECTS_URL` 可选，M0 不用对象存储），缺失即拒绝启动并逐项说明；迁移 Job 只要求项目 / 服务与数据库三项。组装 `StartOptions` 的托管选择项，调用既有 `startCommand`。启动序列不分叉，只跳过服务槽不具备的宿主依赖（`executionHost: 'remote'` 时不做 git 与运行时二进制探测），监听 `0.0.0.0:$PORT`。
- **数据库**：迁移只由 CS 发布流水线的 `migrationCommand`（`agent-workflow migrate`）执行，托管下按 `CS_DATABASE_URL` 直接走 `migratePostgresqlSchema`（全新建库或按 PG 历史只增升级）。PG 迁移器只投影 DDL，单机经 RFC-349 逻辑复制从 SQLite 带过去的初始行（登录策略、框架内置资源、事件族割接等），全新托管库由迁移 Job 从刚迁移完的内存 SQLite 一次复制（单事务、按外键顺序、以登录策略单例行判定已安装；托管无首个管理员引导，复制后的策略记为已完成）。服务用托管的 `DatabaseInstallationPort`：世代身份由 `CS_PROJECT/CS_SERVICE` 确定性派生（来源 `hosted-installation`，不存在本地 SQLite→PG 迁移清单）；与所有 PG 世代一样，它指向产生其数据的操作——迁移 Job 的安装复制：Job 在 PG 元数据里一次性登记这条复制操作与活动世代（幂等；库内已有别的活动世代即拒绝），PG 的世代写入围栏据此放行初始行复制与之后的业务写入。`prepareProvider` 只校验 schema 已是当前版本且本服务世代为活动世代、不迁移，不一致即拒绝启动、等待迁移 Job。
- **配置与主密钥**：应用配置存 system-operations 拥有的 `application_configuration` 单行表（SQLite / PG 同步新增，单机不使用），经既有 `composeApplicationConfigurationBinding({ kind: 'selected' })` 接入设置页；数据库配置只读、来自环境变量。主密钥取 `AW_SECRET_KEY`（base64 的 32 字节），不在临时盘生成。
- **身份**：identity-access 新增 CS 认证适配器（HTTP 与 WebSocket 两个既有参与者端口）：校验 `x-cs-identity-token`（JWKS 只取自 `CS_JWKS_URL` 并按 kid 缓存，iss `crewstation`，aud `service:<CS_PROJECT>/<CS_SERVICE>`，sub `user:<uuid>`，exp）；`external_identities(issuer, subject) → 用户` 映射（新表），首次访问建最低权限用户、不按 email 合并，`AW_ADMIN_SUBJECTS` 中的 subject 首次访问建为管理员。本地密码、OIDC、PAT 与首个管理员引导在托管入口不出现。
- **内容**：技能文件树按 CS RFC-035 的建议存进 aw 数据库（`skill_content_entries`：在用树、不可变版本、发布暂存、删除回收站，每步一个事务；树哈希与文件版规范哈希逐字一致，引用沿用相对布局，两种部署的技能元数据完全相同）。插件安装依赖 npm / git 且注入运行时配置，资源包经本地产物漏斗携带插件与技能树，二者随 CS 原生配置叠加（§4，M2）提供，M0 在托管下以 503 `hosted-capability-unavailable` 明确拒绝并说明原因。对象存储（上传 → 提交 → 引用固定）随需要大体积字节的 owner 在 M1～M3 接入。
- **探针**：公开 `/live`（进程可响应）与 `/ready`（配置、schema、内容存储与路由可用，**不等待执行权**）。
- **执行权**：托管适配器在 M0 恒为 `standby`（原因：远程执行在 M1 提供），执行入口显示未就绪；后台任务集合改为在执行权首次 active 时启动（单机启动即 active，行为不变），离开 active 时按优雅关闭流程退出（§3.2）。
- **前端**：托管时 daemon 在下发的 `index.html` 中注入部署形态标记，前端据此视为网关会话（不保存、不发送本地令牌，WebSocket 不带令牌参数，平台会话失效时经网关重新加载、30 秒内至多一次），不显示本地登录 / 首个管理员引导 / 退出登录 / 口令与个人令牌，设置页隐藏数据库、认证、网络三页；待命横幅说明“远程执行尚未接入”。账户以平台身份呈现：账户菜单显示平台下发的显示名（`cs-<uuid>` 用户名只作技术标识），账户概览写明登录由 CrewStation 平台管理，用户页不提供本地建号与重置密码（成员首次从平台访问时加入，这里只调访问预设与停用）；托管拒绝码 `hosted-capability-unavailable` / `execution-standby` / `setting-managed-by-deployment` 有精确的中英文案与下一步提示。
- **镜像与发布**：`deploy/crewstation/` 提供 Dockerfile（构建单二进制，运行镜像只含二进制与 CA 证书，非 root，固化 `AW_DEPLOYMENT_MODE=crewstation`）与 Manifest 模板（DigitalWorker：服务命令、端口、`/live` `/ready` 探针、套餐、`AW_SECRET_KEY` 密钥与 `AW_ADMIN_SUBJECTS` 配置、`release.migrationCommand`；`tasks` / `data.objects` 随 M1 / M2 加入）；`scripts/crewstation-publish.ts` 按本地部署档案渲染 Manifest，把已提交源码快照推到 CS 项目仓库，再经平台发布接口（`POST /v1/services/:serviceId/releases`，带 `expectedCommitSha`）发布这一提交（`crewstation publish` 是开发会话入口，推送的是会话工作区，不适用于推送好的快照）；切流由项目负责人 `crewstation traffic switch`。
- **本机验收**：本机 CS 建项目、PostgreSQL 数据资源、对象档位、配置与密钥，发布后在浏览器从 CS 入口登录，编辑并保存工作流、Agent、技能、MCP（插件安装与资源包应用显示明确的不可用原因），重建服务 Pod 后数据仍在，执行入口显示未就绪。

### 5.2 M1 实施细化（2026-10-15，按源码核对）

**CS 现状**（CrewStation RFC-027 / 028 / 034 / 035 均已 Done，M1 不需要改 CS 合同）：

- 服务域 v3：`/v3/business-tasks`（父任务，`persistent` 卷 `/work`）、`/:id/materials`、`/:id/subtasks`（`agent` / `command`）、`/:id/events` 与 `/:id/events/stream`（稳定游标、SSE、断线补页）、`/:id/subtasks/:sid/cancel|retry|messages`、`/:id/file|files`（`/work` 内相对路径、单次 ≤ 1 MiB、带版本摘要）、pause / resume / close / finalize。服务槽以可信 Pod 身份调用（平台注入 `CS_PLATFORM_API_URL`，无令牌）；所有执行变更带 `{epoch, leaseId, instanceId}`，陈旧世代 409。
- 执行权 `/v3/business-execution/control` 与 `claim / renew / activate / release / handoffs/:op/ready / migrations/:op/ready`，Manifest `tasks.executionControl: fenced` 且必须声明 `acceptedTaskContractVersions`；协议与 CS 自带 `templates/business-execution-v3/src/control.ts` 一致。
- 任务容器镜像经 RFC-028 平台运行镜像目录构建、按业务授权，`tasks.runtimeImageVersionId` 选择；命令子任务在父任务容器执行，Agent 子任务在各自环境中挂同一 `/work`。
- Agent 子任务的事件是 Runner 归一后的 `text / tool-start / tool-end / session / usage（RFC-034 v2 按模型快照）/ execution-state / result`，**不含运行时原生 stdout 行**；命令子任务的 `output` 是原始输出。

**范围**：执行端口重塑并接入全部执行入口（单机实现）；CS 执行权与写屏障；执行端口 CS 实现（Agent + 命令）与持久绑定、取消、重启接管；工作区 CS 实现（单仓、git 包装器、脚本节点）。系统 Agent（意图、记忆蒸馏、追问、提交说明、评审）、MCP 诊断、运行时冒烟在 M1 只有单机实现，托管下继续按执行组返回 503，随 M2 接入。

**执行端口**（task-execution `application/ports/execution.ts`，取代 `executionEffect.ts`、`agentExecutionBinding.ts` 与参与者 / 回执层）：

```ts
interface ExecutionPort {
  run(
    invocation: ExecutionInvocation,
    sink: ExecutionSink,
    signal: AbortSignal,
  ): Promise<ExecutionOutcome>
  /** 重启后按持久绑定接管；本地实现对已退出或未知句柄返回 unknown */
  adopt(executionId: string, sink: ExecutionSink, signal: AbortSignal): Promise<ExecutionOutcome>
}
interface ExecutionSink {
  /** 句柄在任何输出之前持久化（本地：PID / 启动 nonce；CS：父任务 + 子任务 + 尝试） */
  started(receipt: ExecutionStarted): Promise<void>
  event(event: ExecutionEvent): Promise<void>
  /** 批量边界：本地为管道 chunk 结束，CS 为一页事件结束；调用方在此冲刷缓冲 */
  checkpoint(): Promise<void>
}
type ExecutionEvent =
  | { type: 'runtime'; event: NormalizedEvent } // 本地：driver.parseEvent；CS：映射 text / tool / session / usage
  | { type: 'output'; stream: 'stdout' | 'stderr'; text: string }
```

- `ExecutionInvocation` 的 Agent 形状携带**中立材料描述**（根 Agent 与依赖、技能、MCP、插件、注入记忆、按 Agent 的运行时参数、Git 身份、会话续跑 / fresh）而不是已编译的 argv：本地实现在适配器内完成 `selectMaterial → compile → bind`、托管进程、`parseEvent / parseTerminalResultError`、实时子会话采集、会话捕获、启动清单读取与用量计量，并把结果作为事件交给 sink；CS 实现把同一描述编译成 CS 材料与子任务。调用方（`runNode`、`runSystemAgentCore`、冒烟、脚本）保留信封解析、端口输出、预算、用量记账、会话租约与节点状态，只消费事件。
- 命令形状：argv、env、cwd、超时、stdin；本地为托管进程，CS 为命令子任务（`timeoutSeconds`），输出即 `output` 事件。
- `executionId` 由 aw 定（节点运行 + 尝试，或系统执行 ID），CS 的 `requestKey` 由它派生，HTTP 重试沿用原键。
- 本地实现保持现有全部进程语义（launcher / nonce、回执先于激活、逐行与 chunk 确认、TERM→KILL→reap、reap 之后才清理、未 reap 不清目录）；PID 等本机字段只出现在本地实现与本地启动恢复里。

**CS 执行实现**（task-execution `infrastructure/crewstation/`）：

- 持久绑定 `hosted_execution_bindings`（task-execution 拥有；SQLite / PG 同步新增，单机不写）：`executionId ↔ businessTaskId / subtaskId / attempt / lastCursor / materialDigest / state`；提交前写意图行（写屏障内），子任务受理后补全句柄，事件页处理后推进游标。
- Agent：材料 `POST …/materials`（`systemPrompt` = Agent 正文 + 注入记忆，`skills` = 技能文件；MCP、插件、子代理在 M2 随 CS 原生配置叠加接入，M1 遇到即在派发前以明确原因拒绝，不静默丢弃）→ `POST …/subtasks`（`agentProfileId` 由运行时映射到 Manifest 声明的 Agent 档案，`prompt`、`cwd`、`resumeSessionId`）→ `events/stream` 逐页消费、断线按游标补读，直到 `result`（取 `finalCursor` 之前的全部事件）。
- 事件映射：`text`→文本事件，`tool-start / tool-end`→工具事件，`session`→会话，`usage`→RFC-371 v2 调用用量（按模型快照整份替换），`result`→结果（退出码、原因、stdout / stderr 尾巴）。入库的事件载荷是带标记的归一化 JSON，后端会话树构建器识别它（前端会话页不变）；启动清单与子代理会话在 CS 上不可观测，记为“平台不提供”，不伪造。
- 取消：`POST …/cancel`（带 `expectedAttempt`），以 `result` 收敛；重启接管：新的执行权持有者在后台任务启动时对未结束绑定逐个 `adopt`（从 `lastCursor` 续读事件到 `result`），不按本机 PID 判断远程执行。

**执行权与写屏障**（system-operations `infrastructure/crewstation/`）：

- CS 执行权适配器按 §3.2 的 tick 协议实现 `ExecutionAuthorityPort`：每 5 秒读 control；有迁移操作时本库控制行写 `frozen` 并回报 ready；否则 `claim → renew → 本库写 preparing →（交接时 handoffs ready）→ activate → 本库写 active`；租约 30 s，每 10 s 续租；已 active 后续租失败或被冻结即离开 active，按既有优雅关闭退出（崩溃即退出）。
- 本库控制行 `hosted_execution_control`（system-operations 拥有，单行：epoch、owner、phase、leaseId、expiresAt，只增不减）。
- 写屏障端口（system-operations public）：在“将产生 CS 效果”的事务内（绑定意图、取消、重试）对控制行加锁，校验 epoch / owner / active / 未过期；单机实现为空操作。CS 侧再按 fence 拒绝旧世代。

**工作区**（source-control `infrastructure/crewstation/`）：

- 一个 aw 任务对应一个 CS 父任务（`persistent`），首个执行前按 `aw-task:<installation>:<taskId>` 幂等创建，标签带 aw 任务 ID；任务终态按清理策略 close。
- 仓库在 `/work/repos/<slug>`，任务工作树在 `/work/worktrees/<taskId>`（单仓）；托管仓库只能是远程 URL。
- Git 语义由 aw 自己的工作区助手执行：任务镜像（`deploy/crewstation/task.Dockerfile`，含 git、脚本解释器与同一个 `agent-workflow` 二进制）里的 `agent-workflow workspace <op>`。助手在任务容器内调用**与单机相同的本地 source-control / 脚本实现**（作用于 `/work` 下的路径），因此托管的 git 与脚本语义与单机逐字一致；服务侧的 CS 实现只负责把一次端口调用变成一个命令子任务。规格以 base64 JSON 分片经 argv 传入（CS 上限：1024 个参数、每个 ≤ 32 KB；文件接口只读，命令子任务是唯一写入 `/work` 的途径），结果以 JSON 写在 stdout 最后一行；git 凭据只经项目 Secret 引用注入 env，不进 argv。
- 脚本节点：CS 的 `TaskScriptRunFamily` 以一个命令子任务运行助手的 `run-script`——写入脚本与输入、按依赖规格准备环境、执行解释器——输出即该子任务的 `output` 事件，结果分类沿用本地实现；超出单次命令载荷上限的输入在派发前以明确原因拒绝（对象存储随 M2 / M3）。
- M1 实现的端口：仓库准备（克隆 / 拉取 / 工作树）、git 工作区（快照、diff，供 git 包装器）、工作区读取（经 CS 文件接口）、工作区存在性与维护、Agent git 控制观测；git 包装器实际依赖的隔离工作树创建 / 快照 / 无冲突合并 / 回收、预览索引与 scratch 一并接入同一任务助手；需要 Agent 解决的合并冲突、候选提交 / 推送、上传及员工案例随 M2。

**部署**：Manifest 增加 `tasks`（`taskProfileId`、`defaultVolumeMode: persistent`、`executionControl: fenced`、`acceptedTaskContractVersions`、`runtimeImageVersionId`、按运行时的 `agentProfiles`）；任务镜像在本机 CS 平台运行镜像目录构建并授权给本项目。

**测试**：端口合同用例双实现共享（本地真实子进程；CS 用 v3 合同桩，含断线补页、陈旧世代 409、重复 requestKey、取消竞态）；执行权适配器的 tick 状态机与失权退出；写屏障双引擎；绑定与 adopt；工作区助手各子命令在真实 git 仓库上的用例；单机行为不变由现有全量用例保证。本机验收：在本机 CS 上跑一条“输入 → git 包装器内 Agent 改代码 → 脚本节点 → 输出 diff”的工作流，与单机同一工作流的结果对比；运行中取消与重启服务 Pod 后接管各验证一次。

### 9.1 审视结论

审视对象：本地 M1 三个未推送提交（`962dd1e5c`..`879cb0743`）与约 6.5 万行未提交 M2/M3 在制品（迁移 SQLite 0259～0277 / PG 0035～0053 均未在任何库应用），以及 CS 已推送部署的 RFC-040 / 042。按执行核心、恢复、工作区、内容与备份、控制面与事件、CS 两个 RFC 六个区域逐一读码。

**保留**（方向正确、与 CS 合同吻合）：单机与托管同一业务路径（application / engine / domain 无部署分支）；一个 aw 任务对应一个 persistent CS 父任务；任务镜像助手在卷内调用原生 owner；v3 子任务传输（分页 + SSE、`finalCursor`、requestKey 由执行 ID 派生、取消带 `expectedAttempt`）；原生材料编译；崩溃即退出的执行权；事件入站先持久化后 204、冻结目标集合并复用 verified-webhook 受理；RFC-042 的世代 + 绑定 CAS 方向。

**必须修正的缺陷**（不修即不可发布）：

| 区域     | 缺陷                                                                                                                                            | 后果                                                                     |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 执行     | 优雅关闭 / 交接把 `daemon-shutdown` 当用户取消，发 CS cancel                                                                                    | 每次滚动发布、蓝绿交接都取消远程执行，后继重跑模型                       |
| 执行     | 启动恢复在激活前等待所有未结算绑定拿到远程结果；任一 `gap` / 410 / 4xx 即 `Promise.all` 拒绝 → frozen → 退出                                    | 重启后执行入口 503 直到最长的远程 Agent 结束；可无限崩溃循环             |

| 工作区   | 托管 worktree GC 关闭整个父卷（含 `/work/runs`、`/work/logs`）                                                                                  | 开启自动 GC 后任务无法归档、日志丢失                                     |
| 恢复     | 恢复日志无失败终态；`hosted-recovery-required` 在任一远程节点失败 / 取消时禁止 aw 自身的续跑 / 重试，界面隐藏按钮并指向仅平台管理员可用的 CS 页 | 任务族可被永久阻塞；托管用户失去单机的续跑 / 重试能力（违反 §2.1、§3.9） |

| 控制面   | 冻结期间两个槽启动即抛错崩溃循环                                                                                                                | 违反 C7「待命版本只读」                                                  |
| 事件     | 任一 endpoint 暂停整条投递 503；托管 UI 提供不存在的「直连」                                                                                    | 其他 endpoint 丢事件；选「直连」后事件静默停止                           |

| CS-040   | 材料对象 `material-version` 固定引用从不释放；`nativeConfigVersion` 由只测根 Agent 的探针授予                                                   | 对象空间无界增长；未验证的插件 / MCP / 子代理能力被宣称可用              |
| CS-042   | 无放弃动作；第二次恢复的槽位触发器必然失败；verify 回执异常 / 超时后不可重试；跨模块规则在 DB 触发器里以 500 暴露                               | 一次错误的备份引用永久冻结服务的发布与数据操作                           |

**架构不符**：execution 组合根之外的跨上下文装配与组合层互引（task-execution ↔ resource-catalog、system-operations 组合层直接查库）；助手命令日志落在 Task 的执行绑定表（SC → Task → SC 环）；备份 / 恢复直接读写 12 张他域表；CS 线格式放在 integration domain；平台层 import bootstrap 与业务模块（维护 Worker）；约 20 个托管专用选项穿过 SQLite 根；约 125 条新增跨上下文 import 豁免被标成 `pre-RFC-294-current-debt`，把新增债务伪装成存量。

**过度设计**：恢复消费器 4.3k 行（CS 样例 29 行）含两段式检查点、恢复唤醒驱动、原 owner 续接；事件来源切换（暂停 / 水位 / 历史 / 回退直连）在「仅全新安装、DigitalWorker 不能直收 webhook」下无可达用途；六套几乎相同的对象发布日志；每次备份逐对象 pin；三次全量下载校验；18 对互相修补的未发布迁移（含 `SELECT 1` 与修正未发布索引的迁移）及只为它们存在的约 200 行迁移序列工具。

### 9.2 裁定

**V1 执行生命周期**（task-execution `infrastructure/crewstation/`）

- `daemon-shutdown` 与失权导致的中止一律 **detach**：停止观测，不发 CS cancel，绑定保持未结算；节点按既有规则落 `interrupted`。只有用户取消与节点超时发 CS cancel，并等 CS `result` 收敛。
- 启动恢复不再等待远程结果：节点绑定的运行按原 ID 置回 `pending` 由调度器接管（`compile()` 命中原绑定即 adopt，续读游标）；非节点绑定（助手命令、系统 Agent、冒烟）由后台结算器 adopt 后结算。单个绑定失败只影响该绑定。
- `gap` 是可恢复的输出缺口：记一条截断标记并继续读到 `result`；410 `cursor_expired` 才是 unknown（节点以 `hosted-execution-observation-expired` 失败，绑定结算为 abandoned）。平台 5xx / 网络错误在持有执行权期间无限退避重连（上限 30 秒），不判 unknown。
- usage 快照写入 `tokens`，`max_total_tokens` 生效；`truncated` 映射为证据截断，不再是 drain 超时。
- 每个事件在一个事务里写 journal、游标（携带结果时连同结果），先落库后投影；投影失败不被当作传输故障重试，重放从 journal 前缀重建。写入经执行权栅栏（每事务一次 `FOR SHARE`，见 V7）；后继持有租约导致的写入拒绝一律按 detach 处理。
- 绑定不被任何节点接管时（节点已终结、来自恢复快照、无节点的旧 epoch 执行）由后台结算器处理：节点已终结且无结果的发 CS cancel，恢复快照来的一律停止，其余读到结果后结算；并发上限 8，单个绑定不阻塞其他绑定。
  - 2026-10-19 补正（实机验收）：无节点的执行若在本 epoch 内已由其 owner 记下取消（系统 Agent 一直拿不到额度，自行放弃并脱离），且本进程无人观测，也交给结算器；平台对同键重提仍答 429 时即视为从未受理，直接结算为 abandoned，不等额度。此前这类绑定要等到下一个 epoch 才结算，期间其卷一直算作在用，`system:shared` 的父任务因此不被暂停，持续占用项目额度和内存。

**V2 命令通道**（source-control `infrastructure/crewstation/workspaceCommands.ts`）

- 卷归 Source Control，卷内的非节点命令（工作区、Git、内容、维护操作，不论由哪个 owner 发起）的持久日志与执行器也归它，表 `hosted_workspace_commands`（`submitting → running → settled`，失主的未回执行记 `abandoned`）；Task 的执行绑定只承载 Agent / 脚本节点执行。两者经同一个平台中立观测循环 `platform/crewstation/subtaskStream.ts` 读 CS，生命周期决定权在各自调用方。
- 参数编码总量 ≤ 1.5 MiB（任务容器 `ARG_MAX` 2 MiB 留出 env 余量），超限在派发前以 `hosted-command-input-too-large` 拒绝；上传 / 卷写入分块 768 KiB。
- 助手把结果原子写入卷内结果文件（`.aw/command-results/<key>.json`，fsync + rename），控制面经 CS 文件 API 读回，不再从输出里解析结果行；原样还原原生错误码、HTTP 状态与详情。结果文件缺失表示助手未完成（被杀、超时、崩溃），以命令停止错误报告。
- operationId 只在「同一次逻辑尝试」内复用；失败结果不跨尝试重放（脚本依赖、仓库准备等按节点运行 / 尝试派生键）。
- 只读查询（存在性、列目录、读文件）不落日志，优先用 CS 文件 API。

**V3 工作区**（source-control `infrastructure/crewstation/` 与各 owner 的任务镜像组合）

- aw 任务离开运行态（终态、等待人工 / 评审、取消）时暂停 CS 父任务，继续运行前恢复；删除时关闭。由一个对账器补齐失回执，`close` 在 CS 受理后才落 closing。
- 粗粒度助手操作：候选构建、员工案例准备、开发动作物化、提交 / 发布各一个命令子任务，在卷内调用原生实现；删除逐文件复制的端口适配。
- 托管 worktree GC 只删除工作树目录，父卷只在任务删除时关闭。
- 仓库准备在卷内复用 `gitRepoCache` 原语（临时目录 + rename、递归子模块、快进），不另写克隆逻辑。

**V4 CS 恢复请求**（task-execution）

- 只声明父任务级两种动作：`resume-task`（暂停的容器在原卷上继续）与 `rebuild-workspace`（故障容器在原卷上重建）。节点级重试 / 续跑由 aw 自身界面提供（与单机一致）；CS 只在父任务运行且子任务已停时才提供子任务动作，恰是 aw 重试可用的时刻，重复声明没有增量能力。新卷重新开始就是 aw 的普通「重跑任务」，不作为平台动作声明。
- 信封宽松解析：未知字段忽略，未声明的动作仍可读出以便明确拒绝（`recovery-action-not-supported`），不会让该请求的每次 claim 都失败。
- 删除 `hosted-recovery-required` 门控与界面隐藏：托管下 aw 的续跑 / 重试与单机完全一致；父任务暂停时 aw 自行恢复，父任务失败（容器 / 卷不可用）时节点以明确原因失败并在任务页提示可由平台恢复。
- 消费器（仅执行权持有者运行）：claim → 本库受理（aw 拥有该父任务、请求人有关联的 aw 账号且可执行任务、任务允许人工执行；日志 `admitted → executing → succeeded | failed | rejected`）→ 以 `recovery:<id>` 调 CS 操作 → 等 CS 终态且父任务回到运行 → 以请求人身份调用原 aw「续跑任务」命令（任务已不可续跑时直接完成）→ 结束。瞬时错误在 2 小时期限内顺延，期限到或永久错误即失败；任何路径都有终态，不做占位、任务族保留、启动延迟、两段式检查点与原 owner 续接。

**V5 数据库备份与恢复**（system-operations）

- 托管备份复用单机 PostgreSQL 逻辑备份格式，归档字节存 CS 对象；被备份引用的对象以「释放水位」保留：owner 释放的对象只有在其存活期间没有任何保留中的备份时才物理解除固定。删除逐备份逐对象 pin 与 `hosted_database_backup_objects`。
- 托管不捕获工作树：工作区位于平台持久卷，独立于业务库存活；`includeWorktrees` 在托管下以明确原因拒绝（C10）。
- 恢复：`agent-workflow migrate` 在 CS RFC-042 给出的空目标与 `CS_DATABASE_RESTORE_REFERENCE` 下下载并校验归档，复用单机 PG 导入，再经各 owner 的 `public/participants` 做恢复后归一（与单机 RFC-213 一致：非终态任务 `auto_recovery_suspended`、无回执的执行意图标为放弃），产出 CS 校验回执。删除 hold、恢复保留、检查卷、工作卷捕获及其表；删除 `AW_RESTORE_OBJECT`。

**V6 内容对象**（system-operations `infrastructure/crewstation/objectPublications.ts`，经 system-operations `public/participants` 提供）

- 一套中立的对象发布日志（表 `hosted_object_publications`）（pending → ready → releasing → released，含执行权 epoch、重试时间、封存源与创建 / 释放时间）和一个恢复 / 回收任务；各 owner 在自己的事务里登记并保留自己的引用。取代开发证据、员工、Agent 材料、归档对象、插件 `objects_json`、节点事件 `pending_json` 六套日志。
- 源字节在 ready 后清除，不在 PG 内联保存；任务删除 / 归档释放 `hosted_task_artifacts`；插件安装批量登记；完成行按保留期清理；未结算发布不阻塞备份。

**V7 执行权与迁移就绪**（system-operations）

- 删除逐写 schema digest 校验；托管 `verify` 接受「库内历史以本版本头为前缀」的较新 schema（托管迁移只增）。
- 排他写窗口锁只在冻结 / 解冻时取；`assertHeld` 用 `FOR SHARE`，每事务一次。删除 `hosted_schema_write_window` 表，迁移操作 ID 记在控制行。
- 冻结期间以只读待命提供服务，不崩溃循环；启动不依赖 capabilities 端点可达（首次派发时取）。

**V8 事件入站**（integration）

- 删除事件来源切换功能（状态、操作历史、暂停 / 恢复 / 回退直连、管理 Dialog）；每个来源绑定的通道由配置给定（`crewstation` 或 `shadow`），直连入口在托管下不存在。
- 单个 endpoint 不可投递不影响同一事件的其他目标；信封宽松解析（允许 CS 新增字段）。
- CS 线格式移到 `infrastructure/crewstation/`，补 application 用例与共享 finalize。

**V9 装配与架构账本**

- 托管装配只在 `bootstrap/`：一份托管选择对象传给 PG daemon 根，SQLite 根不再穿托管选项；维护 Worker 的入口与效果注册表由 bootstrap 注入，平台层不 import bootstrap / 业务模块。

### 10.2 托管融合

融合编排（Knowledge Evolution）不再自带文件系统与 Git：种子、提案与版本的字节归 Resource Catalog 的选定技能内容绑定（单机为本地文件，托管为 `skill_content_entries`），工作副本归 Source Control，引擎任务的启动面归 Task Execution。

- **Resource Catalog `SkillTreeVersionOperations`**：`readVersionTree` 严格读某版本的不可变快照（缺失即 null，不回落 live 内容，托管与单机同为 `fusion-skill-unversioned`）；`captureCandidate` / `readCandidate` / `discardCandidate` 管提案候选树（DB 绑定为 `candidate:<id>`）；`stage` 开带锁与日志的版本写入，`inTransaction(tx).commit(staged, { before, after })` 依次执行 before → 复合栅栏（融合自己的过期文案）→ 版本行 → after（记忆标记已融合），日志推进到 db-committed，随后 `publish` 或 `abort`；崩溃恢复沿用既有版本写入恢复。
- **Knowledge Evolution → Task Execution `FusionEngineTaskOperations`**：`launch({ fusionId, iteration, seed: { base, overlay } })`、`collect(taskId)`（取回相对显式基线提交的 diff、结果清单与完整树）、`release(taskId)`。
- **Task Execution → Source Control `FusionWorkspaceEffects`**（prepare / collect / release）：单机在 `fusions/<id>/iter<n>/work`；托管在引擎任务自己卷内的 `/work/fusion`，准备与收集各一条 `fusion-workspace` 任务镜像命令，超过 256 KiB 的树经卷文件往返。
- **流程**：创建时读种子并启动引擎任务；对账收集提案存为候选（`proposed_worktree_path = skill-candidate:<id>`）后释放工作区；批准把候选树 stage → commit → publish；驳回以「当前版本作基线 + 上轮提案作 overlay」重跑；取消释放工作区并丢弃候选。托管选择只经 Source Control `bind()` 的 `fusionWorkspaceEffects` 进入 PostgreSQL 根（托管专用选择）；引擎任务是内部任务，不进删除与 GC，release 即关闭其父任务。
- **已知债务**：准备与准入之间若进程崩溃，工作区（本地目录或托管父任务）不会被回收；融合不保留文件模式（与 ZIP 导入一致）；收集失败（含平台瞬时错误）即融合失败并释放工作区。

### 10.3 任务镜像与旧父任务

### 10.5 V21 持久父任务的任务镜像升级（2026-10-19，依赖 CS RFC-043）

> 依据：v4 实机验收发现 CS 父任务一直沿用创建时的任务镜像。scratch owner 每个发布换新父任务，而 AW 任务卷与 `development:shared` 保留父任务及卷内文件，`development:shared` 因此始终跑不了 V18 的新命令（`workspace-helper-operation-unknown`），发布前创建的任务也调用不了此后新增的命令。CS RFC-043 支持给暂停的持久父任务改钉镜像：`POST /v3/business-tasks/:taskId/runtime-image` 返回 202 操作，经 `GET …/operations/:operationId` 取结果；任务视图的 `runtimeImage` 为当前快照；能力快照新增 `runtimeImageUpgrade: 1` 与本发布声明的 `taskRuntimeImageVersionId`。

- **判定**：仅当能力快照报告 `runtimeImageUpgrade: 1` 并声明了版本、父任务视图报告了 `runtimeImage.versionId`、且二者不同时才升级；请求总是显式带上本发布声明的版本。scratch owner 不升级（仍按发布替换父任务）。
- **主动**（Source Control 生命周期对账）：持久共享 owner 的父任务空闲且已暂停、镜像与发布不同时请求升级；运行中的空闲父任务照旧先暂停，下一轮再升级。请求键为 `<父请求键>@<目标版本摘要>:upgrade:<世代>`，同一世代的重放即查原操作。下一次使用照常恢复，新容器即用新镜像。AW 任务 owner 不主动升级。
- **按需**（`HostedWorkspaceCommands.call`）：卷内命令以 `…-operation-unknown` 失败时，若 AW 任务或持久共享 owner 的父任务没有活动子任务、也没有未结束的工作区命令，就暂停（与对账同一世代键）、升级，再以独立的操作 ID（`<原 ID>:image-upgraded`）重试一次；原 ID 的重放与恢复跟随这次重试。父任务仍有工作时不打断，返回可重试的 503 `hosted-task-image-upgrade-pending`；同一 owner 的并发命令共用一次升级。父任务已是发布的镜像时不重试，原错误照常返回。
- **失败**：平台拒绝（`runtime_image_mismatch` / `runtime_image_not_allowed` / `image_usage_unvalidated` / `image_unavailable` 等 4xx）或升级操作失败时，父任务保持原镜像（按需路径下保持暂停），返回 502 `hosted-task-image-upgrade-failed`，带平台原因码与消息；同一镜像对被拒后 10 分钟内不再请求（对账只报告一次，按需直接返回同一原因）。等待超时为 504 `hosted-task-image-upgrade-timeout`。其余 409 / 429 属于生命周期竞争，不算失败，由下一次观测决定。
- **落位**：判定与升级在 `source-control/infrastructure/crewstation/workspaceImageUpgrade.ts`，由 `composeCrewStationWorkspaceOwner` 注入命令与生命周期；bootstrap 只把能力快照映射成本发布声明的版本；平台客户端新增可选的 `upgradeRuntimeImage` / `getOperation`。单机不变。
- **测试**：`tests/rfc370-v4-durable-image-upgrade.test.ts`。

### 10.6 实机验收补正（2026-10-19，v0.6.26）

- **执行截止时间的起点**（补正 §9.2 V1）：托管执行的截止时间从平台报告进程启动算起（第一条 `process` 不是 `not-started` 的 `execution-state` 事件的 `occurredAt`，回放与实时两条路径一致），与单机子进程的计时相同。提交等额度、进程等环境的时间不计入：前者没有上限（用户取消照常生效），后者由平台以 failed-before-start 结束。此前从绑定创建算起，等额度超过预算的运行一被受理就被取消。
- **技能版本的描述**：任何把 SKILL.md 换掉的版本写入，都把新 SKILL.md 声明的描述随版本行一起提交：融合的整树写入、恢复旧版本，与编辑、ZIP 导入一致。技能列表显示的描述与当前版本的 SKILL.md 始终相同（单机同样适用）。
- **员工上传的引用不透明**：上传引用由选定的制品存储解释（本地为内容寻址的摘要，托管为对象引用）。种子在 Case 上下文里记下已校验的摘要，开发自动化只用这个摘要，不从引用里解析。摘要开始记录之前冻结的本地种子，仍以内容寻址的引用作为摘要；Case 详情的上传字段不变。
- **系统 Agent 的 attempt 按次区分**（v0.6.27 补正）：托管执行按 `(feature, kind, originalId, originalAttempt)` 派生的身份持久，同一身份的再次调用得到已记录的结果（防重复执行，AC06）。因此每个调用方的 `originalAttempt` 必须标识「这一次」：变更叙述改为每次触发生成新的 attempt（内容摘要加 ULID），与意图轮次、蒸馏作业次数、探测 nonce、反问请求一致。
