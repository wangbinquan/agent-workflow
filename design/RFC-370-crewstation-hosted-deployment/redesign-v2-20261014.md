## 1. 为什么重设计

[审视记录](../rfc370-372-review-2026-10-14.md) §4 与本次复核的结论：

| 问题                         | 现状                                                                                                                                                                                                                   | 后果                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 执行权（H7）是第二条平行路径 | 生产 daemon 不传宿主执行配置，永远是 `native`；19 个后台 owner 的四阶段生命周期（start / pause / quiesce / drain）、恢复族、写生命周期、准入租约只有测试在走。SQLite 根约 33 处、PG 根约 13 处在判断走新路径还是旧路径 | 新路径没有生产流量验证；任何改动都要同时维护两条路径；执行权概念散布在 73 个源文件 |

阶段 A 中**已经在生产路径上**、方向正确的部分保留：H1 配置 / 安装端口、H2 HTTP / WS 认证参与者、H3 Source Control 工作区端口、H5 材料端口、H6 各 owner 的内容端口、H8 webhook 受理与传输分离，以及各自的本地适配器与回归用例。

## 2. 设计原则

1. **一条业务路径**：单机与托管走同一套 TaskEngine → WrapperRuntime → NodeExecutor → ExecutionKernel 与同一组后台任务。差异只在装配根选择的适配器，domain / application / engine 不出现 `if (crewstation)`。
2. **端口按语义而不是按进程定义**：执行端口交换“调用 + 归一化事件 + 结果”，工作区端口交换逻辑引用，内容端口交换不可变内容引用；本地文件路径、PID、CS wire DTO 都只出现在各自适配器里。
3. **崩溃即退出的执行权**：不在进程内做“失权 → 暂停 → 排空 → 再授权”的状态机；失去执行权的托管实例退出，由平台重启为待命实例。
4. **平台合同不够就补平台**：CS 表达不了的能力在 CS 仓按其流程立 RFC 补合同，不在 aw 里绕平台（例如用命令子任务冒充平台 Agent、在服务槽 spawn）。
5. **装配集中**：新的托管装配放 `src/bootstrap/`；`cli/` 只保留命令入口。SQLite / PG 两个 daemon 根的合并属于 RFC-294 的 DaemonContainer 波次，不在本 RFC 内做，但本 RFC 不再向两个根增加分叉。

## 3. 目标架构

### 3.1 部署形态与唯一选择点

- 新增 `deployment.mode = standalone | crewstation`，由环境变量 `AW_DEPLOYMENT_MODE` 显式指定，默认 `standalone`；不按“发现了 CS 环境变量”自动切换。
- `crewstation` 模式只支持 PostgreSQL（`CS_DATABASE_URL`），复用 RFC-359 的 PG provider，不新增 SQL 实现。
- 选择只发生一次：`bootstrap/deployment.ts` 读取模式，构造该模式的适配器选择项（执行、工作区、内容、身份、配置、执行权、事件入站），交给既有 PG daemon 根。两个 daemon 根已有“未传选择项即用本地实现”的注入方式，托管只是传入另一组选择项。

### 3.2 H7 执行权：崩溃即退出

**端口**（system-operations `application/ports/executionAuthority.ts`）：

```ts
type ExecutionAuthorityState =
  | { kind: 'standby'; reason: string | null } // 尚未取得或正在交接
  | { kind: 'active'; fence: ExecutionFence } // 可以产生外部效果
  | { kind: 'frozen'; reason: string | null } // 平台冻结（迁移 / 交接）
interface ExecutionFence {
  readonly epoch: number
  readonly token: string
} // 托管时 token 编码 leaseId + instanceId
interface ExecutionAuthorityPort {
  readonly mode: 'standalone' | 'crewstation'
  current(): ExecutionAuthorityState
  /** 首次进入 active 时 resolve；之后离开 active 由 onLost 通知 */
  whenActive(): Promise<ExecutionFence>
  onLost(listener: (state: ExecutionAuthorityState) => void): () => void
  close(): Promise<void>
}
```

公开状态 `GET /api/execution/status` 是它的投影 `{ mode, state, reason }`（shared `ExecutionStatusSchema`）；HTTP 门控与状态路由读同一个按 app 实例登记的读取器（`platform/http/executionAvailability.ts`），MCP 绑定调用走同一条注册处理链，因此同样受门控。

**本地实现**：启动即 `active`（epoch 1），永不丢失。单机 daemon 的单实例仍由既有 flock 保证，行为与今天相同。

**CS 实现**（system-operations `infrastructure/crewstation/`），按 CS 官方 v3 样例的协议：

1. 每 5 秒一次 tick：读 `/v3/business-execution/control`；有迁移操作时，把本库控制行写为 `frozen` 并回报 `migrations/:op/ready`；否则 `claim` → `renew` → 本库写 `preparing` →（有交接操作时回报 `handoffs/:op/ready`）→ `activate` → 本库写 `active`。租约 30 秒、续租 10 秒按 CS 能力值。
2. 本库控制行 `hosted_execution_control`（单行：epoch、owner、phase、expires_at）只增不减；旧世代或旧实例的写入被拒。

**daemon 生命周期**：

- HTTP 服务启动即监听，资源读写不需要执行权。
- 后台任务集合（今天原生启动的那组：任务调度、意图队列、维护、MCP 诊断、webhook 终态、提交后事件泵、资源上限、空闲超时、定时备份、子模块刷新、导入回收、人工门继续、提交事件、记忆蒸馏、开发唤醒、数字员工、事件中心、融合对账）**在执行权首次进入 active 时启动一次**。单机版启动即 active，所以与今天完全相同。
- 托管实例在已经 active 之后离开 active（租约丢失、冻结、交接给新版本）：停止接收新请求、按既有优雅关闭流程关闭后台任务与 provider、以非零码退出；平台重启后作为待命实例重新竞争。已提交到 CS 的执行不受影响，由新的执行权持有者按持久绑定接管（§3.3）。
- 待命实例上，声明了 `executionGroup` 的 HTTP 路由返回 503 `execution-standby`（可重试）；`GET /api/execution/status` 返回 `{ mode, state, reason }`。

**写屏障**（仅托管）：凡是记录“将要产生 CS 效果”的业务事务（派发意图、取消、恢复），在同一事务内对控制行 `SELECT … FOR UPDATE` 校验 epoch / owner / active / 未过期；CS 侧再按 fence 拒绝旧世代变更。两者都满足才算有效效果。单机实现为空操作。

**前端**：执行门控只在 `mode === 'crewstation'` 时生效；单机版或状态未知时不禁用执行入口。待命 / 冻结时显示横幅与原因。

**删除**（以引用分析为准，单机原生路径实际在用的保留）：system-operations 的 `hostExecutionAuthority` 应用 / 装配 / 写生命周期 / 准入；`cli/daemonHostExecution{Bootstrap,Owners,Recovery}.ts`、`cli/embeddedHostExecutionApplication.ts`；各后台 owner 的 `startAuthority` / `quiesceAuthorityLoss` / `drainAuthorityLoss` 变体与 `canDispatch` / `whenActive` / `reportFailure` 穿线；`/api/execution/recover`；platform 层的可用性全局表；对应的测试。

P1 实际删除范围（2026-10-14 按引用分析与提交历史核对）：

- 任务执行的 host 写入目的 / 写选择 / 写上下文 / 准入 / 认领失败 / 驱动终结 / 资源恢复写入整套（`select*Writes` 转发在单机下恒等于直接字段，内联回 `persistence.nodeRuns` 等）；
- “原执行恢复”机制：意图回合执行权与冷恢复、记忆蒸馏执行回执与续跑、系统 Agent 执行回执与原进程恢复、MCP 诊断冷启动模式、融合工作区端口，以及它们的恢复端点（`/api/execution/recover`、`/api/memory-distill-jobs/:id/recover`、`/api/mcps/:id/runtime-test-sessions/:sessionId/recover`、意图回合 recover）和前端恢复按钮。托管重启后对仍在运行执行的接管改由 §3.3 的 `ExecutionPort.adopt` 承担；
- 冷维护服务 / 冷提交后事件泵 / 执行权轮询绑定，以及 `executionAuthority` 无关的根级 host 分支；
- 两张只被上述路径读写的表：`system_host_execution_write_contexts`、`memory_distill_execution_receipts`（SQLite 0257 / PostgreSQL 0033）；
- 依赖 RFC-370 逆变换链复原“原始根源码”的源码 oracle（W29、MCP 诊断族的根完整性 AST 钉死，及其逆变换 helper / fixture）。

保留：路由上的 `executionGroup` 标注（改为新门控）、Agent / 系统 / 诊断 / 脚本执行族与执行效果端口（M1 由 §3.3 重塑）、启动恢复族、H1 / H6 的配置与内容端口。

### 3.3 H4 / H5 执行：调用 + 归一化事件

**端口**（task-execution `application/ports/execution.ts`，取代 `executionEffect.ts`）：

```ts
type ExecutionInvocation =
  | {
      kind: 'agent'
      executionId: string
      workspace: WorkspaceLocation
      runtime: RuntimeSelection
      prompt: string
      material: AgentMaterial
      resumeSessionId?: string
      timeoutMs?: number
    }
  | {
      kind: 'command'
      executionId: string
      workspace: WorkspaceLocation
      argv: string[]
      env: Record<string, string>
      timeoutMs?: number
    }
type ExecutionEvent =
  | RuntimeEvent /* 既有驱动产出的归一化事件：文本、工具起止、会话、用量 */
  | { type: 'output'; stream: 'stdout' | 'stderr'; text: string }
interface ExecutionOutcome {
  outcome: 'succeeded' | 'failed' | 'timeout' | 'canceled' | 'unknown'
  exitCode: number | null
  sessionId?: string
  reason?: string
}
interface ExecutionPort {
  run(
    invocation: ExecutionInvocation,
    sink: ExecutionSink,
    signal: AbortSignal,
  ): Promise<ExecutionOutcome>
  /** 托管重启后按持久绑定接管仍在 CS 上运行的执行；本地实现对已退出进程返回 unknown */
  adopt(executionId: string, sink: ExecutionSink, signal: AbortSignal): Promise<ExecutionOutcome>
}
```

- `executionId` 是 aw 自有的稳定身份（node_run + attempt，或系统执行 ID），CS 的 requestKey 由它派生，HTTP 超时重试沿用原键，不因丢回执重复创建。
- **本地实现**：既有 `RuntimeDriver.buildBusinessSpawn` + 托管进程 + `driver.parseEvent`，把逐行 stdout 解析成事件后交给 sink。解析从调用方挪进适配器，调用方不再接触原始行。
- **CS 实现**：先按 §4 编译材料（`POST …/materials`），再提交 `kind=agent` 或 `kind=command` 子任务；用 `events/stream`（断线按 cursor 补页）消费 `text` / `tool-*` / `session` / `usage` / `output` / `result`，映射成同一种事件；`result` 带 `finalCursor`，尾流取完才结束。持久绑定表 `hosted_execution_bindings`（task-execution 拥有：executionId ↔ CS task / subtask / attempt / cursor / materialDigest）支持重启后 `adopt`。
- **调用方不变的部分**：信封解析、端口输出、预算、用量记账（RFC-371 v2）、会话捕获、节点状态转换仍在 application / engine，只是输入从“原始行”换成“事件”。
- 所有执行入口统一走这个端口：任务单 / 多 Agent、工作组、脚本、系统 Agent（意图、记忆蒸馏、评审、提交说明、追问生成等）、MCP 诊断、运行时冒烟。托管时没有任何入口在服务槽本地 spawn。

### 3.4 H3 工作区

- 一个 aw 任务对应一个 CS 业务任务（persistent 卷），首个执行前按 `aw-task:<installation>:<taskId>` 幂等创建，标签带 aw 任务 ID；任务删除时关闭并按终结策略回收。
- 仓库在卷内 `/work/repos/<slug>`；隔离节点 / fan-out 分片的 worktree 在卷内各占稳定目录；合并仍由 aw 的写锁串行裁决。
- Git 与工作区维护（clone / fetch / worktree / 快照 / diff / 合并 / 提交）在任务容器里以命令子任务执行，命令由 aw 的任务镜像内置工具 `aw-workspace` 提供；文件读取走 CS 版本化文件接口；新任务的输入文件经对象存储随任务创建传入。
- Source Control 现有端口（准备、维护、存在性、Git、候选、读取、上传、隔离、冲突）各增加一个 `infrastructure/crewstation/` 实现，共用一个工作区命令客户端；Task 继续只依赖 SC 公开合同。
- 托管仓库只能是远程 URL（克隆进卷）；单机“本地目录仓库”在托管下不存在，见 §6。

### 3.5 H6 内容

- platform 提供中立字节存储机制（本地文件 / CS 对象存储两个实现），各 owner（技能、插件、资源包、意图工件、评审工件、任务提示词 / 端口 / 归档、数字员工证据）保留自己的引用、版本与保留规则，元数据在 aw 数据库。
- CS 实现按 RFC-035：上传 → 提交 → 引用固定后才发布可消费版本；稳定 requestKey 支持丢回执后沿原操作恢复。

### 3.6 H2 身份

- 托管时 HTTP / WS 认证参与者校验 `x-cs-identity-token`：issuer `crewstation`、JWKS（`CS_JWKS_URL`，不取自请求）、aud `service:<CS_PROJECT>/<CS_SERVICE>`、subject `user:<uuid>`。
- 外部身份映射 `external_identities(installation, issuer, subject) → aw 用户`，首次访问建最低权限用户，不按 email 合并；初始业务管理员来自部署配置的 CS subject 名单。平台角色不自动成为 aw 管理员，aw 的资源 ACL 不变。
- 服务来源（事件投递、恢复回调）校验 `x-cs-source-token`，与用户令牌是两个互不替代的入口。

### 3.7 H1 配置、数据库与探针

- 托管时应用配置存数据库（system-operations 拥有），在设置页编辑；主密钥等来自 CS Secret 注入的环境变量，不在临时盘生成。
- 迁移由 CS 发布流水线的 `migrationCommand`（`agent-workflow migrate`）单入口执行，业务进程不各自迁移。
- `/live` 只证明进程可响应；`/ready` 证明配置、schema、内容存储与路由可用，**不等待执行权**（否则待命版本永远无法就绪切流）。

### 3.8 H8 事件入站

沿用 v1 design §7 的合同：`POST /integrations/crewstation/events` 只在托管模式挂载，事务 inbox 先持久化再 204，按 `(installation, producer, eventId)` 冻结目标集合，逐目标进入既有 verified-webhook 受理与两类观测；直连与 CS 转发同一逻辑来源只启一个通道。

### 3.9 恢复

持有执行权的实例按 CS v3 样例消费恢复请求（claim → 本库受理 → 执行 → 记录）；五种动作映射到 aw 既有的任务恢复 / 节点重试命令，并复核业务 ACL、generation / attempt / 材料摘要。aw 页面发起的恢复走同一业务入口。

## 4. 托管能力等价与 CS 侧补齐

| aw 能力                                  | 托管机制                                                               | 是否需要改 CS            |
| ---------------------------------------- | ---------------------------------------------------------------------- | ------------------------ |
| Agent 提示词正文                         | 原生配置叠加里的 Agent 定义（过渡期可用 `systemPrompt`）               | 是                       |
| Agent 权限、工具、温度等 frontmatter     | 原生配置叠加里的 Agent 定义；平台保留键（模型、凭据、二进制）不可覆盖  | 是                       |
| Skills                                   | 材料 `skills`；超过材料上限时改为对象支撑                              | 大体积时是               |
| 远程 MCP（用户在 aw 里随时创建）         | 内联 MCP 定义（URL + 密钥头），不要求事先在 Manifest 登记              | 是                       |
| 本地 stdio MCP                           | 内联本地 MCP 定义；命令须在 Agent 镜像内存在                           | 是                       |
| 插件（含 aw 的启动清单插件）             | 原生配置叠加里的插件文件                                               | 是                       |
| 依赖 Agent（子代理）                     | 原生配置叠加里的子代理定义（运行时内部委派，按 CS 能力标为不透明委派） | 是                       |
| 节点模型 / 变体                          | aw 运行时 + 模型 → CS Agent 档位映射；变体等模型选项视 CS RFC 结论     | 映射不需要；模型选项需要 |
| 自定义二进制、模型网关                   | CS 管理员的算力档位                                                    | 否（平台配置）           |
| 会话续跑                                 | `resumeSessionId`（按档位能力）                                        | 否                       |
| 用量                                     | CS `usage` 事件                                                        | 否                       |
| 脚本 / Git                               | 任务容器内命令子任务                                                   | 否                       |
| API 自动化（PAT、`/api/mcp` 外部客户端） | 需要 CS 用户域的令牌访问方式                                           | 待 M3 前核实             |

需要的 CS 合同变更在 CS 仓按其流程（`proposal/rfc/`、作者批准、本地 `bun run check`、六项 CI、本机部署）单独立 RFC，暂名“业务 Agent 原生配置叠加材料”；批准前 aw 侧先按 CS 现有合同推进 M0、M1，缺口能力在托管模式启动前明确拦截并说明原因，不静默降级。

## 5. 交付顺序

每一步都是：完整实现与用例 → 集中验证 → 按路径提交推送 → 确切 SHA CI 全绿 →（M0 起）部署到本机 CS 并在浏览器验收。

执行端口重塑（§3.3）从 P1 移到 M1 开头：它要按本地与 CS 两个实现一起定形，放在 CS 适配器之前、同一步里做，避免先按单机形状定一次、接 CS 时再改一次。P1 只做删除与执行权端口，保持每步可单独评审。

### 5.1 M0 实施细化（2026-10-14，按源码核对）

托管服务槽只跑 HTTP 控制面：无持久卷、无 git、无运行时二进制（CS RFC-035 §2：配置 / 权限 / 版本指针 / 小型技能文本进 aw 的 PG，插件包等字节进对象存储，容器本地盘只是可重建缓存，主密钥来自平台 Secret）。M0 只做控制面，执行在 M1。

- **选择点**：`cli/deployment.ts` 读取 `AW_DEPLOYMENT_MODE`；`crewstation` 时校验必需环境变量（`CS_DATABASE_URL`、`CS_JWKS_URL`、`CS_PROJECT`、`CS_SERVICE`、`PORT`、`AW_SECRET_KEY`；`AW_ADMIN_SUBJECTS` 与 `CS_OBJECTS_URL` 可选，M0 不用对象存储），缺失即拒绝启动并逐项说明；迁移 Job 只要求项目 / 服务与数据库三项。组装 `StartOptions` 的托管选择项，调用既有 `startCommand`。启动序列不分叉，只跳过服务槽不具备的宿主依赖（`executionHost: 'remote'` 时不做 git 与运行时二进制探测），监听 `0.0.0.0:$PORT`。
- **数据库**：迁移只由 CS 发布流水线的 `migrationCommand`（`agent-workflow migrate`）执行，托管下按 `CS_DATABASE_URL` 直接走 `migratePostgresqlSchema`（全新建库或按 PG 历史只增升级）。PG 迁移器只投影 DDL，单机经 RFC-349 逻辑复制从 SQLite 带过去的初始行（登录策略、框架内置资源、事件族割接等），全新托管库由迁移 Job 从刚迁移完的内存 SQLite 一次复制（单事务、按外键顺序、以登录策略单例行判定已安装；托管无首个管理员引导，复制后的策略记为已完成）。服务用托管的 `DatabaseInstallationPort`：世代身份由 `CS_PROJECT/CS_SERVICE` 确定性派生（来源 `hosted-installation`，不存在本地 SQLite→PG 迁移清单）；与所有 PG 世代一样，它指向产生其数据的操作——迁移 Job 的安装复制：Job 在 PG 元数据里一次性登记这条复制操作与活动世代（幂等；库内已有别的活动世代即拒绝），PG 的世代写入围栏据此放行初始行复制与之后的业务写入。`prepareProvider` 只校验 schema 已是当前版本且本服务世代为活动世代、不迁移，不一致即拒绝启动、等待迁移 Job。
- **配置与主密钥**：应用配置存 system-operations 拥有的 `application_configuration` 单行表（SQLite / PG 同步新增，单机不使用），经既有 `composeApplicationConfigurationBinding({ kind: 'selected' })` 接入设置页；数据库配置只读、来自环境变量。主密钥取 `AW_SECRET_KEY`（base64 的 32 字节），不在临时盘生成。
- **身份**：identity-access 新增 CS 认证适配器（HTTP 与 WebSocket 两个既有参与者端口）：校验 `x-cs-identity-token`（JWKS 只取自 `CS_JWKS_URL` 并按 kid 缓存，iss `crewstation`，aud `service:<CS_PROJECT>/<CS_SERVICE>`，sub `user:<uuid>`，exp）；`external_identities(issuer, subject) → 用户` 映射（新表），首次访问建最低权限用户、不按 email 合并，`AW_ADMIN_SUBJECTS` 中的 subject 首次访问建为管理员。本地密码、OIDC、PAT 与首个管理员引导在托管入口不出现。
- **内容**：技能文件树按 CS RFC-035 的建议存进 aw 数据库（`skill_content_entries`：在用树、不可变版本、发布暂存、删除回收站，每步一个事务；树哈希与文件版规范哈希逐字一致，引用沿用相对布局，两种部署的技能元数据完全相同）。插件安装依赖 npm / git 且注入运行时配置，资源包经本地产物漏斗携带插件与技能树，二者随 CS 原生配置叠加（§4，M2）提供，M0 在托管下以 503 `hosted-capability-unavailable` 明确拒绝并说明原因。对象存储（上传 → 提交 → 引用固定）随需要大体积字节的 owner 在 M1～M3 接入。
- **探针**：公开 `/live`（进程可响应）与 `/ready`（配置、schema、内容存储与路由可用，**不等待执行权**）。
- **执行权**：托管适配器在 M0 恒为 `standby`（原因：远程执行在 M1 提供），执行入口显示未就绪；后台任务集合改为在执行权首次 active 时启动（单机启动即 active，行为不变），离开 active 时按优雅关闭流程退出（§3.2）。
- **前端**：托管时 daemon 在下发的 `index.html` 中注入部署形态标记，前端据此视为网关会话（不保存、不发送本地令牌，WebSocket 不带令牌参数，平台会话失效时经网关重新加载、30 秒内至多一次），不显示本地登录 / 首个管理员引导 / 退出登录 / 口令与个人令牌，设置页隐藏数据库、认证、网络三页；待命横幅说明“远程执行尚未接入”。
- **镜像与发布**：`deploy/crewstation/` 提供 Dockerfile（构建单二进制，运行镜像只含二进制与 CA 证书，非 root，固化 `AW_DEPLOYMENT_MODE=crewstation`）与 Manifest 模板（DigitalWorker：服务命令、端口、`/live` `/ready` 探针、套餐、`AW_SECRET_KEY` 密钥与 `AW_ADMIN_SUBJECTS` 配置、`release.migrationCommand`；`tasks` / `data.objects` 随 M1 / M2 加入）；`scripts/crewstation-publish.ts` 按本地部署档案渲染 Manifest，把已提交源码快照推到 CS 项目仓库并 `crewstation publish`。
- **本机验收**：本机 CS 建项目、PostgreSQL 数据资源、对象档位、配置与密钥，发布后在浏览器从 CS 入口登录，编辑并保存工作流、Agent、技能、MCP（插件安装与资源包应用显示明确的不可用原因），重建服务 Pod 后数据仍在，执行入口显示未就绪。

## 7. 测试策略

- **单元**：执行权状态机（本地 / CS 两种驱动，CS 用假平台）；CS 事件 → 归一化事件映射；requestKey 派生与重试复用；写屏障拒绝旧世代；身份令牌校验与映射；材料编译。
- **双数据库**：控制行单调写入、写屏障与派发意图同事务；执行绑定与游标持久化；inbox 冻结目标集合。
- **合同**：CS 适配器对照 CS `packages/contracts` 的 zod schema 校验请求 / 响应形状，CS 合同升级时失败。
- **回归**：P1 只换内部边界，既有任务 / 节点 / 系统 Agent / 脚本用例与 e2e 全部保持；删除平行路径时一并删除只验证它的测试，并在提交说明列明。
- **实机**：M0 起每一步部署到本机 CS，用真实浏览器走用户流程；只证明 HTTP 200 不算通过。
