# RFC-628：数字员工被事件抢占后丢失「回复检视意见」

## 1. 背景

### 1.1 现象

研发数字员工处理一条检视意见的完整流程是：汇总待处理的意见 → 在线程里回复「已收到」→ 由 Agent 修复 → 如果改了代码，平台校验并冻结修改、提交并推送 → 最后回到原线程回复「已在提交某某中处理」并附上处理说明。最后这一步叫「回复修复结果」（工作项 `reply-feedback`）。

如果在「回复修复结果」执行之前，员工的事件队列里到来一条声明「抢占续接」的事件，规划器会放弃原本要执行的「回复修复结果」，改去执行事件规则指向的工作项。会抢占的事件有四种：检视意见更新、代码冲突更新、MR 生命周期更新（三者都落到「关注 MR 状态」`observe-mr`）和外部审批更新（落到「等待外部审批」`observe-approval`），规则在 `modules/development-automation/application/employeeTypePackage.ts:2950-3026`。此后没有任何路径回到「回复修复结果」：准备好的回复留在检视处理台账里不再发出；之后如果又来了新的检视意见，新一轮处理还会把这条没发出的回复从台账里删掉。评审人在线程里只能看到「已收到该检视意见，正在处理」，看不到修复结果。

最常见的抢占者是员工自己：它推送修复提交后，MR 的头提交变了，事件观察程序据此发出一条生命周期更新（生命周期事实里含头提交，`modules/integration/application/developmentEventObservers.ts:43-51`；事实内容摘要变化就发事件，`:188-208`）。配置了 Webhook 时，收到推送通知会立即催一次观察（`modules/integration/composition/webhookIngress.ts:93-94`），这条事件很可能与推送几乎同时到达（时间量级是推断，没有实测）。

### 1.2 已修的前一半

2026-11-27 在真实 GitLab 上遇到的现场里，「回复修复结果」先因为读取 MR 事实时撞上头提交正在变化而阻塞；用户恢复之后，流程被抢占，直接去了「关注 MR 状态」。前一半（读取时撞车导致阻塞）已在提交 `033f5fafe` 修掉：读取层遇到头提交或目标分支在读取过程中变化会重新采集（`modules/development-automation/application/developmentMrFacts.ts`，回归用例 `tests/development-mr-facts-recollect.test.ts`）。本 RFC 修后一半：被抢占之后回复丢失。

### 1.3 为什么会丢

- 每个交办只有一个「下一步」指针（`employee_cases.current_work_item_ref`）。规划时如果优先级最高的待处理事件对应的规则声明抢占，就不执行指针指向的工作项，而是执行规则指向的工作项（`modules/digital-employee/application/runtimeService.ts:3042-3047`）；建立这一轮时，指针被改写成这一轮的工作项（`modules/digital-employee/infrastructure/runtimeStore.ts:1417-1430`，改写在 `:1421`），原值没有另存。
- 「关注 MR 状态」结束后的去向只有：MR 已合入或已关闭则结束；触发事件是检视更新且有新意见则重新汇总；触发事件是冲突更新且确有冲突则修冲突；否则去准备审批或判断是否可合入（`employeeTypePackage.ts:5342-5416`）。它允许的后继里没有「回复修复结果」（`employeeTypePackage.ts:2298-2304`），即使结算想走过去，平台也会拒绝（`runtimeService.ts:1535-1543`）。
- 准备好的回复存在检视处理台账（`development.review-resolution`）里，状态为「已准备」（`prepared`）。之后只有两种情况会再碰它：又一次发布 MR 时结算看到「已准备」会转去回复（`employeeTypePackage.ts:5227-5231`）；或者来了新的检视意见，新一轮修复的输出校验把「不在本轮问题集合、又没有最终回复回执」的行从台账删掉（`employeeTypePackage.ts:4743-4761`，删除在 `:4760`）。

### 1.4 同一根因的相邻窗口

抢占判断不看被放弃的是哪个工作项，所以：

- 只回复、不改代码的修复，Agent 修复的整个运行期间到来的事件都会在它结束后立刻抢占「回复修复结果」。
- 改了代码的修复，如果在「校验并冻结代码修改」（`prepare-change`）之前被抢占，修复本身会留在员工工作区里没有提交；除非之后别的流程（例如修流水线后重新发布）顺带把它发布出去，否则没有路径回到提交。

## 2. 目标

1. 已经发布（或只回复、不需要发布）的修复，即使「回复修复结果」被任何一种抢占事件打断，回复最终也会发到原线程；重试（包括被抢占之后的补发）不会把同一条回复发两遍。
2. 被打断之后，MR 已合入或已关闭的终态仍然先结算，不在终态之后再往代码平台写回复（RFC-310 的约定，`design/RFC-310-rule-driven-development-digital-employee/proposal.md:280-286`、`design.md:537-544`）；回复步骤执行时才发现 MR 已合入或已关闭的，同样不发。
3. 新的检视意见到来时，先把上一轮的回复发出（或先把还没提交的修复提交并回复），再处理新意见。代码冲突仍先于回复处理；只有还没提交的修复排在修冲突之前，因为修冲突会重建员工工作区、丢掉未提交的修改。
4. 改了代码、在提交之前被抢占的修复（包括被有新意见的检视更新、确有冲突的冲突更新和进行中的审批更新抢占），只要员工工作区没有被平台重建过，就回到「校验并冻结代码修改」继续提交、推送并回复。
5. 回复时线程已被删除的，从台账移除并在这一轮的摘要里写明，不让整个交办阻塞；这一条对每一条尚未回复的线程都适用。其余发送失败照旧阻塞，恢复后重试。
6. 研发数字员工（`development`）与图驱动研发数字员工（`graph-development`）同样修复。

## 3. 非目标

- **不修复已经在进行中的交办。** 交办创建时钉住员工当时的类型修订号，之后一直按那个修订号的冻结定义运行（`runtimeService.ts:1036` 写入，`:614-623` 读取）；平台没有把进行中交办升到新修订号的机制。本 RFC 也不做这种迁移。用户可见的后果是：升级到包含本 RFC 的版本之后，新发起的交办才受益；升级前已经在看护的 MR 在其余生里仍可能丢回复，需要人工在线程里补一句。
- 不改通用的数字员工运行平台（`modules/digital-employee`），不增加「被抢占的下一步」之类的通用存档，不声明某些工作项不可被抢占，不加表结构、不加迁移。
- 不处理「已确认、尚未修复」时被抢占的情形（下一步是 Agent 修复时被生命周期事件抢占）。现有用例把它当作预期行为锁着（`tests/rfc310-employee-case-runtime.test.ts:2224-2232`）。
- 不恢复被平台重建工作区丢掉的未提交修复（见 §7）。
- 不改代码平台回复接口、事件观察程序和事件优先级。

## 4. 用户故事

- 作为评审人，我在 MR 上提了意见；员工推送修复后，即使它自己的推送立刻触发了一条生命周期事件，我也能在原线程看到「已在提交某某中处理」和处理说明。
- 作为评审人，我在员工回复之前又提了一条新意见；员工先在旧线程回复修复结果，再处理我的新意见，旧的那条不会被吞掉。
- 作为员工的负责人，回复步骤因为代码平台暂时故障而阻塞，我恢复交办后，即使恢复期间攒下的事件抢先执行，回复也会补发，并且已经发出的那几条不会再发一遍。
- 作为员工的负责人，员工改完代码、还没提交时目标分支被别人合入了新提交（触发生命周期事件），或者评审人又提了新意见、MR 出现了冲突，员工都会先把修复提交上去并回复，而不是让修复一直躺在工作区里或被修冲突丢掉。
- 作为员工的负责人，评审人删除了某条线程，员工不会因为回复不了这条线程而一直阻塞；交办记录里写明了哪条线程没有回复。

| 修复已推送，回复前到来员工自己推送引起的生命周期事件，MR 仍开着 | 关注 MR 状态后去审批或可合入判断，回复不再发出 | 关注 MR 状态后转去回复修复结果，回复发出 |
| 同上，但 MR 此时已合入或已关闭 | 交办结束，回复不发 | 不变：交办结束，回复不发（终态先结算） |

| 回复前到来检视更新，且有新意见 | 新一轮处理新意见，旧回复在这一轮被从台账删掉，永不发出 | 先发出旧回复，再汇总、处理新意见 |

| 回复前到来审批更新，审批仍在进行中 | 交办进入等待，回复不发 | 先回复修复结果，再回到关注 MR 状态（同一头提交的审批照常等待，不会重复提交） |
| 回复阻塞后恢复，恢复时有攒下的抢占事件 | 被抢占后回复不发 | 回复补发；已经发出的线程靠同一个幂等标记识别，不重复 |
| 只回复不改代码，Agent 修复期间到来抢占事件 | 回复不发 | 回复发出（只回复的修复在准备好回复时就记为已发布） |
| 改了代码、提交前被生命周期事件抢占，期间 MR 头提交没变 | 修复留在工作区，直到别的流程顺带发布 | 回到校验并冻结代码修改，提交、推送后回复 |
| 改了代码、提交前被有新意见的检视更新抢占 | 修复留在工作区；新一轮处理新意见时把这次的回复从台账删掉，修复被下一次提交顺带发布，线程只有「已收到」 | 先提交、推送并回复这次的修复，再汇总、处理新意见 |
| 改了代码、提交前被确有冲突的冲突更新抢占 | 先修冲突；发布冲突修复时重建工作区，这次的修复被丢掉 | 先提交、推送并回复这次的修复；推送后冲突仍在时，由随之而来的冲突更新触发修冲突 |
| 改了代码、提交前被审批更新抢占，审批仍在进行中 | 交办进入等待，修复留在工作区 | 先提交、推送并回复；之后为新的头提交准备审批，与正常发布后的路径相同 |

| 同上，之后别的流程（例如修流水线）又发布了一次 | 发布后回复「已在提交中处理」，而那次检视修复其实已丢失 | 不回复；台账停在「已准备」（见 §7） |
| 回复时线程已被删除 | 回复接口失败，交办阻塞 | 从台账移除，这一轮摘要写明，其余回复照常发出 |
| 回复时代码平台拒绝回复 | 交办阻塞 | 不变：交办阻塞，恢复后重试 |
| 回复步骤执行时 MR 已合入或已关闭 | 不检查，照常尝试发送 | 不发任何回复，交办随后结束 |

## 6. 验收标准

1. 用新修订号创建的交办，在「回复修复结果」待执行时分别注入生命周期更新、检视更新（无新意见与有新意见两种）、冲突更新（有冲突与无冲突两种）、审批更新（审批仍在进行中），最终都执行了「回复修复结果」，台账变为「已回复」；有新意见时回复先于新一轮汇总，有冲突时先修冲突、修完再回复。
2. 改了代码、提交前被抢占且头提交未变时，分别注入生命周期更新、有新意见的检视更新、确有冲突的冲突更新、审批更新（审批仍在进行中），修复都被提交、推送并回复；之后新意见被汇总处理，冲突由推送后的冲突更新触发修复。
3. 生命周期更新显示 MR 已合入或已关闭时交办结束，代码平台上没有新增回复；回复步骤执行时才发现已合入或已关闭的，同样不发，交办随后结束。
4. 回复阻塞后恢复、恢复时被抢占，最终每条线程恰好收到一条修复结果回复。
5. 改了代码、提交前被抢占且头提交已变时不重新提交，之后别的流程再发布时也不回复「已在提交中处理」。
6. 回复时线程已被删除，交办不阻塞，摘要写明没有回复的线程。
7. 续办之后那次「关注 MR 状态」发现台账里没记过的未解决线程时转去汇总；这一轮处理完后不会对同一批线程再次汇总。
8. 钉在 `development@11`、`graph-development@2` 及更早修订号上的交办，结算、校验与平台工作项的行为与修复前逐条相同（用例显式传旧修订号与旧后继清单断言）。
9. `graph-development@2` 的员工与岗位在升级后自动升到 `@3`，能继续发起新工作；守护进程启动不报岗位名称冲突，内置的图研发 MR 岗位在 `@3` 下可用。
10. design §6 列出的必写用例全部写齐，CI 全部通过。

## 7. 已知限制

- **进行中的交办得不到修复**（见 §3 第一条）。
- **工作区被重建后丢失的未提交修复不恢复。** 平台在 MR 源分支被别人推进、或发布冲突修复之后，会按新的头提交重建员工工作区，只保留平台目录、丢弃业务文件的未提交修改（`modules/source-control/application/employeeCaseWorkspace.ts:142-171`；触发点 `modules/development-automation/application/employeePlatformWorkItems.ts:2077-2104`、`:1964-1974`）。这种情况下修复已经不在工作区，无法安全地重新提交，也不再声称已处理；台账里的这几条停在「已准备」。之后若有新意见开启新一轮，新一轮的修复校验照现状把这几条移出台账（`modules/development-automation/application/employeeTypePackage.ts:4760`），线程若仍未解决，就作为没记过的线程在这一轮回复之后被重新汇总、重新修复（「已收到」不会重复发）；没有新意见触发新一轮时，台账一直停在「已准备」。
- **头提交被强推回原值时会误判修复仍在工作区。** 平台先观察到被强推后的中间提交、重建工作区丢掉修复，之后源分支又被强推回原来的提交时，MR 头提交与工作区基线重新等于台账记录的源头提交，平台会以为修复还在：重新冻结时找不到修改而阻塞，或在别的流程发布时把那次发布当作检视修复的发布并回复「已在提交中处理」。两次观察之间完成的强推不触发重建，不受影响。
- **推送成功、但 MR 创建或绑定失败后被抢占时，修复已在远端，回复不发。** 发布步骤先推送、再创建或绑定 MR，后者失败时整步阻塞、台账没有记下发布（`modules/development-automation/application/employeePlatformWorkItems.ts:1735-1774`）。推送本身会引起一条生命周期更新，恢复时它抢先执行，平台发现源分支头已变而重建工作区，台账成了「已准备、未发布、头提交已变」，既不重新提交也不回复，需要人工在线程里补一句。
- **被续办占用的新检视意见，靠之后的「关注 MR 状态」接手。** 新修订号下「关注 MR 状态」每一轮都会检查有没有还没处理过的新意见，不论这一轮是由什么事件触发的；所以新意见最迟在回复之后的下一轮被汇总，只是比修复前晚一轮开始处理。
- **汇总、确认与修复的下一步被抢占时不续办。** 下一步是「汇总待处理检视意见」时被生命周期更新抢占，新意见要等下一条检视更新；下一步是「回复已收到」或「处理检视意见」时被抢占，台账停在「已汇总」或「已确认」，这些线程已记在台账里，之后的「关注 MR 状态」不再把它们当作新意见，要等别的新意见开启新一轮时才一并处理。这是现状（「已确认、尚未修复」见 §3 非目标）。本 RFC 让续办之后的「关注 MR 状态」也能转去汇总，相应多了一条到达这里的路径：这次「关注 MR 状态」先于事件观察程序看到新意见并汇总，随后观察程序发来的检视更新抢占了确认这一步。
- **线程列表读不全时，回复照发但不核对。** MR 上讨论很多、代码平台的列表响应超过读取上限，或返回的不是合法的线程列表时，平台看不到任何线程。这种情况下「回复修复结果」对每条尚未回复的意见照常回复（与修复前相同），但无法判断线程是否已被删除、是否已经回复过：线程确已删除的，回复会被代码平台拒绝并阻塞（同修复前）；上一次回复已发出而平台尚未记下的，可能重复一条。摘要里会写明这一轮没有读全。
- **线程仍在、代码平台持续拒绝回复时，交办仍会阻塞**，与修复前相同；平台只有一个笼统的回复失败码（`modules/integration/application/mrFacts.ts:546-548`），无法区分暂时与永久失败。
- **审批被驳回、过期或不可用时，恢复交办本身不会让回复发出。** 交办阻塞在「等待外部审批」，下一步保留为这一步（`modules/digital-employee/infrastructure/runtimeStore.ts:2064-2068`）。用户恢复后它重新执行，审批的持久回执已是终态，于是再次阻塞（`modules/development-automation/application/employeePlatformWorkItems.ts:1479-1480`、`:1522-1523`）。只有阻塞期间攒下了检视、冲突或生命周期更新（MR 仍在看护，这三种事件照常进入事件队列；审批已结束，不再订阅审批更新），恢复后的第一次规划才由优先级最高的那条抢占，经「关注 MR 状态」续办回复或提交；否则回复要等新的 MR 事件，或由用户终止交办后人工补发。
- **升级后，图研发的内置 MR 岗位改用新标识与新名称，岗位列表里可能并列出现两份 MR 岗位。** 内置岗位的内容随类型修订号变化，而内置岗位按标识播种、内容不同即报冲突（`modules/digital-employee/application/builtinEmployeeJobs.ts:22-31`、`:48-55`），所以 `@3` 的内置岗位用新标识；岗位名称在同一归属与类型修订号下唯一，而仍被员工引用的旧内置岗位在升级时会以原名迁移到 `@3`（`modules/digital-employee/application/authoringService.ts:524-532`、`:1156-1219`），所以新内置岗位也换名，否则守护进程启动时撞名失败。于是在仍有员工使用旧内置岗位的部署里，`@3` 的岗位列表会并列出现迁移过来的旧内置岗位副本（原名，已升级的员工继续使用）与新的内置 MR 岗位（新名称）。`@2` 的旧内置岗位作为历史保留；尚未发布的「完整 MR 看护」草稿留在 `@2` 下、无法再发布（发布入口要求类型修订号在当前版本中可执行，`authoringService.ts:451-469`、`:2554`），需要在 `@3` 的新草稿里重新选择流水线连接后发布。已经发布过的岗位和员工照常自动升级。
- **说明：补发不会跨轮重复，被移除的线程不会回来。** 回复的幂等标记取台账记录的发布提交（design §3.5），一轮之内（包括被抢占之后的补发）保持不变；新一轮只会在上一轮回复完毕之后开始（续办排在汇总之前），不存在上一轮发了一半、下一轮换了标记重发的情形。回复时因线程已删除而移除的行不会再回来：删除的讨论不会再出现在 MR 事实里。
