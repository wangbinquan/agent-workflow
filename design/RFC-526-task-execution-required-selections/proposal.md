## 1. 背景

task-execution 的组合层在调用方没给时自己造本机实现：

- **一直由回落造、生产路径在用的**：任务的操作配置（提交排除模式与运行时可执行文件的冻结）——没有任何调用方给出，两种部署都由回落按
  `configPath` 读本机配置文件；单机维护 worker 的任务归档内容（部署效果为 `null`）；运行生命周期的工作区存在性——维护 worker、数字员工执
  行里的任务取消与人审停靠都不给，一直是本机文件判断；单机部署自己的节点提示与端口工件选择，也是经“不给内容就造本机的”入口造出来的。
- **只服务用例的**：启动恢复的执行恢复工厂、数字员工执行的程序工具源、provider 运行期的工作区排除档案（daemon 都给）；节点提示、端口工
  件与任务删除效果的 `select*` 助手（daemon 都给，选择助手的回落只在用例里走到）。
- **不是回落的**：启动配置的三处按“没有选定查询”分支，实际是调用方显式选的两种模式（本机同步读取或选定的查询），写法让它像回落。

这些回落让依赖藏在组合层里：哪一份是生产对象、哪一份只是给用例的方便，从调用处看不出来；托管部署下几条路径还在用本机文件判断工作区是否存
在。

## 2. 目标

- **G1 必填注入**：上述 16 处改为调用方给出，只为回落存在的选项与缺省参数一并删去；启动配置按调用方选的模式显式装配两支。
- **G2 装配处显式构造**：bootstrap 在原来回落发生的位置给出同样的对象（同一组工厂、同一组参数、同样的读取时机）：操作配置给本机配置文件的
  实现，每次驱动（含子任务与续跑）都带上；单机部署的节点提示与端口工件由组合层交出的本机内容显式构造；维护 worker 的归档内容与工作区存在性
  显式给出本机实现。任务取消与人审停靠改取部署选择的工作区存在性（这几条路径不做复活转移，存在性不会被查询，行为不变）。
- **G3 门与用例**：RFC-521 门删去 16 条登记，适配器回落 35 → 19；用例经测试助手显式给出与此前缺省相同的对象。

## 3. 非目标

- 单机选择整体收进 `bootstrap/standalone.ts`（与维护 worker 的单机效果一并另立后继）；source-control 的回落（第 1 项最后一步）；任何行为、
  接口与界面变化。

## 4. 用户可见变化

无。

## 5. 验收标准

- **AC-1**：这 16 处回落不再存在；对应选项必填、只为回落存在的选项与缺省参数删去；RFC-521 门的实测与登记逐条相等，适配器回落 19 条。
- **AC-2**：daemon、维护 worker 与单机部署得到的对象与此前相同（同一组工厂、同一组参数，配置在同样的时机读取）；改取部署选择的几条路径不
  查询工作区存在性；用例显式给出的选择与此前缺省相同。
- **AC-3**：bootstrap 不深取 task-execution 的 infrastructure；public surface 不升；计数不升（降的收紧到实测）。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。
