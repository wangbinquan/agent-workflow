## 1. 背景

provider 构造数据库时把句柄上下文（表集、引擎能力、提交后事件泵槽、整文件快照计数）交给句柄
（`platform/persistence/sessionTables.ts` 的 `bindDatabaseHandle` / `inheritDatabaseHandle`）。上下文已经记在句柄对象自己的符号属性上，事务与原生
客户端也各自带着；但同一份记录还同时写进一张模块级 `WeakMap`（`contexts`），查找时先查这张表，它只额外覆盖“不可扩展的句柄”一种情形，
而仓内没有这样的句柄。文件头写着“表身份挂在原生库 / 事务上，绝不挂在进程状态上”，这张表与之相悖。架构报告的模块级可变单例清单里这个
文件 1 条（全仓 48 条）。

## 2. 目标

- **G1 只记在句柄上**：删去模块级 `contexts`；上下文只记在句柄（与它的原生客户端）自己的符号属性上，查找只读这个属性。
- **G2 结局不变**：根库、事务、原生客户端、继承句柄、经原型链派生的对象与包着句柄的代理取到的上下文不变；两个分别构造的库各有各的上下文。
- **G3 门与用例**：新增 RFC-543 用例（文件没有模块级状态；上述各种句柄取到的上下文；不可扩展的句柄在构造时明确报错；带负对照）；模块级
  可变单例清单 48 → 47。

## 3. 非目标

- 其余 47 条模块级可变单例（live schema 的登记、schema 历史运行时、规范 JSON 片段缓存、日志器配置等另立或待定）。
- 上下文的内容、表集的校验与各访问函数的签名不变。

## 4. 用户可见变化

无。唯一的约束收紧：交给 `bindDatabaseHandle` / `inheritDatabaseHandle` 的对象必须可扩展，否则在构造时报 `persistence-handle-not-extensible`（以前会
静默只记进模块表）。provider 构造的根库、事务与原生客户端都是可扩展的普通对象，仓内没有不可扩展的句柄。

## 5. 验收标准

- **AC-1**：`sessionTables.ts` 没有模块级集合；上下文只记在句柄与原生客户端自己的属性上。
- **AC-2**：各种句柄取到的上下文不变；不可扩展的句柄在构造时明确报错。
- **AC-3**：模块级可变单例清单 48 → 47，计数不升；新增 RFC-543 用例并登记 guard-manifest。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。
