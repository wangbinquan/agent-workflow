# RFC-230 — Run 活性证据链：孤儿判定从「有没有进程」升级为「证据链是否断裂」

## 背景

### 事故形态

生产上出现过这样一条任务级失败：

```
error_summary: scheduler error
error_message: node_run <id> is terminal ('interrupted'); refuse to overwrite (wrapper-finalize)
```

任务本身跑得好好的，wrapper（git / loop / fanout）的内层 scope 也正常收敛了，但 wrapper 要落终态时发现**自己那一行已经被别人写成了 `interrupted`**，终态守卫拒绝覆盖，异常冒泡到 `runTask` 的兜底 catch，整个任务以 `scheduler error` 失败。

### 谁改的

周期性孤儿回收器（RFC-108 T17，`services/orphanReconcile.ts`，daemon 常驻、默认 10 分钟一跳）。它的判活口径第一句就是「**没有 pid ⇒ 进程已消失**」。而 wrapper 行**永远不会有 pid**——它不是一个进程，它是一段子图正在被推进的记账行。于是任何内层跑超过 60 秒宽限期的 wrapper，都会在下一跳被判定为孤儿并翻成 `interrupted`。

### 概念层的三个病灶

1. **把「进程活着」当成了「工作还在进行」。** 系统里有两类 run：一类背后确实有 opencode 子进程，活性由操作系统承载；另一类（wrapper）只是编排容器，活性由调度器协程承载。回收器只认识第一类，面对第二类看到「没有进程」，得出「已经死了」——**把证据的缺席当成了死亡的证据**。

2. **后台回收器与前台调度器之间没有所有权约定。** 回收器扮演的是「守夜人」，它假设看到的一切都是无主残骸（典型场景是 daemon 崩溃重启后满地的 running 行）。但它在活着的 daemon 里持续跑，而此刻恰恰有调度器正持有并推进这些行。这个所有权概念仓里本来就有（取消任务靠它判断有没有活的调度器可打断、诊断修复靠它拒绝在活调度器面前动手），唯独回收器没接进去。

3. **同一个动作下面藏着两个相反的判断。** 今天回收 wrapper 的理由是「因为没 pid」；而真正该回收 wrapper 的理由应该是「因为内层一个活的都没有、也没有调度器附着」。两个判断碰巧都指向「收」，所以谁也没发现它一直在误判——**并且真正的孤儿 wrapper（驱动协程已死、daemon 还活着）今天反而是靠误判被顺手收掉的，机制上并不成立**。

### 连带伤害

- 被误收的 wrapper 行若恰好是任务最后一条 running 行，回收器会把**整个任务**也翻成 `interrupted`（`orphanReconcile.ts:101-117`），活任务被后台线程判死。
- 「任务在跑、但每一行 node_run 都已终态」正是既有的卡死诊断特征（`stuckTaskDetector.ts:375`，诊断项 S3）。也就是说这个缺陷不只造成任务失败，它还会**伪造一个卡死现场**，让后续自动诊断去修一个根本不存在的问题。
- 同一缺陷覆盖 agent 行的 **pre-spawn 窗口**：`runner.ts:993-998` 先 mark-running 并写 `startedAt`，pid 要等 RFC-224/227 的封存二进制 + `opencode serve` + attestation 全部走完才落库（`runner.ts:1442-1450`）。这段超过 60 秒同样会被误收。

### 测试为什么没拦住

`tests/rfc108-orphan-reconcile.test.ts` 全部通过注入 `isGone` 来驱动，真实的 `runProcessGone` 的 pid-null 语义**从未被任何测试执行过**，更没有 wrapper 行的用例。

这个盲区**此前已被记过两次**：`design/test-guard-audit-2026-07-21/01-gaps.md` 的 `B2-lifecycle-1`（P1，mock-too-deep）与 `M1-lcov-4`（P1，覆盖率）都精确指出「判活函数是注入式的，四条 reconcile 用例全部注入桩，真实探针三条分支零执行」，并预言了后果：「每 10 分钟一次的周期回收会把正在跑的 node_run 判成 interrupted，进而把任务翻成 interrupted：用户看到『任务被中断，请恢复』，而 opencode 子进程仍在后台写 worktree」。当时的定性是**测试覆盖缺口**；本 RFC 指出它实际上是**语义缺陷**——即便把桩换成真函数，`pid === null ⇒ 已消失` 这条判据本身对容器行就是错的。

## 目标

1. **确立「活性证据」为显式契约**：每一类 node_run 都必须声明自己的活性证据来自哪里，不再默认继承一个只对 agent 成立的前提。
2. **孤儿判定改为证据链解析**：一个 run 只有在其活性证据链**完全断裂**时才是孤儿。「没有直接进程」不再等于死亡，只意味着「去问下一层」。
3. **补上今天真正漏掉的那类孤儿**：wrapper 行仍挂 running、内层全部终态、且无调度器附着——这才是该被回收的 wrapper，本 RFC 后它**第一次**因为正确的理由被回收。
4. **消除误收造成的任务级失败与伪卡死现场**。
5. **给 finalize 加第二道防线**：外部合法终态（用户取消、诊断修复）抢先时，wrapper 收敛到该终态并留痕，而不是拿 `scheduler error` 炸掉整个任务。

## 非目标

- **不改开机清扫**（`orphans.ts` `reapOrphanRuns`）。daemon 重启时全盘翻 running 行是正确的：那一刻整个进程的驱动都不存在了，无证据可言。
- **不改 `autoKill`**。它已经用 `pid IS NOT NULL` 正确圈定了自己的管辖范围（`autoKill.ts:63`），是本 RFC 想推广的正面样例。
- **不引入心跳表 / 租约表**。证据链从既有列与既有纯函数即可解析，不新增数据模型（见 design §4）。
- **不改 wrapper 的业务语义**（迭代、退出条件、merge-back、git_diff 口径一律不动）。
- **不做跨 daemon 的分布式所有权**。本仓是单进程 daemon + flock 单实例，所有权判断以进程内注册表为准即可。

## 用户故事

1. **作为跑长任务的用户**，我的 Code → Audit → Fix 工作流里 git wrapper 内层要跑十几分钟，我希望它跑完就是跑完，不会因为后台线程认为「它没有进程所以死了」而在收尾时整条任务失败。
2. **作为运维者**，当一个 wrapper 真的失去驱动（调度器协程异常消失、daemon 仍活着）时，我希望周期回收器**能**发现并回收它，而不是等到下次重启才被开机清扫捡走。
3. **作为使用诊断修复的用户**，我不希望看到系统自己伪造出来的「任务在跑但所有节点都已终态」卡死项，然后引导我去修一个不存在的问题。
4. **作为取消任务的用户**，我点了取消之后任务就应该干净地收在 `canceled`，不应该因为 wrapper 收尾撞上我的取消而变成一条 `scheduler error` 失败。
5. **作为后续 RFC 的作者**，当我新增一类 run（新 wrapper 种类、工作组回合行、动态工作流编排行）时，我希望系统**逼我回答**「它的活性证据从哪来」，而不是让它沉默地继承一个错误前提。

## 验收标准

- **AC1**：一个内层运行时间远超宽限期的 wrapper（git / loop / fanout），在周期回收器跑过任意多次之后仍保持 `running`，任务不受影响。
- **AC2**：一个失去驱动的 wrapper（内层 run 全部终态、任务不在活跃注册表中、仍挂 `running`）**会**被周期回收器翻成 `interrupted`，并记录回收审计事件。
- **AC3**：任务只要仍被本进程调度器驱动（活跃注册表命中），其任何 node_run 与任务行本身都不会被周期回收器改写。
- **AC4**：agent 行在 pre-spawn 窗口（已 mark-running、尚未写 pid）内，只要驱动存在就不被回收；驱动不存在且从未 spawn、也无子行时**被回收**（`unowned-never-spawned`）。
- **AC5**：wrapper 刚建立、内层尚无任何 run 的空窗期内，**只要驱动存在**就不被回收；驱动不存在时按残骸回收（`empty-delegation`）——瞬时空窗只发生在驱动活着的时候，驱动一旦消失就没有任何协程会再造出下层。
- **AC6**：wrapper 收尾时若发现自己已被外部合法终态（`canceled` / `interrupted`）抢先，任务按该终态收敛并留下审计痕迹，**不再**产生 `scheduler error`；其余非法转移仍然大声失败。
- **AC7**：真实的判活函数（非注入桩）被测试直接覆盖，含 pid-null、从未 spawn、pid 存活、pid 被回收复用四种输入。
- **AC8**：新增 run 类型不得沉默地继承错误前提。**定义层**的 `NodeKind` 由穷尽 switch 强制声明（缺失即 typecheck 失败）；**定义外的 synthetic 行**（commit-push 容器等）由结构规则兜底——有子行即容器、无 pid 无子行无驱动即孤儿——因此新增角色不可能落进「无法归类」的缝里。commit-push 容器行作为首个固定回归样例。
