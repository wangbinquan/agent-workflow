# RFC-484 减速带判据回到「不高于上限即过」：撤回 RFC-479 的低于即红（RFC-294 design §13.4）

- **状态**：In Progress（2026-11-11）。用户 2026-11-02「好，你继续推进RFC294，过程中你以最优架构进行自行判断不用提交给我审批」（2026-11-09
  再次下达），2026-11-10「当前RFC294的设计已经刷新，你按照最新刷新的设计，进行推进」；2026-11-11 用户转述另一会话的发现（架构门禁的说明与
  实际检查矛盾：检查器要求统计值与上限一致、减少也红，设计文档与 `counts.json` 仍写减少自动通过），要本会话判断。本会话按源码核实、判断
  并按授权记为已批准（取舍见 §6，可推翻）；不派 Codex（用户 2026-10-31）。设计门免；实现门由本会话按路径限定、只审功能地自审。
- **母 RFC**：[RFC-294](../RFC-294-backend-layered-target-architecture/proposal.md) design §13.1、§13.3、§13.4，proposal C13，plan S11。
- **修正对象**：[RFC-479](../RFC-479-governance-gap-fill/proposal.md)（Done，`0d591604b`）的 G1 后半句「低于上限即红」；RFC-479 的其余内容
  （4 项收紧、两项 public 合同计数与 composition 控制流入带、§1.2 的覆盖范围列）不变。

## 1. 背景

1. **判据与文档分成两派**。RFC-479 起，`packages/backend/tests/architecture/rfc294Gates.ts` 的 `checkCounts` 把实测低于上限与高于上限同样
   判红（`below max`）。仓内其余描述减速带判据的地方都写「不高于上限即过、下降自动通过」：`architecture/counts.json` 的 `note`、RFC-294
   design §13.1、§13.3、§13.4，plan 的退出门口径段，`status.md`，`scripts/depcheck.ts` 的头注释。只有 RFC-479 自己的三件套、RFC-294 plan 的
   S11 一行与两处 S11 段落、`docs/dev-gotchas.md` 的一条写成相等判据。
2. **§13.4 明文不采用相等判据**。2026-11-09 刷新时新增的 §13.4 写明：上限要收紧到实测，但减速带「仍按‘实测不高于上限即过’执行，不改成
   逐次相等——并发 session 各自下降同一计数时，相等判据会互相打红」。用户 2026-11-10 要求按刷新后的总纲推进；RFC-479 偏离了这一条，却没有
   列出偏离、也没有改 §13.4（本会话的疏失）。
3. **相等判据的代价落在日常改动上**。减速带 60 项里，19 项是各模块 `composition/` 的分支行数，另有按 context 分项的未消费 public 符号与
   public 类型偏差，都会随普通功能改动变化：相等判据下，删掉一个 `if` 或撤一个 public 符号的提交必须同改 `counts.json`，否则 CI 红——这与
   §13.3「普通生产改动不再需要……投影伴随提交」相反；两个会话各自减少同一项，后推的一方合并后也会红。RFC-479 以来 main 上只有本会话的
   RFC-479～482，还没有人撞上，但这是共享 main 的常态。

## 2. 目标

- **G1 判据回到 §13.4**：`checkCounts` 对实测低于上限不报错，列入 `decreases`（带应收紧到的值），减速带用例把它打印成日志；高于上限、未知
  / 缺失 id、非法数值、`reason` 里的 `max=N` 不符照旧报错。
- **G2 文档统一**：把 RFC-479 改成相等判据的几处改回 §13.4 的口径；RFC-479 三件套与 RFC 索引的 RFC-479 行注明这一句由本 RFC 撤回；
  `counts.json` 的 `note` 补上 C13（后继收口时收紧、dated review 核对）；RFC-294 design §13.4 补一句沿革。
- **G3 C13 不变**：上限 = 实测仍是后继收口的纪律，dated review 核对。本 RFC 不放宽任何计数：60 项 `max` 仍等于实测。

## 3. 非目标

- 不改任何计数的口径与 `counts.json` 的数值；不改其他门（`KNOWN` 等逐条清单本来就是双向精确门，减少条目仍须同改，不在本 RFC 范围）。
- 不改 C13、§13.5 的独立对账规则；不改生产代码。

## 4. 用户可见变化

无。开发流程上：减少了某项计数的普通提交，不再因为没改 `counts.json` 而 CI 红。

## 5. 验收标准

- **AC-1**：`checkCounts` 等于上限通过；低于上限通过并列入 `decreases`（带应收紧到的值）；高于上限、未知 / 缺失 id、非法数值、`reason`
  不符报错——单元用例正反对照。
- **AC-2**：仓内描述减速带判据的现行文字（design §1 的清单）都是「实测不高于上限即过；后继收口时收紧到实测（C13）」；RFC-479 的历史
  描述带撤回说明。
- **AC-3**：`counts.json` 60 项 `max` 仍等于实测；架构报告的门不变。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。

## 6. 已作出的取舍（用户授权本会话按推荐决定，可推翻）

1. **改判据、不改 §13.4 去追认相等判据**。§13.4 的理由在本仓的共享 main 工作方式下成立；相等判据把 C13「后继收口时收紧」的纪律扩大成
   每个会话每个提交的义务。RFC-479 担心的余量回长，由 C13（后继收口收紧所触及的项）、§13.5 的独立对账（重出报告、把计数与上限对一遍）与
   减速带用例打印的 `decreases` 日志承担。若用户更想保留相等判据，改动反过来只在文档：§13.1、§13.3、§13.4 与 `counts.json` 的 `note`
   改成相等口径。
2. **不另加「余量」报告章节**。`decreases` 日志与 dated review 的报告对比已够；需要时由 dated review 提出。
