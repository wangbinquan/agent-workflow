# RFC-371 完整候选的集中验证（2026-10-13）

按用户“先完成所有代码开发，再验证”的要求，本次将增量投影、原范围资格、历史维护与价格纠错、持久异常、原生片段与阶段、正式页面接线和回归用例收拢后进入集中验证。统计人口不设置任务、调用或记录总量上限；传输页大小不改变完整计数和 EOF。

生产查询读取已提交的贡献和可逆小时桶。7 天、30 天和精确自定义范围共用这些底层贡献，新增或修订只替换受影响组件。原始完整报告保留为独立对账来源，周期点击不启动该报告 Worker。后台版本提交后通知前台，断连有版本核对和恢复；正式耗时与真实新增后的自动刷新仍须实际验收。

后端首轮源码门为 VALID/FAIL，原回执完整保留。本次修复：断源保留只读取 contribution；小时桶保留共享原生记录的全部 scopes，筛选后重新判断资格；维护 allocations 使用原两元素 parent；预览成功、失败及外层错误均绑定 token、状态与未过期租约；周期异常采样覆盖 open tool，未知状态不能解除异常。单连接空库回归改走实际 bootstrap factory，断源回归保留已记录四桶和原 not-ready 基线。另补真实双 provider 的共享状态/时间边界 oracle、租约接管、完整记录价格纠错与持续工具超时用例。

前端首轮六项功能 findings 已在有限 R2 源码门闭合，回执为 VALID/PASS，P0/P1/P2 均为零；该结果不代签实际测试、页面性能或部署。取消交错、比较失败、历史异常复发、固定维护请求和 reportId 更新后的阶段详情分别保持原数据身份。所有原失败和预算保留。

本机 AW 只做必要静态检查。当前前端类型检查及明确路径 lint 通过。后端静态检查发现本次异常用例的字面量类型问题，已修正；另有未改动的 CLI signalCode、RFC-370 SQLite Statement/Database API 和 RFC-359 signalCode 类型诊断，需要结合确切 hosted SHA 的实际 Bun/类型版本判定，不能据本机输出宣称整仓类型通过，也不能擅自修改其他任务。
