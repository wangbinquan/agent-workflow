# RFC-371：完整报告加载性能修复

用户反馈正式运行观测页加载过慢。本片属于已批准 RFC 的性能修复，不改变统计人口、时间范围、Token 四桶、人民币费率、缺口判定或授权语义。

## 实测问题

2026-10-09 本机正式 AW 页，近七天、137 个任务、595 个尝试、446 次受理调用，完整派生报告写入 37,533 行、16,259 个分组计数和 8,326 份来源回执。第一次进入用时 29,406 ms；另一次刷新采集约 22,436 ms、发布约 11,727 ms，总计 34,163 ms。单任务报告也保留全局历史原生引用，用于判定同一原生记录的多个执行归属，不能简单删除这些引用以提速。原始实测保存在本机 `observability-aw-load-diagnosis-20261009-v1`。

已有单任务报告的状态/分页读取约 20–37 ms。这个读数只代表所测的小范围报告；另一个账号读取本次管理页报告返回 404，不能用这个 404 代签全量报告读取性能。既有数据库已含约 7.19 GB 内容，本片不删除历史报告、源记录或回执。

## 修复设计

1. `application/historicalObservationSource.ts` 在同一次原始快照内复用父任务、任务是否被选中、执行身份的读取结果，以及相同 `[referenceId,sessionId]` 的派生 root 关联。复用现有 `completeWorkingCache`，淘汰后仍可从同一个 TEMP 工作区重读；没有任务/调用数量上限。root 关联首次成功写入原 roots/root-refs/execution-roots 后才缓存，后续完全相同的三份关联免于重复写入；每个不同 reference/session 仍保存。事件遍历、step eventId/occurredAt 更新、原生 root 扫描、page/EOF/版本/回执不省略。所有缓存在后续原生归属读取前完整 flush；执行同键不同内容继续拒绝。
2. `application/completeHistoricalObservationAllocation.ts` 复用同一时区的日期格式器。首个非空日期时才构造，保留原有空数据行为、日期字符串、范围及维度匹配。
3. `infrastructure` 按原 transfer 页批量读取和写入分组计数。每页仍最多 500 个传输项，这是原传输批次而非统计人口限制。保留 page digest/ordinal/replay、root owner 锁、逐项身份校验、声明重复拒绝、任意精度十进制计数、实际数 CAS、整页事务回滚和发布时完整人口核对。批量代码只减少数据库往返，不改变每个分组最终的 `total/actual/declared`。

新增内部 staging helper 仍属于 RunObservability infrastructure；不新增 public 合同、跨 context 依赖、数据表或迁移。SQLite/PostgreSQL 共用同一实现。报告缓存族仍为 13，保留旧终态，现有授权与物理封印资格每次读取继续核对。默认范围、刷新、后台读取时的显示策略不在本片改写。

首版批量实现的正式固定范围对比为 49,237 ms：采集约 17 秒，发布约 32 秒，12 个顶层集合／31 页完整 EOF、人口、四桶、CNY 与缺口均保持。该性能结果不合格。原库只读查询计划确认，将共同 `report_id` 提到 OR 外会只使用主键的报告前缀扫描；修复将每个 OR 分支保留完整 `report_id/section/parent` 主键，继续保留各组实际数 CAS，并追加原真实 SQLite 查询计划回归。失败首测保留，修复后的耗时必须另测，不能以功能 PASS 代签性能改善。

完整主键修复后的正式生成仍为 33,496 ms，其中采集约 24 秒、发布约 9 秒；不能据此宣称总加载已解决。继续只读原库核查发现，Task 的 owner/event 共引用 44,996 次 root 边，而不同 owner/session 只有 1,793 对。追加的同快照 root 边缓存仅减少这些同键同值的 TEMP upsert，不能跳过任何原事件、owner、native page 或 receipt；新增 501 次同关联、不同关联与淘汰后重读回归。此追加设计须经有限设计门后实现，实际提速和完整人口另验。

## 验证与发布

### 原生 part 读取追加设计

root 边缓存后的完整报告仍为 29,393 ms；只读采样期间的另一完整报告为 28,585 ms，尚未解决加载慢。原报告的 2,211 个 root 回执全部读取至 EOF，1,730 个有原生 EOF，共读取 37,673 个 part、6,927 个 step 和 1,785 个 session。实际 OpenCode 文件约 2.3 GB，`part_session_idx` 只有 `session_id`，原逐条 `ORDER BY id LIMIT 1` 的查询计划含 `USE TEMP B-TREE FOR ORDER BY`，不能假定已有 `(session_id,id)` 索引。连接复用的原始 root 元数据探针仅约省 1.8 秒，不作为本批新增方案。

在同一实际文件上的只读 SQL 探针，1,730 个直接 root 的 37,113 行逐条完整投影耗时 4,594 ms；ID 分批后读取字段为 1,276 ms，两者所有字段顺序的完整摘要相同。这仅是原始数据库读法诊断，不是完整 AW 性能验收，也未省略正式读者的子会话。正式修复只缓存同一原生快照、当前 session 内下一批 part ID，最多沿用原 `pageRows` 的传输批次；每个 ID 的原字段仍在实际消费该行时单独按主键读取。这样避免未被选中的记录反复进行 JSON 投影，并保留晚到的损坏 JSON 在原消费位置报错；不提前解析整批字段。

追加改动仅落在 RuntimeManagement infrastructure 的原 `opencodeUsagePass.ts`。原 root 独立 BEGIN/COMMIT/close、TEMP 遍历树、字段表达式及顺序、数值与模型解析、session/part/step 人口、fingerprint、page byte/row 容量、ordinal、pending 重放、原 owner ACK、EOF 与异常回滚全部保持。按原 `part_after` 连续分批至 EOF，每成功处理及写回该原行的游标后才推进 ID 缓冲；空或无效 ID 不能因真假判断被跳过。字段读取必须限定原 session，找不到已选原行必须失败，不能伪装成 EOF。不修改 OpenCode 原库索引，不新增业务写入、公共接口、缓存族或全量人口上限。

新增真实原生 SQLite 回归使用实际非组合索引，覆盖跨多个批次、1,001 条以上、非数字 part、原四桶、完整树及批次/byte 边界同 fingerprint、pending ACK/重放、同快照新增不可见、空键和晚损坏 JSON 的原报错时点；现有原生 reader/worker/owner/历史共享归属回归全文和预算不改。先独立审阅追加设计，再落源码及独立实现门，真实正式完整报告再对照全部物理行与原数字并测耗时。

后续原始同范围 SQL 探针表明，严格保留逐行字段解析的 ID 批次仅为 4,343 ms，相对 4,594 ms 没有足够改善；这个追加设计未落生产代码。批量解析整批字段会提前遇到晚损坏 JSON，本片不为提速改变这个行为。原完整报告进度另测为 30,295 ms，采集约 21 秒、行发布约 5 秒、计数约 3 秒；这两项失败诊断保留。

### 原报告连接缓存追加设计

正式主连接已有 RFC-311 的 128 MiB 页缓存，而统计专用原只读连接未配置容量，仍是 SQLite 约 2 MiB 的默认页缓存。统计连接还要同时处理磁盘 TEMP 工作区里的完整历史关联、数值归属及排序。拟只在 `platform/persistence/reportSqliteSnapshot.ts` 创建的独立原文件连接、任何 TEMP 建表和 BEGIN 之前设置 main 页缓存为 64 MiB、TEMP 页缓存为 32 MiB，并显式保持 `temp_store=FILE`。容量只控制可淘汰的数据库页面工作集，所有任务、调用和派生行仍按原游标至 EOF，超过缓存容量由 SQLite 从原文件及 TEMP 重读；不是人口上限，不把全量 TEMP 搬入无限内存。

该设置仅属于这次报告的专用连接，随原 finally 关闭；不修改原数据库文件、索引、原主连接配置、WAL/synchronous、来源快照身份、原 BEGIN/COMMIT/ROLLBACK、读取合同、任何数值或公共接口。原内存部署复用主连接的分支及 PostgreSQL 分支逐字保持。实际改善另测，不以容量参数存在代签性能通过。新增真实原文件回归必须同时核对连接实际页缓存/FILE 设置、超过一批的完整 TEMP 行、四桶、原主连接配置保持、WAL 原 writer 仍可写且报告快照不见新值、关闭后 TEMP 不泄漏；旧回归全文和预算保持。

- 原历史全量、共享原生记录、恢复、四桶、零/未知、CNY、211/203 System、分页 EOF 等回归完整保留，预算不增不减。
- 增加缓存淘汰后身份冲突、重复父任务读取复用、跨页计数、同页声明/行组混合、重复声明回滚、超过安全整数的计数及原 transfer 重放回归。
- AW 不跑本机产品测试、typecheck、build、新服务或 scale CI。仅精确格式/lint、有限独立审阅及一次必要的原架构投影；功能执行由发布 SHA 的 GitHub Actions 判断。
- 正式服务采用同一固定时间/筛选，逐页至 EOF 对照原报告身份、计数、四桶、已知 CNY、缺口和每个历史版本/引用，再测生成阶段耗时。实测改善前不宣称加速已完成。
- 准确性不能靠只读部分任务、只读部分调用、略过历史歧义或把未知当零换取。本片也不代签全部 RFC、100K/10M 规模或 CS 部署完成。

### 缓存实测及分段诊断

新增连接缓存的固定范围正式报告为 26,202 ms，首个发布页约在 18,895 ms；相对原固定范围 30,045 ms 有改善，但仍不满足页面响应预期。全部 37,533 物理行（含范围外历史引用与所有版本）、16,259 分组计数逐行相同；12 顶层集合／31 页全部 EOF，137 任务／595 尝试／446 调用／198 历史引用、四桶 1,189,241／1,255,680／0／186,002、已知 CNY 4.078952 及全部原缺口保持。原 report ID 为 `25d4b0ae-bda5-448b-bdda-0b517929a845`，新 report 为 `968b35f4-1cdc-4921-9e18-83cc6343306c`。这些结果证明本片没有漏数，不能代签加载慢已完全解决。

下一步仅给明确标记的诊断报告增加内部阶段日志，以实测采集内部各段。判断条件使用既有请求的 `refreshKey` 前缀 `load-performance-`；普通页面请求不启用，不新增查询参数、公共接口、数据表、报告字段、指标或缓存族。composition 创建非抛出的 observer，使用原 `createLogger` 输出 reportId、固定阶段名、累计耗时和本段耗时，不输出原始任务内容或 Token 数字。application 内部输入只有一个可选同步 observer；在原有 await／循环边界后标记资格、任务原人口、完整 owner/event 来源、原生 root 完整读取、原 Task 汇总、历史归属、最终 fold、来源摘要和 transfer seal。不插入业务读取／写入，不跳过原行，不新增异步调度或改变异常、取消、finally 与原步骤顺序。

该诊断必须在原服务的新 Worker 内执行，再只读原服务日志获取同一 reportId 的阶段记录。observer 的时钟／日志失败只丢弃诊断，不能让统计失败；使用既有 logger，不新增 stdout 机制或全局配置。新增纯 observer 回归核对累计／分段时间、固定身份及失败不抛出；原生产语句和旧测试／预算逐字保持。有限设计与实现门另验，阶段日志不进入来源回执、sourceRevision、四桶、费用或发布封印。

### 实际阶段与分组更新追加设计

标记报告 `7ed06ac9-dd06-40da-b52a-88a1c87a80b9` 在原 Worker 的实际日志中：owner/event 1,766 ms、原生完整读取 9,372 ms、Task 构建 2,079 ms、历史分配 2,991 ms、fold 111 ms、source seal 28 ms、transfer seal 955 ms；客户端正式终态为 25,307 ms，首次发布约 18,057 ms。全部 37,533 物理行、16,259 分组计数、12 集合／31 EOF 页、四桶、CNY 和缺口仍逐项相同。这不是已解决加载慢的结论。

继续处理约七秒的正式发布阶段：当前批量计数更新仍为逐组 CASE 和长 OR，每个更新组都比较整条 CASE 链。拟只将两个既有批量 UPDATE 改为 `WITH changed(...) AS (VALUES ...) UPDATE ... FROM changed`，按完整 report_id／section／parent 主键连接，每行直接取自己的十进制文本 total／actual。只读原实际 SQLite 的 EXPLAIN 已确认，500 个 VALUES 行逐条通过完整三字段主键查找目标，不扫描本报告其它组。

原 currentGroups 读取、插入、新旧分组分配、同页重复声明检查、declared=false 资格、actual 原文本 CAS、affectedRows 必须等于完整更新人口、页级原事务与回滚、page/replay/seal、BigInt 运算和所有原公共输入输出逐字保留。VALUES 三列／四列仅装本页已有最多 500 组，不新增人口上限；SQLite 和 PostgreSQL 沿用同一 SQL 与原 provider 编译器、boolean 编码和事务句柄。不会修改源库、表、索引、调用/Token/费用或来源回执。CAST 不用于数值加法，文本计数不转数据库整数。

新增真实双 provider 回归覆盖更新已有的 500 个组：声明及实际数两种 UPDATE 的完整主键查询计划、无逐组 CASE、一次更新语句、全 1,000 行／500 组结果与原重放；原用例和预算保持。生产仅改既有 helper 的两个 UPDATE，先做独立功能设计门后实现、再实现门。实测完整报告及所有原物理记录重新对账，耗时没有实际改善则保留失败并继续定位，不以 SQL 形式存在代签提速。原生读取仍是主要待优化项，本设计不假称已闭合它。

同一已授权验收账号随后读取这个原报告：header 9.93 ms，完整 trends 集合（3 条、EOF）13.97 ms，tasks 首个显示页（100／137、具有续页游标）14.57 ms。这是相同 actor／report 的真实成功读取，不是此前另一账号的 404。这证明保留结果的读取很快，新时间范围首次生成仍慢；从最初 30,045 ms 到约 25 秒的改善不能写成加载问题已解决。人口和明细没有为提速截断，显示页大小也不构成统计上限。
