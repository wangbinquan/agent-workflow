# RFC-371: refresh without hiding a completed report

This is a usability repair within the already approved complete-observability scope. It does not replace the full-population generation path or claim that its approximately 25-second cold build is solved. The current completeReportClient performs an explicit new POST on a refresh revision, and the formal component suppresses all content whenever isFetching or building. Repeated refresh clicks can queue multiple full reports because the existing service serializes jobs.

## Intended behavior

On the first visit, keep the existing LoadingState while there is no verified report. When an explicit refresh of the same exact filter/task scope starts, retain the most recent completed report only for that same scope while the existing backend builds and validates the new report. The retained header keeps its original asOf timestamp, all original counts, four token buckets, CNY and gap qualification. Show a compact shared status notice that the displayed result is the previous completed snapshot and the new one is being generated. Replace the entire report/content and all child page identities together only when the new report has readable ready or not-ready-with-facts content. Never mix rows or totals from two report IDs.

Disable the existing Refresh action while its current request is pending/fetching/building so ordinary repeated clicks cannot add more expensive report jobs. Returning from a Task or selecting another tab can use the retained valid report while the same report header GET is in flight. Its asOf remains visible.

## Scope and invalidation

The fallback scope is exact JSON of the current capability family, unchanged filters and taskId, excluding only refresh revision. Keep one previous content object per existing hook instance, not an unbounded history or another data authority. The whole and Task hooks remain separate. A filter/time/selection/task change cannot display the previous scope. Keep existing requestKey, scope-metrics/13, backend EOF/validation, retainedIds, permission behavior, report service and page APIs unchanged. No population limit or timeout relaxation.

The hook may expose derived displayContent and refreshingPrevious in addition to its existing actual query fields. It records the last accepted content via an effect after the query has returned an already scope-checked ready or qualified not-ready result. A fetch error, failed report, or terminal not-ready without facts forbids fallback immediately and clears the previous snapshot for that scope. The existing child-page failure invalidates the parent cache to not-ready without facts; do not resurrect the earlier numeric totals through fallback or during that refetch. Do not reuse old scope-metrics/7 or /12 entries. A currently completing request always uses the same original query cache and new report ID; fallback never enters the query cache as a server response and never supplies the retained ID used to choose GET versus POST.

Keep the loading hint compact when a prior report is displayed. Use shared NoticeBanner size=compact/tone=info, existing button disabled styling and completeAsOf; add matching zh/en status text in the existing dictionary. Initial loading remains the original primitive. Summary/quality only in overview, removed CSV/filter cards, exact token bars and all drill-down/return/focus behavior stay unchanged.

## Implementation and verification

Limit production edits to completeReportClient.ts, CompleteRunObservability.tsx, the existing runObservability i18n dictionary, and a small pure display-selection helper only if needed. Add meaningful hook/component regressions in a new refresh-specific test file without changing any existing assertion, population or timeout. Cover initial pending, same-scope refresh POST+building retaining exact prior four buckets/CNY/asOf/rows, one disabled action and no duplicate POST from another click, final whole new report replacement, filter and Task isolation, same-report GET refetch, error/failed/missing-facts behavior and the original detail-failure invalidation. Preserve the existing 1001-task and 10001-call old tests unchanged; never write the old snapshot into the new query entry. Use actual deferred fetches and the existing QueryClient rather than mocked hook return values.

The implementation gate, exact source/canonical metadata publication and hosted exact-SHA CI remain mandatory. No local product tests/typecheck/build/new service or E2E will run. After hosted verification, inspect the original local formal page: old qualified numbers and timestamp must stay visible during one refresh, the refresh control must stay disabled until terminal state, new identity/timestamp replaces the prior report, and no report/job repetition is triggered. Check shared spacing, keyboard focus and 390/1440 widths. The separate native/history cold-generation bottleneck and both RFC completion remain open.

## Implementation candidate

The original QueryClient observes one disabled boolean validity entry for the displayed report ID; it contains no token, cost, row or snapshot copy and is garbage-collected when no longer observed. A retained-detail failure marks this ID false before awaiting the existing global report invalidation, including when the old server query has already been garbage-collected and the new report status GET is blocked. Only a successfully settled original, scope-checked report response qualifies its content again. The actual POST/GET query and retained IDs are not replaced by display data. During a same-ID header GET, display only the hook's already accepted snapshot, and preserve initial loading when no such snapshot is available.

The new regression file uses the existing QueryClient with gcTime=0, original hook and page request path, deferred HTTP responses and the formal component. It checks exact four buckets/CNY/time/trend retention, one disabled refresh and no duplicate POST, complete new replacement, first load, changed filter and Task isolation, same-ID GET, original-detail failure during a blocked new GET after old-cache removal, terminal failed/missing facts and HTTP errors without numerical resurrection. Existing regression files and budgets remain unchanged. These tests are authored but have not been run locally; exact-SHA hosted results and formal-page acceptance are separate pending steps.
