# 增量统计与实时查询纠正方案

2026-10-12，接续已批准的 RFC-371 §7 持久化、事件与恢复。本文纠正当前完整报告实现偏离增量投影设计的问题，不把已经接入的缓存、局部提速或已完成报告复用记为增量统计完成。

## 当前缺陷和纠正目标

当前 `calculationSourceKey` 将全部 55 个关系的 revision、原生来源证明和 Actor scope 放进同一个键；任意相关记录变化都可以使全部 Task 数值缓存和历史准备缓存失效。`completeObservationReportService` 按一次请求启动完整 Worker，周期第一次请求仍要恢复全部历史准备、重新分配、生成并落库整份报告。前台只对 building 报告轮询，ready 后没有随新用量自动更新的链路。

这不是“统计必须完整”的必要代价。完整性应由可靠源记录、提交水位、缺口和对账证明保证；日常读请求不应触发重新采集或全量重算。原始事实审计报告与交互统计查询分开：报告继续保留来源、EOF、完整归属和逐条核对能力；总览、趋势、维度和明细查询读取同一份持久增量投影。

纠正后，一个新增或修订的事实只影响它的归属组件和相关统计桶。近 7 天、近 30 天及自定义范围读取同一投影，在一个已提交版本上查询，不分别重新解析原始事实。前台随后台提交新版本自动更新；只在首次历史补齐、算法版本变化、明确修复和对账失败时重建投影。重建期间继续展示已知用量、分类 Token、人民币和缺口状态。

## 现有能力及新增落位

复用 `usageIngestion` 的唯一事件、修订顺序、迟到修订重建、累计基线、来源 cursor 与账本同事务。复用 `usageSelection` 的原生范围去重、现有冻结人民币价目版本和平台独立 valuation。不能退回仍有限制的旧 `taskObservationSnapshot`／`taskObservations` 查询；原 1,000 次调用与 10,000 条记录边界不能进入新查询路径。

新增领域规则在 run-observability/domain，增量应用和查询在 application，中立数据库／队列端口在 ports，持久实现和来源适配在 infrastructure。原 bootstrap 明确装配双数据库消费者；Task、system、memory、intent、诊断及平台来源仍通过各 owner 的 public 合同提供事实。不能在 UI 查询时读运行时文件，不能为统计创建另一份业务数据库，不能新增 routes/services 的跨域内部 import。

| 层次       | 持久内容                                                                      | 日常处理                                       |
| ---------- | ----------------------------------------------------------------------------- | ---------------------------------------------- |
| 原始事实   | 原账本、执行身份、来源记录／修订、原生步骤、平台 usage／valuation、原归属关系 | producer 按原协议提交；原水位和证据保留        |
| 待处理变更 | 稳定事实键、来源修订、受影响归属键、待处理／完成状态                          | 同源提交产生持久工作；重启继续未完成项         |
| 已应用贡献 | 该事实上一份有效贡献、四桶已知值与缺口、人民币、实际模型、归属和时间          | 比较上一贡献与最新事实，撤销旧贡献并应用新贡献 |
| 统计投影   | Task／Agent／runtime／model／purpose／source、时间桶、计数、缺口计数、索引    | 只更新受影响项，与变更完成及投影版本一起提交   |
| 查询快照   | 投影版本、asOf、精确筛选、当前可见范围、来源水位／延迟                        | 只读该版本的统计和明细；分页不选择统计总体     |

## 每笔变更的正确处理

事实身份使用原 source、canonical execution／invocation、record 与 revision。重复同值事件是 no-op；同键异值沿原冲突诊断处理。旧修订迟到先由原账本收敛，再替换该事实的贡献；不能把累计表盘读数当成新增 Token。修订导致下降、模型变化、时间或归属变化时，撤销上一贡献再应用新贡献，不能只做正数累加。

四桶各自保存已知值、覆盖计数和未知计数，金额保存原精确人民币值及其覆盖状态。缺失不是零；已知数值不会因为其它桶或费用未知而消失。所有计数及 Token 使用原任意精度整数，人民币使用原精确十进制规则，不能使用浮点 SUM 或前台加总。

原生 parent／child 的重复范围、共享步骤、多 owner 候选、accepted 与历史步骤重叠，不能孤立地对一条记录盲目增量累加。通过原生身份和归属反向索引定位受影响的范围组件，沿原去重／冲突／分配规则收敛该组件；更新其旧、新贡献。修复只影响这个组件及相关桶，不使无关 Task 和全站统计失效。无法归属的已知步骤保留原候选和缺口，不复制到每个候选任务中。

Task／尝试／受理调用计数由原生命周期事实更新，单独记录非模型任务、未受理尝试、未知尾部和确认零用量。Token 已入账、valuation 后到时只更新金额，不再次计入 Token。费率版本冻结、runtime 实际模型、CS 金额可见性继续沿原合同；新费率不重新给旧调用计价。

## 持久消费和历史补齐

变更工作与原事实提交有可靠的事务关联。进程内通知只用于唤醒；通知丢失不能丢记录。消费者处理待完成项，在一个原数据库事务里更新贡献、相关桶、变更完成状态和投影版本；事务失败全部回滚。重启、重复领取、消费者处理后尚未通知前台的崩溃都必须可重放且不重复贡献。

不能把自增 ID 的最大值当成所有并发事务已提交的水位。消费沿每个原来源的已提交顺序和完成证明推进，或使用持久待处理项及原消费者租约；不能越过未提交／失败项后把它遗忘。微批只限制一次工作量，待办及统计人口不设总上限。

首次上线先完整分页读取原事实并建立持久投影；保存可恢复的补齐进度。补齐期间的新提交进入同一持久变更链，按原修订幂等收敛，不能在历史扫描与实时消费之间留窗口。原历史 native 读取失败只留下该来源的缺口和待重试工作，不阻塞所有已知数据。历史补齐到真实 EOF 后再完成对应覆盖证明。

正常新增、修订、结束、补采和重连不能启动全站扫描。全量对账沿原审计入口单独运行，比较全部人口、归属、四桶、人民币与缺口；不在每次周期点击时运行。发现差异必须保留失败证据并修复，不把缓存或投影数字称为未经对账的完整结果。

## 范围、过滤及稳定分页

保留两种已有时间口径：Task 创建时间选择任务并读取任务全程消耗；实际消耗时间选择用量发生时刻。两者分别建立索引和时间投影，不能共用一个错误的 day 字段。缺发生时间的事实保留时间未分配状态，不用采集时间代替。

时间桶用于加速完整区间；精确 from/to 的边界仍从已持久的贡献索引读取，按原半开区间计算，不能只用日桶近似用户范围。时区、夏令时、自定义边界和历史迟到值都必须与原全量 oracle 一致。Agent、runtime、model、purpose、source、仓库和任务筛选遵循原维度语义，共享候选的筛选不确定性继续保留。

一次查询选择一个已提交的投影版本和 asOf。汇总、趋势、列表及后续分页绑定该版本；后台更新时不能让第一页与第二页来自不同人口。使用版本化投影行／贡献可见区间或等价的持久快照合同，不能为了固定分页在每次点击周期时复制全量事实。新版本发布后前台整体切换汇总和当前页；已有任务／泳道下钻保持原范围和返回位置。

当前 Actor 的可见 Task 范围仍由原 owner 查询合同决定，聚合不能先取全站数字再由前台隐藏。权限、名称和资源关联变化按受影响关系更新查询资格与显示；不把所有数字缓存全局清空作为普通变化的处理方式。新查询没有最大任务数、最大调用数、最大记录数或隐含截断；I/O 页大小只控制传输，所有相关统计和明细均可到真实 EOF。

## 前台自动更新

后台在投影提交后发布最小 revision／invalidation，前台通过既有 WS hook 模式合并高频通知，查询当前已提交的新版本。WS 不传未经提交的用量、不承担账本可靠性。断连按小响应的版本接口轮询并恢复；没有新版本时不生成报告、不重算统计、不重复传全部明细。后台页面降频，返回前台时立即核对版本。

更新期间显示上一份已核对的结果及其 asOf；新版本完整响应后整体替换，不闪空白、不伪造滚动 Token。周期切换保持同一比较截止时间，手工刷新或自动追新明确推进它。总览和各页签共用已提交版本，Task 下钻沿已有稳定句柄。运行时只在上游实际提供用量并持久提交后更新，不能承诺模型尚未上报时逐 token 显示。

AW 独立部署消费本地全部来源；CS 部署消费平台提交的用量及授权人民币，断连保留已入账事实和可见延迟，不切换本地计费。CS 项目级与系统管理级读取同一平台投影，按项目和当前授权范围查询，不各建重复账本。

## 实施和退出判据

1. 先修当前已发布的 source projection descriptor 与 trace receipt CI 错误，保留原失败、原断言和预算；当前周期截止时间修复和历史缓存只作为已知过渡状态，不称为最终性能方案。
2. 落地贡献替换、受影响范围索引、持久变更消费和可恢复历史补齐。为 SQLite／PostgreSQL 保留同一领域规则及真实事务回归。
3. 接通完整范围与维度查询、版本化明细和前台 revision 更新。原完整审计报告保留为对账 oracle，普通界面查询不再触发它。
4. 在原服务实际增加一笔标记用量、重复上报、修订和迟到估值，核对只更新受影响范围、无重复计数、四桶／人民币／缺口一致，页面无需手动刷新即可显示新版本。
5. 真实测量首次历史补齐、7 天／30 天／自定义范围切换、前台自动更新和断线恢复；核对所有统计与全部实际明细 EOF。测试在确切提交的 hosted CI 执行，不恢复已停止的 observability-scale，不以减少人口或跳过用例取得性能结果。

核心回归必须证明：一笔新增不能重新读取无关任务或全库 native 文件；重复 no-op；下降修订撤旧加新；共享原生范围不重复；四桶含零／未知和超过 JS 安全整数；独立、平台 usage／valuation 不重计；中途崩溃和重启续跑；补齐与实时并发无遗漏；范围和时区边界；稳定多页版本；完整旧 oracle 精确对拍；前台新增后自动更新及周期切换不启动完整报告 Worker。

本文是当前实施依据。增量链路、双引擎迁移、版本化查询、日桶与周期复用、前台通知和回归用例已形成开发候选，进入集中验证；尚未证明正确性、远端 CI、部署或实际耗时。两个 RFC 保持 In Progress，不把方案文件、门检视、已有正数用量或局部提速替代真实验收。
