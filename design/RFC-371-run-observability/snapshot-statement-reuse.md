# RFC-371：原完整报表 SQLite 工作区复用编译语句

2026-10-11。此方案延续原完整统计、原数据库快照和私有 TEMP 工作区。固定时间范围的原页面范围有 137 个任务、595 个执行尝试、446 次调用，最新原 API 构建封存仍约 10.9 秒；缓存再次打开快，不代表首次构建性能达标。

## 实际问题和范围

`reportSqliteSnapshot.ts` 的 `workspaceFor` 每次 `all/run` 都调用原 SQLite 句柄的 `query(statement)`。当前原环境 Bun 1.3.13 的 `src/js/bun/sqlite.ts` 只缓存最先出现的 20 种 SQL。报表在工作区查询前已有身份、原来源和初始化查询，因此工作区固定 SQL 可能在数万次执行中重复准备。最近完整原报告记录 `workspace.get` 64,812 次、`put` 60,391 次、`page` 62,023 次；不能减少这些调用所覆盖的人口或删掉来源凭据来缩短时间。

改动只限原 SQLite 快照的 `workspaceFor`。复用当前私有 `ReportWorkingStatements` 和实际 Bun `Statement`，不建立新数据库、镜像、服务、worker、快照、备份或测试环境。PostgreSQL 工作区及原来源只读代理保持原协议。

## 实现

为每次 `workspaceFor` 创建私有 `Map<完整 SQL 文本, 原 Statement>`。首次请求调用相同 `sqlite.query`，成功返回后才缓存；后续 `all/run` 仍执行原 Statement 的同名方法，并逐次绑定当次完整参数。缓存仅保存编译语句，不能保存行、JSON、错误、人口、EOF、任务归属、Token 或价格。

Map 与原快照句柄同寿命，不能跨快照、跨报告、跨数据库文件或代际复用。快照原 `COMMIT`、`ROLLBACK`、`sqlite.close()` 顺序保留；工作区的 `active()`、信号检查、参数校验、批大小、JSON 编解码、键排序和完整翻页继续由原 `privateReportWorkspace` 执行。准备失败不入缓存，执行失败由原路径抛出，不重试、不吞掉错误。该工作区 SQL 只包含既有的固定关系与有界批参数形态，人口增长只增加执行次数。

## 验证和验收

复用现有真实 SQLite 报表快照测试，增加一个回归：同一快照重复读写两套不同参数且经过 20 种其他原语句后，工作区准备次数只随 SQL 形态变化，执行次数继续增加；字段、当前绑定、EOF、写后读和下一快照的真实值符合原接口。保留原测试正文、数值和预算，不运行本机测试/类型检查/构建，交由 hosted CI。

实现须经独立功能门检视。原 API 采用同一固定时间范围复测，并从同一个只读原库快照逐条比较全部报告行、计数、原生原始凭据和实际 API EOF。只有完整事实相同，且真实首次读取耗时下降，才能报告性能改善；内部复用完成不能代签页面达标。
