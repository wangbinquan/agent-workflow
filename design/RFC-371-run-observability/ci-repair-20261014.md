# RFC-371 CI 修复候选（2026-10-14）

原完整实现已在 `651f956dfcb1be90f6a1d9d6086f9139f2215e53` 上库。该提交主 CI `38429501809` 为 21 success / 49 failure / 2 cancelled；Windows 平台、视觉定时和 maintenance 定时也失败。原失败日志保留，不把静态通过或后继 CI 追记为旧提交通过。

这轮修复保留完整统计、四类 Token、CNY、原始事实及全部数值对照，没有增加任务或调用人口限制。已采集记录在调用登记为零时也要显示；缺口列表按事实集合排序，避免组件到达顺序改变同一报告。原始 allocator 与增量路径使用相同 occurrence 注解，数值人口仍按原 cohort/半开时间窗选择；历史-only 夹具只清理零记录 helper 合成的孤立 capture，实际 native WAL、owner、EOF 和每个数值比较保留。索引分页及时窗夹具明确声明原 request scope，不以收据时间补造消费时刻。

容量读取改为 ORM 原 named-row `all()[0]`，不把 raw `get()` 的 tuple 当对象。PostgreSQL 维护预览及旧视图保护改用既有 nested string JSON 能力，公平 GC 的原游标仍分包推进。完整 JSON 数组提取落在 platform persistence，数据库 provider 类型只从标准 tuple 派生；每份原生渲染有穷尽性 sink，feature 不再分叉。原迁移单语句检查改为区分 CASE END 和 trigger END，保留额外语句拒绝及回归。

页面修复同窗刷新保留已核对数据、正确的权限 fixture 和 searchbox role、标准样式/i18n/overlay 登记，以及真实列表尚未恢复足够高度/原维度触发器时保留返回位置。回到任务/模型贡献后的焦点、主页面/弹窗滚动断言不放宽。新增 storage 卡也参加原两种宽度的对齐验收。设置页 Linux 视觉基线来自该 exact-SHA hosted CI 的完整 actual PNG；只反映已批准的费用观测字号统一，原基线字节与该 CI 的 expected PNG 相同，没有重绘、裁剪、改阈值或更新其他页面/OS。

## 定时性能失败的具体归因与修复

`38429502007` 的原 100k Task / 3m node_run / 10m event 数据下，control/maintenance 的 event-loop gap 为 707.2/768.5ms，原阈值 500ms。随报告保存的 daemon 原日志直接显示存储状态 `SELECT count/min FROM observation_projection_changes WHERE completed=false` 在主线程耗时 659–691ms；同一时点出现 loop-stalled。现在三项原完整 backlog/lease 计数通过既有能力矩阵选择原 provider：物理 SQLite 在已有只读 capacity Worker 内用同一个原快照读取，PG 原连接通过单条 SQL 异步读取同一原事实快照，避免 source 转入 work 时跨快照重复计数。并发读只共享正在执行的同一次读，结束后下一读重新获取当前事实，取消归原生命周期；不使用持久旧结果或人口上限。新回归保留 10,001 原 pending 行、17 个未完成 work、两个 lease、真实 heartbeat、原数据未改变、失效/取消明确失败，以及超过 IEEE754 的十进制累计。原 500ms/1s/SQL/并发/数据规模条件全部保持，修复是否通过仍由新 exact-SHA hosted 定时 CI 判定。
