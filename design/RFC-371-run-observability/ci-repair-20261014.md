## 定时性能失败的具体归因与修复

`38429502007` 的原 100k Task / 3m node_run / 10m event 数据下，control/maintenance 的 event-loop gap 为 707.2/768.5ms，原阈值 500ms。随报告保存的 daemon 原日志直接显示存储状态 `SELECT count/min FROM observation_projection_changes WHERE completed=false` 在主线程耗时 659–691ms；同一时点出现 loop-stalled。现在三项原完整 backlog/lease 计数通过既有能力矩阵选择原 provider：物理 SQLite 在已有只读 capacity Worker 内用同一个原快照读取，PG 原连接通过单条 SQL 异步读取同一原事实快照，避免 source 转入 work 时跨快照重复计数。并发读只共享正在执行的同一次读，结束后下一读重新获取当前事实，取消归原生命周期；不使用持久旧结果或人口上限。新回归保留 10,001 原 pending 行、17 个未完成 work、两个 lease、真实 heartbeat、原数据未改变、失效/取消明确失败，以及超过 IEEE754 的十进制累计。原 500ms/1s/SQL/并发/数据规模条件全部保持，修复是否通过仍由新 exact-SHA hosted 定时 CI 判定。
