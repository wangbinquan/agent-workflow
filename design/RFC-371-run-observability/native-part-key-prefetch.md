# RFC-371：完整历史统计的原生记录键预读

本修复继续已批准的完整统计与加载提速。`opencodeUsagePass.ts` 当前在同一只读 SQLite 快照里按每个 part 的会话和游标重新执行范围查询；在原报告的 1,730 个根、37,113 条直接原始记录上，范围查询诊断耗时 4,503.93ms。预读原有排序中的最多 200 个 ID、再逐条按原主键取原数值字段，诊断耗时 1,423.89ms；全部原字段摘要、37,113 行、8,717 个消息精确一致。这是原库只读 SQL 诊断，不是产品协议、完整后代或正式报告提速的验收。

修改限定 runtime-management/infrastructure 的原生 SQLite reader，复用既有只读连接、BEGIN、原队列、原消息字段缓存和原 ACK。一次只缓存同会话中不超过剩余扫描包大小且最多 200 个 part ID；200 是可重复读取的内部传输块，绝不是任务、调用、记录或树深总量上限。继续按原 `WHERE session_id=? AND id>? ORDER BY id` 的数据库顺序取得下一块，首块不加入空游标下界；不新建索引、不添加或改变 collation、不以 JavaScript 排序或比较 ID。

只预读 ID，不预读 Token、模型或正文。原范围 SQL 的 JSON 投影可能在排序前求值；物理在前、ID 在后的坏 JSON 也可能令本次查询失败。不能把这种失败延迟到 ID 真正轮到消费时。每个会话首次扫描 part 前，在同一快照用只返回资格标量的 `json_valid` 查询，检查该会话的所有 part.data 及沿原消息关联的 message.data。仅当全部都是有效 JSON 时采用键预读；任何无效、NULL 或不能确定的 JSON 都让整个会话继续执行原字段范围 SQL，保持原排序计划、错误和已可 ACK 页前缀。资格查询不调用 json_extract，不输出原正文，不推进原游标、计数、指纹或 ACK；缺失消息按原 NULL 字段语义允许。它只能选择读取方式，不能筛掉记录或制造 EOF。

合格会话中，每个 part 轮到扫描时才以原主键和会话执行原字段投影及原消息关联，保留原一行 `LIMIT 1`。模型缓存仍反映当前逐条消费时的原 TEMP 状态。空或 NULL 键仍执行原字段范围查询并由原判据拒绝，不能默默过滤后封为完整。不合格会话中的所有查询、错误和逐条状态继续使用原路径，不部分切换。

ID 缓存属于本次原 reader。会话改变时重取，已消费块结束时以原 part_after 继续；只有原行已进入指纹、原计数和原 TEMP 游标后才移动内部位置。若数值行会超过原 pageBytes，保持该 ID 未消费，下一包重新读取同一原行。待 ACK 的包仍返回同一冻结字节，不能用缓存预读推进 cursor、counts、ordinal、digest 或 EOF。每个根仍独立 BEGIN/COMMIT，物理连接复用不会复用任何 ID 缓存。

原数据库快照绑定保证预读后到逐行读取之间原表不变。读取语义必须由真实 SQLite 验证，包括 BINARY 与 NOCASE 主键/会话、消息跨会话、无消息、空键、坏 JSON、大小超过包的行、混合 start/finish、后代遍历和报告内多个根。所有原字段、四桶、模型、发生时间、原累计指纹、人口计数和缺口逐项保持；不修补或推断历史缺口，不改人民币估值和统计范围。

实施前独立设计门；实施后独立功能门、原架构配套和精确 SHA hosted CI。新增回归使用真实只读 SQLite、独立原单行范围 SQL 作为对照，验证完整原分页/ACK/EOF 以及坏记录时原范围查询的失败前缀。包括同会话物理插入 b坏/a好 的逆序 part、相同逆序的坏关联 message，以及先 ACK 合法记录后原查询才遇到坏记录的情况，逐项比较错误前可持久页、四桶、计数和指纹。旧 60,002 条 part、10,001 steps、1,025 sessions、80 层深度、Worker 和连接复用回归全文和预算保持。运行只在 GitHub Actions；本机不运行 AW tests/typecheck/build/services/E2E。

正式验收仍须用产品报告重新计时，读取所有顶层与明细页到实际 EOF，并核对相同范围的 137 tasks、595 attempts、446 invocations、198 historical references、原每条身份、四桶和冻结 CNY。完整新范围首次构建耗时与已有报告首屏分别记录；不能把 SQL 诊断或旧报告快速显示代签为首次构建成功。
