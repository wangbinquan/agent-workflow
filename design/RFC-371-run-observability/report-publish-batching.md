# RFC-371 完整报告分批发布

状态：实现设计，处于用户已批准的完整观测实施范围。2026-10-10。

## 原始证据

同一个明确标记的本机验收任务 `01M4D92W7EEGXHNGX69628DZFV`，报告 `da68192e-5c3c-407a-aae8-6bdc1d29e9b5` 完成耗时 18,297 ms。四类 Token 和人民币估值与上一份报告的完整 summary 相同：输入 30,636、缓存读取 42,496、缓存写入 0、输出 2,746，总计 75,878，估值 ¥0.104488。

原始后端阶段日志显示：所有者及事件收集 1,953.31 ms，历史原生用量收集 7,204.71 ms，历史分配 2,542.89 ms，传输封存 594.67 ms。原始快照创建至传输封存约 12.49 秒；传输封存日志时间为 04:30:24.049 UTC，终态数据库更新时间为 04:30:29.499 UTC，相差约 5.45 秒。快照建立前仅 355 ms，不能把这段落库耗时误报为 Worker 启动开销。

对原库只读核对，报告保留 31,826 条派生行、14,997 个分组计数、7,798 份来源收据和 110 个原始传输页。当前服务逐页调用 `store.stage`，每个传输页开启一个写事务，最后独立发布摘要。历史关联证据也属于报告，不能通过丢弃这些记录提速。

另一个只读 SQL 研究对全部 49,527 条原始 part 投影进行了正反顺序核对。逐条读取耗时 2,623.49 / 3,153.30 ms，连续键批量读取耗时 1,359.22 / 2,302.87 ms；全部原始字段、顺序和 9,321 个 step-finish 的投影哈希相同。该研究尚未实施，也没有证明完整报告或异常前缀协议已通过验收。本次先落地报告发布事务合并。

## 设计

- 保留原始 500 项传输页、页 ordinal、previousDigest、digest、行 ordinal 和收据，不修改来源选择、时间范围、归属分配、分类 Token 或人民币计算。
- 缓存端口增加 `stageBatch(id, owner, pages)`。原始 `stage` 保留，单页入口和批量入口共用同一页处理函数；不复制页校验和计数逻辑。
- 每次批量入口在一个原始数据库事务中，按传入顺序处理每页。每页仍读取本事务内的当前 progress，维持原始重放、声明、分组计数和更新逻辑。中途任何页失败，整批回滚，之前已完成的批次保持原样。
- 服务从原始封存 spool 连续读取，累计 8 页后提交，原始 EOF 正常校验后提交最后不足 8 页的批次。8 只约束单次事务持有的传输页数，不限制任务、调用、记录、总页数或统计范围；消费所有页直到原始 EOF。
- 原始 manifest 的最后校验仍由 spool 完成。服务必须确认原始遍历正常结束才发布摘要；丢页、错误顺序、错误计数、异常和取消沿原始失败路径处理。
- SQLite 和 PostgreSQL 使用同一事务端口，原始 Worker 读快照和来源收据语义保持不变。最多在内存持有 8 个现有传输页，不建立全量内存集合。

## 实施与验收

1. 完成有限范围的独立功能设计检视，随后修改端口、服务及缓存实现。
2. 单页实现提取为同一事务内的页处理函数。既有单页重放、重复声明、任意精度和 500 分组测试全部保留。
3. 增加两个数据库提供者的多页原子性验收：跨页计数与收据、整批及部分重放、后页错误整批回滚、成功重试与 EOF 后尾批提交。统计总量必须跨过 8 页边界。
4. 使用已授权的同一标记任务重新构建完整报告，比对原始 summary、全部页、分组计数、派生行和收据，并记录实际耗时。只读 SQL 研究的耗时不能代替正式报告验收。
5. 本机不运行 AW 产品测试、类型检查、构建或新服务。静态格式与 lint 可检查；产品回归以远端精确提交的 CI 为准。原有页面保留报告的约 0.7 秒重开结果与本次重算性能分别记录。

本设计不代表首次构建性能、全类型真实任务验收、大规模验收、CS 发布或整体 RFC 已完成。
