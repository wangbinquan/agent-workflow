# RFC-371 历史原生消息检查的重复解析优化

这是已批准 RFC-371 完整实施中的只读性能研究，资格查询改写尚未实施。首次构建和手动刷新仍执行完整扫描，任务范围、调用范围、价格、归属、分页和页面展示合同保持。

## 问题与原库取证

原工作组验收报告的历史读取阶段耗时 5,607.76ms，其中原游标 `next` 累计 4,442.03ms。原读者在每个会话进入点检查片段及消息 JSON；它按片段关联消息，因此同一消息有多个片段时重复解析同一消息正文。此次只处理这个重复解析点。

2026-10-10 对原 OpenCode 数据库使用同一只读事务检查全部 2,743 个会话、13,030 条消息、49,527 个片段。先运行原资格查询累计 2,093.72ms，再将消息资格按消息检查一次、仅纳入实际被该会话片段引用的消息，累计 399.39ms。反向顺序诊断中，先运行候选查询为 1,967.22ms，随后原查询为 419.29ms；两种顺序的全部会话资格结果分别相等。

首次查询冷读与后续缓存预热主导了上述差值，未证实查询改写带来提速。因此这项候选保留为未实施研究，继续定位原完整读取与构建的实际耗时。原完整构建 14,819ms 和总览刷新 17,573ms 保留，不将只读 SQL 的差值当作整页收益。

## 技术设计与功能等价条件

遵循 RFC-294 的模块及层次合同，改动仅在 `runtime-management/infrastructure/opencodeUsagePass.ts` 的原数据库资格查询，继续实现原 native usage pass 端口。`run-observability` 不读取外域表，不增加公共接口、持久表、来源缓存、后台进程或新的扫描实现。

原条件为：当前会话存在坏 JSON 片段，或存在被当前片段关联且 JSON 无效的消息。改为两个 `UNION ALL` 分支，最终 `LIMIT 1` 仅判断是否存在异常：第一个分支检查当前会话的全部片段；第二个分支检查同一会话的消息，用 `EXISTS` 保留原片段的 `message_id` 与 `session_id` 关联。未被任何片段引用的消息不参与资格，缺失消息保留原语义；NULL 或不匹配的关联不会变成有效关联。这个存在性结果不限制原扫描人口。

只替换上述资格 SQL。原片段数值和模型投影、按原 ID 排序的范围与点读、坏 JSON 时的原范围回退、错误位置、四桶转换、指纹、每页 ACK、原事务和连接释放保持。资格查询失败仍进入原回退，不捕获或吞掉后续原读取错误。不能通过“消息检查一次”合并同一消息的多条消耗记录。

## 后续采用条件与验收

只有原完整报告的实际分析确认收益后，才考虑采用资格查询改写。采用前完成有限设计功能检视；在现有真实 SQLite native pass 测试中覆盖同一消息多片段的全部四桶、模型、片段数和 EOF，以及共享消息 JSON 损坏仍拒绝完整结果的回归。全部现有大人口、深树、NULL、未知数值、坏原件、冻结快照、分页和取消断言及预算保留。执行结果以发布提交的 GitHub CI 为准，本机不运行产品测试、类型检查、构建或 E2E。

实现检视后，按原规则核对当前候选的完整架构配套，精确提交远端。用原本机后端和已授权验收身份重建同范围报告，核对全部来源页、分组、收据、数值、分类 Token、人民币和缺口；时间字段按各自 `asOf` 核对。记录整页用时与阶段用时，不将上述只读查询差值直接记作页面收益。首次构建、全类型任务、规模验收及 CS 发布部署继续按各自实际证据验收。
