# RFC-371 长稳存储补正（2026-10-13）

用户已批准 AW / CS 同步补齐长稳缺口、完整保留统计事实、不设任务或调用总量限制，全部实现和用例写完后集中验证，再提交远端并部署 CS。本文件补充既有 RFC，不创建替代统计口径。

## 不变量与数据生命周期

1. 原始用量、原生采集证据、计价依据和审计事实不受自动回收影响；小时/日汇总以及当前贡献完整保留。分页、事务批量、维护时间片只控制一次工作量，所有任务最终遍历到 EOF。
2. 页面报告是可重建派生缓存。相同主体、权限范围、筛选和已发布版本复用同一报告；读取、分页和维护引用保护版本。普通报告闲置 7 天后可释放其派生行，活跃访问续期；这不改变任意历史日期的完整查询。过期链接明确恢复到同一筛选范围的新完整快照，不能把新旧分页混用。
3. 无租约的旧缓存先获得完整 7 天迁移宽限期。回收只有白名单派生表写权限；不得通过通用表名参数删除事实。报告、范围成员、历史版本必须按同一个提交的引用集合决定可回收性。
4. AW 历史保留当前版本、每个有效报告和未完成准备工作实际引用的版本，以及包含这些水位的历史区间。旧报告不会保留其后所有无引用的中间变更；只回收无任何受保护水位的闭合区间。范围引用绑定报告，孤立范围可重建。维护中的原报告及其原版本不因闲置回收。
5. CS 对每个任务/role/key 保留当前版本和每个有效 report/maintenance 水位所需的历史锚点；可先采用最早水位加一个锚点的保守保留。缓存版本保留当前、报告引用、维护引用；准备中的源工作不得被误删。全部读取/发布与回收使用已有数据库事务和报告准入锁。
6. 回收分小事务、可中断、可重放；确认完成的派生源通知可归并，但原始事件、证据、价格审计不删。失败保留工作和错误，成功提交后才推进恢复游标。

## 容量与运行状态

管理端显示数据库/统计表及索引占用、可复用空间（引擎支持时）、事实与派生数据占比、增长率、最近回收结果、积压和最旧等待时间。只在真正获得承载数据库的卷容量后计算剩余天数；远程数据库不能拿应用宿主空闲磁盘冒充数据库空间，未知显示未采集。

容量采样按小时覆盖写入；历史以日汇总保留，不随页面刷新制造样本。容量压力和投影积压进入已有异常呈现，不替换任何已知 Token / CNY 数字。磁盘/数据库失败不得 ACK 未落盘事实、清空队列或显示完整；恢复后沿原持久身份重放去重。可扩容的存储及备份是无限新增事实的必要运行条件，系统不能用删除事实模拟无限容量。

## 设计门 R1 闭合补充

- AW 水位为 7 时必须保留版本 3 写入、12 结束的 `[3,12)` 历史行及 membership。仅删除 `toRevision` 非空、且不包含任何当前/报告/未完成准备水位的闭合区间；CS 每键锚点包含 `document=NULL` 删除标记。当前行不受回收影响，仍被引用的较新版本同样保留。
- AW 报告选择/登记/续期/退役共用数据库事务级 lifecycle advisory lock；登记时复核目标版本仍存在，已回收便在锁内改选当前完整版本，再计算请求键。GC 同锁原子重核到期和维护引用，将租约改为 `retiring`、释放可复用请求键后提交，再分批释放派生行。新请求生成新随机报告 ID；旧 ID 永不复活。范围成员登记也在该协议下，并持久关联引用它的报告。
- CS 回收取得已有报告准入的独占锁，正常读取/发布持共享锁。GC 同事务更新独立 lifecycle guard 代次；固定报告 REPEATABLE READ 在登记引用前锁读此 guard，若其快照跨过回收提交则发生可重试的序列化冲突，重新整笔选快照，不保留旧快照中的幽灵行。租约续期与退役共用准入锁，退役后不能续期；引用删除分包，当前任务及正在执行的维护水位和删除锚点继续受保护。
- 回收退役的是可重建报告缓存；页面遇到过期报告明确回到原筛选建立新报告，并清除旧分页游标。旧错误与新快照不能混合，既有事实与费用始终不删。
- CS 提交通知归并采用同一事务 `DELETE RETURNING` 的确切行数增加持久 clock；保留总 revision 恒等，不使用 `MAX(sequence)` 代替已提交人口，迟交事务仍计入。

## 实现记录（验证前候选）

- AW 使用独立 `observation_work_retention` 表记录准备工作水位和等待时间，兼容已部署迁移，不改写已发布表结构。投影水位只读取统计头，维护排序编号不参与保留判断。
- CS 的报告任务快照按数据库 JSONB 的规范字节计算 SHA-256，共享不可变文档；报告只保存引用。摘要碰撞写入由数据库不可变约束拒绝，原报告内容完整性验证继续使用既有语义摘要。
- 两套独立维护 worker 失败即记录错误与异常，数据库不可写时保留源队列并等待恢复；采样每小时一次、一天一行。异常历史只写状态变化，避免稳定异常每分钟制造重复历史。
- 新增真实数据库用例覆盖超过多个处理批次的人口、原始事实逐项保留、续期与退役交错、CS 序列化快照重选、迟交提交通知、迁移宽限、回滚恢复及页面过期链接恢复。处理批次不是任务/调用总数限制。

## 2026-10-13 本机慢 SQL 修复

本机实际 `[db-slow]` 日志确认，两条逐工作项重复执行的查询耗时约 180～330 ms，CPU 接近墙钟：旧贡献的 join 被 SQLite 优化为按 `kind` 扫描全部当前贡献；任务元数据按 `kind/section/task_id` 查询缺少匹配索引。另有描述元数据回收按 `key` 反查，漏掉联合主键第一列 `kind`，对每个候选重复扫描历史索引。

- 旧贡献读取以持久工作项的组件表为 CROSS JOIN 外侧，通过 `(work_id,component)` 和 `(kind,component,key)` 定位，保持原合并分配器要求的全局 key 顺序、分页至 EOF、全部组件及迟到修订。
- SQLite 0252 / PostgreSQL 0028 只追加两个当前投影索引：任务定位 `(kind,section,task_id,key)` 与采样定位 `(kind,section,key)`，不改既有迁移或事实。
- 描述元数据反查显式覆盖 contribution / aggregate 两类，通过已有主键精确定位；其余孤立范围、版本和完成工作采用持久有序扫描游标，避免每轮重扫不能删除的活跃前缀。
- 维护无清理成果或失败时退避一分钟；有成果时至少等待一秒及本轮执行耗时的 19 倍。该调度只控制派生回收，不延迟原始用量采集或限制统计人口。慢 SQL 的原阈值、SQL 裁剪和 CPU 字段保持，并通过有轮转上限的 daemon logger 持久化，便于直接诊断。
- 本机同一只读候选页：描述项检查 500 行从 1793.37 ms 到 0.96 ms；同一工作项旧贡献 31 行从 3267.67 ms 到 0.92 ms，返回身份和顺序一致。此为真实库上的只读 SQL 对照，不等同于整个服务、全部 SQL、CI 或页面均验收通过。

回归覆盖真实执行 SQL 的索引计划、211 个组件 / 621 条贡献跨页全量有序读取、超过 1000 条存活描述项后的孤立项回收、旧版本保护、失败退避、默认慢 SQL 文件日志。用例随实现完成，AW 功能验证仍由 hosted CI 执行。原 R1/R2 功能门仅覆盖其冻结候选，本补修另行检视；CS 同步维护调度修复。

## 容量采样的主线程阻塞修正

原本机日志在 2026-10-13 06:40:59 UTC 记录容量 `dbstat` 查询 107,325 ms，紧邻事件循环停顿 107,391 ms。表空间统计是本轮新增能力，原实现错误地在服务同步 SQLite 连接执行全 B-tree 遍历；它与 Token 原始事实读取无关，却阻塞所有 HTTP/WS 请求。

修正把物理表/索引容量遍历移到独立只读 Worker，并使用 SQLite 原生 `aggregate` 模式；总库页数、可复用页数、WAL 和承载卷空闲量仍用轻量元数据读取。遍历保留每张表、每个索引，不加数量限制。Worker 错误或不支持 `dbstat` 时，容量分项保持未采集，已得到的总量继续显示；禁止退回服务主线程扫描。停止/失权取消容量 Worker，且不把正常取消记作存储故障。发布单二进制明确包含新增 Worker 入口；测试覆盖全表/索引字节相等、源事实不变、主循环继续运行、只读失败不建库、取消和编译入口。

同一原大库的新只读诊断仍需 125,465 ms，因此不宣称物理扫描本身已经变快；实际返回全部 276 表、22,664,904,704 字节，其中索引 6,960,963,584 字节。期间调用方计时器执行 2,469 次、最大间隔 95.26 ms，证明本次遍历没有再把调用方事件循环阻塞两分钟。诊断进程还报告 Bun 的 tsconfig directory mismatch，原日志保留，正常启动路径及 hosted Worker 用例继续验收。原 50 ms 慢 SQL 阈值和真实 CPU/SQL 保留；后台耗时仍会被记录，不能通过屏蔽日志假装性能通过。

历史分页另追加 SQLite 0253 / PostgreSQL 0029 的 `(kind,section,key)` 与 `(kind,section,parent,key)` seek 索引。同一版本、同一 200 条结果摘要一致，原访问路径 118.32 ms，修正真实 SQL 9.38 ms。已提交贡献但仍等待来源补证的工作不再钉住无关旧历史；尚未应用的准备水位、活跃报告和维护引用继续保护。维护区分扫描进度与回收数，受保护大前缀可推进，真正空轮及失败仍退避一分钟。

## 持续活跃的旧报告：按实际引用回收

原保守的最早水位策略会让长期打开的旧报告保留其后全部派生版本，即使这些中间版本没有任何引用。AW 改为在原同一生命周期事务里逐个检查受保护水位：当前头、未退役报告、尚未完成且尚未应用的准备工作。历史与 membership 只保留覆盖其中至少一个水位的半开区间；版本和两代索引收据按实际引用存续。任意精度的十进制 revision 继续用长度和文本顺序比较，不转机器整数。当前开放区间、原始事实和既有续期/退役/维护保护协议保持。

新增双引擎回归覆盖 4,804 条历史与 membership、多次游标绕回、持续访问的旧报告、另一个未完成工作水位、完成工作后回收、报告到期后回收，以及超出64位的水位。逐轮核对所有保留行的完整四桶/人民币文档、版本和两代索引身份、原211条实际用量文档；不改原断言或预算。本追加代码和用例先写齐，静态 SOURCE 和 hosted CI 分别核对；不把这段实现说明当作运行验收通过。

有限 SOURCE R40 为 VALID/FAIL（P2 一项，旧回执保持）：pending 报告的 status 先读版本12，随后 head=13并回收12时，原 activate 会在锁内绑定过期的12。后继修正让 activate 在同一生命周期锁内重核选中版本；尚未绑定且版本已回收时选择当前头，当前头不存在则保持原 pending 并明确 not-ready。已经绑定的报告仍返回原版本，不能重写为新报告。新增真实数据库选择→推进→回收→激活交错，并核对真实租约、原活跃报告和缺头失败的回滚。

若当前头仍未完成 bootstrap，retain 与 activate 的回退继续保留水位0的 pending，等后续完整头出现才绑定；避免永久绑定到未完成版本。交错用例还核对未完成13→完整14、新请求相同数据代次和原过滤条件不变。

保护集合用共享 SQL 的 MATERIALIZED CTE 每个 DELETE 只构造一次，并去除重复水位；避免对候选行逐条重读全部租约/工作关系。只把 MATERIALIZED 识别为 CTE 语法，原SQL函数闭集、provider守卫、500行调度包和全部原测试保持。数值统计仍完整，与运输包大小无关。本修正的功能及性能继续分别由 SOURCE 和 hosted CI 核对。

R42 的后继接齐正式 request/status：按 retain/activate 实际返回的水位决定 building，水位0不进入明细组装。总览与任务两种正式查询回归要求 pending期间无任何数值读取，随后同一reportId恢复原270/1任务、四桶和人民币精确值。GC默认未加CTE时仍生成原DELETE字节，原描述项索引计划和三条原探针断言保持。旧SOURCE失败回执、旧CI失败和执行边界继续保留。
