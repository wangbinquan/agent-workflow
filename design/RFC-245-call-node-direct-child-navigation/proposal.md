# RFC-245 · 调用节点点击直达子任务

- 状态：Done（2026-08-01；实现、完整性审计与上库授权完成）
- 日期：2026-08-01
- 触发：用户「在任务详情界面，点击工作组或者工作流节点，应该直接跳转打开子工作组 / 工作流任务，
  不应该弹出右侧框」
- 相关 RFC：RFC-243（统一执行器 / 调用节点 / 父子任务）、RFC-158（评审节点点击直达）、
  RFC-161（反问节点点击直达）、RFC-222（任务删除）、RFC-099 / RFC-231（资源与任务 ACL）、
  RFC-244（高密度任务运行中心，仅共用 `ParentTaskBadge` 的可见性口径，无实现耦合）

## 1. 背景

RFC-243 给画布加了两个调用节点 kind：`call-workflow`（调用工作流）与 `call-workgroup`
（调用工作组）。它们在父任务里不产生任何自己的会话——真正的执行内容全部发生在它派生的
**独立子任务**里，调用行只留一个 `node_runs.child_task_id` 指针
（`packages/backend/src/services/task.ts:3670` 已在 wire 上）。

但任务详情画布至今把它们当普通节点处理：点一下 → 打开右侧 `NodeDetailDrawer` → 抽屉里再点
「子任务」按钮（`components/tasks/ChildTaskLink.tsx`）→ 才到子任务详情。**两跳，且中间那一跳
的抽屉对调用节点几乎没有可读内容**（调用节点无自己的 opencode 会话，Session 页是占位；输出端口
的值是子任务结果的转发副本）。

同一类问题在画布上已经解决过两次，而且是同一套解法：

- **RFC-158**：评审节点点击 → `/reviews/:nodeRunId`，绝不开抽屉。
- **RFC-161**：反问 / 跨代理反问节点点击 → `/clarify/:nodeRunId`，绝不开抽屉。

两者的共同判据是：**这个节点自己没有内容，内容在另一个页面**。调用节点是这条判据的第三例，
而且是最强的一例——它的「另一个页面」是一个完整的子任务。

还有一个反向缺口：即使用户绕两跳到了子任务，**也回不来**。`/tasks` 列表的子任务行有
`ParentTaskBadge`（`routes/tasks.tsx:478-519`），而 `/tasks/:id` 详情页对 `parentTaskId`
零回显，只能靠浏览器后退。

## 2. 目标

- **G1 单跳直达**：任务详情画布上点 `call-workflow` / `call-workgroup` 节点 = 直接打开它这一代
  派生的子任务详情页。
- **G2 调用节点不再弹右侧抽屉**：画布点击路径下，任何情况都不开 `NodeDetailDrawer`。
- **G3 可点性可见**：可点的调用节点在卡片上显示一行「点击进入子任务」提示 + 指针光标，与评审 /
  反问节点同一视觉语言。
- **G4 可往返**：任务详情页在 `parentTaskId` 非空时给出父任务入口，让「父 → 子」变成闭环。
- **G5 零回归**：编辑器画布、非调用节点、其余三个 canvas surface 的节点数据字节级不变
  （沿用 RFC-158 / RFC-161 的 golden-lock 纪律）。
- **G6 跳转落地干净**：「任务详情 → 任务详情」这条本 RFC 新扶正的路径不得残留上一个任务的页面
  状态（设计自查发现的既有缺陷，见 design D8）。

## 3. 已确认的产品决策（用户拍板，2026-08-01）

- **D1 — 无子任务可跳时一律不可点，绝不开抽屉**。覆盖四种情形：调用节点尚未派发、正在等子任务
  限额、启动前就失败（环检测 / 深度 / 引用不可见）、子任务已被删除或对当前用户不可见。
  用户明确选择了比推荐项更严格的一档：抽屉对调用节点在画布上彻底下线，不做「没得跳就回退开
  抽屉」的兼容。
- **D2 — 多代运行取严格最新一代**。loop 多迭代、显式 retry 换代都会产生多行调用 `node_runs`；
  按全仓 `isFresherNodeRun` 的纯 id 口径取最新顶层行的 `childTaskId`，并让调用节点画布状态色共用
  同一个 current-run oracle。重试刚换代、
  新子任务 id 还没落库的瞬间按「无子任务」处理（D1），**绝不指向已被取代的旧子任务**。
- **D3 — 提示行 + 指针光标**（与评审 / 反问节点一致），不做「只改光标」的隐性可点。
- **D4 — 本次一并补父任务入口**：任务详情头部在 `parentTaskId` 非空时渲染父任务链接。

## 4. 非目标

- **不改 `NodeDetailDrawer` 本身**，也不给调用节点做右键菜单 / 双击等第二入口。
- **不动后端**：`node_runs.childTaskId` 与 `tasks.parentTaskId` 都已在 wire 上，本 RFC 纯前端。
  设计门抓出的两个仓级问题（node_run id 单调性、retry cascade 不取消下游 call 子任务）
  已登记进 `docs/audit-backlog.md`，**本 RFC 不修**。
- **不碰 fanout 内层 call**：RFC-243 v1 由 validator 拒绝（`call-workflow-in-fanout-unsupported`），
  故 v1 不存在分片调用行。
- **不重构 `toFlowNodes` 的位置参数签名**（现 13 个，本次追加为 14，登记为后续项，见 design §8）。
- **不改子任务详情页的其它内容**，父任务入口只是头部 meta 的一行。
- **不给非 call 节点改「节点运行」表格的行为**：新增的「运行详情」入口只出现在 call 行上。

## 5. 用户故事

- **US1**：我在父任务画布上看到「调用工作组 audit-squad」节点正在跑。点它，直接进入那个工作组
  子任务的聊天室，而不是先弹一个几乎空白的右侧抽屉。
- **US2**：在子任务里看完结果，点头部的「父任务 · <名字>」回到父任务详情，继续看整条 DAG。
- **US3**：调用节点因跨定义环检测在启动前就失败了。它在画布上是红的、没有提示行、点不动；我到
  「节点运行」表看到错误列，点该行的「运行详情」照常打开抽屉——事件、统计、以及**重试（含级联
  开关）** 都还在。（设计门查明：抽屉是调用节点唯一的 Retry 与历代 attempt 入口，画布点击直达
  必须同时补上这个非画布入口，否则等于删功能。）
- **US4**：我在工作流编辑器里点同一个调用节点，仍然照常打开右侧 Inspector 编辑它的引用和参数
  ——编辑器 surface 完全不受影响。
- **US5**：这个调用节点在 loop 里跑了三轮。点它进入的是**第三轮**那个子任务，与节点当前状态色
  描述的是同一代。

## 6. 验收标准

- **A1**：任务详情画布点一个有可见子任务的 `call-workflow` / `call-workgroup` 节点，路由跳到
  `/tasks/{childTaskId}`，右侧抽屉不出现。
- **A2**：同一个调用节点在没有可跳子任务时（四种情形任一），点击不跳转、不开抽屉、卡片无提示行、
  光标不是 pointer。
- **A3**：多代运行时跳转目标 = ULID 最新顶层调用行的 `childTaskId`；旧代的子任务永远不会成为
  跳转目标。
- **A4**：可点的调用节点卡片显示提示行且带 `data-call-nav` 属性；不可点的没有该属性
  （编辑器画布上任何调用节点都没有）。
- **A5**：编辑器 / 工作组预览 / 意图预览三个 surface 的调用节点节点数据与本 RFC 前逐字段相同
  （golden-lock 单测）。
- **A6**：`/tasks/:id` 在 `parentTaskId` 非空且父任务可见时渲染父任务链接；父任务不可见 / 已删除
  时渲染中性不可点标签（与列表 `ParentTaskBadge` 同一降级口径，绝不出现死链）。
- **A7**：`/tasks` 列表零改动（并发的 RFC-244 已重写该路由并以服务端
  `listContext.parentAvailability` 取代客户端探针；本 RFC 的父任务组件为详情页专用）。
- **A8**：`bun run typecheck && bun run lint && bun run test && bun run format:check` 全绿。
- **A9**：右侧抽屉开着时从一个任务详情跳到另一个任务详情，落地页不残留空抽屉栏与其它
  task 作用域状态（见 design D8）。
- **A10**：首次 children 请求早于子任务落库（返回 `[]`）后，子任务起来时节点能自动转为可点
  ——不会被永久判成「已证明缺席」（设计门 P0-2，见 design D9）。
- **A11**：call 行的「运行详情」入口能打开抽屉，Retry（含级联开关）与历代 attempt 切换可达。
- **A12**：`callNavs` 单独变化（可见性翻转）时，卡片提示行与光标跟随更新，不与点击行为分叉。
