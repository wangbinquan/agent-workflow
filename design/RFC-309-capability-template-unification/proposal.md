# RFC-309 · 模板归一：一套模板，即流程，且能起跑（产品视角）

> 技术设计见 [design.md](./design.md)，任务分解见 [plan.md](./plan.md)。
> 前置：[RFC-304 代码能力平台](../RFC-304-code-capability-platform/proposal.md)（Done）、
> [RFC-307 能力流程可见可改](../RFC-307-capability-flow-visible-editable/proposal.md)（Done）。

## 1. 背景：三句用户原话

RFC-307 让流程看得见、改得动之后，用户连着提了三件事，指向同一个方向：

> 「流程和模版两个页签什么关系」
> 「是不是应该在模版里配置流程，大家直接用模版就行了」
> 「如果我要基于模版创建一个需求开发任务，入口在哪」

三句话拆出三个缺口，第三个最致命：

| 缺口                     | 现状                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| **① 两层模板是多余概念** | 「部门框架」+「小组绑定」是**两个资源、两个列表、两套复制导出**，而它们合起来才是一份可用配置 |
| **② 配置与流程是两扇门** | RFC-307 的「流程」页与「模板」页操作同一批对象：前者管内容、后者管生命周期，使用者要自己拼    |
| **③ 平台内根本起不了头** | **没有任何「发起一轮」的入口**——不是难用，是不存在                                            |

## 2. 事实核查（写档前按源码逐条核实，`file:line` 见 design §1）

**缺口③是实锤，且 RFC-304 自己记着这笔账。** `/api/code/*` 全部是 GET，唯二的写是
矩阵配置；`openRound` 只有三个调用者，整条链的唯一起点是 `webhookDispatch`。
RFC-304 `plan.md` 的 T46b 写着：

> 三入口：issue 标签 webhook / `/code` 界面 / 平台 API —— **◐** issue 标签入口已通；
> **`/code` 与 API 入口待做**

也就是说 RFC-304 承诺三个入口、交付了一个。今天要跑一轮需求实现，**唯一办法是去
GitLab/GitHub 给 issue 打标签**。

**好消息是地基都在，只是没接上。** 三处：

- **「复制一份改自己的」的机制早就写好了**：RFC-304 **T64 模板上游关系**——四态
  （`current` / `update-available` / `conflicted` / `orphaned`）+ 三方差异预览 +
  「只合并未被你覆盖的字段」——`domain/templateUpstream.ts` 已完整实现，
  `upstream_id` / `upstream_version` / `base_digest` 三列**两张表里都已经在了**。
  它是 RFC-307 关闭时记下的两笔假账之一：**零生产导入、无路由无界面、⛔ 转出**。
- **「平台发起」在域层已是一等公民**：`domain/clarifyRouting.ts` 的 `ClarifyOrigin`
  明写 `{ kind: 'platform' }` —— "Started from the platform's own UI or API"，
  且该联合体**故意没有 default 分支**（「加入口必须是编译错误，不是静默继承」）。
- **需求输入本就允许没有回写通道**：`RequirementInput.writebackHandle` 是 optional，
  注释写明「缺失意味着没有回写通道，这是 clarify 路由需要知道的事实，而不是要糊过去的东西」。

## 3. 目标

1. **一套模板**：删掉「框架 / 绑定」两层，合并为**一个** `capability_template`。
   谁都能复制一份改成自己的；复制关系由 T64 记录，上游更新时能三方合并。
2. **模板即流程**：打开一份模板看到的就是它的流程图，点某步就地配置。
   独立的「流程」页签消失；能力级流程降为**只读参考**。
3. **能从模板起跑**：在平台内选一份模板、选一个仓库、给出起点，就能发起一轮。

## 4. 关键裁决（均经用户逐条拍板）

| 编号   | 裁决                                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1** | **真合并成一张表**，不是「只合并概念、保留两表」。理由：数据模型里的 1:N 若不消除，UI 上就永远表达不了，迟早要再动一次                      |
| **D2** | **保留脚本/钩子的权限门**——合并的是**对象**，不是**权限**。写 `scripts`/`hooks` 仍需 `scripts:author`；改 agent / 提示词 / 参数只需模板写权 |
| **D3** | **起跑覆盖全部能给出锚点的能力**：`requirement` / `mr-review` / `ci-fix` / `mr-comment-fix`。`mr-monitor` 不开——它是常驻循环，不是「一轮」  |
| **D4** | **手动发起不要求矩阵已启用**。矩阵只管「自动响应 webhook」；手动发起自带模板，只校验仓库可访问 + 模板完整 + agent 可见                      |
| **D5** | **权限点直接改，不建兼容桥**（用户原话「过去的权限还没人用」）。8 点变 4 点，指向已删点的存量 grant 由迁移直接丢弃                          |

## 5. 能力影响清单（RFC-224 事故沉淀要求：收缩型变更必须逐项呈报）

本 RFC 删除既有资源类型与权限点，按仓规 §7 逐项列出：

| 被移除/改变                                                               | 影响                                                                     | 处置                                                                                           |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `capability_frameworks` / `capability_bindings` 两个资源类型              | 两个列表、两套 CRUD、两个 `/copy`、两种配置包 op 归一                    | 迁移为 `capability_templates`；导入旧配置包仍受支持（见 design §6）                            |
| 8 个权限点 `capability-{frameworks,bindings}:{read,create,update,delete}` | RFC-305 的 81 点闭集变 **78**（−8 +4 +1 发起点）；四个角色预设点数随之变 | 换成 `capability-templates:*` 4 点；**D5：存量 grant 直接丢弃**                                |
| `repo_capability_config.binding_id`                                       | 矩阵单元格指向的对象改名                                                 | 迁移改指 `template_id`                                                                         |
| RFC-307 的独立「流程」页签                                                | 入口位置变化（不是能力消失）                                             | 并入模板详情；能力级只读流程移到能力目录                                                       |
| 「一个框架被多个绑定共享」这一关系                                        | 部门改一次脚本、所有小组自动生效 —— **这条能力确实被移除**               | 换成 T64 的**上游关系**：改上游后各模板显示 `update-available`，三方合并（是**显式**而非自动） |

> ⚠️ 最后一行是真正的能力收缩，请特别确认：**自动传播** → **显式合并**。
> 代价是部门修脚本后各组要各自点一次更新；收益是没有任何一组会在不知情时行为改变。

## 6. 用户故事

- **US-1（复制即用）**：我看到一份别的组在用的模板，复制一份、把 reviewer 换成我们组的
  agent，其余照旧。上游改了脚本我会看到「有更新」，点开是三方差异，我可以只合并没被我
  改过的字段。
- **US-2（模板即流程）**：我点开一份模板，看到的就是它十三步长什么样；点第五步就改第五步。
  不需要先弄懂「框架」和「绑定」是什么关系。
- **US-3（起跑）**：我写好一份需求，选一个仓库、选这份模板，点「发起」。平台开一轮，
  给我一个可跟踪的回执；它要问我问题就在平台里问（因为不是从 issue 进来的）。
- **US-4（权限如实）**：我没有 `scripts:author`。我照样能复制模板、改 agent 和提示词；
  脚本步我**看得见**但编辑器只读、保存置灰——不是把它藏起来假装不存在。

## 7. 验收标准

- **AC-1** 只剩一个模板列表；新建 / 复制 / 导出 / 删除各只有一条路径。
- **AC-2** 迁移后：每个原绑定成为一份模板并继承其框架的脚本/钩子，`upstream_id` 指向
  原框架；零绑定的框架也各成一份模板（脚本不丢）。
- **AC-3** 矩阵单元格迁移后仍指向同一份配置（行为不变）。
- **AC-4** 打开模板 = 看到它的流程图；点任一步就地配置并写回该模板。
- **AC-5** 能力级流程在**没有任何模板**时仍可查看（RFC-307 AC-1 不得回归）。
- **AC-6** 无 `scripts:author` 时脚本/钩子只读、保存置灰；有则可写。**两条分支都要有测试**
  （仓规：禁用分支与正向功能同等对待）。
- **AC-7** 四条能力都能从模板发起：`requirement`（标题+正文+文档）/ `mr-review`（MR 号）/
  `ci-fix`（流水线号）/ `mr-comment-fix`（MR 号 + 讨论串 id）。
- **AC-8** 手动发起**不要求**矩阵启用，也不要求已配 webhook 触发器；但仓库不可访问 /
  模板槽位没填全 / agent 对发起人不可见时**拒绝并说明原因**。
- **AC-9** 手动发起有回执（RFC-304 AC-34）：立即返回轮次标识，界面可直达该轮。
- **AC-10** 平台发起的需求，其澄清问题走**平台**通道（`ClarifyOrigin.platform`），
  不尝试回写任何 issue。
- **AC-11** T64 四态与三方差异预览接上界面：复制来的模板能看到 `update-available`
  并执行「只合并未被覆盖的字段」。
- **AC-12** 旧配置包（含 `capability-framework-create` / `capability-binding-create`）
  仍能导入，落成合并后的模板。

## 8. 非目标

| 非目标                         | 理由                                                                 |
| ------------------------------ | -------------------------------------------------------------------- |
| 结构可编辑（增删步骤、重连边） | 仍是 RFC-304 D3，RFC-307 §4 的理由不变                               |
| `mr-monitor` 手动发起          | 它是常驻循环，不是轮次概念                                           |
| 自动传播上游脚本改动           | D1 的直接结果，见 §5 最后一行；显式合并是刻意选择                    |
| 部门/小组的组织建模            | 用户明确「不需要区分」；归属仍由既有 owner + visibility + grant 表达 |

## 9. 开放问题（呈用户确认）

- **Q-A** 零绑定的框架迁移成模板后，它的 `agentBySlot` 是空的 ⇒ 状态为「未配完」。
  是**保留为草稿**（列表里标注「待补 agent」），还是迁移时直接跳过不生成模板？
  **默认取保留**——脚本是真实资产，丢掉比留一份未配完的更糟。
- **Q-B** `mr-comment-fix` 手动发起要填「MR 号 + 讨论串 id」，讨论串 id 需去代码托管页面
  拷贝、极易填错。是否需要**先按 MR 号拉取讨论串列表让用户选**（多一次出站调用），
  还是先做纯手填、错了给明确报错？**默认取纯手填**，把拉列表列为后续优化。
- **Q-C** 手动发起的**权限点**：复用 `repos:write`，还是新增 `code-rounds:launch`？
  **默认取新增**——「发起一轮」会消耗模型额度并向代码托管平台写东西，与「能改仓库配置」
  不是同一件事，不该被后者顺带授予。
