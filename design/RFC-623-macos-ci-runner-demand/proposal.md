# RFC-623：第三轮 CI 优化——减少 macOS runner 申请

状态：In Progress，2026-11-26。用户已明确授权“评估可落地的方案并按你的推荐实施”，保持测试覆盖和现有门禁标准；本 RFC 记录该授权内的方案选择。

## 背景与目标

RFC-615 的功能候选 6c92 / run 45846353277 曾因 macOS arm64 runner 未领取而取消一片；文档候选 edad / run 45857372743 的末片等待 44m13s。后者完整 70/70 成功，等待不是测试超时。

最新连续五轮（45884250904、45886498851、45890130833、45893307751、45893530203）的最后工作均为后端分片；20 个 macOS E2E job 等待中位数7m58s、最大17m04s，执行中位数9m20s、最大13m48s。全部工作观测峰值20，每轮约571–589 runner-min、计算跨度约57–59分钟。不能把整轮准入等待、后端调度等待全部记成macOS容量问题，也不能由样本确定实际账户配额。

目标：减少macOS runner申请与重复准备，改善容量紧张时的尾部等待；用完整真实计时重平衡E2E，并保留原功能、覆盖、超时及严格结果判据。收益最终按hosted实际运行分别核验，不能承诺外部容量或固定提速比例。

## 方案裁决

采用macOS E2E物理/逻辑分片4→3，Linux3片、Windows4片保持。更新各平台文件计时为完整clean reporter样本，继续用现有整文件planner和执行器。每轮macOS申请由1个build+4个E2E变为1+3，E2E申请减少25%，macOS总申请减少20%。完整CI为69个job，其中68个计算job；13组门禁保持，完整E2E产物由11变为10，测试集合不缩减。

离线设计容量分析使用6c92完整clean来源（121个macOS spec、532个test，全部exact-once）：三片四worker调度模型最大635.274s，加原样本job余量109.695s为744.969s；工作量1.5倍敏感性为17m43s。两片同条件22m09s，拒绝采用。模型仅用于选型，文件窗口受负载影响，且不等于hosted墙钟承诺。

不采用：仅改max-parallel（仍有四次申请）；换macOS镜像冒充独立容量池；改Intel而减少arm64覆盖；两个物理job捆绑四逻辑片（新增进程、期限和清理机制且20分钟余量较差）；提前占runner等待build artifact（可能反向阻塞build）；未经容量证据增加/减少计算lane。付费larger/self-hosted涉及资源与权限，不在本轮新增。

## 用户故事与验收

- 开发者仍对每个SHA获得完整CI，既有两条计算lane与不取消验证语义保持。
- macOS当前arm64环境、完整Playwright发现集合、过滤、workers、重试、单测timeout及20分钟job上限保持；平台build smoke、SQLite/PG、coverage和全部13组required输出保持。
- E2E每个已发现文件与test ID准确执行一次；新三片集合与相同输入旧四片集合一致，无遗漏/重复。
- timing collector只接受source SHA实际声明的已知3/3/4或历史3/4/4拓扑，不根据拿到的文件数猜测；少一份旧四片产物仍必须失败。
- 完整实现与回归编写完成后集中验证，静态/相关测试、独立复核与exact-SHA hosted结果分别记录。
- 交付分别报告初始准入等待、macOS领取等待、实际执行、最后门禁等待和总墙钟；保留失败与外部容量事实。

## 能力影响

不删除测试、provider、平台或门禁，不放宽任何期限或失败判据；只改变相同全集的分片分配与所需runner数量。未知新文件沿用原60秒默认权重、继续执行。
