# RFC-291 — 意图会话提交入库后的自动挂载

> 产品视角。技术设计见 [`design.md`](./design.md)，任务分解见 [`plan.md`](./plan.md)，
> 设计门记录见 [`design-gate-2026-08-12.md`](./design-gate-2026-08-12.md)。
>
> **v2（2026-08-12）**：双路设计门判 FAIL 后修订——新增 G5/G6（call 边 handle 绑定、handle 高水位）、
> B4，弱化 B2/US-3 的 copy 承诺，收窄 AC-16，补 AC-8b 谱系语义与 AC-9b/AC-18~21。

## 1. 背景

用户实证（2026-08-12）：

> 「一个意图创建任务所提交的节点，应该被自动挂接到该意图创建任务里，不然我提交入库的东西我继续改的时候，发现没挂载不让改。」

在意图会话（`/intent`，UI 里也称「意图任务」）里，用户描述目标 → 构建 Agent 产出变更集 → 用户点「提交入库」（`intent.commitSubmit`）落库。**落库后的资源不会进入该会话的挂载清单**，于是用户在同一个会话里继续说「把刚才那个 agent 的 prompt 改一下」时，构建 Agent 要么只能发一条挂载建议等用户批准，要么直接撞 `intent-target-not-mounted` 校验被拒。

### 1.1 现状机制（源码事实）

| #   | 事实                                                                                                                                  | 锚点                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | 提交成功的大事务只更新 `commitSeq` / `contextRevision` / `currentDraftId`，**完全不碰 `contextManifestJson`**                         | `packages/backend/src/services/intent/applyChangeset.ts:1070`              |
| 2   | 下一轮生成只把 `root: true` 的清单条目喂给 dump                                                                                       | `services/intent/turnEngine.ts:489`                                        |
| 3   | 于是新建资源**未作为根、不可从任何现有根到达、且落在 inventory cap 内**时只拿到摘要条目（`detail: false`）；落在 cap 之外连摘要都没有 | `services/intent/dumpBuilder.ts:481-493`（摘要入清单）/ `:474`（cap 截断） |
| 4   | 草稿校验拒绝 update 一个 inventory-only 目标                                                                                          | `services/intent/resolveChangeset.ts:135`                                  |
| 5   | resolve 阶段二次拒绝，抛 `intent-target-not-mounted`                                                                                  | `services/intent/resolveChangeset.ts:474`                                  |

### 1.2 这是路径不一致，不是既定设计

从**既有资源**发起会话（资源详情页的「用意图修改」入口）时，平台会把该资源作为挂载根写进会话初始清单（`services/intent/session.ts:212-250` `buildInitialManifestInTx`），UI 文案也明写「已挂载到本会话，AI 将直接基于它给出变更」（`intent.modifyTargetNote`）。

也就是说，「要改就得先挂载」是平台既定语义，且平台已经在替用户自动挂了——**唯独漏了「本会话自己刚创建出来的产物」这一条路径**。别人的资源挂，自己刚造的反而不挂，这就是用户撞到的坑。

### 1.3 顺带暴露的四个相邻缺陷

调研与**设计门**核实到四处与本缺陷同源（都属于「该进上下文详情的东西没进 / 进错了」）的既有问题。
用户 2026-08-12 逐条拍板，全部纳入本 RFC：

- **失效挂载让整轮生成硬失败**：挂载的资源被删除或失去可见性后，dump 直接 `throw`（`dumpBuilder.ts:241`），整轮生成失败。前端只在挂载列表里显示「资源不可用」，用户没有自救路径（除非手动取消挂载）。自动挂载上线后会话里挂着的资源变多，踩中概率显著上升。**设计门补充**：这条比初判更深——真正 materialize 一个 skill 时 `readSkillContent` 会重新查库并抛 `skill-not-found`（`skill.ts:501-515`），完全绕过根检查，所以只改 `:241` 不够。
- **依赖闭包缺两条边**：`expandClosure` 的 workflow 分支只走 `agent-single` 节点的 `agentId`（`dumpBuilder.ts:191`），`call-workflow`（`workflowName`）与 `call-workgroup`（`workgroupName`）引用的子工作流 / 工作组**不进闭包**（`workflow.ts:809`、`:829`）。挂了父工作流去改，它调用的子工作流拿不到详情。
- **call 边在 dump 里既泄漏裸 ULID、又无法映射到 handle**（设计门 P1-a）：`dumpBuilder.ts:399` 让 call 节点**原样**进 dump，连同 `workflowId` / `workgroupId` 两个 canonical ULID——与「模型永远看不到 ULID」的隔离原则（`manifest.ts:5-7`）直接冲突。更要命的是同名场景：两个可见的同名工作流 W1（较老）/ W2，父节点缓存指向 W2 时，模型无法判断这条边对应 `mounted/` 里的哪个 handle；若实现者为满足隔离抹掉 id，模型回写后缓存丢失，**下次启动按名字回落到 W1**——用户以为在改被调用的工作流，实际运行的是另一个。补齐闭包边（让子工作流可改）会把这条从潜伏抬成必踩。
- **handle ordinal 跨轮被回收复用**（设计门 P1-d）：`manifest.ts:51-52` 注释承诺「Counters only ever grow」，实现做不到——每轮 dump 从空清单重建、inventory 只保留 cap 内（`dumpBuilder.ts:474`），被淘汰或已删除的非 detail 条目不进新清单，高水位随之回退。结果是新资源拿到历史 ordinal，**旧对话里的 `res#agent#3` 指向另一个资源**。本 RFC 让退根条目（copy 原件、同源旧副本）增多，进一步放大。

## 2. 目标

- **G1**：意图会话提交入库后，本次创建的**每个**资源自动成为该会话的挂载根，下一轮可直接修改，无需用户手动挂载、也无需等构建 Agent 发挂载建议。
- **G2**：copy 语义下（改他人 / 内置资源被复制成新副本，或用户主动选择 copy），会话的**显式挂载根**切换到最新副本——挂副本、原件与同源旧副本退根。
- **G3**：挂载的资源失效（被删 / 失去可见性）时，生成轮次跳过它并明示，不再整轮硬失败；判据覆盖到**逐资源 materialize**，而不只是初查。
- **G4**：补齐依赖闭包缺的 `call-workflow` / `call-workgroup` 两条边，并把 dumpBuilder 里手写的第三份 agent 引用读取收口到既有权威提取器。
- **G5**：dump 里的 call 边给出**可映射到 handle** 的绑定，canonical ULID 不再进入模型上下文；模型回写后 id 缓存不丢失，dump 所示目标与启动期实际执行的目标恒等。
- **G6**：handle ordinal **永不复用**——同一会话里一个 ordinal 不会先后指向两个不同资源。

## 3. 非目标

- **不设挂载数量上限、不做自动 GC**（用户 2026-08-12 拍板）。一次变更集最多 64 个 op，全挂后 dump 可能变大；缓解手段是用户可在「已挂载元素」里手动取消挂载，不由平台替用户裁剪。
- **不回填存量会话**：历史提交创建的资源不追溯挂载。`intent_provenance` 表技术上支持回填（`session_id → resource`），但回填会让老会话的上下文突然变大，且用户可能已按自己的意图手动挂过。存量会话仍可手动挂载。
- **不改动非会话入库路径**：资源包导入（RFC-271 `resource_import_journal`）没有会话归属，不在本 RFC 范围。
- **不改动挂载的权限判据、handle 词法（`res#<type>#<n>` 一个字符不动）、fence 体系**。⚠️ v2 起**确有两处结构增量**（设计门裁决）：清单条目新增可选 `copiedFromResourceId`（copy 谱系根）、会话行新增 per-type handle 高水位列。两者都向后兼容、缺省即退化为既有行为。
- **不放松 `intent-target-not-mounted` 校验**：它是正确的守卫（未 dump 的资源没有 fence，改它等于盲写）。本 RFC 让新建资源**合法地满足**该校验，而不是绕过它。

## 4. 用户故事

- **US-1（主线）**：我在意图会话里说「给我建一个代码审计 agent 和配套技能」，提交入库。接着我说「审计 agent 的 prompt 再严格点」——构建 Agent 直接改，不再要求我先去挂载。
- **US-2（工作流）**：我一次性造出「实现 → 审计 → 修复」工作流和它引用的三个 agent。提交后我说「审计那步改成按文件分片」——工作流和三个 agent 都在上下文里，直接改。
- **US-3（copy）**：我基于同事的 agent 提修改，平台强制复制成我的副本并入库。接着我说「再调下超时」——会话的显式挂载根已经是我的副本，改的是副本而不是同事的原件。（若我同时还挂着引用该 agent 的工作流，原件仍会作为它的依赖出现在上下文里——见 B2 的说明。）
- **US-4（失效）**：我在别处删了会话里挂着的一个 agent。回到会话继续对话——本轮正常生成，只是明确告诉我（和构建 Agent）那个资源已不可用、本轮跳过，而不是整轮报错。
- **US-5（子工作流）**：我挂着一个父工作流，它用 `call-workflow` 调子工作流。我说「把子工作流那步的超时调大」——子工作流的完整定义在上下文里，可以直接改。

## 5. 行为变更清单

本 RFC **不属于** `CLAUDE.md §7` 定义的「能力收缩型」（不以安全 / 隔离为由关闭既有能力）。但有四处用户可观察的行为变化，逐条列出：

| #      | 变更                                                                                                        | 影响                                                                                                                                                                                              | 逃生舱                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **B1** | 提交入库后「已挂载元素」列表新增本次创建的全部资源                                                          | 列表变长；下一轮 dump 包含这些资源全文，token 占用上升（新建 skill 会连同文件树一起 dump，单文件上限 128 KB）                                                                                     | 用户可对任意一条点「取消挂载」；取消后不会被自动挂回（自动挂载只在**提交那一刻**发生一次）            |
| **B2** | copy 场景：原件被自动取消挂载；同一**谱系根**再次派生新副本时，上一个同源副本也退出挂载根，只留最新副本     | 原件与同源旧副本**不再是显式挂载根**。⚠️ 这不等于「不可达」——若它们仍被其它挂载根引用（例如引用该 agent 的工作流），闭包照样把它们纳入详情、仍可被直接 update（设计门 P1-b 推翻了初版更强的承诺） | 用户可手动把原件或旧副本挂回（`addIntentMount` 未改动）；两者的 handle 都保留在清单里，会话历史不断链 |
| **B3** | 挂载资源失效时，dump 从「整轮硬失败」改为「跳过 + 明示」                                                    | 该资源本轮不出现在 `mounted/`；构建 Agent 在 `## Access notes` 里读到它不可用。**非** not-found 类的真实 I/O 故障仍照常失败，不被降级掩盖                                                         | 无需逃生舱——这是纯粹的可用性提升；若用户希望彻底清掉，仍可手动取消挂载                                |
| **B4** | dump 里 call 节点的表示变化：删 `workflowId` / `workgroupId`，改为 `workflowRef` / `workgroupRef`（handle） | 模型看到的父工作流正文形态改变（与既有 `agentRef` 同构）；`workflowName` / `workgroupName` 保留不变。落库形态不变——resolve 时回写成 canonical id                                                  | 不涉及用户操作面；工作流在画布/YAML 侧的表示与导出完全不受影响                                        |

## 6. 验收标准

### 自动挂载（G1）

- **AC-1**：会话提交入库成功后，本次变更集里每个 `create` 落库的资源在 `intent_sessions.context_manifest_json` 中都有一条 `root: true` 的条目，六类资源（agent / skill / mcp / plugin / workflow / workgroup）逐类覆盖。
- **AC-2**：提交后的下一轮生成，这些资源出现在 `mounted/` 下（`detail: true` 且带 fence），构建 Agent 可以直接以它们的 handle 作为 `update` 目标提交变更集，不再触发 `intent-target-not-mounted`。
- **AC-3**：自动挂载与 `contextRevision` 的提交期递增在**同一个事务**里完成；提交成功而挂载缺失的中间态不存在。
- **AC-4**：重复提交（同一 `clientMutationId` 的 replay）返回既有回执，不重复追加清单条目、不改变 handle 编号。
- **AC-5**：handle **ordinal 永不复用**——同一会话里一个 ordinal 不会先后指向两个不同资源；同一资源在其清单条目存续期间 handle 恒定。（条目被淘汰后重新出现可能换 handle，属已知限制，见 design §8.3。）

### copy 语义（G2）

- **AC-6**：copy 派生出的新副本按 AC-1 自动挂载为根。
- **AC-7**：被复制的原件在同一事务里被取消挂载（清单条目保留、`root` 置 false），handle 不回收。
- **AC-8**：若原件本就不是挂载根（详情来自依赖闭包），AC-7 是无操作，不报错、不改动其它条目。
- **AC-8b（最新副本唯一）**：同一**谱系根**再次派生新副本时，所有同源旧副本自动退出挂载根（条目与 handle 保留），只有最新副本是根。谱系按**根**而非直接来源计算——`O→C1→C2` 之后再从 O 派生 C3，C1 与 C2 **都**要退根（设计门 P1-c）。派生关系**跨生成轮次持久**：一轮 dump 重建清单后仍能识别同源旧副本。

### 失效挂载（G3）

- **AC-9**：挂载根在下一轮不可见（被删 / 失去可见性），该轮**完整正常收尾**（不只是 `buildIntentDump` 不抛错）：跳过该根，其余挂载与 inventory 照常。判据覆盖两处——初查（catalog 缺失）与**逐资源 materialize 失败**（如 catalog 加载后才被删的 skill）。
- **AC-9b（真错不吞）**：非 not-found / not-visible 的失败（文件 I/O 损坏、序列化异常等）**照常抛出**，不得降级成「资源不可用」。
- **AC-10**：被跳过的根在新清单里保留条目（`root: true` / `detail: false` / handle 不变），前端「已挂载元素」继续显示为「资源不可用」，并标注生成时会跳过。
- **AC-11**：构建 Agent 在 `INTENT.md` 的 `## Access notes` 段读到本轮被跳过的挂载（仅 handle + 资源类型，**不回显名字**——不可见资源的名字不属于该 actor 的可见面）。该断言要覆盖**上游接线**（turnEngine 确实把参数传下去了），而不只是渲染函数本身。

### 闭包扩边（G4）

- **AC-12**：挂载一个含 `call-workflow` 节点的工作流，被调用的子工作流进入 `mounted/` 详情并可作为 update 目标；子工作流自身的 call 节点继续递归展开。
- **AC-13**：`call-workgroup` 同上（工作组是闭包叶子，其 agent 成员继续按既有规则展开）。
- **AC-14**：call 目标的解析判据与启动期冻结（`services/execution/closure.ts` `freezeCallClosure`）**同源**：id 缓存优先（该行名字仍等于选择器名字且对当前 actor 可见），否则在可见同名行里取最老 ULID。两处共用同一裁决实现。
- **AC-15**：call 目标不存在 / 对当前 actor 不可见时，按既有 `hiddenDependencies` 语义计数上报，不抛错、不泄漏名字。**边界**：这里的「不泄漏名字」只约束 hidden / unavailable 报告与 `## Access notes`；父工作流正文里作者自己写的 `workflowName` 是 authored 数据，照常保留（设计门 P2-e 澄清，避免实现者过度删名）。

### 回归防护

- **AC-16**：**闭包展开**不再手写 agent 节点 walker——统一走 `services/resourceRefs.ts` 的权威提取器。
  ⚠️ 断言口径限定在闭包展开路径：dump **renderer** 仍必须识别 `agent-single` 才能做 `agentId → agentRef`
  转换（那是 AC-18 的载体），要求「文件里不出现该字面量」会把正确实现判红（设计门 P2-d）。
- **AC-17**：既有 `intent-target-not-mounted` 的两处校验（`validateDraftChangeset` + `resolveIntentBundle`）保持原语义，对**未挂载**目标仍然拒绝——**两处各自断言一次**，不能只测其一。

### call 边绑定（G5）

- **AC-18**：dump 出的 call 节点**不含** `workflowId` / `workgroupId`，改为携带 `workflowRef` / `workgroupRef`（会话 handle）；目标不可解析时标记为隐藏，不泄漏 id。`workflowName` / `workgroupName` 原样保留。
- **AC-19（回写不丢缓存）**：把 dump 出的父工作流原样回传为 update 变更集并提交后，落库的 `workflowId` 与 dump 时所示目标**同一行**；同名两行（W1 较老 / W2 被缓存指向）场景下不得回落到 W1。dump 所示目标、闭包纳入的目标、启动期 `freezeCallClosure` 冻结的目标**三者恒等**。

### handle 高水位（G6）

- **AC-20**：退根 → inventory cap 淘汰 → 新建资源，新资源**不复用**历史 ordinal（用 `inventoryCap` 测试缝确定性复现）。
- **AC-21**：迁移前的旧会话行（高水位列为默认空）行为退化为既有逻辑，不报错、不迁移。

## 7. 已拍板（2026-08-12）

- **Q1 存量会话回填**：**不做**（§3）。历史会话里之前提交创建、当前未挂载的资源不追溯挂回；仍可手动挂载。若后续需要，可依 `intent_provenance` 另开一批。
- **Q2 copy 链跟到最新**：**做**——见 B2 / AC-8b。用户原话「你现在需要挂载最新的修改副本啊，不然下次修改的基础都没了」：会话里对同一原件反复派生时，挂载根必须是**最新**那个副本，旧副本退根，避免下一轮改在过时的基础上。
- **Q3 call 边 handle 绑定与 ULID 泄漏（设计门 P1-a）**：**纳入本 RFC 一并修**（G5 / 面 E）。实现上沿用既有 `agentRef ↔ agentId` 模式同构扩展，不发明新机制。
- **Q4 copy 承诺强度（设计门 P1-b）**：**弱化承诺**——只保证「不再是显式挂载根」，不保证不可达。理由：改父资源时本就应该看得到它引用的子资源正文；为兑现「不可达」而把被引用件降级为 reference-only 会损害正常场景。
- **Q5 handle ordinal 回收（设计门 P1-d）**：**纳入本 RFC 修**（G6 / 面 F）——持久化 per-type 高水位并同步修正 `manifest.ts:51-52` 那句与实现相反的注释；不做全量映射持久化（§8.3 取舍）。
