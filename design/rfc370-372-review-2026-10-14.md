## 2. RFC-372 现有反问的脑图模式

### 2.1 做得好的

- **范围收敛到位**：
  - 问题、答案、草稿、提交和续跑都复用 `clarify_rounds` 与原有的封存 → 派发 → continuation 链路，没有第二条执行链。
  - 早期扩大范围建的 10 张表，经双数据库向前迁移退役：SQLite 0248、PG 0024。
- **提交前做竞态校验**：服务端在原有锁里同时核对 `questionSetKey` 和全部问题都已确认，挡住了“另一个标签页用旧问题集合提交”的情况。
  - 代码：`packages/backend/src/modules/collaboration/infrastructure/clarify/seal.ts`
- **追问可以安全重试**：`requestId` 和 `requestBasis` 写在问题 JSON 里，丢了响应后用同一个 ID 重试，不会重复追加问题。
- **前端复用公共组件**：
  - 复用了 Dialog、Segmented、Field、TextArea、TextInput、VirtualList、TreeDisclosure、ErrorBanner。
  - 新增的分类树编辑器 `CategoryTreeEditor` 按公共组件的形态放在 `components/` 下。
  - 画布颜色取自 CSS 主题变量，并监听主题切换后重绘；672 行 CSS 全部在 `.mindmap-*` 命名空间内，没有写死的颜色。

### 2.2 问题

**中｜追问时模型看不到原任务的需求**

- 现象：提示词只带了分支问答、分类、节点指引和用户补充，没有发起 Agent 的任务输入，也不接原会话，而是在共享的临时工作区里另起一个系统 Agent。
- 影响：做“根节点全图补问”时，模型只能从已有问题倒推背景，容易问出泛泛的问题。
- 依据：
  - `packages/backend/src/modules/collaboration/application/clarifyFollowup.ts:80-96`
  - `packages/backend/src/modules/task-execution/composition/clarifyFollowupGenerator.ts:86`
- 建议：在提示词里附上原任务输入的摘要（长度要有上限）。

**中｜装配层写了业务逻辑**

- 现象：追问生成器的装配文件直接查 `nodeRuns` 表、解析冻结参数、决定回退用哪个运行时。RFC-294 要求装配层只负责接线。
- 依据：`packages/backend/src/modules/task-execution/composition/clarifyFollowupGenerator.ts:31-66`
- 建议：把查表和运行时选择下沉到 task-execution 的 adapter 或 application 层，装配层只负责注入。

**低｜基础设施层反向引用应用层内部模块**

- 依据：`packages/backend/src/modules/collaboration/infrastructure/clarify/seal.ts:1`
- 建议：改为通过端口注入“追问是否空闲”的检查。

**低｜“正在追问”的进程内状态存了两份**

- 现象：同一个在途状态分别存在 operations 闭包和 activity 模块里，需要同时释放。
- 依据：
  - `packages/backend/src/modules/collaboration/application/clarifyFollowup.ts:22`
  - `packages/backend/src/modules/collaboration/application/clarifyFollowupActivity.ts:5`
- 建议：合并成一份。

**低｜沿用存量写法，没有借机往目标架构挪一步**

- 现象：新增的读取代码直接读任务执行模块的 `tasks` 表，还依赖旧的 `@/services/taskWriteLocks`。
- 依据：`packages/backend/src/modules/collaboration/infrastructure/clarifyFollowupStore.ts:16,22`
- 建议：随 collaboration 后续的 RFC 收口。

**低｜“已确认”标记依赖字段顺序**

- 现象：确认依据和问题集合摘要都是把问题对象直接转成 JSON 字符串再算哈希。以后只要某条读取路径改为按 schema 重新解析，字段就会被重新排序，所有已确认的答案会同时失效。
- 依据：`packages/shared/src/clarifyMindmap.ts:16`
- 建议：先把字段排序再算哈希。

**低｜追问是同步长请求，最长 180 秒**

- 现象：功能没配置时返回 400 `ValidationError`，语义上应该是 503。实测第一次根补问就超时过一次。
- 影响：以后经过托管网关时，长请求更容易被代理切断。
- 依据：
  - `packages/backend/src/routes/clarify.ts:135`
  - `clarifyFollowupGenerator.ts:88`
  - `RFC-372-mindmap-clarify/real-aw-ux-acceptance-20261013.md:33`
- 建议：改为“提交 → 轮询或 WS 通知”；功能不可用时返回 503。

**低｜迁移文件和提交的归属混杂**

- 现象：
  - 以 rfc372 命名的 SQLite 0248 建了 14 张 RFC-371 的 `observation_projection_*` 表；
  - PG 0024 带上了 RFC-371 的 55 个变更捕获触发器；
  - RFC-371 的触发器生成器首次入库时用的是 RFC-372 的提交 `95ec4a8ee`（提交说明里已写明并发产出）。
- 建议：以后迁移按 RFC 分开生成，方便追溯。

## 3. RFC-371 运行观测与统计

### 3.1 做得好的

- **口径清楚，且写进了领域层**：
  - 四类 Token 互不重叠；
  - 未知不等于零；
  - 失败的执行也计入消耗；
  - 父子不重复计算；
  - 人民币用精确十进制，价格按版本冻结。
- **新模块已登记**：`run-observability` 已加入 RFC-294 design 的模块合同表。
- **前端复用公共组件**：
  - 复用了 Card、TabBar、TableViewport、Dialog、Select、Segmented、EmptyState、LoadingState、ErrorBanner、NoticeBanner，表格统一用 `data-table`；
  - 新增的 `ExecutionSwimlane` 是公共组件；
  - Token 价格配置接进了现有的“设置 → 运行时”页；
  - 用户砍掉的 CSV 导出已经删干净。

### 3.2 实现与架构问题

**高｜用数据库触发器捕获其他模块表的变更**

- **规模**：一共 55 张表装了触发器。
  - SQLite：0245 建了 165 个 `obs_src_*`，0249 又建了 165 个 `obs_delta_*`。
  - PG：0021 建了 165 个语句级触发器，0024 建了 55 个行级触发器。
- **涉及其他模块的业务表**：其中 15 张不属于观测模块：
  - users、tasks、task_repos、task_collaborators；
  - node_runs、node_run_events；
  - agents；
  - intent_sessions、intent_turns、intent_turn_events；
  - mcp_runtime_test_sessions、mcp_runtime_test_turns、mcp_runtime_test_events；
  - memory_distill_jobs、memory_distill_events。
- **影响**：
  - 每写一次 `node_run_events` 这类高频表都要多写一行；
  - 已经实际造成过 node_runs 写事务互相等待（`RFC-371-run-observability/ci-repair-20261014.md:88`）；
  - PG 在 0031 才把 `obs_src` 改成空函数，但触发器本身还在；SQLite 一侧每次写入仍会更新同一行计数。
- **建议**：改用由各数据所属模块（owner）提交的“提交后事件”（`platform/events/committed`），删掉这些触发器。

**高｜借 platform 层绕开模块边界**

- **现象**：
  - `platform/persistence` 按 schema 合同用原生 SQL 遍历其他模块的私有表，还写死了业务表名和列名的匹配规则（如 `source|root|session|task…`）。
  - 依赖图守卫看不到这类读取：表面上“没有跨模块 import”，实质仍是直读私有表。
  - platform 层因此承载了约 3.3K 行观测业务代码。
- **冲突**：违反 RFC-371 design §1 和 RFC-294 “跨模块只走公开接口”的规定。
- **依据**：
  - `packages/backend/src/platform/persistence/observationProjectionRouting.ts:28-38`
  - `packages/backend/src/platform/persistence/observationProjectionChangeSchema.ts:14-24,48`
  - `packages/backend/src/platform/persistence/observationSourceRevisionSchema.ts:12`
- **建议**：观测相关代码移回 `run-observability`；跨模块的数据由各模块的公开查询或事件提供。

**高｜四套派生数据并存**

- **四套**：
  1. 有调用次数上限的实时查询；
  2. 完整报告的后台生成（报告、页、计数、回执、租约）；
  3. 计算缓存；
  4. 增量投影。
- **现象**：装配代码靠报告 ID 是否以 `projection-` 开头来决定走哪一套；设计里只建议 6 张表，实际建了 80 张。
- **依据**：`packages/backend/src/modules/run-observability/composition/completeObservationReports.ts:80-87`
- **建议**：只保留增量投影这一套，其余删除。

**中｜前后端都有死代码**

- **现象**：
  - 前端 `RunObservability.tsx`（647 行）已经不在页面上使用了，但代码和测试都还在。
  - 后端的 `GET /api/observability/overview`、`/tasks`、`/tasks/:id` 三个接口只被这个死组件调用，仍然在线，背后约 1.1K 行代码。
- **依据**：
  - `packages/frontend/src/routes/observability.tsx:10`
  - `packages/frontend/src/components/observability/RunObservability.tsx:294,304,316`
  - `packages/backend/src/modules/run-observability/infrastructure/http/observationRoutes.ts:134,158,193`
- **建议**：一并删除（遵循 `CLAUDE.md`“删除优于废弃”）。

**中｜提前写了未接线的 CrewStation 代码**

- **现象**：
  - CrewStation 观测客户端只被测试引用；
  - 应用层多处判断 `authority.kind === 'crewstation'`，还写死了显示名 `'CrewStation'`；
  - platform 的 SQL 里也在判断 `'crewstation'`。
- **冲突**：违反 RFC-370 “应用层不按部署平台写分支”和“阶段 A 验收前不写 CrewStation 适配代码”的规定。
- **依据**：
  - `packages/backend/src/modules/run-observability/infrastructure/crewstation/observationSource.ts:34`
  - `application/taskObservations.ts:77,277`
  - `application/invocationValuation.ts:53`
  - `application/incrementalObservationDimensions.ts:99`
  - `platform/persistence/observationProjectionRouting.ts:208`
- **建议**：领域里改用中立的“托管 / 平台管理”说法；客户端等 RFC-370 阶段 B 再接入。

**中｜体量和性能代价不成比例**

- **体量**：生产代码约 5.4 万行，测试 134 个文件、4.3 万行。生产代码的构成：

  | 部分                             | 行数  |
  | -------------------------------- | ----- |
  | 观测模块本体                     | 29.9K |
  | 任务执行和运行时管理里的采集代码 | 9.7K  |
  | platform 层                      | 3.3K  |
  | 前端                             | 8.1K  |
  | shared                           | 2.4K  |
  | `db/` 下的表定义                 | 0.8K  |

- **性能**：
  - 10-12 时，同月份的热报告仍要约 10 秒；
  - 存储容量统计曾经直接在服务的数据库连接上执行全库扫描，阻塞事件循环 107 秒；
  - 本机实例的数据见 §3.3。
- **依据**：
  - `RFC-371-run-observability/period-reuse-performance-20261012.md:3,15`
  - `RFC-371-run-observability/long-running-storage-20261013.md:60`
- **建议**：先完成上面三项“高”的收敛，再评估规模。

**低｜几处分层细节**

- **现象**：
  - HTTP 入站代码放在 `infrastructure/http/`，没有放在 `inbound/`；
  - 直接读资源目录模块的 `agents` 表；
  - 装配层里有约 70 行生命周期编排。
- **依据**：
  - `run-observability/infrastructure/completeObservationAgentNames.ts:2`
  - `composition/completeObservationReports.ts:113-180`
- **建议**：随上面的收敛一起调整。

### 3.4 界面实测

**正常的部分**

- 页头、筛选、页签、卡片、表格风格与 `/tasks`、`/settings` 等核心页一致。
- 暗色正常；390 宽时筛选项纵向堆叠、页签可横向滚动。
- 下钻任务后可返回统计页，并保留原筛选。

**问题**

- **中｜页面过长。**
  - 实测高度：
    - “任务追踪”约 19.5K px：两张 100 行表；
    - “Agent 分析”约 32.1K px：41 行，加三张 100 行表；
    - “性能与数据质量”约 51.4K px：一张 200 行表，加四张 100 行表。
  - 每行都重复写一遍四类 Token 标签，行高约 84px；“原始历史执行”表在三个页签里重复出现。
  - 建议：每页默认少展示几行，四类 Token 改为列，重复的表只保留一处。
- **中｜文案偏实现视角。**
  - 例子：“原调用登记缺失的历史执行引用”“原生采集记录”“开始前基线”“零消耗证明”“受理时未记录运行时名称”。
  - 版本号直接显示为毫秒时间戳，例如“修订 1791345879517”。
  - Agent 名称显示“未观测”。
  - 节点名直接显示内部 ID，例如 `__wg_leader__`、`__repo_prep__`、`__de_plan_agent__`、`__commit_push__:output`。
  - 任务名直接显示 `employee:<ULID>`。
  - RFC-371 proposal §2 承诺“页面主语言是任务、Agent、执行、调用、等待”。
- **中｜系统执行与业务任务混在一起。** “任务消耗”列表里，“记忆提取 · task-run”“分支追问”“变更叙述”等系统执行和业务任务并列成行。
  - 建议：单独分组，或挂到所属任务下面。
- **中｜默认显示旧数据，且异常列表噪音大。**
  - 打开页面时，统计停在约 4 小时前。
  - “异常与恢复记录”有 200 行“持续异常”，大部分是“人民币费率缺失”或历史缺口，难以从中找到需要处理的项。
- **低｜时长显示为原始毫秒。** 例如“394,564,140 ms”。单个任务的详情里也显示 P50/P95，没有意义。
  - 依据：
    - `packages/frontend/src/components/observability/CompleteObservationDetails.tsx:349`
    - `CompleteObservationTrace.tsx:123,156`
- **低｜几处布局小问题：**
  - “Token 与成本”页签的双列卡片里，表格右侧被截断：数值显示不全，人民币列被挤到横向滚动区之外。
  - 异常表“规则/状态”两列太窄，文字被折成 3 到 4 行的竖排。
  - 趋势图只显示有任务的日期，时间轴不连续，而且还要翻页。
- **低｜快捷时间范围没用公共组件。** “近 1 天 / 近 7 天 / 近 30 天 / 全部时间”是自写的按钮组（`aria-pressed`），没有用公共的 `Segmented`。
  - 依据：`packages/frontend/src/components/observability/ObservationFilters.tsx:138-148`
- **低｜单机版界面出现 CrewStation 文案。**
  - 运行时价格说明、“当前采集能力”和平台同步相关的文案里出现“CS 托管 / CrewStation”，但托管部署还没有上线。
  - 依据：
    - `packages/frontend/src/i18n/observationPricing.ts:3`
    - `packages/frontend/src/i18n/runObservability.ts:269,317,333-334,423,460`
- **加载时间**：从打开各页签到加载提示消失约 3.8–8.7 秒；这个数字包含约 1.5 秒固定等待，结果来自无头浏览器。

## 4. RFC-370 CrewStation 托管部署（阶段 A）

### 4.1 做得好的

- **端口放在了正确的模块里**：
  - 执行效果端口 `ExecutionEffectPort` 归任务执行模块；
  - 工作区 / Git 归源码管理模块；
  - 执行材料和协议归运行时管理模块；
  - 配置和安装归系统运维模块；
  - 登录认证归身份模块；
  - 本地实现统一放在各模块的 `infrastructure/local/` 下。
- **执行与内容切面已在生产路径上**：以执行切面为例，启动时没有指定实现，就默认装配 `composeLocalTaskRunRootSelection` 等本地实现，新端口不是只有测试在用。
- **没有混入 CrewStation 生产代码**：阶段 A 本身没有 CrewStation 生产代码（RFC-371 那份除外，见 §3.2）。
- **门控沿用既有写法**：HTTP 的执行可用性门控用 RouteMeta 的 `executionGroup` 声明。

### 4.2 问题

**高｜执行权（H7）做成了第二条平行路径**

- **现象**：
  - 生产入口不传入宿主执行配置，单机 daemon 一直是 `native` 模式；本机实测 `GET /api/execution/status` 返回 `{"mode":"native","status":null}`。
  - 19 个后台任务的装配、恢复命令和嵌入式启动入口，只有测试会启用。
  - 结果：SQLite 启动入口里约有 33 处、PG 启动入口里约有 13 处在判断走新路径还是旧路径，新路径没有任何生产流量验证。
- **冲突**：设计 §1.1 要求“本地实现保留现有的单实例语义”，也就是单机版也应该走这个新接口。
- **依据**：
  - `packages/backend/src/cli/start.ts:1970`
  - `packages/backend/src/routes/daemon.ts:51`
  - `packages/backend/src/cli/daemonHostExecutionOwners.ts`（新增，940 行）
  - `packages/backend/src/cli/embeddedHostExecutionApplication.ts`（仅测试引用）
- **建议**：让单机版也走 H7 的本地实现（始终处于 active），去掉新旧路径的分叉。

**中｜启动入口文件继续膨胀，没有往 `bootstrap/` 收敛**

- **现象**：
  - 三个主要入口的行数变化：

    | 文件           | 开工前 | 现在 |
    | -------------- | ------ | ---- |
    | `cli/start.ts` | 3693   | 4700 |
    | `server.ts`    | 3819   | 4648 |
    | PG 启动入口    | 2358   | 2917 |

  - 另外新增了约 1.5K 行装配代码；目标架构里的 `src/bootstrap/` 目录仍然是空的。
  - 三四个启动入口要靠“19 个后台任务名单”的测试来保持一致，这本身就容易漂移。

- **建议**：把启动入口合并到 `bootstrap/`，后台任务名单只定义一次。

**中｜执行端口仍是“本地进程”的形状**

- **现象**：
  - 端口只有 `submit` 和 `recoverOriginal` 两个方法；
  - 结果用的是按行回调的标准输出、退出码、`spawn-failed/unreaped`；
  - 设计 §5.1 写的查询状态、读事件、发消息、取消都没有。
- **依据**：`packages/backend/src/modules/task-execution/application/ports/executionEffect.ts:11,19,44,76`
- **建议**：阶段 B 开工前，用 CrewStation v3 的任务、子任务、事件游标逐项对照一遍端口。

**中｜platform 层反过来依赖业务模块**

- **现象**：platform 层引用了系统运维模块的公开类型，还用模块级全局表加 `bind…` 函数来接线。RFC-294 规定，这种全局注册式接线只允许出现在 bootstrap 里。
- **依据**：`packages/backend/src/platform/http/hostExecutionAvailability.ts:7-12,22,30`
- **建议**：由 bootstrap 注入一个中立的端口。

**低｜前端门控比后端还严**

- **现象**：执行状态查询在加载中或出错时，28 个前端文件里共 31 处执行入口都会显示“检查中”并被禁用。单机版的后端永远放行，但前端可能因为一次状态请求失败，把执行按钮全部禁掉。
- **依据**：`packages/frontend/src/hooks/useHostExecutionAvailability.tsx:20,35`
- **建议**：拿不到状态时按 `native` 处理，或只在托管模式下才启用门控。

**低｜单次提交过大**

- **现象**：阶段 A 的接线提交 `b9b27bfd8` 改了 276 个文件（新增 23,187 行，删除 1,479 行），其中生产源码 173 个。这和 RFC-294 G7 “每一波独立提交、独立验收”的原则有冲突。
- **建议**：后续按切面拆成子 RFC 或分波次，每一波仍然先完整开发、再集中验证。

### 4.3 界面

单机版是 `native` 模式，执行状态横幅和恢复入口都不显示，所以本次实测看不到 RFC-370 的新界面。相关的前端门控问题见上表。

## 5. 三个 RFC 共有的问题

1. **架构账本在变大，而且看不出是谁引入的。**
   - 2026-09-28 → `e6fb19d07` 的变化：

     | 指标           | 2026-09-28 | `e6fb19d07` | 增量  |
     | -------------- | ---------- | ----------- | ----- |
     | 架构例外       | 4884       | 6440        | +1556 |
     | 跨模块 import  | 5496       | 7350        | +1854 |
     | 后台任务       | 332        | 412         | +80   |
     | 全局注册式接线 | 497        | 522         | +25   |
     | 原生定时器     | 76         | 88          | +12   |

   - 新增的例外，`introducedByRFC` 全部标为 `pre-RFC-294-current-debt`（RFC-294 之前的存量债）。生成器把所有与旧代码之间的依赖都按存量债归类，账本因此分不出哪些是这期新加的。
   - 新增的依赖边主要来自：

     | 方向                          | 新增边数 |
     | ----------------------------- | -------- |
     | `run-observability` → 旧代码  | +317     |
     | `task-execution` → 旧代码     | +285     |
     | 旧代码 → `task-execution`     | +230     |
     | `runtime-management` → 旧代码 | +136     |

   - 每次增长都靠“一次性增长声明”放行，起不到拦截作用。

2. **主干 CI 两天多没有绿过。** 最后一次成功是 `61c82662c`（2026-10-12 07:33Z）；之后约 53 次失败、8 次取消。`e6fb19d07` 的失败中，类型检查一项出在 RFC-371 代码；审视时，原负责会话已在本地提交修复，尚未发布。RFC-372 是在这段时间里按用户批准的功能标准关闭的。
3. **交接文档已经读不动了。** `STATE.md` 约 2.9 MB；RFC-370 和 371 的目录分别约有 214 和 161 个文件、2.5 MB 和 3.0 MB，大量段落是“以下全文保持”的流水记录。`CLAUDE.md` 要求新会话先读 `STATE.md`，现在这个体量已经没法完整读入，“当前有效的合同”只能从流水里一条条翻。

## 6. 建议的处理顺序

1. **RFC-371 收敛**（需要用户决定方向）：
   - 用各模块的提交后事件替代数据库触发器，删掉已经是空函数的触发器；
   - 观测相关代码从 platform 层移回自己的模块；
   - 只保留增量投影一套，删除旧的实时查询接口、`RunObservability.tsx` 及多余的派生表；
   - 评估派生数据的保留策略和规模。
2. **RFC-370 执行权与装配根**（需要用户决定方向）：
   - 单机版也走 H7 的本地实现，去掉新旧路径分叉；
   - 启动入口合并到 `bootstrap/`。
3. **RFC-370 阶段 B 开工前**：用 CrewStation v3 的接口对执行端口逐项对照。
4. **RFC-371 界面整理**：
   - 系统执行单独分组；
   - 时长和版本号改成人能读的格式；
   - 每页默认少展示几行，长表分页；
   - 文案改成用户视角，删掉单机版里的 CrewStation 字样；
   - 快捷时间范围改用 `Segmented`。
5. **RFC-372 小修**：
   - 追问时带上原任务的需求摘要；
   - 查表逻辑移出装配层；
   - `seal.ts` 改为依赖端口；
   - 算哈希前先把字段排序；
   - 初始视口适配全图；
   - 追问改为异步。
6. **治理**：
   - 新增的架构例外按真正引入它的 RFC 记账；
   - `STATE.md` 拆成“当前状态”和“归档”两部分；
   - 一次性迁移按 RFC 分开生成。
