## 1. 背景

RFC-381 之后，任务执行是两个 provider 装配差异最大、SQLite 进程内重复最多的一组。2026-10-20 的四路只读研究（任务执行、数字员工、
开发自动化、意图）确认：

- **SQLite 进程内有四个会话级任务驱动协调器，配置各不相同**：
  - S 的路由启动协调器：本地同步模式，带记忆提炼，不带子 Agent 实时捕获；
  - S 的宿主动作协调器：启动时快照，不带提炼，供开发自动化与数字员工的宿主任务使用；
  - V 的数字员工协调器、V 的任务路由协调器：选择模式。

  V 还另建了一整套任务路由操作、启动参与者、定时任务立即运行、概览、澄清指令路由、工作组房间工厂与持久化，全部在生产中生效。
  PostgreSQL 只有一个会话协调器。
- **由此产生的行为差异**：
  1. **SQLite 续跑丢配置**：单机重启后的自动续跑与生命周期修复续跑，把启动配置原样展开，没有经过 `runtimeConfigOpts`。
     提交推送的模型、运行时、语言、排除规则、修复重试、diff 上限，以及合并 Agent 的模型与运行时，全部退回默认。
  2. **记忆提炼覆盖不全**：执行结束的记忆提炼（RFC-366）只在 SQLite 的路由启动与 HTTP 启动上生效。PostgreSQL 的启动、
     两边的续跑、数字员工与开发自动化的宿主任务都不提炼。
  3. **启动设置读取时机不一**：子 Agent 实时捕获、克隆超时与基线同步窗口，有的路径实时读取，有的路径用组合时的快照，
     改设置后要重启才生效。
  4. **PostgreSQL 缺门控续跑前置步骤**：PostgreSQL 的会话协调器没有「门控续跑前置步骤」（澄清收敛与待执行的工作区回退效果）。
     评审回退或澄清回答之后，续跑在 PostgreSQL 上可能不执行这一步（需用例确认）。
  5. **引擎异常处理不一致**：SQLite 只记日志，任务停在运行中，直到空闲超时或重启修复；PostgreSQL 把任务置为失败并终结意图。
     S 的宿主动作环境注释声称已与 PostgreSQL 对齐，实际上异常在到达失败上报之前就被吞掉了。
  6. **PostgreSQL 会话读错运行注册表**：维护任务的「活跃任务」输入与工作区清理的运行中守卫读的是进程级注册表，
     看不到 PostgreSQL 自己的驱动。
  7. **动态工作流校验不一致**：PostgreSQL 以系统身份列资源目录，与 RFC-381 修复的定时任务校验同源，可能误拒内置 Agent 引用
     （需用例确认）；SQLite 直接读库。

## 2. 目标

- **G1 中立构造函数**：任务执行组由 `cli/daemonModules/taskExecution.ts` 中一个 provider 中立的构造函数产生，两个 provider 的
  会话组合各调用一次。provider 差异只经适配器表（查表，不比较 provider 名）进入：执行模块与认领方式、进程并发作用域、
  融合引擎适配器、仓库准备重试命令、provider 运行时组合函数。
- **G2 SQLite 进程内去重**：任务执行成员每会话只构造一次。
  - V 改用注入实例，回退分支调用同一构造函数；删除 V 在生产中重复构造的任务路由操作、两个协调器、启动参与者、定时启动、
    概览、澄清指令路由、房间工厂、持久化与任务目录来源。
  - 宿主任务（开发自动化、数字员工）改用会话的根工作流启动内核，删除 SQLite 专用的宿主协调器。
- **G3 唯一协调器与运行配置**：每会话一个任务驱动协调器、一个实时运行配置来源，由会话协调器、根续跑与宿主任务共用。
- **G4 统一行为**：按 §6 统一 §1 列出的七处差异。

## 3. 非目标

- 每次调用现建的驱动协调器（子任务启动、续跑、PostgreSQL 融合、SQLite 融合、人工门唤醒、仓库准备重试）改经工厂端口，
  两个 provider 运行时函数合一：后继 RFC-385。
- 门控续跑的唤醒机制、工作组房间续跑、仓库准备重试语义、融合适配器：另行决定（RFC-385）。
- 数字员工与开发自动化模块组（RFC-383）、意图模块组（RFC-384）、SQLite HTTP 装配并入中立挂载表与删除测试回退（RFC-386）、
  部署 profile（S2c）。
- 不改 API 路径、事件、schema；不做任何安全相关改动。

## 4. 用户可见变化

单机 SQLite：

1. **续跑沿用设置**：重启后的自动续跑与生命周期修复续跑沿用设置页的提交推送与合并 Agent 设置（此前退回默认）。
2. **引擎异常即失败**：任务立即显示失败（「task drive failed」）并可重试；此前停在运行中，直到空闲超时或重启修复。
3. **提炼覆盖更全**：续跑，以及数字员工与开发自动化的宿主任务，也按现行提炼策略做执行结束的记忆提炼（策略关闭则无变化）。
4. **设置即时生效**：子 Agent 实时捕获、克隆超时、基线同步窗口在所有启动与续跑路径上实时生效，此前部分路径要重启。

PostgreSQL（单机与托管）：

1. **提炼覆盖更全**：执行结束的记忆提炼覆盖启动、续跑与宿主任务。
2. **续跑执行前置步骤**：评审回退、澄清回答之后的续跑执行门控前置步骤（若用例确认此前缺失）。
3. **识别运行中任务**：维护任务与工作区清理能识别正在运行的任务。
4. **不再误拒内置 Agent**：动态工作流引用内置 Agent 不再被误拒（若用例确认此前误拒）。
5. **设置即时生效**：单机的子 Agent 实时捕获、克隆超时与基线同步窗口改为实时生效。

## 5. 验收标准

- **AC-1 构造位置**：任务执行组由 `cli/daemonModules/taskExecution.ts` 的一个构造函数产生；S 与 P 各调用恰好一次；`server.ts`
  只在 `deps.x ?? <同一构造函数>(...)` 回退中调用（结构锁）。
- **AC-2 单实例**：SQLite 守护进程内，会话级协调器、任务路由操作、启动参与者、定时启动、概览、澄清指令路由、房间工厂、持久化、
  任务目录来源各只有一个实例。三个入口根中不再出现 `createTaskDriveCoordinator(` 与 `new DefaultTaskDriveCoordinator(`
  （结构锁与注入实例同一性的行为测试共同证明）。
- **AC-3 行为统一**：§1 的七处差异按 §6 统一，各有双引擎回归用例（design §5）。标「需用例确认」的两项先以用例确认修复前的行为；
  若确认无差异，记录依据，不做改动。
- **AC-4 旧锁与账本**：受影响的旧锁改指新位置，不放宽断言意图；`architecture/commons-debt.json` 中三个入口根到 task-execution
  内部的 R1 条目随构造迁移删除或改指；`architecture/counts.json` 不升。
- **AC-5 CI 全绿**：推送后 exact SHA 的 GitHub Actions 全绿。

## 6. 已作出的取舍（用户授权本会话按推荐决定，可推翻）

1. **构造粒度为每个 provider 会话一次**：同 RFC-380。
2. **一份实时运行配置**：会话组合给出 `runConfiguration()`，每次调用由 `taskLaunchConfiguration.start()` 投影，内容包括：
   - `runtimeConfigOpts`（带记忆提炼入队器）；
   - 子 Agent 实时捕获；
   - 应用目录、配置路径；
   - 克隆超时与基线同步窗口。

   会话协调器、根续跑与宿主任务共用这一份。模式同 RFC-381 的融合运行配置。
3. **会话协调器在两个 provider 上都带门控续跑前置步骤**：SQLite 的现行语义。
4. **引擎异常一律经失败上报**：任务置为失败并终结意图，即 PostgreSQL 的现行语义，也是 S 宿主动作环境注释所述的本意。
5. **宿主任务使用会话的根工作流启动内核**：SQLite 的 provider 运行时补出与 PostgreSQL 相同的 `routeLaunch.workflow`。
   宿主任务的身份解析与取消暂按现状保留，由 RFC-383 统一守护身份时一并处理。
6. **动态工作流校验统一为读库的中立上下文**：即 SQLite 现行实现，改中立名称；PostgreSQL 不再依赖启动步骤设置的系统身份。
7. **PostgreSQL 会话的活跃任务与清理守卫改读本会话的执行模块**。
8. **每次调用现建的协调器留给 RFC-385**：本 RFC 不改它们的构造方式。
9. **偏离项**：构造函数放在 `cli/daemonModules/`（同 RFC-379～381），S2c 迁入 `bootstrap/`。
