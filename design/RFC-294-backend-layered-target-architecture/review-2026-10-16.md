# 2026-10-16 RFC-294 全面审视：设计校正与架构腐化整改

## 0. 结论

用户要求全面审视 RFC-294 的实现情况，指出原始设计中已不合理的部分与需要马上整改的架构腐化，并据此刷新 RFC-294。
本文是这次审视的源码证据与判断；刷新后的三件套（[proposal](./proposal.md) / [design](./design.md) / [plan](./plan.md)）
只保留结论与合同，刷新前全文归档在 `archive-20261016-{proposal,design,plan}.md`。

**总判断：RFC-294 的大方向仍然正确，而且物理迁移已基本完成；但"代码进了 `modules/`"之后，腐化换了形态，
在模块内部、装配根和执行链上重新长了出来。原设计有八处已不合理，需要修订；有十类腐化需要马上止血。**

1. **已经真实落地**：`modules/` 已占后端源码约 68%（1,664 文件 / 30.9 万行），`services/` 从 08-30 的 14.6 万行
   降到 5.6 万行；route→DB、transport→DB、route/MCP 的 `AppDeps` 反向依赖均为 0；后端值级 SCC 从 08-26 的 5 降到 1，
   `KNOWN_VIOLATIONS` 从 37 降到 8；W2/W3 的协调器、闭集注册表、WrapperRuntime 与已提交事件是真实生产链；
   RFC-359 的事务统一属实（同步 `dbTxSync` 已无生产调用点）。
2. **腐化的新形态**：`composition/` 成了新的 `services/`（全仓非入口 composition 文件 232 个、约 4.0 万行，其中约
   2.3 万行是业务或机制实现，且仍在增长）；装配根从 08-26 的约 2.7k 行膨胀到约 12.3k 行，SQLite 与 PostgreSQL 两个根的
   装配约 55% 逐字重复，同一个 SQLite daemon 内若干模块还经 `server.ts` 被构造第二次并已造成两个缺陷；context 之间
   出现值级环；`platform/` 开始承载领域状态机并反向依赖模块；执行链"四级内核"中只有 WrapperRuntime 是真实层。
3. **一个正确性风险**：NodeRun 的"谁更新"仍按 ULID 字典序判定，而铸造用的是普通 `ulid()`——代码注释自己承认同毫秒内
   约一半逆序；托管部署（RFC-370）让铸造进程跨主机迁移，判据还会依赖主机时钟。W7 的第一刀应从"建模改进"提为
   "正确性修复"。
4. **治理的投入与产出失衡**：自 08-15 起约六分之一的提交（10 月上半月超过五分之一）只为维护账本，常驻约 34 MB 账本
   JSON、比全部生产源码还大；而"只降不升"的库存照样上升（增长许可 1,245 次，全部自助放行），96% 的 exception 只是
   "碰到了尚未迁移的文件"，部分指标测的也不是它名字所说的东西。持久的改善全部来自少数几条 depcheck 式规则。

## 3. 现状：值得保留的主链

- **执行与事务**：`TaskDriveCoordinator`、三路 TaskEngine 注册、14 类 NodeExecutor 注册、WrapperRuntime 的
  Loop/Git/Fanout 策略、生命周期 CAS 与已提交事件同事务、人工门持续续跑，均有真实调用链。
- **双库**：`platform/persistence/databaseTransaction.ts` 被 168 个文件引用，`databaseSessionFor(` 出现在 117 个文件；
  同步 `dbTxSync` 只剩定义、没有生产调用点。剩下的 provider 债主要是两个 daemon 根的重复（F2），不是业务算法双份。
- **托管轴的大方向**：部署模式的分支基本被压在 application 层以下——application/domain/engine 没有 import
  `infrastructure/crewstation` 或 `platform/crewstation`，也没有 `if (crewstation)`；例如
  `modules/system-operations/application/ports/executionAuthority.ts:15-29` 定义端口，本地与 CrewStation 两个实现分别在
  `infrastructure/local/` 与 `infrastructure/crewstation/`。
- **新模块的正面样板**：RFC-371 v2 的 `modules/run-observability` 共 17 个文件、约 2.0k 行，domain 纯净、application 只依赖
  本域端口、持久化只在 infrastructure、只有一个装配文件。它是"删掉 v1、按目标分层重做"而不是"逐条账本迁移"得到的。

## 4. 原始设计中已不合理的部分

### R1. 在总纲里手写精确接口

- **原设计**：design §3.3 规定逐 symbol / 逐字段 / 逐方法的 public-surface 账本 schema；§3.5 用 1,560 行 TypeScript 写出
  跨模块接口的 exact V1；§4～§15 另有大量类型桩。
- **现实**：design.md 共定义 327 个类型 / 接口名，HEAD 的 backend 与 shared 源码中只出现 78 个（24%），其余 249 个
  （76%）从未存在；§3.5 的 193 个名字里 142 个不存在。08-30 review §A2 已裁决"接口以 `public/*.ts` 为唯一事实、§3.5 外迁"，
  六周后仍未执行。successor 落地时普遍改名、改形（RFC-368 的类型名按其 design 调整；RFC-370 v2 的 `ExecutionPort` 也与
  总纲不同），总纲文字反而成了需要逐条"对账偏离"的负担。
- **修订**：总纲只定方向、边界、层次规则、不变量与 owner；精确接口以代码（`modules/*/public/*.ts`、
  `application/ports/*.ts`）和后继 RFC 的 design 为准。旧 §3.5 等归档，不再作为任何退出门。

### R2. 用全量精确账本治理架构

- **原设计**：D9 / AC-11 / AC-12 与 N1 要求每个 production symbol 有 owner、每条跨 context 边有 exact exception、
  每个 public 字段 / 方法 / consumer 入账，CI 双向对拍，并以 provenance pin 固定内容。
- **现实**（见 F9）：仓库常驻约 34.4 MB 账本 JSON（`module-symbol-owners.json` 约 12.9 MB、`cross-context-imports.json`
  约 10.3 MB、`public-surfaces.json` 约 7.0 MB），是全部生产源码（约 28.2 MB）的 1.2 倍；`tests/architecture/` 80 个文件
  约 3.5 万行，生成器 `rfc294Canonical.ts` 5,089 行。自 2026-08-15 起 3,368 个提交中 1,628 个（48%）改动 `architecture/`、
  554 个（16.4%）是 `chore(architecture)` 伴随提交，10 月上半月升到 22.4%（08-30 review 时为 10.8%）；同期账本 churn
  约 286 万行，是生产源码 churn 的 2.4 倍。抽样 08-26 以来 711 次失败 main CI 中的 75 次：36% 含账本类失败、12% 只因账本
  失败（误差约 ±11 个百分点）。它挡住退化了吗？没有：持久的改善（`KNOWN_VIOLATIONS` 37→8、route→DB 15→0、`AppDeps`
  54→0、后端 / 全仓 SCC 5/7→1/3）都来自 depcheck 一类规则，并在 09-10 前后已经完成、此后持平；而“只降不升”的库存持续
  上升：09-15→10-14 间 exception、跨 context 边、public surface、mutation 入口分别增长约 40%、44%、35%、21%；以已提交投影
  比较，ambient 自 W3 收口时的 448 升到 508，background 自 265 升到 355，exception 自 09-22 重分桶后的 4,802 升到 5,726。
  增长靠许可放行：08-15 以来 432 个提交授予了 1,245 次 `allowGrowth`、440 个提交又全部退役，
  `tests/architecture/rfc317-ledger-highwater.test.ts:113-146` 只检查“增长时有许可、下一笔已退役”——这是自助放行，
  不是棘轮；`ledger-baselines.json` 中 ambient 与 background 的基线分别被抬高过 27 次和 50 次。exception 里 96%
  （legacy-outbound 3,562 + legacy-inbound 1,943）只是“碰到了尚未迁移的文件”，可行动的只有 221 条（temporary-internal-debt
  112、off-DAG 97、depcheck 8、external-layer 4）；每条 exception 都由生成器按模板写出（`why` 模板、
  `introducedByRFC: 'pre-RFC-294-current-debt'`、`expiresOn: '2027-12-31'`，见 `rfc294Canonical.ts:3969-3981`），
  09-05 以来新增的 2,637 条里有 2,635 条声称是 RFC-294 之前的存量。更关键的是指标本身失真：ambient 的 93% 是
  `registerRoute` 一类路由注册
  （`tests/architecture/rfc294Canonical.ts:3837-3839` 把所有 `register*` 都算进来），而真正的模块级可变单例
  （`bind*` WeakMap 侧表、`childBudget` 单例 setter、按 DB 句柄缓存的 locator 等，跨 26 个文件共 35 个导出的
  setter / bind / reset）反而没被计入；background 账本 355 条里只有 11 条 managed、255 条阶段为 unknown、
  约 62 条根本不是作业（常量、schema、辅助函数）；legacy-outbound 3,562 条边约 80% 指向 `db/` `util/` `platform/`
  `auth/` 这类内核式文件，其中 `db/schema.ts` 的 913 条有 904 条来自 infrastructure——这是允许的形态，不是债。
- **真正起作用的门**是少数几条：depcheck 的 `no-circular` 与 `KNOWN_VIOLATIONS`、route/transport→DB、模块内分层、
  `node_runs` 单一 INSERT 站点、offered 边 ⊆ 设计 DAG。
- **修订**：D9 改为"少量硬结构门 + 按需生成的报告"：硬门不设增长许可，确需增长就改设计；全量库存改为按需生成、
  默认不提交，不再要求 provenance 两笔提交。具体改造由治理后继 RFC 实施（S4）。

### R3. "四级线性执行链"与无处落位的 ExecutionKernel

- **原设计**：TaskEngine → WrapperRuntime → NodeExecutor → ExecutionKernel 四级，RFC-287 的 `runAssembly` 是 kernel 第一刀，
  最终归 `task-execution/engine/kernel/assembly/`。
- **现实**：
  - TaskEngine：`engine/task` 共 93 行，引擎都是一行委托（`modules/task-execution/engine/task/dag/dagTaskEngine.ts:9-11`）；
    真实主体是 `composition/taskEngineApplication.ts:199` 起的 731 行函数，每次运行重建引擎注册表（`:593`），还保留一条
    无 owner 的旧派发分支（`:640-685`）。三个引擎里有两个的主体不在 task-execution：workgroup 轮次在
    `modules/resource-catalog/composition/workgroupTurns.ts:13`（在 `cli/start.ts:2244` 与 `server.ts:2332` 各装配一次），
    动态工作流在 `services/dynamicWorkflowRunner.ts`。
  - NodeExecutor：`engine/node` 338 行是壳加网关；`composition/nodeExecution.ts:48-58` 的 `legacyArgs` 把每种 kind 绑回
    `composition/nodeMechanics.ts`（5,507 行）里的 `run*Node`，例如 `runAgentSingleNode` 在 `:3720`，独占 1,324 行。
  - WrapperRuntime：`engine/wrapper` 1,103 行，是唯一真正拥有策略的层（如 `loopStrategy.ts:30`）。
  - ExecutionKernel：源码中没有这个符号，也没有 `engine/kernel` 目录。`runAssembly` 仍在 `services/schedulerAssembly.ts:184`，
    五个调用方全在 composition（`nodeMechanics.ts:328/2743/4731`、`wrapperMechanics.ts:744/1276`）；隔离与合并在
    `modules/task-execution/infrastructure/isolatedAgentRun.ts` 与 `platform/workspace/local/isolation.ts`，
    许可与限流在 `services/{taskWriteLocks,processNodeConcurrency,taskFanoutPools}.ts`。
  - 执行也不是"链"：git/loop wrapper 回到 `runScope` 递归，fanout 的分片绕过 NodeExecutor 直接调 `runAssembly`，
    workgroup host 经 `executeHost` 进入 `nodeMechanics.ts:328`。真正的执行上下文是 22 个顶层字段的 `TaskMechanicsState`
    （`services/execution/taskMechanicsState.ts:41-74`，含 5 个信号量与一个 `driveScope` 回调），在 10 个 composition
    文件的 55 个签名间传递。
- **修订**：目标结构改写为"任务控制面（协调器 + 三个任务引擎）→ 递归 scope 解释器（DAG scope、frontier、wrapper 策略，
  显式允许递归）→ 节点执行器（每种 kind 拥有自己的主体）→ 执行机制库（assembly、隔离 / 合并、许可、铸造、进程）"。
  kernel 是引擎内部的机制库，不是链上一级；每一层必须拥有自己的决策，不允许"类型化委托壳"。workgroup 与动态工作流
  引擎迁回 task-execution。

### R4. "单 daemon"非目标与缺失的部署维度

- **原设计**：proposal §7 "不以微服务、容器或多进程 daemon 为目标；当前仍是单 daemon"，全文没有部署 profile 的概念。
- **现实**：RFC-370 托管部署已有服务槽（蓝绿两槽）、迁移作业、任务镜像内的 `workspace` 子命令、执行权租约
  （standby / active / frozen）、对象存储与远程执行。当前的接入方式是：`main.ts:376-379` →
  `cli/deployment.ts:25-44` 读 `AW_DEPLOYMENT_MODE` → `bootstrap/crewstation.ts:32-128` 返回一份 `StartOptions`
  覆盖（`cli/start.ts:471` 起的接口有 55 个可选槽），各模块再用 `selected ?? createLocal…()` 形态的 `select*` 助手择一。
  `cli/deployment.ts` import `@/bootstrap/crewstation`，`bootstrap/crewstation.ts` 又 import `@/cli/start` 的类型，二者互相依赖。
  进程内的不变量（例如 apply 收敛的进程内活跃集合与 10 分钟年龄判定、进程内锁）在多实例下不再充分。
- **修订**：新增部署 profile 维度（D10）：端口按语义定义在拥有方 context 的 `application/ports`；适配器放
  `infrastructure/<profile>/`（`local`、`crewstation`），厂商线协议只在 `platform/<vendor>/`；选择只在 bootstrap 发生一次，
  以每模块一份类型化的适配器集合表达；domain、application、engine、入站适配器、platform 与入口根都不得按部署模式分支；
  进程角色显式化；进程内不变量要么声明为 standalone-only，要么改为持久 claim；跨进程协议必须类型化。

### R5. "唯一 bootstrap 根，W9 最后再收"

- **原设计**：`bootstrap/{composition,http,workers,shutdown}.ts` 是唯一装配根，DaemonContainer 留到 W9。
- **现实**：根在 W9 之前就失控了（F2）。`server.ts` 4,571 行、`cli/start.ts` 4,240 行、
  `cli/postgresqlDaemonApplication.ts` 2,819 行（N1 时不存在）、`main.ts` 659 行，四者合计约 12.3k 行，是 N1 时
  （约 2.7k 行）的 4.6 倍；另有位于 `platform/` 的 Worker 根 `platform/background/maintenanceWorker.ts`（930 行、
  29 个模块级 `let`）。而 `src/bootstrap/` 只有 3 个文件、251 行的托管覆盖层。
- **修订**：允许多个**薄**入口根（daemon、Worker 线程、CLI 命令、任务镜像助手），但它们共享**一张**模块工厂图；
  SQLite/PostgreSQL 与 local/hosted 都是这张图里的适配器选择，不是另起一个根。W9-A 的容器提前到下一批（S2），
  因为托管工作正在往两个 daemon 根里不对称地加装配。

### R6. 按"指向 legacy 文件的边"计债，并以 W9/W9-D 兜底

- **原设计**：凡 module 指向非 module 文件的边记 `legacy-outbound`、凡 legacy 指向 module 的边记 `legacy-inbound`，
  逐条给 `removeAfterWave`。
- **现实**：已提交账本的 5,726 条 exception 里 2,942 条归 W9、1,079 条归 W9-D，合计 70%；`platform/` 自己也被计作
  legacy；指向 `util/errors.ts`、`db/query.ts`、`databaseTransaction.ts` 的边被当作债，而它们大多是合法的平台依赖。
  这样的账既不能排期，也看不出哪里在变坏。
- **修订**：债按具体结构规则记（环、跨 context 内部 import、composition 承载实现、platform 反向依赖、入站适配器绕过
  public 等），每条有明确后继；平台原语与 infrastructure 访问 schema 是合法依赖；删除 W9-D 兜底桶。

### R7. 已过时的波次依赖与退出门

- W4-B「15 个 route→DB 切片」、W4-D「`AppDeps` 54→0」早已归零（RFC-349 的 application-owned DB ports 顺带完成），
  继续保留会误导排期；真正的余项是入站适配器仍绕过 public：59 个 route 文件中 29 个 import `services/`、11 个深引模块
  内部；legacy 一侧，`services/` 到模块内部（绕过 public）的边有 490 条，legacy 文件（含各根）对 147 个 composition 文件
  存在 363 对深引用。
- W7 依赖 W5（"后端零环"）没有技术理由：NodeRun 身份与 `util/git` 环族无关，这条依赖只是把一个正确性问题排在一项
  无关清理之后。
- `code-capability` 被描述为"只剩 upstream merge 一个兼容写点的退役孤岛"、19 个文件；现实是 51 个文件、5,634 行，

### F9. 治理成本与失真

- 数据见 R2。补充：按 `docs/dev-gotchas.md` 的现行做法，一次普通生产改动要经过约 10 个步骤、2 笔提交（账本增长时 3 笔）：
  先完成全部编辑（census 之后任何一个字节的改动都会让全局 sourceDigest 失效），手工给增长的账本写许可并退役上一笔的许可，
  带 `--snapshot-sha HEAD` 运行 census，再把 `architecture/` 与 status.md 成组暂存、提交，随后再补一笔
  `chore(architecture)` 投影；共享脏树上还要另做导出。任何一步漏做都会让 CI 在与本次改动无关的守卫上变红

  （约 1,310 / 8,605 行）在讲账本机制，同一条许可规则被重述了 7 次；`zsh` 分词导致投影漏推的事故已第六次复发。
- **止血**：不再新增全量库存类账本或新的增长许可类别。
- **后继**：S4（治理简化：保留硬门、库存改按需生成不提交、修正 ambient / background 的计数口径、加入 context 无环与
