# 2026-10-14 仓库架构与 RFC-294 落地调研

## 1. 定位、结论与证据范围

用户要求全面审视代码仓架构及 RFC-294 的落地情况，并将 RFC-294 作为长期架构重构 RFC 维护。本记录保存本轮调研结论，
供后继 RFC 选题、划定范围和验收对账使用；此次发布不启动新的生产重构。

**总体判断：仓库已经形成具有实质执行、事务、恢复能力的模块化单体，但仍处于目标架构迁移中。机制归一的进度明显领先于
context 边界、组合根收缩和生命周期治理。RFC-294 应继续保持 In Progress，按已批准的独立 successor 逐项收敛。**

这不是“只有目录迁移”的仓库：TaskDriveCoordinator、TaskEngine/NodeExecutorRegistry、WrapperRuntime、committed events、
统一数据库事务和生产 Reaction admission 都能沿调用链找到真实接线。另一方面，进入 `modules/`、route 不再直连 DB、
账本分类完整、局部 RFC Done，均不能单独证明整波退出。

## 2. 仓库整体架构判断

| 维度 | 已形成的能力 | 当前主要约束 |
| --- | --- | --- |
| 部署与进程 | Bun 后端、React 前端、共享 schema/领域值与 System Mock；daemon、HTTP/MCP、CLI 共用大量业务能力 | 多个实际启动入口和兼容装配面仍较重，根中仍需分离业务选择与纯接线 |
| 后端模块 | `modules/<context>` 已有 domain/application/ports/infrastructure/composition 等层次 | 物理模块不等于完成边界切换；legacy services、内部 import 和大 composition 文件仍承担实质业务 |
| 执行内核 | coordinator、闭集 engine/executor registry、wrapper lifecycle、唯一 NodeRun mint 已落 | 任务机械步骤、老 task service 与装配层间耦合仍大，不能将 W2 Done 扩记为 W4/W7 Done |
| 数据持久化 | SQLite/PostgreSQL 共享事务与场景实现，migration/admission/boot 已有统一基础 | 仍需按 context 收回跨域持久化职责；W6 的两个场景 lifecycle 尚未统一 |
| 事件与恢复 | lifecycle 写入和 committed event 同事务，delivery、continuation 与恢复链有实际实现 | 后台工作尚未整体纳入目标 registry/readiness/stop receipt 合同 |
| 架构治理 | AST census、owner/public/required-port/exception 等账本及依赖守卫齐备 | 部分指标是语法库存；存在守卫漏检和分类误差，不能将账本变绿等同于架构目标达成 |
| 前端与 shared | 共用 schema、工作流 transition、会话呈现和功能路由已具规模 | 超大 route/controller 与 frontend/shared 值级环仍在，需沿用户用例拆分职责 |

当前 SCC 仍可精确定位：后端是 `gitRepoCache/gitSubmodule/gitVersion/util/git` 一族；前端是
`ConversationFlow ↔ SubagentBlock`；shared 是 `outputKinds/list ↔ registry`。
这些是已登记的依赖债务，不能因其已在 allowlist 内而当作已消除。证据见
[depcheck 的 exact 违规登记](../../scripts/depcheck.ts) 中 `KNOWN_VIOLATIONS`。

## 3. RFC-294 逐 Wave 对账

“Done”沿用 successor 已有的范围与验收记录；“未关闭”表示整波退出条件未满足，不抹去已落纵切。本表不重开已关闭 RFC，
也不把本次静态审视当作重新执行其全部测试。

| 区域 | 本轮判定 | 已落与剩余范围 |
| --- | --- | --- |
| P0 | 保留既有关闭结论 | RFC-328/333/342/343 等的正确性纵切已完成；后续架构迁移单列 |
| W0-R | 治理基础已落，判读口径需校准 | canonical、owner、接口和依赖分母已存在；本报告 §4.1/4.2 的缺口需独立治理，不据此将生产迁移记为完成 |
| W1 | 既有行为已落，架构余项随后继收敛 | 保留 RFC-287 的行为基线；target module、owner 与相关边界仍按其余波次退出 |
| W2 | Done | coordinator、engine、executor、wrapper 均有真实生产链；大 `nodeMechanics` 和旧 service 的职责收缩仍需后继处理 |
| W3 | Done | lifecycle 与 committed events、人工门 continuation 已落；全局后台生命周期仍归 W9 |
| W4 | 部分完成 | A/C/E0/E2/E3/E4a/E4b/E6/E7 已关闭；RFC-363 关闭 E1/W5 启动与工作区纵切；RFC-361/365/368 分别交付 E9 的 EC provider、Event target、Reaction 切片；B/D 余项及完整 E1/E5/E8/E9/E10 仍开放 |
| W5 | 部分完成 | Task/SC source、preparation、workspace reader 已有生产切换；Git SCC、repo/cache/group/worktree/content ownership 与其余 consumer 仍待收敛 |
| W6 | 场景内双库合一，公共 lifecycle 未统一 | Intent 与 ResourcePackage 各有 claim/apply/compensate/recover 编排；不能把 provider 合一记为两类场景共享一个 AtomicApply engine |
| W7 | frame/scope 与 single mint 已落，v2 identity 未完成 | RFC-354/359/369 提供前置；generation/seq、identityVersion、回填和 freshness reader 切换未完成 |
| W8 | 可选、延后 | 旧 RFC-289 关闭；需 W7 后独立立项批准，不阻塞核心 W9 |
| W9 | 已有实质生命周期基础，整体未退出 | provider runtime session、handle、polling/drain 已落；全局 container、背景任务 registry、阶段/依赖/readiness 与 facade 退出尚未完成 |

## 4. 六项主要发现

### 4.1 模块分层守卫尚未覆盖完整目标合同

目标设计的层依赖矩阵要求 application 通过端口使用 FS/进程/WS 等 effects，但
[module-layer-rules 守卫](../../packages/backend/tests/architecture/rfc294-review-module-layer-rules.test.ts)
中的 `DOMAIN_FORBIDDEN` 只对 domain 生效；application/engine 主要检查 `@/db/schema` 字面路径和 infrastructure import。

已提交的 [Intent maintenance](../../packages/backend/src/modules/intent/application/maintenance.ts)
在 application 层直接 import `node:fs`，`sweepIntentScratch` 实际执行 `readdirSync/statSync/rmSync`。
因此 `MODULE_LAYER_RULE_DEBT=[]` 只能说明该守卫覆盖的规则未留下登记债，不能证明目标层次矩阵已全满足。
application 层存在的 WS 等已登记依赖，也应与此类未覆盖形态区分。

**建议**：先明确每层允许的 import/运行时 effects，再完善语义相符的规则、存量明细和反例。
迁移按实际 owner 逐项交付；不得通过放宽断言或批量搬目录获得“零违规”。本次只登记，未修改守卫或业务实现。

### 4.2 canonical 的部分分类不能直接解释为目标债务

`packages/backend/tests/architecture/rfc294Canonical.ts`（RFC-376 已删除） 的 `observedContextEdges`
将 module 指向 backend 中非 module 文件的边统一列为 `legacy-outbound`。
这使部分本来允许的中立 `platform/contracts` 依赖也进入该类。例如
[retryAttemptCap](../../packages/backend/src/platform/contracts/retryAttemptCap.ts) 被 TE/DE 复用，正是既有设计允许的中立算法共享。
需要保留完整边分母，同时将合法目标形态与待迁移依赖分开表达。

同一文件的 ambient 采集按 `configure/install/register/set` 方法名与关键词识别，`set*` 直接标为 `global-setter`。
其中 `setRuntimeEnabled` 的若干调用实际是业务/持久化命令，不是设置进程全局依赖；实例 registry 注册也不必然是 ambient wiring。
因此这些计数是待分析库存，不能直接宣布对应数量的全局单例。

同理，background inventory 的 `managed` 标记和原生 timer AST 数量不能当作运行时治理覆盖率：
已无生产 caller 的旧启动 helper、执行局部 timer、真正 daemon job 必须分开；transaction “co-located-risk” 也不是已证实的事务内外部副作用。

**建议**：治理后继区分依赖目的地与调用所有者、实例绑定与全局槽、定义与实际启动点。
校准 generator、完整分母和规则后再重采，不手改 JSON 降数。原始库存可保留，目标债务应有独立明确的判定。

### 4.3 W4 的 consumer 与组合根收缩仍是主线

两个能直接看到“声明存在”和“生产边界完成”差别的例子：

- **Task Catalog**：[route](../../packages/backend/src/routes/taskCatalog.ts) 仍 import composition；
  [module contract](../../packages/backend/src/modules/task-catalog/composition.ts) 接 full `Actor`/字符串过滤并返回 JSON string；
  [query service](../../packages/backend/src/modules/task-catalog/application/taskCatalogQueryService.ts) 内继续聚合并序列化。
  当前统一目录行为已存在，但与 E10 要求的 public typed query/source contract 仍有距离，不能据页面可用关闭 E10。
- **Development Automation**：
  required-ports 声明（`packages/backend/src/modules/development-automation/composition/required-ports.ts`，已于 RFC-375 删除）
  包含 requirement、interaction、MR facts、pipeline evidence、code-host effects、agent action、upload placement、reconciler 等合同，
  canonical 仍将这一组无 provider/consumer 接入的接口记为 declared debt。声明不等于调用链已切换。

此外，[nodeMechanics](../../packages/backend/src/modules/task-execution/composition/nodeMechanics.ts) 仍是承载大量执行机械步骤的
composition 大文件，且调用 `runAssembly`；[task service](../../packages/backend/src/services/task.ts) 仍包含大量业务。
`server.ts` 中多个 compose 入口也须逐一核对实际生产和测试兼容职责，不能仅按名称判为重复生产算法。

**建议**：每个 context 的迁移同时交付 public command/query、consumer-owned required port、exact provider、真实 consumer
和对应 B/D 收缩；不能只搬 provider 文件、追加接口或继续扩大 composition。保留现有 wire/业务语义作为验收基线。

### 4.4 W6 仍有两个场景生命周期，不能重复做 provider 合一

[IntentApplyEngine](../../packages/backend/src/modules/intent/infrastructure/intentApplyEngine.ts)
独立处理 claim、幂等重放、apply、compensation 与 convergence；
ResourcePackageAtomicApply（`packages/backend/src/platform/persistence/postgresqlResourcePackageAtomicApply.ts`）
也有自己的 claim、prestage、transaction、commit、roll-forward 和 compensation。

后者虽带历史 `postgresql` 文件名，已被两个 provider 共用。当前欠账是两类场景之间的 lifecycle 归一，
不是重新消除一对 SQLite/PostgreSQL 副本。

> 更正（2026-10-22，RFC-395 II-a A6）：上文第二个文件已删除，资源包引擎迁至
> `packages/backend/src/modules/resource-catalog/infrastructure/resourcePackageAtomicApply.ts`，两类场景共用
> `packages/backend/src/platform/atomic-apply/` 的状态机与恢复。原链接改为纯文本路径，以免链接检查指向不存在的文件。

**建议**：提取唯一 AtomicApply lifecycle，并把领域规则留在 scenario participants；以真实 claim/replay/补偿/崩溃恢复链证明收敛。
P0-B 的既有恢复正确性保持，不能把相似代码合并当作唯一验收条件。

### 4.5 W7 的 single mint 不等于 v2 identity

[nodeRunMintParticipant](../../packages/backend/src/modules/task-execution/infrastructure/nodeRunMintParticipant.ts)
已提供唯一插入路径，已有 frame/scope/lineage。
但 freshness（`packages/backend/src/services/freshness.ts`） 的 `isNewer` 仍比较 `candidate.id > incumbent.id`；
[nodeRunSupersession](../../packages/backend/src/modules/task-execution/domain/nodeRunSupersession.ts) 仍按同节点/帧/迭代下的 ID 顺序推导新旧。

固定基线的 `node_runs` schema 未落完整 identityVersion、generation/seq 与目标消费关系；
其他表存在 `seq` 或已有 retry/frame 字段，都不能作为 W7 完成证据。

**建议**：按原计划一起定义 identity、generation、顺序、回填与全部 freshness/consumption readers 的切换。
复用 single mint 和 RFC-369 的 supersession 语义，避免增设第二个铸造点或长期双套新旧比较规则。

### 4.6 W9 已有可复用基础，但尚无完整目标 registry

[daemonProviderRuntimeSession](../../packages/backend/src/bootstrap/daemonProviderRuntimeSession.ts) 已提供 provider runtime 会话、
factory/close participant 管理与关闭排空；
[daemonProviderRuntimeHandles](../../packages/backend/src/bootstrap/daemonProviderRuntimeHandles.ts) 有 managed worker 和带 AbortController 的 polling handle。
`cli/start.ts` 已将 committed-event/after-commit/continuation 及若干 DE/Event/Fusion 循环接入这些实际根。
因此不能继续把 W9 描述为“全靠散落 setInterval、没有生命周期”。

但 [platform/background/definitions.ts](../../packages/backend/src/platform/background/definitions.ts) 主要提供 definition 与冻结，
阶段仍是 `before-ready/after-ready`；实际 root 仍列举 factory 集合。
这未等价实现设计中的 boot-recovery/pre-listen/pre-ready/post-ready、依赖拓扑、blocking readiness、统一调度/健康、逆序关闭和 stop receipt。

**建议**：从已接线的 provider session/handle 扩展 W9-A/B，建立唯一管理入口；按真实启动图接入所有适用工作。
execution-local timer 仍由其 aggregate 拥有，旧 helper 是否运行须追 caller。W9-E 的物理恢复与 generation 继续按双 provider 合同另行验收，
不能因该波未关闭而否认仓内已存在的 migration/generation 机制。W9-D 的最终 facade 清理仍等待前置满足。

## 5. 前端与 shared 的关联结论

前端不是 RFC-294 后端 wave 的全部分母，但会影响跨域合同和后续可维护性，需在相关功能 RFC 中一并治理。

- [WorkflowCanvas](../../packages/frontend/src/components/canvas/WorkflowCanvas.tsx) 已超过四千行，编辑、交互、状态同步等职责集中。
  其 `commitTransition → applyWorkflowTransition` 已是应保留的统一语义入口；拆分应沿 controller、查询、交互和呈现边界进行，
  不应把统一 transition 再拆成互相漂移的多套写逻辑。
- [数字员工类型页面](../../packages/frontend/src/routes/digital-employees.$typeRef.tsx) 同样超过四千行，承载多个页签、查询与表单。
  建议随相关功能 RFC 按用例拆容器和查询，并保持路由、共享组件及现有交互语义。
- [ConversationFlow](../../packages/frontend/src/components/node-session/ConversationFlow.tsx) 与
  [SubagentBlock](../../packages/frontend/src/components/node-session/SubagentBlock.tsx) 的互引、
  [outputKinds/list](../../packages/shared/src/outputKinds/list.ts) 与
  [outputKinds/registry](../../packages/shared/src/outputKinds/registry.ts) 的互引应按共同值/注册方向拆除。
  后端 SCC 的改善不能代表全仓已无环。

这些是结构改进建议，不是本次已批准的 UI 重设计；需要可见交互变化时仍遵守原型与用户批准流程。

## 6. 后续收敛顺序与验收口径

以下是调研建议，非批量开发授权。各 successor 应冻结自己的完整范围、开发及测试用例，再集中功能验证；
不通过缩小范围反复跑门来替代剩余开发。现有功能正确性、能力取舍与验收标准继续有效。

| 顺序 | 建议范围 | 必须交付的退出证据 |
| --- | --- | --- |
| 1 | 校正治理与入口状态 | 分层规则覆盖实际违例；合法平台合同、业务 setter、实例注册与真实债务分开；generator/分母/反例一致；successor 抵扣准确 |
| 2 | W4 按 context 完成 consumer 切换与对应 B/D | public/required/provider/consumer 的真实调用链；旧入口消费者退出；transport 不再装配领域；原功能与 wire 保持 |
| 3 | W5 与相关 E1/E5；W6 可在合同稳定后独立推进 | SC repo/cache/workspace/content owner 与 Git SCC 收敛；两个 Apply 场景共享唯一 lifecycle，领域恢复语义保持 |
| 4 | W7 identity 全链路 | schema/mint/backfill/freshness/consumption readers 全部切换；重放、重试、并行与历史数据有一致判据 |
| 并行准备 | W9-A/B 基于已落 provider lifecycle 设计与迁移 | 唯一实例装配与适用 background 工作注册；真实启动、ready、失败和停止链，而非只有 definition/账本 |
| 最终收敛 | 按前置完成 W9-C/E/D；W8 独立选做 | generation/restore 双 provider 行为、旧 facade/ambient consumer 退出；原波次退出条件逐项有证据 |

长期推进时每次对账应分开记录：

1. 目标合同是否批准，后继的用户裁决是否改变了原要求。
2. 生产 provider/consumer/根是否实际接线，旧路径是否真的退出。
3. 功能与恢复验收的候选内容、执行环境、具体结果。
4. full SHA 的 hosted CI 终态，以及它覆盖和未覆盖的范围。
5. 本次关闭了哪些 exact debt/子切片，哪些责任仍归后继 wave。

RFC-294 作为长期总纲持续维护这些关系；整体迁移在必选波次满足原退出门后方可 Done。
本次完成的是定位、调研记录与状态同步，未改变生产代码、测试、架构生成物或并发在制实现。
