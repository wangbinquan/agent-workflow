# 2026-11-09 RFC-294 独立对账：结构阶段完成判定与实质缺口

## 0. 结论

用户 2026-11-09 要求独立调研 RFC-294 的架构是否合理、实现到了哪一步，并在证据充分的前提下按发现修订总纲。
本文是这次对账的源码证据与判断；修订后的三件套（[proposal](./proposal.md) / [design](./design.md) / [plan](./plan.md)）
只保留结论与合同。本文不重开已关闭的后继 RFC，也不授权任何未立项的生产改动。

**总判断：目标架构合理，结构骨架已经真实落地；但“模块内分层”与“最小 public 合同”在多数由 `services/` 整体迁入的
存量模块里只是形式达标，而 plan 的剩余清单没有覆盖这两处。按 design §14 原有的 17 条终局判据：9 条达标、3 条接近、
4 条未达、1 条没有可靠度量。**

1. **结构阶段完成**：值级依赖方向、装配根、执行链、NodeRun 身份与 apply 生命周期（P0、W2、W3 与 S1～S8）在 2026-11-03 全部关闭，
   本轮独立复核属实（§4）。
2. **设计自身有三处薄弱**（§5）：分层只规定了“不许 import 什么”，没有规定 infrastructure 不许承载什么；public 合同
   有类型污染门，却没有清偿后继，并留着两个口子；task-execution 体量过大，它与 collaboration 的边界过宽。
3. **若干全仓判据没有全仓的门，也没有后继承接**（§5 R11）：`composition/` 只装配的收口锁只到 task-execution；
   43 个跨 context 内部文件对在 S5 / S6 关闭后无人认领；`architecture/counts.json` 有三项上限远高于实测且没有精确清单兜底。
4. **进度口径回到了搬迁计数**（§5 R13）：11-03 之后主干九成以上提交是本 RFC 的后继，W9-D 以“`services/` 还剩几个文件、
   `R1` 还剩几条”为主度量，而它们正是 10-16 审视否定过的口径（D9）。

## 5. 设计校正（R9～R13）

### R9. 分层只定义了“禁止 import 什么”，没有定义 infrastructure 不许承载什么

- **原设计**：design §3 的层次矩阵逐层列出可以依赖与禁止依赖；infrastructure 一行的禁止项里有“业务 command 调度”，但
  §13.1 的硬门只测 import 方向。
- **现实**：infrastructure 可以依赖一切（持久化、平台机制、本模块端口），于是旧 `services/*.ts` 最省事的去处是原样搬进去，
  再在 application 里放一个只有一个方法的端口。模块代码 42.2 万行里 infrastructure 占 45.4%（19.1 万行），domain 9.7%，
  application 27.1%。证据见 F11。10-16 审视的 F1（“`composition/` 成了新的 `services/`”）在 task-execution 上被 S6 清掉之后，
  同一批逻辑的相当一部分落进了 infrastructure。
- **修订**：把“用例入口与规则判定在 application / domain、infrastructure 只实现端口”写成正向规则（G1、design §2 / §3）；对新代码
  与此后的搬迁立即生效（C10）；对存量不设全仓清零门——没有既便宜又忠实的机器判据（按 throw 所在层设门会误伤持久化适配器对
  CAS 失败的合法翻译）——改为按价值分三路归位（D14）：纯逻辑整块迁出（S13）、随 public 合同收敛迁出（S9）、随功能 RFC 顺带迁出。
  design §12 把持久化写入协议（如任务生命周期写入序列）定在 infrastructure，这一条不变；本条针对的是准入判定与用例编排。

### R10. public 合同：类型污染有门，但没有清偿后继，并留着两个口子

- **原设计**：design §3.2 / §3.3 禁止导出 Drizzle table / row、repository 实现与“让调用者自己拼状态迁移”的出口；RFC-376 决定
  “C7（无 consumer 不公开）只进报告”。
- **现实**（直读 `packages/backend/tests/rfc294-architecture-preflight.test.ts:496` 与
  `packages/backend/tests/architecture/rfc294Gates.ts:1318`）：类型污染有精确、双向的门（`PUBLIC_SURFACE_DEBT`，94 条，新增即红）。
  但是：
  1. 这 94 条没有清偿后继，W9-D 二十多步里“public surface 偏差 94 不变”。其中 43 条是持久化句柄与 drizzle 类型（SQL 条件片段、
     收裸 db 句柄的查询工厂），39 条是开放类型（函数类型、`unknown` 等），6 条是日志器类型，其余 6 条。
  2. 检测器对 `public/operations` 整体豁免（`rfc294Gates.ts:1437-1444`，为 RFC-344 的操作描述工厂而设）。8 个模块有这个入口，
     其中 4 个借它导出了操作描述与句柄合同以外的值（F12）。
  3. 未消费的 public 符号 322 个只进报告。
- **修订**：public 合同质量列为不变量并指定清偿后继 S9（D15）：类型污染清单归零、`public/operations` 只含操作描述及其句柄合同、
  未消费符号进减速带并清零（修订 RFC-376 的“C7 只进报告”）。新增约束 C11。

### R11. 若干全仓判据没有全仓的门，也没有后继承接

- **现实**：
  - design §14 的“composition 内实现 = 0”是全仓判据。S6 的退出门写的是“task-execution `composition/` 只剩装配”，它的收口锁
    也只读 task-execution（`packages/backend/tests/architecture/rfc423-composition-assembly-only.test.ts:13-16`，
    `rfc414-composition-io-out.test.ts:13-14` 同）；全仓只有 RFC-376 的 `composition-forbidden-import-files`（14 个文件）测 import。
    10-16 review F1 点名的“development-automation 员工类型包归位”没有立项。S6 关闭后，这条全仓判据既没有门也没有后继（F13）。
  - S2 的收口记录写“装配层无隐式缺省与有无分支”。它在 profile 合同层成立；模块 composition 的本地适配器回退与装配处把可空选择项
    转回 `undefined` 的写法仍在（F14）。
  - “跨 context 内部 import = 0”：design §3.1 的现状偏差段把余项记给“S5 / S6 待清偿债”，plan 的 S5 记给“S6 及后继各域 RFC”；
    二者都已关闭，43 个文件对与 55 对 type-only 越 DAG 边没有 owner（F19）。
  - `architecture/counts.json` 有 6 项上限高于实测。3 项有精确清单兜底（跨 context 内部文件对 48 / 43、导出桶 21 / 1、不可达文件
    27 / 18）；另外 3 项没有：`legacy-horizontal-files` 381 / 175，`legacy-service-implementations` 213 / 56，`legacy-thin-facades`
    42 / 0，回涨到上限以内不会红（F16）。
- **修订**：新增约束 C12（锁与记录写明覆盖范围）、C13（减速带随收口收紧）与决策 D16；全仓的 composition-only 门归 S10，内部文件对
  与越 DAG 边归 S9 / W5 / 运行时驱动一族，治理补洞归 S11。

### R12. G4 与 design §4.2 的个别文字与 2026-08-26 硬规则不一致

- **现实**：proposal G4 要求“同一事务内重读授权依赖的状态”，design §4.2 写“资源 / 行级授权……在 command 内完成”。CLAUDE.md
  2026-08-26 硬规则把事务内二次重验列为不立项的工作，并规定访问控制“只做路由层单门、复用既有 ACL kernel”。10-16 的 R7 已把
  加固类条目移出各波退出门，但 G4 与 §4.2 的文字没有同步，AC-4 / AC-8 照原文无法全部兑现。
- **修订**：G4 与 design §4.2 按硬规则对齐（只改这两处文字）；事务、提交后事件与 outbox 的要求不变。本文不评价任何访问控制
  的强度。

### R13. 进度口径回到了搬迁计数

- **现实**：自 2026-10-16 起主干约 480 个提交（docs 162、fix 137、refactor 102、test 41、feat 17）；11-03 至 11-09 的 93 个提交里
  86 个标注 RFC-294（含文档提交与 W4-B / D 的逐路由步骤）。`design/` 下 RFC-374～476 共 103 个目录，其中 100 个的 proposal 挂靠
  本 RFC。W9-D 的 22 个 refactor 提交平均每个改 62 个文件、+812 / −373 行。plan §1.1 的 W9 一格记了 22 步的流水账，逐步报告的是
  `services/` 文件数与 `R1` 条数。这正是 R2 / D9 否定过的口径：计数下降不等于结构规则成立，例如 `services/` 文件迁入
  infrastructure 后计数下降，R9 的问题原样保留。
- **修订**：结构阶段与实质阶段分开记账（D17）：P0、W2、W3 与 S1～S8 为结构阶段，已完成；此后的进度以 design §14 的不变量与
  S9～S13 的退出门为主口径。W9-D 余项按 owner 族成批（plan §4.7），不再一文件一 RFC。定期做独立对账。
