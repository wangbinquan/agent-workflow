# RFC-294 架构设计与实现现状 review（2026-08-30）

- 性质：对 RFC-294 总纲（设计）与其已落 wave（实现）的一次全量 review；**不是新 RFC**，不授权任何未立项 wave。
- 采样基线：committed `HEAD=origin/main=625017c084db2f7eb6c9ec34c87eba41ffaf04cd`，committed
  `architecture/current-report.json`（sourceDigest `sha256:05937043…`）；源码断言一律按已提交 blob（`git show HEAD:`）
  核对，共享工作树里 RFC-345 / RFC-346 的在制品不计入。
- 落地范围：本文 §5「落地记录」列出本批同时落地的文档与门禁改动；§6 列出因共享树在制品而推迟的项及其原因。
- 数字：本文只引用采样时刻的值并注明；此后一律以生成文件 [`status.md`](./status.md) 为准，不再手抄。

## 0. 结论

RFC-294 的**方向没有问题、W2/W3 的落地质量很高**：跨域 import 全走 `public/*`（HEAD 上只有 7 条非 public 的跨模块
import，全部是设计允许的 required-ports 或已入账的临时债）、四级引擎 registry 已闭合、W2/W3 全程零 wire/行为变化、
`depcheck` 6s、canonical 守卫 5～7s——门本身不慢。

走到 W4 门口时暴露出三类需要调整的问题：

1. **治理账本的成本已经过重，且开始"自证"而不是"证码"**（§A）：10.8% 的 commit 是账本 refresh/pin、账本涨一次要三笔提交、
   10.5MB JSON 重写 72 次、`.git` 里 17% 是账本 blob；同一组指标在三件套里手抄 ≥5 处并已互相漂移。
2. **机器门与设计文档之间有几处实质性不一致，让一部分违规被记成"目标态"**（§B）：设计 DAG 禁止的 offered 边被账本记为
   `offered-consumption / removeAfterWave=null`；design §3 的模块内分层规则没有任何 cruiser 规则；92.5% 的 exception 塞在
   "W4/W9" 一个粗桶里；378 个 legacy 文件全叫 facade 但只有 6 个是真 facade。
3. **`composition/` 层被用成了业务机制的落脚点，`engine/` 是壳**（§C）：TE/DA 两个模块 22.6K 行 mechanics 住在装配层，
   owner 账本记成 `targetLayer=composition`，没有棘轮会推它们归位；51% 的 public symbol 零消费者；20/23 required port 无 provider。

## 2. 发现与调整（A 治理与文档）

### A1. RFC-294 自身仍是 `Draft / 待批准 D1～D9`

`proposal.md:3`、`plan.md:3` 写着"仍待用户批准 D1～D9"，而它名下已有 8 个 wave 由 successor RFC（328/331/332/333/334/339/341/
342/343，及 in-progress 的 344/345/346）逐一获批落地，每个 successor 都要复述一遍"294 未批"。**裁决**：总纲标 Approved，
依据是各 successor 的 D-list 批准；Approved 不自动授权任何未立项 wave（§RFC workflow 第 8 条不变）。

### A2. 文档体量与数字漂移

- 三件套 5756 行 / 450KB；`design.md §3.5` 一节 1560 行 exact 接口 TS；全文约 145 个 SHA/digest token。
- 同一组指标在 ≥5 处重述（proposal §2、design §2、design §17、plan §1、plan §14）且**已经互相不一致**：design §17 写
  AppDeps 54 / modules 415 / ambient 440；plan §1 写 53 / 454 / 448；committed report 是 48 / 463 / 456；SCC 文档 4/6 vs report 3/5。
- 文档自己写着"数字只从 committed manifests/report 重放，不在本文另设分母"，但每波都在手改 5 处；`design.md` 历史 +4703/−751 行。
- `CLAUDE.md` §RFC 第 8 条要求每个新 RFC 都读它——这是每个 session 的固定税。

**裁决**：拆成**稳定架构合同**（原则、DAG、分层矩阵、接口——后者以 `public/*.ts` 为唯一事实，文档只留引用）与**迁移账**
（wave/证据/SHA 只留 `plan.md`）；指标表由脚本从 `current-report.json` 生成为 `status.md`，散文不再出现具体数字。
本批先落生成器与投影守卫，并把 proposal §2 / design §2 / design §17 的手抄数字冻结为历史快照、指向 `status.md`；
`plan.md` 的 §1/§14 与 `design.md §3.5` 外迁留待 RFC-345 的文档在制品发布后（§6）。

### A3. 账本提交协议的成本

- 自 2026-08-13（RFC-294 落档）以来 1313 个 commit 里 **142 个（10.8%）是 `chore(architecture): refresh/pin`**；账本涨一次要
  **三笔提交**（`docs/dev-gotchas.md` §"N1 账本涨了要三笔提交"）；`module-symbol-owners.json` 10.5MB 已重写 72 次；`architecture/`
  的 blob 在 `.git` 里占 **87.6MB / 520MB（17%）**；CI 因 provenance replay 必须 `fetch-depth: 0`。
- 根因是 provenance 自引用：N1a 要求 `currentSnapshotSha` 指向一个**已提交**且文件 byte-equal 的 commit，所以内容先落一笔、再
  用那笔的 sha 回填。但四份治理账本各自已被更强的判据钉在源码上（commons R1/R2 exact equality、guard-manifest 两向钉死、
  ledger-baselines「与源码逐字相等」+ T17），byte-replay 除了摩擦什么都没证明。

**裁决**：N1a 只保留 `contentDigest == digest(当前 payload)` 与 `originSha / currentSnapshotSha` 为 HEAD 可达祖先两条；
`currentSnapshotSha` 语义改为"生成器运行时对照的已提交祖先"（直接 `--snapshot-sha HEAD`）。不涨的刷新一笔即可、涨账两笔
（`projectGovernanceArtifacts` 已保留 N1 条目上的 `allowGrowth`）。`module-symbol-owners.json` 只对 public symbol 记
`signatureDigest`、按 context 拆文件属生成器改造，留下一次 canonical 重生成时做（§6）。

### A4. `STATE.md` 3549 行里前 3139 行是状态段落

第一个 `##` 在 3140 行。已完成 RFC 的段落该归档到 `design/plan.md` 索引（本批未动：STATE.md 上有两个并行会话的在制品段落）。

## 3. 发现与调整（B 机器门的洞）

### B1. observed 跨域边没有对照设计 DAG 校验

`design.md §3.1` 明确 task-execution 不得消费 collaboration / digital-employee 的 offered surface（TE 只拥有 required port；
design 原文把 TE→DE `WorkspaceFailureClass` 称为"双向 debt，W4-E9 删除"）。HEAD 上有：

- TE→collaboration：`task-execution/application/ports/humanGateOpenParticipant.ts:5`、`acceptHumanGateDecision.ts:6`、
  `parkTaskAtHumanGate.ts:5`、`composition/humanGate.ts:6`（4 文件 / 5 import）；
- TE→digital-employee：`public/participants.ts:3`、`composition/required-ports.ts:1`、`composition/digitalEmployeeExecution.ts:2`、
  `composition/digitalEmployeeBuiltinToolCatalog.ts:8`（4 文件 / 5 symbol）；
- DE→TE：`digital-employee/application/adapters/task-execution-adapter.ts:1`。

`cross-context-imports.json` 把这 9 个文件的边全记成 `role=offered-consumption, removeAfterWave=null`——即"目标态"。原因在
`tests/architecture/rfc294Canonical.ts:3374`：只做 `targetEdges === TARGET_CONTEXT_EDGES`（常量对常量），从不检查
observed ⊆ target；生成器（`rfc294Canonical.ts:765` 附近）对任何 exact `public/*` 导入一律给 `offered-consumption`。AC-12
所说的"双向相等"实际只覆盖了一半。

**落地**：新守卫 `rfc294-review-offered-edge-dag.test.ts`——每条跨 context 的 exact `public/*` 导入，其 (from→to) 必须是
DAG 的 offered 边；唯一例外是 identity-access 的 type-only authority/context 边（§3.1 type-only matrix 与散文）。9 条存量入
`OFF_DAG_OFFERED_EDGE_DEBT`，只降不升。生成器的分类修正留到下一次 canonical 重生成（§6）。

### B2. 模块内分层规则没有机器门

`design.md §3`"新增常驻规则 1～3"（domain 禁 Drizzle/DB/fs/ws/routes/server、application 禁具体 DB table 与 `infrastructure/**`）
在 `.dependency-cruiser.cjs` 里**没有对应规则**（只有 routes/transport/util/auth/services/circular 六条）；RFC-317 的 outbound
census 只盯 `@/services|@/routes|@/ws|@/mcp` 与 `drizzle-orm|hono` 包。HEAD 上：

- **17 个 `application/` 文件 value-import `@/db/schema`**（task-execution 10、code-capability 5、integration 2）；
- **8 条 application→infrastructure 边**（collaboration adapter 直接 `new SqliteHumanGateOperationStore`、task-execution
  `applySourceTerminationEffect.ts` 直接 import registry/participant 实现等）；
- domain 层为 0（`task-execution/domain/digitalEmployeeHost.ts:200` 的 `node:fs` 只是字符串字面量里的代码样例，AST 判据不计）。

exception 账本的 `external-layer-debt`（75 条）只记 `drizzle-orm` vendor import，application→`@/db` 为 0 条。

**落地**：新守卫 `rfc294-review-module-layer-rules.test.ts`（三条规则 `domain-adapter-import` / `schema-table-import` /
`infrastructure-import`，与 RFC-317 census 不重叠），25 条存量入 `MODULE_LAYER_RULE_DEBT`（17 schema + 8 infrastructure；domain 规则在零基线上封住）。
**对 in-flight RFC 的影响**：RFC-345 contract checkpoint（`fbc0ec093`）的 `modules/resource-catalog/application/{resourceAcl,
resourceAuthorization,participants/resourceAuthorization}.ts` 直接 import 本模块 infrastructure（4 条）——已随本批入账（`removeAfterWave: W4-C`，
`ledger-baselines.json` 按 T17 带一次性 `allowGrowth`），由 RFC-345 T9 改为 composition 注入后销账。

### B3. exception / facade 账本无法驱动排期

- 1462 条 exception **全部** `expiresOn: 2027-12-31`（过期机制等于没有）；**1353 条（92.5%）`removeAfterWave: "W4/W9"`**
  一个粗桶；1376 条 `introducedByRFC: pre-RFC-294-current-debt`。
- `facades.json` 把 **378 个 services 文件全部标 `boundary-facade`**，但按 `design.md §19.3` 的定义（只许 re-export / shape
  适配）真正的薄 facade 只有 **6 个**（`clarifyAutoDispatch/clarifyRerunLedger/clarifySeal/clarifyQueue/resourceAccessPolicy/
  clarifyRounds`）；`services/task.ts` 7396 行带 DB/授权也叫 facade。

**裁决**（本批未改生成器，规则见附录 A）：`removeAfterWave` 按 W4 子波细分——`targetContext` 字段已经有了（TE 200、RC 77、
RM 42、IA 38、SC 30、COL 30、WI 29、INTEG 28、platform 27、SO 18、intent 16、memory 9、KE 4），机械可做；status 拆成
`legacy-implementation` 与 `thin-facade`；每个子波的 exit gate 只数自己的 id。

### B4. `KNOWN_VIOLATIONS` 有 9 条 `removeWhen: "属独立切片（未编号）"` 且无 `removeWave`

违反该文件自己的规则（`scripts/depcheck.ts:41-42, 66-67`）。全是 util/git 与 agent/workflow 环族，都属 W5，补 `removeWave: 'W5'`
即可。本批未动：`scripts/depcheck.ts` 上有 RFC-344 收口在制品（§6）。

## 4. 发现与调整（C 代码结构 / D 排期）

### C1. `composition/` 成了业务机制的落脚点，`engine/` 是壳

TE `composition/` 11886 LOC（`nodeMechanics.ts` 5522 行、**108 个 `@/services/*` import**；`wrapperMechanics.ts` 1841；
`taskEngineApplication.ts` 867；`dagFrontier.ts` 497），DA `composition/` 10734 LOC（`employeeTypePackage.ts` 5388、
`digitalEmployeePlatformWorkItems.ts` 2260、`digitalEmployeeWorkspace.ts` 1346）；TE `engine/` 只有 1394 LOC 的 port 形状 shim
（`engine/node/agentNodeExecutor.ts` 28 行，全部委托给注入的 port）。`design.md §2` 定义 composition"只装配，不做业务判断；
不得 query DB、做业务 if/switch 或翻译 DTO"。owner 账本却把这些文件记成 `currentLayer=targetLayer=composition,
removeAfterWave=null, status=current-module`——**没有任何棘轮会推它们进 engine/application**；225 条 TE→services 边虽记为
W4/W9 债，但边清零后文件仍会留在 composition。另外 98 条 legacy→module 深层 import 大多指向 `composition*`（routes/services/cli
直接 import composition，而设计说只有 bootstrap 可以）。

**裁决**（已写进 `design.md §2`）：`composition.ts` + `composition/required-ports.ts` 是仅有的装配文件；其余 `composition/`
文件视为待归位实现（mechanics → `engine/*`，员工类型包 → `application/`），目标层与清偿波次进 owner 账本并与其 legacy 边
同波清偿；生成器分类修正随下一次 canonical 重生成。

### C2. 公共面膨胀，与 §3.3 "无 consumer 不公开"相反

405 个 public symbol 里 **207 个（51%）零消费者**（collaboration 46/77、DE 30/44、IA 30/45、TE 29/129、code-capability 19/19、
SC 18/24、EC 17/22）。23 个 required port 里 **20 个 `declared-debt`、0 个 provider**；其中 DA 的 8 个
（`AgentActionExecutionPort`、`MergeRequestFactsPort`、`PipelineEvidencePort`、`ReconcilerPorts`…）**provider 与 consumer 都是 0**。

**落地**：新守卫 `rfc294-review-public-consumer-ledger.test.ts`——零 consumer public symbol 与死 required port 逐条入账
（`UNCONSUMED_PUBLIC_SYMBOL_DEBT` 207、`DEAD_REQUIRED_PORT_DEBT` 8），只降不升。这不是禁止 additive contract（plan §2 第 2 步）：
新增零 consumer 的 public symbol 必须同批入账并点名清偿波次。**对 in-flight RFC 的影响**：RFC-345 / RFC-346 下一次
canonical 重生成后新增的零 consumer symbol 会红——同批补账本条目并在 `ledger-baselines.json` 的
`rfc294-review-unconsumed-public-symbols` 上按 T17 写 `allowGrowth`。
后续生成器改进：把只被其他 public type 递归引用的嵌套 DTO 从分母里剔除。

### C3. 目标 context 缺口与 task-execution 巨型化

6 个目标 context 尚无模块（memory、knowledge-evolution、runtime-management、workspace-insight 尚无；system-operations 由
RFC-346 刚起步；intent 只 1 个 domain 文件）。legacy 553 文件里 **200 个目标是 task-execution**——TE 已是 125 文件 / 26.8K LOC /
129 个 public symbol，全迁完会到 ~325 文件、约占后端 40%。其中 runner/nodeIsolation/isolatedAgentRun/managedProcess 按
`design.md §2` 应归 `platform/runtime|process`，owner 账本却 target 到 TE。**建议**：先把这批 `targetContext` 改成 `platform`，
再评估 TE 是否需要在设计里拆出 `execution-runtime` 子 context。

### C4. 残留脚手架与指标回升

本地空目录 `src/bootstrap/`、`modules/work-start/public/`（`work-start` 不是目标 context）、`modules/task-execution/ports/`、
`modules/task-execution/application/queries/`——git 不追踪空目录，不构成仓库变更，各会话自行清理。
`direct native setInterval` 从 20/19 涨到 **24/21**（RFC-338 worker），与"指标上升一律阻断"相悖，账本没拦。

### D1. W4 关键路径上的 E0 没人做

`plan.md §8` 的子波依赖：`A→E0`、`E0+C→E1/E2`、`E1+E2→E3`、`E0→E8`、`E0+C→E9`、`E0+E9→E10`——**E0（identity-access trusted
authority factory + presence/WS 收编）是 11 个子波里 6 个的共同前置**，目前并行的是 A（344）、C（345）、E7（346），E0 连
Draft 都没有。C 与 E7 独立开是合规的；344 收口后下一个应立 **W4-E0**。（写进 `plan.md §3.2` 留待 §6。）

### D2. W4-B / W4-D 是横切面

`server.ts` 自 08-13 已 30 次提交、`routes/` 99 次。plan 已说"按 context 折进各 E 子波"，但账本（B3）没按子波分桶，所以每个
子波的 exit gate 无法数自己的 route id。节奏不是瓶颈（08-26→08-30 落了 10 个 RFC），一致性才是；A2/A3/B1/B2 越早做越便宜。
