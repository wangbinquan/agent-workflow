# 2026-10-31 W7 余项核销记录（NodeRun 身份与 provenance）

## 0. 结论

W7 余项按 [plan](./plan.md) §4.5 的退出门与另列三项逐条核对，**核销，不需要生产改动**。依据是已提交源码 `83c74bca6` 与
[RFC-395](../RFC-395-database-target-schema-rebuild/proposal.md)、[RFC-374](../RFC-374-node-run-sequence/proposal.md)、RFC-311、
RFC-306 的记录。核对由只读子代理完成，本会话抽查了关键证据（先后比较器只比 `seq`、`isFresherNodeRun` 只定义在迁移 oracle、
本机实例的处置）。

第二条退出门里的「nullable parent」按归档原文的口径判定（见 §2 第 2 项）。这是本会话依据用户 2026-10-30 的授权作出的判定，
用户可以推翻；推翻时另立新号 RFC，内容见该项末尾。

本次核对顺带发现 [review-2026-10-30](./review-2026-10-30.md) 有一句写错了，已在原文更正：本机实例是**归档后全新安装**，
没有经过 epoch 切换；只有托管实例 `agent-workflow` 是真实迁移（RFC-395 proposal 第 99 行、`t19-local-instance-2026-10-28.md`）。

## 1. 口径

退出门（plan §4.5）：每个输入的 producer run 可解释；生产 freshness 不依赖 id 或 nullable parent；两种 provider 迁移通过。
另列三项须纳入对拍：prompt 正文外置的版本化双读、DevelopmentMission→…→NodeRun 的 provenance 矩阵、RFC-306 `skipped` /
consumed 语义。三项的原始含义见 `archive-20261016-plan.md` §11（第 1196～1209 行）。

源码路径如无特别说明均相对 `packages/backend/src/`；`TE schema` 指 `modules/task-execution/infrastructure/persistence/schema.ts`，
`DA schema` 指 `modules/development-automation/infrastructure/persistence/schema.ts`。

**1. producer 可解释。** 新行一律 `recorded`，`producer_run_ref = producer_run_id` 由外键保证；历史行只有在 `legacy-derived`
并带证据时才允许没有外键（CHECK `node_run_inputs_producer_provenance`）；`inputs_recorded` 区分「已记录」与「未记录的历史行」。
`replaceInputs` 拒绝缺失、跨任务、节点 / 分片不符与重复的 producer；铸造在同一事务里提交输入边、`seq` 分配与选择。记录点：
普通节点 `resolveUpstreamInputs`（`composition/nodeMechanics.ts:5200-5317`）、fanout 容器（`engine/wrapper/fanoutStrategy.ts:191`）、
聚合器（`composition/wrapperMechanics.ts:1259-1299`）。模型变化（不是缺口）：RFC-395 不建逐端口列（其 design §5.1：没有读者、
历史无法证明），同一来源节点的所有边解析到同一个 run，所以按节点记录已足以解释；RFC-294 design §6.2 的「哪一个输出端口」
以 RFC-395 的这一裁决为准。fanout 分片行不单独记输入，由容器行的边加 `shard_value_hash` 解释。

**2. 不依赖 id 或 nullable parent。**

- **id**：共享比较器只比 `seq`；目标 supersession 只比 `seq`，且只有可执行行能取代别人；NULL-`seq` / id 回退只留在 oracle 副本
  `migration/oracle/supersessionSql.ts`。`isFresherNodeRun` 只定义在 `migration/oracle/legacyPickers.ts:5`，其余命中是注释
  （其中 `collaboration/infrastructure/review.ts:537` 的「pure ULID id-order」已过期）。两道守卫：`rfc374-node-run-order-guard`
  （R1～R4，例外只有 oracle 与四处非 freshness 的排序）、`rfc395-d4-mint-order-boundary`（覆盖后端、shared、前端）。
- **parent**：身份不再由 parent 推断——槽位键只取写者给出的事实（`domain/runSelection/mintIdentity.ts:27`），parent 表示归属而不是
  角色（`domain/nodeRunRole.ts`），当前 run 取自 `node_run_selections`；`historical_parent_id` 在每个铸造点显式写入
  （RFC-395 design 第 332 行）。`historical_parent_id IS NULL` 仍作为「顶层」判据用在 RFC-369 结构取代
  （`supersessionSql.ts:59,66-67`，消费者 `application/resolveSchedulerRunRow.ts`、`infrastructure/mergeStateLifecyclePersistence.ts`）、
  frontier 与顶层 / 子行筛选（`runSelection/table/reader.ts`、`application/runHistory.ts`），由 `rfc395-selection-table-equivalence`
  在两种 provider 上锁定。
- **判定**：归档原文要删的是「nullable-parent freshness **推断**」（`archive-20261016-plan.md:1196`），门是「不猜 ULID」（:1209），
  proposal G5 是「不再猜测这行是谁」。今天 parent 是写者显式写入的归属事实，`IS NULL` 是对事实的查询而不是对缺失数据的猜测，
  按此口径满足。
- **若改按严格口径**（顶层判定也不得读 parent，改由角色、槽位种类与 owner 事实表达）：另立新号 RFC，替换上述 parent-null 谓词并做
  oracle 对拍；这不是简单映射，因为自澄清停驻行继承提问方的 parent。可选的测试侧补强：加一条守卫，把 parent-null 谓词限制在目标
  reader 内。

**3. 两种 provider 迁移。** PostgreSQL：托管实例 `agent-workflow` 真实迁移（RFC-395 plan op3，数据指纹不变）。SQLite：用本机真实
数据的副本演练到 `activated`，12 项检查通过、首写前回滚（RFC-395 plan 第 651～656 行）；本机实例本身按用户裁决归档后全新安装。
测试：`rfc395-v3-switch-providers`（含跨 provider 用例）、`rfc395-v3-switch-crash-matrix`、`rfc395-v3-switch-rollback-providers`、
`rfc395-q3-phase-*`、`rfc395-v3-old-epoch-restore`、`rfc395-restore-epoch-routing`、`rfc395-v2-run-sequence`、
`rfc395-schema-equivalence`、`rfc395-provider-catalog-equivalence`；`postgresql-evidence.yml` 的 `crash-large-and-soak` 与
`compiled-external-postgresql`（`6c169a931` 上 run 40983776893 为绿）。

**4. prompt 正文外置。** RFC-311 T21：超过 4 KiB 外置到 `{taskId}/prompts/{nodeRunId}.md`，永久双读、旧行不回填。epoch 2 把它收成
一个版本化 ContentRef（`node_run_configs.prompt_ref_json`）；读写 `application/nodeRunPrompt.ts:58-106`（4 KiB 以下内联、写失败回落
内联、文件不可读返回 null），旧行由 `migration/run/prompts.ts` 离线转换，缺文件记 `v2-run-prompt-missing`。测试：
`rfc311-node-run-prompt`（含结构守卫）、`rfc370-node-run-prompt-content`、`rfc395-a4-content-codecs`。形态变化：在线双读变成一个
编解码器 + 离线转换。

**5. DevelopmentMission→…→NodeRun。** 每一层都持久化精确引用与修订：action run 记 `mission_id` / `mission_revision` / `decision_id`，
attempt 记 `action_run_id` / `rerun_seq` / `attempt_seq` / `execution_ref`（= task id）；开发自动化的表不引用 NodeRun id，RFC-395
对这些表全部 KEEP 并保留全部 id（其 `table-mapping.md`）。W7 的身份改造在这条链上没有可破坏的东西，原计划的「对拍矩阵」因此
不适用。

**6. RFC-306 `skipped` / consumed。** oracle 把 done 与 skipped 都视为已结算（`legacyPickers.ts:101-116`）；生产按
`statusIn: ['done','skipped']` 选 producer，skipped 的 producer 也记录消费边（`nodeMechanics.ts:5281,5292,5306`）。对拍：
`rfc395-selection-table-equivalence`（两种 provider，含 skipped 与 exhausted，及跨代复用）；行为：`rfc306-exit-condition-and-revival`、
`rfc306-scheduler-branch`（仅 SQLite）。

## 3. 可选的测试侧补强（不阻塞核销）

- `helpers/model/runSelectionSeed.ts` 的随机种子不生成 `skipped`；`rfc395-v2-*` 转换用例没有种 skipped producer。
- DevelopmentMission→Task 引用链没有专门的链路用例。
- 没有守卫限制新增 parent-null 谓词（见 §2 第 2 项）。
- 过期注释：`collaboration/infrastructure/review.ts:537` 等处仍写「id 顺序」。

这些都不改变生产行为，可在触及相关文件的后继里顺带补上。
