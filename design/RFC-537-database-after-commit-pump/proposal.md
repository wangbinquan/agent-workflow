## 1. 背景

写入已提交事件的事务提交之后，写方调 `publishCommittedEventsAfterCommit(eventRefs)` 把这批事件交给“即时投递泵”：泵当场投影（WS 等）并
唤醒持久投递的分发器；没有泵时返回 `false`，持久投递照样会送到。泵是进程级的（`platform/events/committed/runtime.ts` 的模块级
`activePump`，由 daemon 会话的 `after-commit-event-pump` 句柄在启动时登记、停止时清掉）：同一进程里有两份会话时，写方把事件交给最后登记的
那一份，与写方提交所在的库无关。架构报告的模块级可变单例清单里这一文件 2 条（全仓 58 条）。

## 2. 目标

- **G1 泵随数据库句柄走**：泵挂在数据库句柄的会话上下文上（一个客户端、它的事务与它的原生会话共用同一份上下文）；daemon 会话启动时把自己
  的泵挂到自己的库上，停止时只摘下自己挂的那一个。
- **G2 写方按提交所用的库投递**：`publishCommittedEventsAfterCommit(handle, eventRefs)` 从这个句柄的上下文取泵；空批次、没有泵、泵抛错时的
  结局与此前相同。
- **G3 门与用例**：新增 RFC-537 用例（运行时文件没有模块级状态与登记函数；daemon 会话把泵挂在自己的库上；两个库各投各的；事务句柄取到的是
  客户端的泵；带负对照）；读旧形状的用例随改；模块级可变单例清单 58 → 56。

## 3. 非目标

- 其余 56 条模块级可变单例（见 RFC-536 plan 末尾的三类）。
- 即时投影、分发器唤醒与持久投递的语义不变；哪些写方在提交后投递、投递哪一批不变。

## 4. 用户可见变化

无。

## 5. 验收标准

- **AC-1**：`runtime.ts` 没有模块级状态与登记函数；泵挂在数据库句柄的上下文上，daemon 会话挂在自己的库上、停止时摘下。
- **AC-2**：25 处写方都按提交所用的句柄投递；两个库各投各的，事务句柄取到客户端的泵；空批次、无泵与泵抛错的结局不变。
- **AC-3**：模块级可变单例清单 58 → 56，计数不升；钉住旧形状的锁随改，新增 RFC-537 用例并登记 guard-manifest。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。
