# RFC-616：过程度量——工作流、工作组、数字员工的统一过程观测

- 状态：Draft，2026-11-26（设计门后修订）；待用户批准后进入实现。
- 配套：[技术设计](./design.md) · [交付计划](./plan.md) · [页面原型](./prototype/index.html)（示例数据，可点击）
- 来由：用户 2026-11-26「我现在想增加一个度量，也就是按工作流来统计每个工作流的每个任务的各阶段时长、token消耗、人工介入次数等等所有针对过程的度量，目的是帮助团队去分析这个工作流中的能力提升点从而进行改进。……尤其是针对人介入点，比如检视点的检视时间、检视意见个数，平均每人检视意见个数等等指标，针对反问就是反问轮次、反问问题数、平均回答时间等等指标，还有就是针对脑图一样，平均深度、轮次、时间等等。你按照我的想法可以继续扩展度量指标能力，和我充分讨论清楚要做的东西再动手」。
- 本文的口径经同日多轮讨论逐项确认，决定清单见 §13；其中设计门之后改动的四条口径单列，待审批时确认。

## 1. 背景

平台现有的“运行观测与统计”（RFC-371 v2）回答的是**用量**：一段时间里花了多少 Token、多少钱、由哪个任务和 Agent 花掉。它没有“能力”这个维度（工作流、工作组、数字员工），也没有任何**过程**指标：一个任务在各个环节各花了多久、哪里在等人、评审打回了几次、反问了几轮。

团队要改进一条工作流，需要的正是后一类信息：

- Agent 的产出被评审打回得多不多，返工花了多少；
- 人在哪个环节是瓶颈，是没顾上看，还是内容难评；
- 哪个节点最贵、最慢、最容易失败；
- 改了提示词或流程之后，这些数字有没有变好。

这些事实大多已经落库（节点执行记录、评审文档版本与意见、反问轮次与回答、运行时调用），只是从来没有按“能力”汇总过，也没有统一的口径。

## 2. 目标与非目标

### 2.1 目标

1. **三类能力都可度量**：工作流、工作组、数字员工。每类都能看到它运行过的全部执行单元、每个单元各环节的执行情况，以及各环节在统计上的表现。
2. **人工介入点是重点**：评审（时长、意见数、人均意见数、轮次、决定分布）、反问（轮次、问题数、回答时间、回答方式）、脑图（深度、轮数、追问次数、用时），以及工作组和数字员工各自的人工环节。
3. **面向改进**：给出时间和 Token 花在哪里的拆分、瓶颈排行、按规则算出的提升点提示、热力图、文本主题分析，以及改动前后的两段对比。
4. **统一的观测模型**：业务代码不为某个指标单独加字段、单独写读表逻辑（用户 2026-11-26「能不能做统一观测打点感知能力，不要到处做特殊打点」）。节点执行、人工门、运行时调用三路直接读取现有账本并归一；只新增“人的操作”一路的声明式感知（方案 A，见 §3）。
5. **入口**：运行观测与统计下的新页签；工作流、工作组、数字员工各自的页面可以直接跳到自己的度量。

### 2.2 非目标

- 不改变任何执行行为：不新增门、不改调度、不改任务生命周期。本 RFC 只读取事实并新增一路“人的操作”记录。
- 不做阈值告警、通知、CSV 导出、自定义阶段分组、手工基线标记、页面停留时长采集。
- 不为旧版 Mission 流水线（已停止接新任务，没有 Token 记录）提供度量。
- 不保留已删除任务的过程度量：任务删除后，它的节点执行、评审、反问记录随之删除，过程度量里不再出现（Token 调用记录按 RFC-371 v2 既有规则保留）。启用任务归档时同理。
- 不做按工作时间（扣除夜间与周末）折算的时长。
- 不做逐时刻的精确时间划分：时间拆分是按区间算出的近似值（§12）。
- 不回填“人的操作”一路的历史：首次打开时间、追问发起人、重试与取消的操作人，只对上线之后发生的操作有记录。

## 3. 统一的观测模型（产品视角）

所有度量只认下面这几种东西。三类能力各有一个适配点把自己的事实归一成它们，指标只在度量引擎里按这套模型计算。

| 概念 | 含义 | 工作流 | 工作组 | 数字员工 |
| --- | --- | --- | --- | --- |
| 能力 | 被度量的对象 | 一条工作流 | 一个工作组 | 一名数字员工 |
| 执行单元 | 能力的一次运行 | 一个任务 | 一个任务 | 一次交办（任务列表里数字员工分类下的一条） |
| 阶段 | 单元内部的环节 | 画布上的节点；循环、扇出、Git 包装器是可展开的父阶段 | 两个视角：轮次、成员；动态工作流模式按生成的节点 | 职责图上的工作项，按职责区域和泳道分组 |
| 执行区间 | 一次有开始和结束的机器执行 | 一次节点执行 | 一次 Leader 轮或成员执行 | 一轮工作项执行 |
| 人工门轮次 | 一次“等人处理”的区间，从就绪到处理完 | 评审一轮、反问一轮 | 反问一轮、人类成员交付、完成确认、方案确认 | 方案审核一轮、外部审批、阻塞到恢复 |
| 人的操作 | 某人在某一刻做的一件事 | 打开评审或反问、提意见、请求追问、重试、续跑、取消、修复、同步工作流、给任务提问 | 发消息、直接派单、交付、确认或驳回、改配置 | 恢复、终止 |
| 调用 | 一次运行时进程调用，带 Token 与成本 | 既有的运行观测调用记录 | 同左 | 同左 |

每个执行区间都带一个**执行原因**，分六类，用来回答“这次执行是首次还是返工”：

| 执行原因 | 含义 |
| --- | --- |
| 首次执行 | 正常流程里的第一次执行（含循环各轮、扇出各分片、工作组各轮和各张派单） |
| 评审返工 | 评审“迭代”或“退回”之后的重跑 |
| 反问后续跑 | 人回答反问之后的续跑 |
| 失败重试 | 自动重试（输出不合格式、进程失败等） |
| 其它重跑 | 上游变化连带的重跑；失败、中断或取消之后的续跑；人工重试之后的重跑 |
| 系统工作 | 平台自己的工作：仓库准备、合并冲突处理、提交与推送、脑图追问生成，以及记忆提取、变更叙述这类事后的平台工作 |

**四路感知。** 前三路已经各有唯一的写入点，直接读取；第四路是本 RFC 新增的。

| 感知什么 | 来源 | 本 RFC 的改动 |
| --- | --- | --- |
| 节点执行 | 节点执行记录（唯一铸造点和状态写点） | 不新增写入，只读取并归一 |
| 人工门 | 评审文档版本与意见、反问轮次与回答、人工门统一操作 | 不新增写入，只读取并归一 |
| 运行时调用 | 运行观测的调用记录 | 不新增写入 |
| 人的操作 | 路由的唯一登记点（HTTP 与 MCP 共用） | **新增**：在路由登记时声明“可观测”，由登记点统一记录操作人和时间；路由处理函数里不写任何打点代码 |

第四路只记录声明为可观测的操作，不是全量访问日志。同一人对同一对象的“打开”按会话合并：30 分钟内的重复打开并入同一条记录，只更新最近时间，避免页面轮询刷量。

第四路记录的是“这个操作成功返回了”。凡是账本里已经有的次数（追问次数、人工重试次数、各类决定的次数）一律以账本为准，第四路只用来补充“谁、在什么时候”。

## 4. 用户故事

1. **工作流维护者找瓶颈。** 我打开“需求到合入”工作流的度量，看到总历时中位数 9 小时 40 分，其中 64% 在等人，等待方案评审占 41%。我切到阶段分析，在画布热力图上看到编码实现最耗时、方案设计的产出被打回率最高。
2. **看评审质量。** 我在“人工介入”里看到方案评审首轮通过率 38%，每轮 4.9 条意见，意见数随轮次从 6.4 条降到 0.4 条。我点“文本主题分析”，模型归纳出“异常与边界情况没有覆盖”是出现最多的一类意见，并给出改提示词的建议。
3. **看反问是否必要。** 反问的回答里 58% 直接采纳了推荐项，说明这些问题 Agent 本可以自己决定；提示里建议把默认决定写进提示词。
4. **验证改动。** 我改了方案设计的提示词，两周后用“以版本号为分界”的对比，看首轮通过率和评审返工占比有没有变好。
5. **工作组负责人。** 我看支付模块攻坚组：平均 6.8 轮，Leader 的协调开销占 Token 的 22%，完成确认被驳回 19%，人类成员交付时长中位数 1 小时 52 分。成员 × 指标的着色表里一眼看出谁的派单失败率高。
6. **数字员工负责人。** 我看研发数字员工：合入率 74%，交付周期中位数 1 天 6 小时；职责图上“按类型修绿”颜色最深，平均 2.6 轮、失败率 14%。
7. **普通成员。** 我只看到自己发起或参与的任务的统计，页面注明统计范围；按人的明细我看不到，只看到人均值。
8. **从能力页面进入。** 我在工作流编辑页点“更多 → 查看度量”，直接进到这条工作流的度量。

## 5. 指标目录

统计量的约定：

- 时长按墙钟时间计，不扣夜间和周末；给中位数和 P90，个别处给均值并注明。
- 样本按执行单元的创建时间落在时间范围内来选。
- **时长类、一次通过率**只算成功完成的单元；失败、取消的单元单独计数；运行中的单元在明细里列出，不进分布。
- **Token 与成本**算全部已结束的单元，失败和取消的消耗也是真实消耗；运行中的单元还没花完，不进统计。开始时间早于最早一条调用记录的单元没有 Token 记录，同样不进统计，页面注明个数。
- 样本数少于 5 的比率和分位数照常显示并标注样本数，提升点提示对样本数有最低要求（§8）。

### 5.1 能力列表（每个能力一行）

| 能力类型 | 列 |
| --- | --- |
| 工作流 | 任务数、成功率、总历时中位数、等人占比、每任务 Token、每任务成本、每任务人工介入次数、一次通过率 |
| 工作组 | 模式、任务数、成功率、总历时中位数、平均轮数、每任务派单数、协调开销、每任务人工介入次数 |
| 数字员工 | 交办数、合入率、交付周期中位数、每次交办 Token、每次交办成本、一次通过率、阻塞率 |

列表只用便宜的事实计算，不求提升点提示；提示在进入某个能力的详情后给出。

### 5.2 单元整体（三类通用）

| 指标 | 口径 |
| --- | --- |
| 总历时 | 结束时间减开始时间 |
| 自动执行时长 | 单元处于“运行中”状态的累计时长，减去调用节点等待子任务里的人处理的时间，即任务详情页已有的“有效运行时长”；数字员工取各轮执行的计量时长之和 |
| 等人时长 | 所有人工门轮次区间的并集长度（含经调用节点派生的子任务上的人工门），限制在单元起止之内；与自动执行重叠的部分算作自动执行。按门的种类给出拆分。这是近似值，见 §12 |
| 排队与中断 | 总历时减去上面两项 |
| 流动效率 | 自动执行时长 ÷ 总历时 |
| Token 与成本 | 单元名下全部任务（含经调用节点派生的子任务）的全部调用，与运行观测任务页的“任务全程用量”同一口径；四类 Token 分列。有用量不完整或未定价的调用时，沿用既有页面的“用量为下限”“含未定价”标记 |
| 按执行原因拆分 | Token 按 §3 的六类执行原因拆分，各项相加等于单元的 Token 总量。时长给各类原因在节点执行时长合计里的占比：并行的节点同时计时，合计不等于自动执行时长，所以不给绝对值 |
| 人工介入次数 | 人工门的处理次数（作废的轮次不算），加上人工重试的次数，再加上续跑、修复、同步工作流、取消这些操作的次数（后一项只有上线后的） |
| 一次通过 | 工作流和工作组：成功完成，且过程中没有评审返工、没有失败重试、没有失败的执行、没有人工重试。守护进程重启后的恢复、上游变化连带的重跑、反问后的续跑不影响它。数字员工见 §5.8 |

### 5.3 阶段（工作流的节点）

| 指标 | 口径 |
| --- | --- |
| 每任务执行次数 | 该节点的执行区间数；评审和反问节点显示轮次 |
| 时长 | 该节点各次执行的时长之和，给中位数和 P90；包装器显示自己从开始到结束的时长，不与内部节点相加 |
| Token、占全部 Token 的比例 | 调用按节点执行归到节点；调用节点的 Token 是它调起的子任务的调用合计 |
| 失败率 | 失败的执行 ÷ 已结束的执行（被评审取代而作废的执行不算失败） |
| 自动重试率 | 执行原因为失败重试的执行 ÷ 全部执行，并给出最多的失败码 |
| 产出被打回率 | 以该节点为评审对象的评审轮次里，决定为迭代或退回的比例 |
| 反问触发率 | 该节点执行过的任务里，它提出过反问的比例 |
| 循环 | 每任务轮数的均值和最大值、触顶率。开了“触顶后继续”的循环分不出“最后一轮恰好满足退出条件”和“触顶后继续”，这类循环显示为“触顶或跑满上限” |
| 扇出 | 每任务分片数、分片失败率 |

节点跨版本按节点 ID 汇总；已经从工作流里删掉的节点仍在表里出现，标“已移除”。

平台自己的执行（仓库准备、提交与推送、合并冲突处理、动态工作流的编排器）不在画布上，归到固定的“系统工作”阶段。调用节点显示它自己的耗时和它调起的子任务的 Token 合计；子任务内部各节点的拆分在被调用的工作流自己的度量里看。

### 5.4 评审

一轮 = 一版内容就绪到作出决定。两种作废的版本不算一轮，也不计入决定分布和意见统计：被上游刷新作废的，以及兄弟评审被打回时连带作废的（它记录的是系统的处置，不是人的决定）。它们等待的时间仍计入等人时长。

| 指标 | 口径 |
| --- | --- |
| 评审时长 | 本轮内容就绪到作出决定；中位数和 P90 |
| 响应等待、处理用时 | 把评审时长拆成“就绪到有人首次打开”和“首次打开到决定”。只对上线后的轮次有值 |
| 每轮意见数 | 本轮提出的意见条数 |
| 人均意见数 | 本轮意见数 ÷ 本轮提意见的人数，再对各轮取平均；没有意见的轮次不参与 |
| 评审轮次 | 每任务、每个评审节点的有效轮数。评审节点在循环里时，循环每轮各算一次评审过程 |
| 决定分布 | 通过、迭代、退回各占多少 |
| 首轮通过率 | 一次评审过程里，第一个有效轮次就通过的占比 |
| 返工耗时 | 打回到下一版就绪 |
| 意见数随轮次的变化 | 第 1、2、3……轮的平均意见数 |
| 文档采纳率 | 多文档评审里，被采纳的文档占比 |
| 按人 | 每人作出的决定数、提出的意见数、响应时长中位数。只对能查看全部任务的角色显示 |

### 5.5 反问

一轮 = Agent 提出问题到人提交回答。被取消或放弃的轮次单独计数，不进回答时间。

| 指标 | 口径 |
| --- | --- |
| 触发率 | 触发过反问的单元占比 |
| 轮次 | 每单元、每个提问节点的轮数 |
| 每轮问题数 | 本轮问题个数 |
| 回答时间 | 提出到提交；中位数和 P90。同样可拆成响应等待和处理用时（上线后的轮次） |
| 回答方式 | 每个问题归入四类：采纳推荐项、选了其它选项、自己写、跳过。推荐采纳率只在有推荐项的问题上计算 |
| 停止反问 | 提交时选择“不再追问”的轮次占比 |
| 按人 | 每人回答的问题数、响应时长中位数。只对能查看全部任务的角色显示 |

### 5.6 脑图

脑图是反问的一种交互模式，§5.5 的指标同样适用，另加：

| 指标 | 口径 |
| --- | --- |
| 深度 | 分类下的初始问题为第 1 层，每追问一次加 1。给平均深度（一张脑图全部问题的层数均值）和最大深度 |
| 脑图轮数 | 同一提问节点提交了几次脑图 |
| 追问次数 | 一张脑图内请求了几次追问 |
| 问题数 | 初始问题数与追问生成的问题数 |
| 用时 | 脑图出现到提交 |
| 追问生成 | 每次追问生成的耗时与 Token |
| 决定的成熟度 | 已决定、暂定、没有标注、跳过各占多少 |
| 预设分类覆盖率 | 节点配置的分类里，有问题落入的占比 |

### 5.7 工作组

| 组 | 指标 |
| --- | --- |
| 整体 | 任务数与成功率、总历时、轮数与触顶率、每任务派单数（按来源：Leader、人直接派、自领）、协调开销（Leader 的 Token ÷ 全部 Token）、协议重试率 |
| 按轮次（Leader 派单模式） | 跑到第 k 轮的任务数、该轮平均派单数、平均耗时、平均 Token、Leader 在该轮 Token 里的占比 |
| 按成员 | 每任务接单数、执行时长中位数、Token、派单失败率、协议重试率、反问次数；人类成员给交付时长。执行归到哪个成员，与任务房间页的规则一致；多个成员共用同一个 Agent 时，单张派单的执行分不出成员，单列为“未归属”。按人的明细只对能查看全部任务的角色显示 |
| 人的介入 | 人发的消息数（聊天与直接派单）、人直接派单数、人类成员交付时长、中途改配置次数 |
| 完成确认 | 等待时长、驳回率、每次驳回后多跑的轮数 |
| 反问 | 同 §5.5，按 Leader 和成员区分 |
| 方案确认（动态工作流模式） | 等待时长、驳回轮数 |

自由协作模式没有 Leader 轮次，不显示“按轮次”，改给运行次数预算的使用情况。动态工作流模式下每个任务的节点由模型临时编排、互不相同，所以不做跨任务的节点汇总，改为按参与的 Agent 汇总；单个任务的节点明细在任务明细里看。

### 5.8 数字员工

| 组 | 指标 |
| --- | --- |
| 整体 | 交办数、结局分布（已合入、无需修改、其他结束、执行失败）、合入率、交付周期（交办到结束）、每次交办的 Token 与成本、阻塞率 |
| 交付周期拆分 | 以职责图第一个职责区域的主干走完为界分成两段；研发类型即“交办到 MR 创建”和“MR 创建到合入”。并给出其中的等人时长 |
| 一次通过率 | 已合入的交办里，没有执行过返工类工作项、也没有阻塞的占比。哪些工作项算返工由员工类型声明：研发类型为修复检视问题、修复流水线、修复冲突。类型没有声明时显示“不适用” |
| 按工作项 | 每次交办的轮数、每轮时长（从这一轮创建到结算，含排队）、尝试次数、Token、失败率 |
| 方案审核 | 同 §5.4 |
| 人提的反馈与外部审批 | 每次交办人提的反馈条数（研发类型为 MR 上的检视意见）、外部审批的次数与等待时长；处理这些反馈的轮数在“按工作项”里看 |
| 阻塞 | 阻塞次数、阻塞时长（阻塞到恢复）、当前仍在阻塞的交办的原因分布、人工恢复与终止的次数 |

数字员工把某个工作流当工具执行工作项时产生的内部任务，同时计入该工作流自己的度量，来源标为“数字员工调用”。

### 5.9 稳定性（三类通用）

失败码分布、自动重试次数、中断次数、恢复续跑的执行次数、因超出时长或 Token 上限被取消的次数、人工重试次数（取自账本）、续跑与修复操作的次数（取自人的操作，只有上线后的）。

## 6. 页面与入口

页面形态以[原型](./prototype/index.html)为准，下面是结构。

**入口。**

- 运行与仓库 → 运行观测与统计 → 新页签“过程度量”。
- 工作流编辑页“更多”里的“查看度量”；工作组详情页“更多”里的“查看度量”；数字员工卡片操作区的“查看度量”（数字员工没有独立详情页）。

**能力列表。** 顶部切换能力类型（工作流、工作组、数字员工），时间范围沿用页面已有的选择器并增加“近 90 天”。每个能力一行，列见 §5.1。只列出在时间范围内有可见单元的能力。

**能力度量详情。** 顶部是统计范围说明和对比方式；下面按能力类型分页签：

| 能力类型 | 页签 |
| --- | --- |
| 工作流 | 概览、阶段分析（画布热力图或表格）、人工介入（评审、反问、脑图）、任务明细、提升点 |
| 工作组 | 概览、轮次、成员、人工介入、任务明细、提升点 |
| 数字员工 | 概览、职责图、人工介入、交办明细、提升点 |

- **概览**：关键指标卡；“时间花在哪里”“Token 花在哪里”两条分段条；按周的趋势（总历时中位数、每单元 Token、一次通过率三选一）；前三条提升点提示。
- **任务明细 / 交办明细**：每单元一行，可按状态和来源筛选，行内展开看各环节；可以跳到任务详情。
- **提升点**：全部规则提示，加文本主题分析。

**来源筛选**（工作流）：手动、定时、Webhook、事件、接口、子任务、数字员工调用。

## 7. 可见范围

- 沿用运行观测现有的规则：能查看全部任务的角色（管理者、管理员）统计全部单元；其他人只统计自己发起或参与的单元。页面始终注明统计范围。
- 能力是否出现在列表里，只取决于在时间范围内是否有可见单元。工作组的名称取任务上冻结的组名；工作流和数字员工取当前名称（任务上没有冻结工作流的名称）。工作流被删除后，它的历史度量仍可查看，名称显示为“已删除的工作流”。
- 按人的明细（评审人、回答人、人类成员）只对能查看全部任务的角色显示；其他人看到人均值。
- 文本主题分析的范围和结果可见性见 §9。

## 8. 提升点提示

提示由固定规则从指标算出，不调用模型。第一版的规则和阈值如下，阈值写死在一处，不提供配置界面：

| 规则 | 触发条件 | 适用 |
| --- | --- | --- |
| 等人占主导 | 等人时长占总历时 ≥ 50%，成功单元 ≥ 5 | 三类 |
| 人工门响应慢 | 某类人工门的时长中位数 ≥ 4 小时或 P90 ≥ 24 小时，轮次 ≥ 5 | 三类 |
| 产出常被打回 | 某阶段的产出被打回率 ≥ 40%，评审轮次 ≥ 5 | 工作流、数字员工 |
| 返工成本高 | 评审返工占 Token ≥ 25% | 工作流 |
| 反问多为采纳推荐 | 推荐采纳率 ≥ 50%，问题 ≥ 10 | 三类 |
| 选项不合用 | “自己写”的回答 ≥ 30%，问题 ≥ 10 | 三类 |
| 循环常触顶 | 循环触顶率 ≥ 10%，任务 ≥ 5 | 工作流 |
| 自动重试多 | 某阶段自动重试率 ≥ 15%，执行 ≥ 10；附最多的失败码 | 三类 |
| 一次通过率低 | 一次通过率 ≤ 30%，成功单元 ≥ 5 | 三类 |
| 协调开销高 | Leader 的 Token 占比 ≥ 20%，任务 ≥ 5 | 工作组 |
| 完成确认常被驳回 | 驳回率 ≥ 15%，确认 ≥ 5 | 工作组 |
| 人类成员交付慢 | 交付时长中位数 ≥ 1 小时且占总历时 ≥ 15% | 工作组 |
| 阻塞多 | 阻塞率 ≥ 20%，交办 ≥ 5 | 数字员工 |
| 工作项反复执行 | 某个工作项每次交办平均执行 ≥ 2 轮，交办 ≥ 5 | 数字员工 |

每条提示有三个级别（优先处理、值得关注、供参考），带数字依据和跳转。

## 9. 文本主题分析

- **做什么**：把原文交给模型，归纳反复出现的主题；每个主题给出条数与占比、涉及的阶段、原文摘录、模型的改进建议。
- **覆盖的文本**：评审意见与退回理由；反问的问题与回答（含脑图）；工作组里人发的消息和完成确认的驳回意见；数字员工收到的人提的反馈（由员工类型提供，研发类型为 MR 上的检视意见）。
- **数字由平台算**：模型只负责把每条原文归到主题；条数、占比和摘录由平台按归类结果从原文里取，摘录保证是原文。
- **范围与可见性**：任何有任务读权限的人都可以运行。能查看全部任务的角色分析全部单元，结果对同类角色共享；其他人只分析自己可见的单元，结果只对本人可见。
- **触发**：默认手动，在度量页点“分析”，按当前能力和时间范围运行；结果保存，范围内有新内容时提示可以重新分析。设置里可以改成每周自动运行。自动运行以全部单元为范围，结果只对能查看全部任务的角色可见。
- **成本**：每次运行消耗 Token，计入运行观测的“系统执行”。单次分析的输入有上限（条数和字节数），超出时取最近的内容并在结果里注明。
- **运行时**：设置里新增“过程分析运行时”，不填时用默认运行时。

## 10. 热力图

- 工作流：在只读画布上按所选指标给节点着色。画布取时间范围内最近一个任务所冻结的工作流定义。可选指标：自动执行时长、Token、等人时长、产出被打回率、失败率。
- 数字员工：在现有职责图上按所选指标给工作项着色。可选指标：每轮时长、每次交办的轮数、Token、失败率。
- 工作组：成员 × 指标的着色表，每列各自着色。
- 着色按数值从低到高分五档（按排名分档，避免一个极端值把其余全部压到最浅一档），同一色相由浅到深；不适用该指标的节点不着色。每张热力图都有等价的表格。

## 11. 两段对比

- 对比上一时段：当前时间范围对比紧邻的上一个等长时段。
- 以版本为分界：工作流用版本号，数字员工用员工修订号，把时间范围内的单元分成分界之前和之后两组。工作组不记录任务所用的组版本，只支持按时段对比。
- 对比作用于概览的关键指标卡（显示变化幅度和变好或变差），以及阶段表里的时长和 Token 两列。

## 12. 数据口径与边界

- **历史数据**：节点执行、人工门、调用三路读现有账本，上线前的任务同样有度量。Token 与成本只在有调用记录之后才有（运行观测 v2 上线之后）；更早开始的单元不进 Token 统计。很早的任务没有运行时长记录，不进时间拆分的统计。这两类单元的个数都在页面注明。
- **只有上线后才有的数据**：响应等待与处理用时的拆分、追问的发起人与时间、人工重试与续跑与取消的操作人、续跑与修复操作的次数。
- **不记录的数据**：评审意见是否被采纳或解决；作废版本上的意见；评审人的指派历史；数字员工已经解除的阻塞的原因（原因在恢复时清空，只有当前仍在阻塞的交办有原因）；只留在历史处置归档里的早期反问轮次。
- **近似**：
  - 时间拆分只在“自动执行加等人超过了总历时”时才从等人里扣掉重叠。并行分支上一边等人、一边有别的节点在跑，中间又发生过中断时，等人会偏高、“排队与中断”偏低。
  - 时长按执行原因只给占比，不给绝对值（§5.2）。
  - 失败、中断、取消之后的续跑，与人工重试之后的重跑，在账本上是同一种记录，都归“其它重跑”，分不开。“一次通过”因此用“有没有失败的执行、有没有人工重试”来判定，不受这一点影响。
  - 开了“触顶后继续”的循环只能给“触顶或跑满上限”（§5.3）。
  - 数字员工每轮时长包含排队和退避时间；脑图追问生成的耗时与 Token 按任务和时间区间归到对应的脑图轮次。
- **规模上限**：单次统计最多覆盖 2,000 个单元（能力详情）或 5,000 个单元（能力列表）；超出时取最近的单元，并在页面注明统计不完整。

讨论中没有单独确认、按推荐写入本文的事项，请在审批时一并确认：

1. 时长用墙钟时间，给中位数和 P90（§5）。
2. 时长类只算成功完成的单元；Token 与成本算全部已结束的单元（§5）。
3. 子工作流任务计入被调用工作流自己的度量，同时在父工作流里体现为调用节点的耗时与 Token；子任务里等人的时间计入父任务的等人时长。
4. “人的操作”只记录声明为可观测的操作；“打开”按 30 分钟会话合并；不采集页面停留时长（§3）。
5. 提升点提示的规则和阈值固定，不提供配置界面（§8）。
6. 自动运行的文本主题分析以全部单元为范围，结果只对能查看全部任务的角色可见（§9）。
7. 能力是否出现在列表里只取决于有没有可见单元，画布取最近一个任务冻结的定义；工作流名称取当前名称，已删除的显示“已删除的工作流”（§7、§10）。
8. 单次统计的单元上限为 2,000 和 5,000（§12）。
9. 动态工作流模式不做跨任务的节点汇总，改为按 Agent 汇总（§5.7）。

设计门（2026-11-26，独立只读检视，只审功能）之后改动的四条口径，同样请确认：

10. **“一次通过”（工作流、工作组）**：成功完成，且没有评审返工、失败重试、失败的执行、人工重试。守护进程重启后的恢复不影响它。原先写的是“没有其它重跑”，那会把重启恢复也算成不通过（§5.2）。
11. **数字员工的“一次通过”**：由员工类型声明哪些工作项算返工。研发类型为修复检视问题、修复流水线、修复冲突；跨仓协作与审批准备是正常流程，不算返工（§5.8）。
12. **Token 口径与运行观测任务页一致**：单元名下任务的全部调用都算，记忆提取、变更叙述这类事后的平台工作归“系统工作”。这样同一个任务在两个页面上的 Token 数相等（§5.2）。
13. **时间拆分是近似值**，时长按执行原因只给占比（§12）。

## 14. 验收标准

- AC-1 三类能力的列表、详情各页签按 §5、§6 呈现；数字与任务详情页、运行观测既有页面能逐项对上（同一任务的有效运行时长、评审轮次、反问轮次；没有子任务的任务的 Token 与运行观测任务页相等）。
- AC-2 评审：时长、意见数、人均意见数、轮次、决定分布、首轮通过率、返工耗时、按人明细正确；被刷新作废和被连带作废的版本不计为一轮，但它们等待的时间计入等人时长。
- AC-3 反问与脑图：轮次、问题数、回答时间、回答方式、停止比例、深度、追问次数、成熟度分布正确；取消和放弃的轮次不进回答时间。
- AC-4 执行原因六类划分覆盖全部现有重跑原因；Token 按原因的拆分加总等于单元总量，时长按原因的占比加总为 100%；人工重试留下的占位记录不算执行也不算失败，只计一次人工重试。
- AC-5 时间拆分三项加总等于总历时；人工门与运行重叠的时间只算一次；子任务里等人的时间不算进父任务的自动执行；没有运行时长记录的单元不进时间拆分并被计数。
- AC-6 “人的操作”：声明为可观测的操作被记录（操作人、对象、时间、传输方式），HTTP 与 MCP 两种入口都记录；未声明的不记录；操作失败不记录；记录失败不影响原操作；30 分钟内重复打开只更新同一条。
- AC-7 可见范围：普通成员的每个数字都只来自自己可见的单元；按人明细对其不返回；页面注明统计范围。
- AC-8 提升点提示：每条规则在阈值两侧的行为正确，样本不足时不触发。
- AC-9 文本主题分析：手动与定时两种触发；结果里的条数与占比等于归类结果的实际计数；摘录是原文；个人范围的结果对他人不可见；进行中、失败、重启后的状态正确；消耗计入系统执行。
- AC-10 热力图：工作流画布、数字员工职责图、工作组着色表按排名分五档；未开启热力图时画布与职责图的呈现与改动前完全一致。
- AC-11 两段对比：按时段与按版本分界两种方式的分组正确，变化方向（变好或变差）与指标含义一致。
- AC-12 入口：三处能力页面的跳转到位；深链可分享并保留能力类型、能力、页签、时间范围。
- AC-13 规模：2,000 个单元的能力详情在本机 SQLite 上 2 秒内返回；超出上限时返回不完整标记并在页面注明。
- AC-14 界面复用现有公共组件；新增的指标卡、分段条、条形与折线、热力图例作为公共组件落位；桌面与 390 像素窄屏、明暗主题可用。
- AC-15 全部实现和测试用例完成后集中验证；对应提交的主 CI 通过。

## 15. 能力影响清单

本 RFC 不关闭、不收缩任何既有能力，也不改变任何执行行为。新增一张“人的操作”记录表、一张文本主题分析结果表、两个设置项、一个后台作业（执行文本主题分析；每周自动分析默认关闭）、路由登记信息上的一个可选声明字段，以及员工类型包合同上的两个可选成员（声明返工类工作项、提供人提的反馈）。
