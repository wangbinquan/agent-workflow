## 0. 约束

1. 只在 `main` 上开发，不建分支、不用 worktree、不用 stash；提交按明确的路径清单，带 pathspec。
2. 先完成全部开发和用例编写，再集中验证；不把需求拆成小批反复跑测试。
3. 结构历史不可改写：两张新表的结构版本（T23）放在表结构定稿之后、集中验证之前生成。
4. 门检视只审功能。
5. design §15 的十一条待核实项，在动到对应代码之前先对源码复核；与设计不符时先改设计文档并在本文件记录。

## 3. 集中验证清单

全部任务的实现与用例写完后一次执行：

1. `bun run typecheck`、`bun run lint`、`bun run format:check`。
2. 后端：本 RFC 新增与改动的用例文件；所有引用了被改文件的既有用例（按 import 关系选出）；架构守卫全集。
3. 共享包与前端的用例全集。
4. `bun run scripts/schema-history.ts --check`。
5. 规模：2,000 个任务的夹具上实测能力汇总的耗时（AC-13）；2,000 次交办、每次 20 轮的夹具上实测数字员工轮次的读取（design §6.3）。后者超出预算时，在本 RFC 内给轮次表补一个按交办的索引（多一个结构版本），并在 §4 记录。
6. 本机起服务，按 proposal §14 的验收标准逐条走一遍三类能力的页面，1280 与 390 宽度、明暗主题。
7. 变异检查：对每组核心规则（执行原因归类与占位行、时间拆分、排名分档、评审作废轮次、会话合并、范围过滤、提示阈值）各做一处人为改错，确认有用例变红。
8. 实现门：按路径限定的独立只读检视，只审功能。

发现本人缺陷后修复，并只复验受影响的范围。

修订时我对着源码复核了上表涉及的事实，另外发现一处检视没有指出的问题，一并改了：

- **人工重试留下的是占位行。** 人工重试时平台先给目标节点和受连带的下游各铸一条状态为失败、从未启动的占位行，真正的重跑随后以“恢复续跑”的原因铸出（`task-execution/infrastructure/taskRouteOperations.ts:2405-2461`、`task-execution/application/resolveSchedulerRunRow.ts:62-76`）。把占位行当执行会凭空多出一次失败，而且恢复续跑在账本上分不出起因。所以占位行不算执行，人工重试的次数直接数占位行；“一次通过”改用“有没有失败的执行、有没有人工重试”来判定（design §4.1、§7；proposal §5.2、§12、§13 第 10 条）。

设计门之后改动了四条产品口径（proposal §13 第 10 至 13 条）。用户 2026-11-26 批准整份 RFC 并要求完整实现（「完整实现整个RFC直到完结，允许提交上库到远端」），这四条与九条默认口径随之确认。

#### 与设计的出入

实现时与设计不同、或设计没有写到的地方。除特别说明外，产品口径不变。

1. **响应合同是类型而不是校验 schema。** 查询参数与请求体用 schema 校验；响应体只声明 TypeScript 接口（`packages/shared/src/schemas/processMetrics.ts`）。
2. **记录器的绑定点。** 设计写“`mountApiRoutes` 绑定记录器”；实际由 `RunObservation.mount` 在挂载自己路由的同一处绑定，装配根只多传一个“当前可写”的判断。没有新增公开符号。
3. **文本主题分析的“重试”。** 模型输出不合格式时纠正重试一次，是同一条分析里的第二次调用（带各自的调用标识）；用户点“重新分析”是一条新的分析记录。
4. **运行器端口。** 由 run-observability 的 `public/participants` 发布，task-execution 用既有的系统 Agent 运行通道实现（目标依赖图里已有这条边）。
5. **排名分档放在 shared。** 前端着色与后端提示用同一个函数（`packages/shared/src/processHeat.ts`）。
6. **列名。** `observation_insight_analyses` 的触发方式列名是 `trigger_kind`。两张新表的枚举列只带 `c.enum` 自动生成的取值约束，没有再写一份同义的显式 CHECK（同模块三张旧表的显式 CHECK 是历史转换留下的）。
7. **失败码。** 合同里没有单独的“失败码”方法；失败码从节点执行行统计。
8. **数字员工汇总带 `typeRevision`。** 职责图要按员工当时的分类修订取清单。职责图由页面另取员工分类（需要数字员工的读权限）；取不到时显示说明，表格照常。
9. **设置项的位置。** 两个设置项在设置页“系统 Agent”分区的第七张卡，不在“运行时”分区。
10. **没有做的两处原型细节。** “用满反问上限”的指标卡与按人明细里的“身份”列没有做：账本里没有对应的来源。
11. **人工门事实的口径细化**（`collaboration/domain/processGateRounds.ts`）：评审原文取全部意见，另加“退回”决定的理由；“迭代”决定存的理由是意见的渲染副本，不重复计入。空白回答计为跳过。没有启用脑图的轮次不带脑图度量。反问实例按“提问节点 + 分片”区分。
12. **数字员工事实的口径细化**（`digital-employee/infrastructure/processEmployeeFacts.ts`）：没有泳道的工作项泳道为空；人提的反馈由类型自己的投影给出，投影缺失或返回值不合法时为“未提供”，不是 0；上下文读不出来的交办不计反馈。
13. **工作组成员表。** 名单里的成员即使没有任何执行能归到它（它与别的成员共用一个 Agent），只要接过单就列出，接单数照常，执行类指标为空；归不到具体成员的执行在“未归属”一行。协议重试率的分母是组内全部宿主执行（含归不到具体成员的），不含平台工作。
14. **e2e 的范围。** 工作流与工作组用真实运行的任务；数字员工的交办要有代码托管与仓库才能产生，页面用合同形状的应答加真实的员工分类职责图来走。文本主题分析在 e2e 里走“这个时间范围内没有可分析的文本”分支：e2e 的运行时替身只应答带输出信封的提示词。
15. **`plan.md` 里写错的两个落点。** T13 的装配在 `bootstrap/daemonHttpComposition.ts`、`daemonApplication.ts`，不在 `server.ts`；T17 的运行通道绑定也在 `daemonHttpComposition.ts`，不在 `daemonModules/observation.ts`。

16. **重跑落在包装器整体上的情形**（实现门发现，design §4.1 第 4 条随之改写）。评审把循环对外暴露的产出打回、人对扇出点“重试”时，原因写在包装器自己的行上，新一次调用里的内部行又按首次执行铸出。所以内部行取所在调用的原因：调用行写明了原因就用它（评审返工、反问后续跑、失败重试、恢复续跑）；没写明但不是同帧里的第一次调用，记连带重跑；嵌套在被重新调用的包装器里的首次调用，沿用外层调用的原因。包装器槽位上的 `retry-node` 占位行计一次人工重试，不算一次调用（否则循环轮数、触顶率、扇出分片数的均值会被 0 拉低）。
17. **人工重试次数取账本与操作记录中较大的一个。** 对已取消或被中断的包装器“重试”不留占位行，只有操作记录能看到；一次重试至多各留一条，取较大值。上线前的这类重试没有记录（见“已知的限制”）。
18. **一次通过多一个条件**：没有以失败或触顶收场的包装器调用。循环触顶不会留下失败的节点执行，原规则会把这样的任务判成一次通过。
19. **阶段的等人时长只取成功单元。** 与“时长类只算成功完成的样本”一致；进行中的任务里还开着的门不再让这个数随时间变大。阶段的人工门轮次仍取全部单元。
20. **提示的样本门槛检查在比率自己的分母上。** 循环触顶看已结束单元里的调用次数，工作项反复执行看执行过该工作项的交办数，一次通过率低看被判定过的单元数（数字员工只判定已合入的交办），采纳推荐看带推荐项的回答数。`ProcessClarifySummary` 为此多一个字段 `answersWithRecommendation`。proposal §8 写的“任务 ≥ 5”“交办 ≥ 5”仍然同时要求。
21. **数字员工的人工介入不重复计数。** 只有阻塞中的交办能被恢复，所以“恢复”操作与它关闭的那段阻塞是同一件事，只计阻塞那一轮。阻塞一直持续到交办结束的区间不算“阻塞到恢复”的一轮（标作废，等待时间照计，阻塞次数照计），终止操作单独计一次。
22. **工作组的五处修正。** 协议重试率按原始原因 `wg-protocol-retry` 计，不含进程失败后的重试；一轮的耗时算到该轮最后一个回合结束，包括归不到具体成员的回合；只有 Leader 派单模式有 Leader——其它模式下不列 Leader 行、不给 Leader 的 Token 分段、协调开销为空而不是 0，名单里存着的那位成员按普通成员统计；平台工作在任务明细里保留“平台工作”的类型和产品名；任务结束时被平台关闭的完成确认与方案确认不算一次决定（`ProcessWorkgroupGateRunRow.canceled`），等待时间照计。
23. **对比的两处修正。** 按时段对比时，版本选择器只列当前时间范围内的单元；按版本分界时，脑图追问生成的耗时与 Token 只取当前一组。
24. **数字员工的 Token 也拆出系统工作。** 工具运行名下的平台调用（记忆提取、变更叙述等）按原因归“系统工作”，仍记在所属工作项上。
25. **最近一次成功的分析不被清理。** 保留最近 5 条之外，另保留最新的一条成功结果；页面单独读取它，所以连续失败多少次都还显示（design §10.2 与 §12 两句原本互相矛盾）。
26. **读不出定义时不标“已移除”。** 冻结的工作流定义或员工分类清单读不出来时，执行过的节点、工作项按标识列出，不带“已移除”；只有读到了定义而定义里没有的才是已移除。
27. **评审停在待决定、而评审执行已被平台关闭。** 任务被取消或结束时，平台关闭等待中的评审执行，评审版本保持待决定；此后重试会新开一次评审。这样的轮次按作废处理，在评审执行结束的时刻关闭，等待时间算到那时为止（原实现会一直算到任务结束）。待处理评审的既有口径同样要求评审执行处于等待中。
28. **脑图分类覆盖率按名称求交。** 人工门事实不再给“覆盖的分类数”，改给这一轮问题所落的顶层分类名；引擎与节点配置的分类名求交。问题落在配置之外的分类不算覆盖。
29. **三处取整与取值。** 时间拆分各段的均值由平均总历时按比例分配，各段相加恰好等于总历时；任务明细里一个环节的等人时长取区间的并集；执行过而从未反问、有 Token 而没有返工的阶段，反问触发率与返工 Token 占比是 0，不是“无数据”。
30. **没有单元的时间范围里的名称。** 工作组的名称冻结在任务上、数字员工的名称随交办带出；所选时间范围内没有单元时，改取查看者可见的最近单元上的名称，不再显示成“已删除”。
31. **页面。** 筛选与对比、着色指标、任务状态筛选等控件行改用公共的 `FilterBar` / `FilterField`，能力页的标题改用 `PageHeader`；选项多的分段控件放进 `.page-filter`，窄屏时在自己的框内横向滚动；阶段表与任务明细按树的顺序列出、按层级缩进；任务列表的图例取全部已加载行的并集，整张表共用一套配色；链接指向的任务不在已加载的页里时单独读取并置顶展开；“刷新”在过程度量页签上重新读取全部查询（时间范围按整分钟移动，同一分钟内原本不会重读）；文本主题分析标出结果所覆盖的时间范围；热力说明改为“按图例从低到高”（暗色主题下色阶是越亮越高）；分段条里的文字在三套主题下对比度不低于 4.5:1；工作组与数字员工的概览补上三类通用的流动效率、人工介入、时间拆分与按执行原因的 Token 拆分；数字员工的方案审核表按工作项表述。

32. **看页面时发现的五处**（集中验证第 6 步，不是用例报出来的）。能力页的“返回列表”按钮被标题栏拉满整行、文字居中，改为靠左并保持自身宽度；任务明细表在 1280 宽度下把任务名挤成一字一行，名称列加了最小宽度，表在自己的视口里横向滚动，“来源”“完成确认”两列不折行；趋势图的绘图区原先不小于 440，390 宽度的屏幕上最后一个点、它的数值和日期标签都落在可见区域之外，现在按卡片宽度绘制（最窄 280），窄屏时数值标在点的上方；没有数值的“人工介入”指标卡显示成“— 次 / 任务”，改为单独一个“—”；数字员工的“每交办 Token”“每交办轮次”读不通，改为“每次交办 Token”“每次交办轮次”。

33. **“有没有用量记录”的判定**（发布后在真实环境里发现，§4.7）。设计写的是“开始时间不早于最早的调用记录”；改为“名下有调用记录，或者开始时间不早于最早的调用记录”。新装实例的第一批任务因此不再被排除出 Token 统计。
34. **没有定价时成本的写法**（发布后在真实环境里发现，§4.7）。能力列表、概览的“成本”、按原因的表、任务明细和提示里的成本，在调用没有定价时原先显示“¥0.00”；改为与运行观测其它页签一致：全未定价写“未定价”，部分定价写“¥x 起”。能力列表的每一行为此多带一个“含未定价”的标记（`ProcessSubjectRow.unpriced`）。
35. **“其它重跑与系统工作”拆开，系统工作按用途列出**（发布后用户反馈，§4.7）。设计把“其它重跑”和“系统工作”在图上合成一块弱化色，名字是“其它重跑与系统工作”；真实任务里这一块是全图最大或第二大的一块（13%–55%，全部是记忆提取），而页面既没说它是什么，也没说该去哪里调。改为：图上六类原因各占一块，系统工作用单独的颜色（图表配色加第五个分类色，取自同一参考色板的第五位，亮暗两套都过了配色校验）；汇总多带一项 `systemWork`（系统工作按用途的分项，各项之和等于系统工作那一块）；图下方在这两类有消耗时各写一句说明，系统工作列出各用途的 Token，并给出“设置 › 系统 Agent”的入口；表里系统工作下面逐项列出。

#### 已知的限制

实现门指出、复核属实、本 RFC 不处理的几项：

- **没有开始时间的执行不计时长。** 评审返工给上游重铸的行不带开始时间，由 Agent 与脚本在启动时补上；调用节点和被重新调用的包装器不补。这类行计入执行次数与 Token，不计入时长，也不算“已结束的执行”。影响的场景是评审紧跟在调用节点或包装器之后并被打回。账本上没有可用来推算的时间。
- **上线前对已取消或被中断的包装器的“重试”没有痕迹**，不计入人工重试。
- **已记录、页面还没有用到的操作**：评审提意见、请求追问、给任务提问的两种操作。它们按 design §5.4 的表记录（AC-6），汇总响应里没有对应的字段。
- **人工门的统计取全部单元**（不限成功单元）：门的统计描述的是门本身。
- **任务明细按环节给人工门的合计**，不逐轮列出。
- **数字员工的工作项表不显示对比基线**；proposal §11 的对比范围是概览指标卡与工作流的阶段表。
- **事实实现的用例多数用夹具落行。** 由真实流程产生行的有：评审的决定、意见与连带作废，工作组的回合、派单、完成确认与方案确认，平台在任务结束时对等待中的门的清扫，组装后的应用上真实路由的操作记录。其余行形状来自对写入方源码的核对。

### 4.7 发布后在真实环境里的验证（2026-11-26 至 27）

用户要求用本机的 `bun dev`（数据目录是真实的 `~/.agent-workflow`）看页面，并顺带验证数据库的升级。

**数据库升级。** 这份库是 2026-10-27 新装的 epoch-2 库，结构历史只有版本 0；当前代码是 15 个版本（0 到 14，其中 13、14 是本 RFC 加的）。先在一份拷贝上用已提交代码的二进制执行 `migrate`：4.6 秒，自动留了升级前备份。随后 `bun dev` 在真实目录上启动时自己完成同样的升级：先写 `backups/pre-migration-0-14-*.tar.gz`，再依次应用 1 到 14，约 3 秒。两次的结果一致：`integrity_check` 与 `foreign_key_check` 无输出，表由 254 张变为 268 张（多出的 14 张是这 14 个版本新建的），没有表被删除，既有表的行数除结构历史本身（1 行变 15 行）外没有变化。升级后工作流、代理、工作组、数字员工、任务的列表接口与过程度量的三个列表接口都正常应答。

附带观察到的一件事（不属于本 RFC，没有处理）：库文件由 9.1 MiB 变为 42 MiB，增加的部分全部在 `aw_meta_schema_history.artifact_json`——每个结构版本存一份约 2.3 MiB 的完整合同与计划，升级上来的库保留全部 15 份（36.4 MiB），而直接装到最新版本的库只有 1 份（2.4 MiB）。此后每加一个结构版本，每个升级上来的库再多约 2.4 MiB。

**真实任务。** 这份库里没有任何任务，于是用自带的两条示例工作流各发起一个真实任务（运行时是本机的 opencode）：一个只有一次 Agent 调用，一个带一轮反问（Agent 提了 4 个问题，经接口作答）。时长、时间拆分、反问的轮次与问题数、回答方式、响应时长、按人统计都与实际一致。

**发现并修掉的一处缺陷（第 33 条出入）。** 两个任务的 Token 在能力列表和汇总里显示为“—”，数据说明写着“开始于最早的调用记录之前，不进 Token 统计”；而任务明细里同一个任务显示 111K，运行观测的任务页也有数。原因在 design §5.3 的规则本身：样本只取“开始时间不早于最早一条调用记录”的单元，而单元自己的调用总是在单元开始之后才开始——一套新装实例里最早的任务（这里是同一秒内发起的两个）恰好全部被排除。已有库里受影响的只是拥有最早那条调用的一两个单元，通常早已不在时间范围内，所以用例和演示数据都没有暴露；用例里调用与任务又总在同一毫秒开始。改为：单元名下（含子孙任务、数字员工的宿主任务）有调用记录，或者开始时间不早于最早的调用记录，就算有用量记录。规则收在领域层的 `usageRecorded`，工作流与工作组、数字员工两处构造单元的地方共用；数据说明的文案相应改为“开始于最早的调用记录之前，自己也没有调用记录”。回归用例：纯规则四条（`rfc616-process-domain`）、用例层三条并改一条（`rfc616-process-queries`，含列表深度与“只有子任务留下调用”）、数字员工一条（`rfc616-process-kinds`）、真实库上“同一秒发起的两个首批任务，各自的调用晚一秒开始”一条（`rfc616-process-assembled`，两种数据库）。

**发现并修掉的第二处（第 34 条出入）。** 这份库没有配置任何价格（新装实例都是这样），页面上所有成本都显示“¥0.00”，读起来像是免费；运行观测其它页签的约定是“未定价的 Token 绝不显示成免费”。汇总原本就带“含未定价”的标记（数据说明里有一句话），任务明细的行也带，但显示时只在金额后面加了一个加号；能力列表的行则没有这个标记。改动：列表行补上标记（三类能力共用一个判定 `anyUnpriced`，与数据说明同源）；前端加一个 `pricedCost`，五处显示成本的地方统一走它，文案复用运行观测的两个既有词条。回归用例：后端列表行三类能力各一条、真实库一条（并入“首批任务”那条）；前端格式函数一条、页面三条（列表、概览与原因表与提示、任务明细）。

关于第 33 条，这条规则仍有一个已知的不精确处：调用记录启用时正在运行的任务（启用前已开始、启用后才留下调用）会被当作有完整记录，它的 Token 只是下界。这类任务只出现在运行观测上线的那一次升级前后，数量是当时在跑的任务数，原规则把它们排除在外。两害相权取其轻：新规则错的是一次性的少数旧任务，原规则错的是每一套新装实例的第一批任务。

**真实的工作组与数字员工（2026-11-26 至 27，用户要求）。** 在同一套真实环境里补了另外两类能力的真实数据，逐项与数据库记录核对，数字全部一致：

- 工作组：四个组、五个真实任务。两个 Leader 派单的任务成功（两轮、每轮的时长与 Token、Leader 的协调占比、成员各自的时长与 Token）；一个自由协作的任务因轮数触顶失败（成功率 0、触顶率 1、一次协议重试计入失败重试）；一个带真人成员的组走了完成确认——先驳回、后通过，两次等待 76.9 秒与 46.7 秒，与扮演这位成员的脚本记下的时刻相差不到一次轮询间隔，流动效率 45.7%，首次通过率 0。成员里没有真人时完成确认不生效（RFC-207 的既有规则），那个组的任务因此没有等待，这不是统计的问题。
- 数字员工：本机的 GitLab 作代码平台，两名开发员工、三次交办。第一次交办在发布 MR 时因推送鉴权失败受阻 353.5 秒（本机 GitLab 是明文 HTTP，代码平台连接要配传输映射才会用平台令牌推送），补上配置后恢复，MR 在 GitLab 合入后交办以“已合入”结束：受阻次数、受阻时长、恢复操作、以发布 MR 为分界的前后两段时间、各职责的次数与时长都与事项记录一致。第二名员工的岗位另绑了“处理检视意见”，两次交办：一次在 MR 上收到检视意见后返工（汇总、回复已收到、处理、再提交各一轮），合入后结束；一次的 MR 被直接关闭，交办以“其他结束”收场。合入率 50%、阻塞率 50%、返工类工作项的轮数、每次交办的 Token（两次的均值）、自动执行时长（计量回执之和）同样逐项一致。

核对中看到、没有处理的几件事：

- 自由协作里成员自领的派单在库里不带承接人，所以成员表里这两位成员的派单数是 0，而任务一级的派单数是 2。
- 工作组任务里相邻两步之间有过 20 多秒的空档（当时本机负载很高），这段时间算在自动执行里。
- 数字员工处理检视意见花的 Token 在“Token 花在哪里”里算作“首次执行”：这类能力的原因只按轮次的尝试序号区分首次与重试，返工是通过类型声明的返工类工作项（职责图、交办明细里的返工轮数）表达的。页面上因此会出现“评审返工 0”而员工确实处理过检视意见的情形。
- **数字员工流程本身的一处缺陷（与度量无关）**：员工推送修复提交后紧接着执行“回复修复结果”，这一步刷新 MR 事实时撞上 MR 的头提交刚好从旧值变成它自己推上去的新值，采集按约定整组丢弃并返回 `mr-facts-head-race`；工作项把它当成阻塞，交办停下来等人恢复。恢复之后流程直接去“关注 MR 状态”，没有重新执行“回复修复结果”——检视线程里只有“已收到该检视意见，正在处理”，修复结果始终没有回复上去，线程也没有被处理完。采集函数的约定是“调用方重采”（`modules/integration/application/mrFacts.ts` 文件头），而三处调用（确认检视意见前、回复修复结果前、MR 详细事实）都把任何失败直接判为阻塞（`employeePlatformWorkItems.ts`）。本轮只记录，没有修。
  - **后续（2026-11-27）**：前一半已修——员工工作项读 MR 事实的那一层（`modules/development-automation/application/developmentMrFacts.ts`）在事实源报告「读的过程中分支动了」时重采，最多读三次，其它失败照旧原样返回；回归用例 `packages/backend/tests/development-mr-facts-recollect.test.ts`。这样刚推送完就回复不再因这次撞车而阻塞。后一半没有修：一个已经准备好、尚未回复的检视处理说明，若在回复之前被检视 / 冲突 / 生命周期事件抢占（这三条反应规则都声明抢占续接，`employeeTypePackage.ts` 的 `handle-review` / `handle-conflict` / `handle-lifecycle`），随后的「关注 MR 状态」只会走向重新分类、修冲突、审批或就绪评估，回不到「回复修复结果」（它不在「关注 MR 状态」允许的后继里）。修它要改员工类型的工作项后继关系，按类型修订号生效，属于产品行为变更，需要单独立项。
  - **后续（2026-11-27，RFC-628）**：后一半已由 `design/RFC-628-employee-reply-after-preemption/` 立项并修复——「关注 MR 状态」结算时按检视处理台账续办（修复已发布则回到「回复修复结果」，未发布且头提交未变则回到提交），`development` 升 `@12`、`graph-development` 升 `@3`；钉在旧修订号上的进行中交办不受影响。

**用户反馈后改掉的第三处（第 35 条出入）。** 用户看页面后问：“其他重跑与系统工作是什么，这块看着没法理解，也不知道应该怎么优化”。按调用记录查了这几个真实任务：系统工作全部是记忆提取，两个工作流任务里占 Token 的 48% 和 55%，工作组任务里占 13%–27%——这一块在图上却是一块没有名字的弱化色。改动见第 35 条。实现时在真实数据上先看到所有用途都落在“其它”：用量切片按“阶段 + 原因”合并时，合并函数逐字段重建切片，把用途丢了；修正后加了一条查询层的回归用例。页面上各用途的名字与“设置 › 系统 Agent”里的卡片同名；页面不认识的用途按记录的原样显示，不并进“其它”。另有一条用例把页面认识的名字和各处实际记录的名字绑在一起，记录方改名时会失败。
