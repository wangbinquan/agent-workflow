# RFC-395：数据库阶段目标模型与一次迁移

- **状态**：Draft（2026-10-21）。用户要求全面调研数据库并「落地 RFC」；本次交付设计，尚未批准生产实现或执行真实数据迁移。
- **代码基线**：`3fcb14dbf8ab27cf451934942ea6b9cd647077f8`，`main`；源码逻辑合同摘要 `sha256:8e6510d4d0927d538692ecf22cde0b1fa9a97c733a9e044af8d9768418ecb956`。
- **母 RFC**：[RFC-294](../RFC-294-backend-layered-target-architecture/proposal.md)，承接 schema contribution、NodeRun 身份 / provenance、AtomicApply 与 provider 中立持久化目标；不代表 RFC-294 全部退出。
- **阅读顺序**：本文 → [技术设计](./design.md) → [迁移合同](./migration.md) → [逐表处置](./table-mapping.md) → [实施计划](./plan.md)。调研证据见 [research.md](./research.md)。

## 1. 决策摘要

建立一份按业务领域拥有、显式声明语义类型与约束的目标 schema。SQLite 与 PostgreSQL 都保留；业务算法只有一份，两个 provider 各自产生原生 DDL 与查询适配。完成整套实现、旧数据转换器、历史读者与测试后，在维护窗口中将旧库转换到独立新库，校验完整，再进行一次正式切换。

本 RFC 的成功判据是业务事实有唯一权威表达，正常业务路径不再理解旧 schema。表数量可以因为合理拆分增加；不以压缩表数为目标，不把所有资源、事件或执行记录塞进万能表。

主要裁决如下：

| 领域 | 目标变化 | 直接消除的妥协 |
| --- | --- | --- |
| Task | 执行主体、执行定义快照、生命周期、启动来源、工作区分别建模 | Agent / Workgroup 为满足必填 workflow 字段创建隐藏 host workflow |
| 工作区 | 单仓与多仓使用相同的仓库挂载集合，主仓只是 ordinal 0 的投影 | `tasks.*` 主仓镜像、`worktree_dir_name` / `mount_path` 两套身份 |
| NodeRun | 明确角色、容器、逻辑执行代、尝试、selected run、实际消费边；按仓库存 checkpoint | nullable seq / id 排序回退、parent 多义、单仓字段与多仓 JSON 字段并存 |
| 协作 | round 保留不可变问题快照，答案 / 草稿 / 归属按问题存储 | 修改一个答案却锁 Task、整份 JSON 读改写 |
| 资源引用 | 独立编辑的依赖用 typed 关系表；Workflow JSON 的依赖用可重建索引 | 名称与 ID 混用、`LIKE` 扫 JSON、多个可写真相源 |
| 内容与制品 | 统一版本化内容引用与生命周期，保留小内容 inline 和不同内容后端 | 技能二进制 base64 作为正常数据库格式、路径与内容来源散落 |
| Apply | 共享 AtomicApply 状态机与恢复机制，保留场景 journal / 幂等域 | Intent、资源包等重复实现相同提交 / 恢复流程 |
| 历史 | 逐表区分当前业务、历史读服务、迁移遗留；迁移证据进入专用记录 | clean install 仍承担旧 writer drain 与旧列兼容 |

## 2. 背景与证据边界

当前源码声明 217 张业务表：现有合同 211 张参与 PostgreSQL 在线投影，6 张归档后省略；共 2,639 列、141 个外键、207 个 CHECK、390 个显式索引。两条迁移链分别有 260 / 37 个 SQL 文件。这些数字是库存，不是健康度评分。

真正的问题可从使用处反证：`tasks.workflow_id` / `workflow_snapshot` 必填使启动代码为非 Workflow 任务补造 host；任务主仓字段与 `task_repos[0]` 互相镜像；NodeRun 回滚同时解释单仓字段、多仓 map 与历史缺失；澄清答案整包更新；provider 合同从 SQLite 表反射，再靠字段名推断 JSON 与 owner。

前序只读调研还发现本机 SQLite 的物理版本与源码合同不同，详见 research。它证明迁移不能只认迁移条目数或当前源码，不代表所有部署都处于该版本。尚无真实 PostgreSQL 数据库迁移证据。本 RFC 不把静态调查、文档检查、真实迁移、exact-SHA CI 或上线验收混为一个完成状态。

## 3. 目标与非目标

### 3.1 目标

- **G1 完整覆盖**：217 张源表每张有明确 owner、保留 / 拆分 / 关系化 / 共用机制 / 归档处置；实际数据库额外表也有预检处置，不忽略剩余数据。
- **G2 明确阶段终态**：新建库与迁入库使用同一目标合同和同一业务路径，正常运行不维护旧列、旧表或双写。
- **G3 保留功能**：现有启动、恢复、retry、rollback、协作、资源包、数字员工、事件、观测、归档与备份能力保持；API 兼容由边界投影承担。
- **G4 双 provider 等价**：同一业务语义在 SQLite / PostgreSQL 下成立；数字、时间、JSON、字节、排序、NULL 和事务失败有明确合同。
- **G5 可审计搬迁**：每条旧记录有转换、保留、历史化或明确阻塞结论；无法推断的信息不伪造；数据库与外部内容一起校验。
- **G6 删除债务**：以 design 的删除清单和实际读写点为准验收，不能只提交新表后保留所有旧路径。

### 3.2 非目标

- 不把 PostgreSQL 变成唯一后端；不强制用户同时更换数据库产品。
- 不拆为微服务或多个在线业务数据库，不引入跨库分布式事务。
- 不统一成万能 ORM、万能资源表、万能 event 表或所有场景共享一张 saga 表。
- 不改 TaskEngine → WrapperRuntime → NodeExecutor → ExecutionKernel 链路，不开启 RFC-294 W8 fanout 内链新能力。
- 不顺带重做全部 UI、事件模型、数字员工产品模型或已关闭的观测系统；不恢复 RFC-372 已删除的旧脑图 / 材料模型。
- 不执行线上清理、VACUUM、删库、取消未完成任务或真实搬迁；这些是批准实现后的独立运行操作。

## 4. 用户故事与能力影响清单

| 用户旅程 / 部署形态 | 迁移后承诺 | 中断或限制 |
| --- | --- | --- |
| 单机 SQLite 或独立 PostgreSQL 启动 Agent / Workflow / Workgroup | 真实主体和冻结执行定义可查询，原启动 API / 可见历史一致 | 正式切换有维护窗口 |
| 托管 PostgreSQL 的任务接管 / 崩溃恢复 | 原任务、执行代、回执和作用域可追溯；按新进程生命周期重新接管 | 旧进程必须停止写入，不能复制存活 lease 当作新 owner |
| 单仓、多仓、内部工作区、子任务 | 同一仓库集合模型；无分支、detached、unborn 与继承关系保留原语义 | 不靠空字符串拼出“有效分支” |
| 已等待人工或 interrupted 的任务 | 继续等待或可恢复；已有回答、审批、产物、重试关系保留 | 无法证明可恢复性的任务阻塞迁移，须逐项解决；禁止自动取消 |
| 查看旧任务、旧代码工作项、观测与费用 | 原 ID 可查，历史证据与原字节可访问；不明字段标示为未知 / 推导 | 历史不足的记录不可伪称精确重建，但既有展示和检索需有历史读者 |
| 修改问题答案 / 导入资源包 / 恢复技能版本 | 原行为与错误码保留；新存储有明确修改粒度和幂等恢复 | 不因拆表要求用户重新作答或重新导入 |
| 数据库备份与恢复 | 备份包含引用的外部内容清单，恢复后核对可读性 | 单独复制 SQL 文件不再被视为完整内容备份 |

没有计划关闭既有产品能力。维护窗口、切换后旧二进制不能打开新库、切换后产生新写入时不能直接退回旧快照，是需批准的运行契约。若实施发现必须关闭能力，必须修订本清单并重新确认，不能作为“迁移实现细节”隐含执行。

## 5. 验收标准

- **AC-1 覆盖与守恒**：源 217 表及真实源库的额外表全部有处置；所有源行在迁移 receipt 中可追踪；拆分 / 合并用语义守恒而非强求表级行数相等。
- **AC-2 主体与工作区**：Agent / Workgroup 启动无 host workflow 插入；单仓、多仓共用一套写读 / 回滚；物理主仓镜像字段与旧 map 字段删除。
- **AC-3 执行身份**：新写入的 seq 非空且每任务唯一有序；保留历史负数回填序号；所有执行选择 / retry / resume / supersession / 聚合消费同一合同。历史来源明确，不按 ID 猜新执行顺序。
- **AC-4 协作与引用**：同轮不同问题并发编辑不丢更新；封口原子；资源依赖查询使用 typed 关系或版本化 selector 索引，不靠 `LIKE` 扫 JSON，定义与索引原子一致；现有名称选择器与可移植导入导出的解析语义保留。
- **AC-5 内容与机制**：技能 BOM / 任意二进制往返字节一致；inline / 文件 / 数据库 / 对象内容可恢复；AtomicApply 场景状态机共用，领域幂等键、事务与恢复责任保留。
- **AC-6 schema 与 provider**：owner / codec 不从前缀或列名猜测；无 SQLite 类型伪装 PostgreSQL 业务 DB；双 provider 的原生 DDL、约束、查询、序列和错误映射对拍通过。
- **AC-7 一次切换**：SQLite → SQLite、PostgreSQL → PostgreSQL 均完成非空真实引擎演练；覆盖崩溃恢复、切换前撤回、切换后恢复、数据库 + 内容备份恢复。SQLite → PostgreSQL 保留已有能力并有独立矩阵。
- **AC-8 兼容退出**：design §10 的删除项逐项归零；旧数据转换只在迁移 / 历史模块，不进入新业务命令；新库不运行旧 writer drain。历史查询适配不冒充运行时双读。
- **AC-9 用户旅程**：完整启动 → 执行 → 等待人工 → 恢复 → 完成 → 回滚 / 重试 → 历史查询及导出，双 provider 和现有部署形态均有行为证据。
- **AC-10 交付证据**：全部生产改动与测试编写完成后集中验证；必需的 hosted exact-SHA CI、设计门 / 实现门和真实搬迁回执分别记账。文档落档不将本 RFC 标 Done。

## 6. 与已有决策的关系

本 RFC 承接 RFC-294 的目标结构，但将其 §6.3 对 NodeRun 的 expand / backfill / shadow / reader 切换序列，改为**离线转换目标库 + 对拍 + 一次整体切换**。原因是本次有跨聚合拆表、列收缩和 provider 合同重建，继续逐列在线兼容会扩大双写与回退面积。转换器仍保留幂等回填、旧数据 oracle 和明确删除条件；不在旧在线库长期双写。

本项属于需在批准 RFC 时确认的迁移方式调整，不修改母 RFC 的执行层次与领域边界。RFC-374 的独立 seq 分配机制继续使用，不改为 `max(seq)+1` 或热 Task 计数器。RFC-371 观测三表、RFC-372 澄清模型、RFC-370 内容发布生命周期保留其已成立的职责。

RFC-393 已迁移启动代码；RFC-394 正在修改部署 profile。实施时以当时已提交的 `bootstrap/` 合同装配，本文不锁死旧 `cli/start.ts` 或并发 session 的未完成接口。
