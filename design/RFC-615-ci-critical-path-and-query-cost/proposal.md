# RFC-615：CI 第二轮——重复计算、查询成本与计算队列

## 授权与目标

用户在 RFC-611 验收后明确要求：「继续按你的建议做第二轮优化，把剩下两项 CI 失败解决掉，后端长尾和排队耗时也继续压下来，保持测试覆盖和现有门禁标准。」本 RFC 具体化这次实施授权，包含已存在失败路径的修复；无需重复请求同一授权。

第一轮核心候选 `92222f0c3` 的 run 45797271947 为 70/70 成功。后续 `523725652` 的 run 45808141402 为 67 个工作作业成功、2 个失败及聚合失败：历史行桥 5515.07ms 越过默认 5000ms；PG G1 P95 5843.65ms 越过 max(SQLite 52.28ms × 50, 250ms)。相关源码和直接依赖未变，后者的具体运行期机制尚未确定，本机 PG17.12 的一次诊断为17.63ms，不能替代云端归因。

后一次完整 run 的实际工作跨度为38m30s，首个作业前等待63m24s，聚合作业再等20m11s且执行仅2s。后端最长14m37s，15分钟预算只剩23秒。

目标：

- 消除历史行桥不参与结果的中间hash和同步调用内重复规范化，保留13历史版本、逐边校验与原5秒用例。
- 消除G1 prefix的重复相关查询，保留过滤、权限、排序、树语义、分页与性能防退化阈值；补齐冷/维护后及custom/generic计划证据。
- 每个backend作业内复用不可变测试准备产物，实际升级、生产catalog编译、真实compiled binary/子进程/故障步骤继续执行。
- 计算阶段完成即释放并发名额，聚合检查排队不再占住计算队列；每个SHA完整验证和CI required原判定不变。

## 保留的标准

不删除或跳过测试，不放宽job/test预算、性能阈值、coverage/provider/platform要求，不把PG异常直接定性为误红，不通过重跑证明修复，不取消其他提交，不购买或假设额外runner容量。原69个工作作业与唯一CI required仍构成完整门禁；改为可复用workflow不增加另一套执行器。

## 验收

1. 原两项失败用例在原预算、原性能判据下通过；新增变异/分页/计划回归覆盖优化边界。
2. 原测试全集、平台矩阵、PG lane、失败/取消/跳过的汇总语义保持；required context仍为CI required。
3. 缓存键覆盖实际输入；跨isolate竞争不读半成品，每case副本独立；缓存不绕过冻结历史字节核验。
4. 完成所有实现和测试用例后集中验证，再发布并跟踪exact-SHA CI；分别记录运行、计算队列等待与聚合等待。
5. 用实际计时判断后端长尾和等待收益，不将缓存调用次数或预测值冒充墙钟提速。
