## 1. 背景

子任务预算（同时活跃的子任务数上限与调用链最大深度，RFC-243 / RFC-287）住在 task-execution 的 `infrastructure/childBudget.ts` 的模块级
状态里：进程级单例 `ChildTaskBudget`（第一个用到子调用节点的任务懒建，换数据库时按查询对象的身份重建）、`taskId → 是否子任务` 的缓存、
实时容量与实时深度两个模块级变量，以及它们的 setter 与测试用的 reset。架构报告的模块级可变单例清单里这一个文件占 8 条（全仓 79 条）。

同时有一处功能缺陷：设置页“调用链最大深度”写着“保存后立即生效”，保存时的热应用输入也带着 `maxInvocationDepth`，但 2026-09-01 的
`d38ada9ed`（路由改走封闭的 provider 操作）把 `setMaxInvocationDepth(updated.maxInvocationDepth)` 一并删掉了，生产里再没有调用方——此后改深度
要等下一个根任务启动才生效。

## 2. 目标

- **G1 预算由会话构造**：每个 daemon 会话在装配 task-execution 时构造一份子任务预算（与执行许可登记表同处），经运行期选项交给子调用节点，
  会话的生命周期事件与配置热应用调这一份；`childBudget.ts` 里不再有模块级状态与它们的 setter / reset。
- **G2 恢复深度的热应用**：保存设置时，子任务容量与调用链最大深度都在同一个线性化点（节点池热应用之后）推给会话的预算，深度保存后对随后
  派生的子任务立即生效。
- **G3 门与用例**：新增 RFC-533 用例（`childBudget.ts` 没有模块级可变状态与导出的 setter / reset；会话预算的容量与深度热应用、懒建与生命周期
  的行为；深度热应用的回归用例；带负对照）；读旧形状的锁与用例随改；模块级可变单例清单 79 → 71。

## 3. 非目标

- 其余 71 条模块级可变单例（`process-registrations` 里的两条策略登记、执行看门、几处按对象挂的侧表、platform / util 的进程级缓存等）：另立后继；
  需要保留的进程级缓存按 plan 由后继 design 提出、经用户确认后修订 design §14 的口径。
- 预算的准入语义（计数状态、排队与放行顺序、超时告警）不变。

## 4. 用户可见变化

- 设置页保存“调用链最大深度”后，随后派生的子任务按新值判定（恢复 2026-09-01 之前、也是界面文案所写的行为）；已在跑的调用链不受影响。
- 其余无。

## 5. 验收标准

- **AC-1**：`childBudget.ts` 没有模块级可变状态与导出的 setter / reset；预算每个会话一份，由 bootstrap 在装配 task-execution 时构造并交入。
- **AC-2**：子任务容量的热应用、懒建与生命周期放行与此前相同；调用链最大深度保存后对随后的派生立即生效（回归用例在 HEAD 上红、在候选上过）。
- **AC-3**：模块级可变单例清单 79 → 71，计数不升；钉住旧形状的锁随改，新增 RFC-533 用例并登记 guard-manifest。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。
