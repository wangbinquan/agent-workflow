# RFC-317 B0/T1 采数报告（2026-08-23）

- **采数 SHA**：`efc1bdb01`（= `dcb1476ac` + 本 RFC 的落档提交）
- **采数环境**：`git worktree add --detach` 物化出的**分离干净工作树**。主工作树当时带着并发 session 的大批未提改动（`modules/digital-employee`、`modules/task-execution/public`、`employeeTypePackage.ts` 等），直接在上面采数会把别人的在制品算进基线（`docs/dev-gotchas.md` 有此定式）。

## 0. 口径声明（**先读这一节**）

本报告的数字与 RFC 落档时写的数字**不同**，因为口径不同。落档时的数字来自 `rg -c` 行计数，是**估算**；本报告是**正式分母**，此后一律以本报告为准。

| 量 | 落档时（`rg` 行计数） | 本报告（AST 边计数） | 差异原因 |
| --- | ---: | ---: | --- |
| R1 inbound 违规 | 66 条 / 19 文件 | **94 条 / 28 文件** | `rg` 只匹配 `from '@/modules/…'` 单行静态 import；census 走 AST，覆盖 `import type` / `export … from` / `import()` / `require()` 与相对路径写法，且**按具名绑定去重后逐 (specifier, kind, syntax) 计边**——同一文件对同一目标既有 value 边又有 type 边算两条 |
| R2 outbound 违规 | 33 条 | **22 条** | `rg` 数的是 `modules/**` 下**全部层**的 `from '@/services/` 行（含 infrastructure 14 + composition 9）；census 只围栏 `domain/application/engine/public` 四层，另把 `drizzle-orm` / `hono` 也算进去 |
| bounded context 数 | 12 | **11** | `modules/work-start/` 在 HEAD 上**根本不存在**——它是本机 checkout 上的一个**空目录残骸**（`work-start/` + `work-start/public/`，零文件、未跟踪、无人引用；git 不跟踪空目录，所以它在某次 checkout/revert 后残留下来）。落档时的 12 是在脏工作树上 `ls` 出来的 |

第三条顺带印证了审计的一条结论：**空 context 在所有守卫下都得满分**——这里连「空 context」都不是，是一个连 git 都不知道的目录，而它此前在任何清单里都会被当成第 12 个 context。

## 7. 本次采数顺带发现（已入 `findings.md` 之外的新事实）

1. **`modules/work-start/` 是空目录残骸**：零文件、未跟踪、无人引用。不删（未跟踪文件按仓规不主动动别人的东西），但它证明了「空 context 得满分」不是假想——它甚至没进过 git。
2. **R2 的 22 条全在 `application` 层**：`domain` / `engine` / `public` 三层今天零违规。这让 R2 的清偿路径比预估清晰得多。
3. **生成清单时踩到的正则 alternation 顺序 bug**：`\.(?:ts|tsx|json)` 会把 `Dialog.tsx` 匹成 `Dialog.ts`，导致 9 个前端公共原语被误判为「文件不存在」而整批漏进清单。改成 `\.(?:tsx|ts|json)` 后 73 → 82。这条已列入 T69 要沉淀进 `docs/dev-gotchas.md` 的教训——**匹配文件后缀时长后缀必须排在前面**，且任何「扫出来的数量比预期少」都要先怀疑正则而不是接受结果。
