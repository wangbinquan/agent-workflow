## 1. 背景

架构报告的模块级可变单例清单还有 61 条。platform 与 db 层有三处进程级登记，都是 design §3 常驻规则 5 点名的 `register*` / `bind*`：

1. **配置生效监听**（`platform/configuration/configAppliedListeners.ts`）：进程级的 `配置路径 → 监听者` 表。保存设置后，system-operations 的应用
   配置按路径通知；daemon 会话（仓库镜像刷新）与维护服务（维护时间表）按同一路径登记。
2. **执行可用性**（`platform/http/executionAvailability.ts`）：进程级的 `app → 执行状态读取器` 表。daemon 的 HTTP 装配给 app 绑定读取器，路由
   登记表的处理链与 `GET /api/daemon/…` 按 app 查它，未处于执行态时带执行分组的请求回 503。
3. **事务观察**（`db/transactionScope.ts`）：进程级的 `客户端 → 事务耗时观察者` 表。建 SQLite 客户端时带了观察者就登记，事务结束时按客户端
   取出调用（维护 Worker 用它上报事务耗时）。

## 2. 目标

- **G1 配置生效监听归应用配置**：每份应用配置建一组监听（登记、通知），保存后的通知、daemon 会话与维护服务的登记都用这一组；不再有按路径
  的进程级表。
- **G2 执行状态读取器随 app 走**：读取器记在它服务的 app 对象上，处理链与状态查询从 app 本身读；“绑定两次即拒”“未绑定的 app 不门控、状态
  查询要求绑定”逐字不变。
- **G3 事务观察者随客户端走**：观察者记在它所属的客户端对象上，事务结束时从客户端本身读。
- **G4 门与用例**：新增 RFC-536 用例（三个文件没有模块级集合与写模块状态的登记函数；装配处交对了；两组监听、两个 app、两个客户端互不相通；
  带负对照）；读旧形状的锁与用例随改；模块级可变单例清单 61 → 58。

## 3. 非目标

- 其余 58 条模块级可变单例：维护 Worker 的效果模块登记（托管 Worker 入口在 init 之前登记；Worker 根的薄入口锁与“标准 Worker 不带托管代码”的
  约束要求先改 Worker 入口的形状，另立后继）、已提交事件的即时投递泵、ws 的三处登记与遗留测试库标记（关系到凭据与访问判定，按只审功能的门
  规则单独处理）、平台持久化的 schema 绑定、日志器、platform / util 的进程级缓存等；需要保留的进程级缓存由后继 design 提出、经用户确认后修订
  design §14 口径。
- 三处登记各自的语义不变：通知只在设置持久化之后、监听抛错只记日志、异步监听全部等完、执行门控与 503 的内容、事务耗时的上报时点。

## 4. 用户可见变化

无。

## 5. 验收标准

- **AC-1**：三个文件没有模块级集合与写模块状态的登记函数；配置生效监听每份应用配置一组，daemon 会话与维护服务登记、保存后的通知用同一组。
- **AC-2**：执行状态读取器与事务观察者随各自的对象走；门控、状态查询与事务耗时上报与此前相同。
- **AC-3**：模块级可变单例清单 61 → 58，计数不升；钉住旧形状的锁随改，新增 RFC-536 用例并登记 guard-manifest。
- **AC-4**：受影响用例全部通过；推送后 exact SHA 的 GitHub Actions 全绿（环境性红格逐格归因、如实记录）。
